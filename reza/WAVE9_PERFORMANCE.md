## ۱. مسئله — چه چیزی در مسیرِ درخواست/رویداد بود؟

نقشهٔ راه برای Wave 9 این‌ها را از مسیرِ درخواست حذف می‌کند:
`JSON.stringify(کلِ store)` · I/O سنکرونِ فایل · بکاپ/گزارشِ سنگین.

اندازه‌گیریِ خطِ پایه (store نمایشی **۵٫۶MB** — ۱۰۳۵ کاربر، سندباکس، سه‌بارِ بهترین):

| عملیات | کجا | هزینه روی رشتهٔ اصلی |
|---|---|---|
| `JSON.stringify(store)` + `writeFileSync` | تیکرِ `persistStore` (هر ۲ ثانیه، وقتی dirty) | **~۳۰–۴۸ ms** |
| همان، برایِ بکاپ (`POST /api/admin/backup`) | **درونِ هندلرِ درخواست** | **~۳۰–۴۸ ms در هر درخواست** |
| `readFileSync` فایلِ استاتیک | هر درخواستِ `/` و `/USER_GUIDE.html` | index.html ‏~۲MB و راهنما ~۲٫۴MB |
| `appendFileSync` + `statSync` در `record()` | هر رویدادِ ممیزی | I/O سنکرون در هر رویداد |
| اسکنِ O(n) گزارشِ عمومی روی users/classes/… | `GET /api/public-report` | با رشدِ داده خطی بدتر می‌شود |
| L1 کشِ bootstrap | `server/cache.js` | فقط-رشد (نشتِ حافظه در مقیاسِ ملی) |

این اعداد با store نمایشی است؛ در مقیاسِ ملی (میلیون‌ها رکورد) هر تیکِ persist
صدها میلی‌ثانیه رشتهٔ اصلی را قفل می‌کرد — یعنی تاخیر برای **همهٔ** درخواست‌های
هم‌زمان، نه فقط عملیاتِ سنگین.

## ۲. طراحی — رشتهٔ کارِ عملیاتِ سنگین (Heavy Worker)

**الگو:** یک Worker دیرزیاد (`server/workers/heavy.js`) آخرین اسنپ‌شاتِ store را
نگه می‌دارد؛ `JSON.stringify`، نوشتنِ فایل و اسکنِ گزارش در **رشتهٔ پس‌زمینه**
انجام می‌شود. رشتهٔ اصلی فقط پیامِ کوچک می‌فرستد.

**تازگیِ داده با نسخه‌ها (نه با تایمر):**

```
markDirty()  →  workers.bump()  →  mainVersion++
هر op (persist/backup/report)  →  اگر workerVersion < mainVersion:
                                   اسنپ‌شاتِ تازه (structured clone) → ورکر
                                 سپس: op روی اسنپ‌شاتِ ورکر
```

نتیجهٔ مهمِ این طراحی: در **حالتِ پایدار** (بکاپ/گزارشِ پشتِ‌سرِ هم بدونِ نوشتنِ
تازه) هیچ clone و هیچ stringify‌ای روی رشتهٔ اصلی انجام نمی‌شود — بکاپ عملاً
**مجانی** می‌شود. تازگی هم تضمینِ سخت است: نوشتنِ تازه همیشه پیش از op بعدی به
ورکر می‌رسد (آزمون W9-5/W9-6d).

**چرا structured clone بهتر از stringify است؟** `postMessage` کلون را با کدِ
بومیِ C++ انجام می‌دهد (چند برابر سریع‌تر از `JSON.stringify`ِ جاوااسکریپتی)
و رشتهٔ متنیِ بزرگ هم روی رشتهٔ اصلی ساخته نمی‌شود.

## ۳. تغییرات — فایل به فایل

| فایل | تغییر |
|---|---|
| `server/workers/heavy.js` ✨ | رشتهٔ کار: نگه‌داریِ اسنپ‌شات + چهار op: ‏`snap` / `persist` (نوشتنِ اتمی tmp+rename، mode 0600) / `backup` (فقط‌داده + نگه‌داریِ ۱۰ نسخه + prune) / `report` (گزارشِ عمومی از اسنپ‌شات) |
| `server/worker-service.js` ✨ | مدیرِ ورکر: spawn دیرزیاد و unref، مسیریابیِ پیام با id و timeout، هم‌جوشیِ اسنپ‌شات‌ها (زنجیرهٔ سریالی)، شمارندهٔ نسخه، `stats()` و `terminate()` |
| `server/index.js` | `persistStore` → مسیرِ ورکر با هم‌جوشی (busy/queued) و فال‌بکِ سنکرون؛ `persistStoreSync` فقط برای exit/SIGTERM/SIGINT و خطای ورکر؛ `serveStatic` → خواندنِ async + کشِ mtime؛ `markDirty` → bump نسخه |
| `server/static-cache.js` ✨ | کشِ استاتیک: خواندنِ async، اعتبارسنجیِ mtime/size (بازخوانی بعد از build)، سقفِ بایت با LRU |
| `server/admin.js` | `backupNow` → `workers.runBackup` (پاسخِ HTTP فقط بعد از نشستنِ فایل روی disk — قراردادِ قبلی دست‌نخورده)؛ مسیرِ درون‌پروسه‌ای به‌عنوانِ فال‌بک (`backupNowInline`)؛ تایمرِ خودکار async |
| `server/public-report-core.js` ✨ | هستهٔ محاسباتیِ خالصِ گزارشِ عمومی — یک منبعِ مشترک برای endpoint و ورکر (بدونِ نسخهٔ دومِ منطق) |
| `server/public-report.js` | محاسبه از ورکر + فال‌بکِ درون‌پروسه‌ایِ همان هسته |
| `server/audit.js` | حالتِ `PAYESH_AUDIT_ASYNC=1`: صفِ درون‌حافظه → نوشتنِ دسته‌ایِ مرتب در پس‌زمینه (`appendFile` در setImmediate)؛ تصمیمِ چرخش به فلش می‌رود (بدون statSync در مسیرِ رویداد)؛ `flush()` / `flushSync()` (خروجِ فرآیند در index.js سیم‌کشی شده). **پیش‌فرض sync است** تا قراردادِ خواندنِ هم‌زمانِ فایل در آزمون‌ها دست‌نخورده بماند |
| `server/cache.js` | L1 محدود: سقفِ ورودی (پیش‌فرض ۲۰۴۸، `PAYESH_L1_MAX_ENTRIES`)، حذفِ اول منقضی‌ها بعد LRU، تازگی در خواندن، `l1Stats()` و `setL1MaxEntries()` |

## ۵. سازگاری و پدافند

- **شکستِ ورکر هرگز عملیات را نمی‌کشد:** persist → نوشتنِ سنکرونِ قدیمی؛
  بکاپ/گزارش → مسیرِ درون‌پروسه‌ایِ قبلی. ورکر دیرزیاد است و در شکست، فراخوانِ
  بعدی دوباره بالا می‌آورد.
- **خاموشی:** `exit`/`SIGTERM`/`SIGINT` → `persistStoreSync` + `flushSync` —
  همان تضمینِ دوامِ قبلِ Wave 9.
- **قراردادهای حفظ‌شده:** فایلِ بکاپِ پاسخ همیشه موقعِ پاسخ روی disk است
  (server8/server9)؛ بکاپ فقط‌داده (بدونِ `__*`)؛ mode ‏0600 (security2)؛
  GC در نقطهٔ اسنپ‌شات (server14-gc — هر ۴ جهش همچنان کشته)؛ گزارشِ عمومی
  بایت‌به‌بایت هم‌ارزِ هستهٔ مرجع (W9-6b/e).
- **انکرهای جهش:** خطوطِ هدفِ جهش در `index.js`/`admin.js` عمداً دست‌نخورده
  ماندند؛ M16–M20 و جهش‌های GC همگی همچنان کشته می‌شوند.

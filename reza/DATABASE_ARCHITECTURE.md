## 1. هدف Wave 2

هدف Wave 2 تبدیل لایه دیتابیس به یک قرارداد مهندسی‌شده، versioned و قابل سنجش برای مسیر National Scale است. این Wave هنوز به معنی پایان Wave 1 و PostgreSQL-only شدن کل production نیست؛ اما زیرساخت دیتابیس را برای آن آماده و قابل تست می‌کند.

اصول اجراشده:

- migrationهای versioned و immutable
- rollback صریح برای هر migration
- استفاده از PostgreSQL Identity برای شناسه‌ها
- قیدهای پایگاه داده برای invariantهای مهم
- transaction برای مسیرهای نوشتاری حیاتی
- OCC در سطح SQL برای داده‌های حساس


```sql
"id" INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

## 3. Constraints

در `server/schema.sql` و migrationها انواع زیر وجود دارد:

| نوع | وضعیت | نمونه |
|---|---|---|
| PRIMARY KEY | ✅ | `id ... PRIMARY KEY` |
| FOREIGN KEY | ✅ | `fk_grades_student`, `fk_*_school` |
| UNIQUE | ✅ | `uq_enrollments_student_year`, `uq_schedule_teacher_slot` |
| CHECK | ✅ | `chk_classes_capacity`, `chk_users_status` |
| NOT NULL | ✅ | جدول‌های داخلی مانند `server_processed_uids`, `server_auth_codes` |

نکته: برخی constraints قبلاً در schema وجود داشتند؛ migration `003_constraints.sql` آن‌ها را idempotent نگه می‌دارد تا اجرای دوباره یا اجرای پس از `001_initial.sql` امن باشد.

## 4. شناسه‌ها (IDs)

### تصمیم Wave 2

در PostgreSQL، شناسه‌ها باید از خود دیتابیس بیایند، نه از `max(id)+1`.

اقدامات:

1. `tools/migrate-to-pg.js` برای ستون `id` این نوع را تولید می‌کند:

```sql
INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

2. `server/schema.sql` با همین قرارداد هم‌راستا شد.

3. `server/ids.js` در حالت PostgreSQL ابتدا sequence وابسته به identity column را از catalog می‌گیرد:

```sql
SELECT pg_get_serial_sequence($1, $2) AS seq
```

و سپس از `nextval` همان sequence استفاده می‌کند.

4. fallback `max(id)+1` فقط برای حالت غیر PostgreSQL/JSON باقی است و مسیر production PostgreSQL از آن عبور نمی‌کند.

## 5. Transactions

تابع `transaction()` در `server/db.js` موجود و فعال است:

```text
BEGIN → callback(client) → COMMIT
خطا → ROLLBACK → throw خطای اصلی
```

مسیرهای حیاتی زیر اکنون از `db.persistOpsBatch()` عبور می‌کنند که در PostgreSQL یک transaction واقعی می‌سازد:

| مسیر | فایل | مجموعه |
|---|---|---|
| ثبت دانش‌آموز | `server/routes/students.js` | `users` |
| ثبت حضور | `server/routes/attendance.js` | `attendance` |
| ثبت نمره | `server/routes/grades.js` | `grades` |

در حالت JSON/memory رفتار سازگار قبلی حفظ می‌شود.

## 6. OCC — Optimistic Concurrency Control

برای داده‌های حساس، فقط بررسی حافظه کافی نیست. Wave 2 مسیر PostgreSQL را هم به `UPDATE ... WHERE id AND version` مجهز کرد.

در `server/db.js`، اگر `op.base_version` وجود داشته باشد:

```sql
UPDATE "grades"
SET ...
WHERE id = $id AND version = $base_version
```

اگر `rowCount === 0`:

```text
status = 409
code = occ_conflict
```

مسیرهای REST مربوطه خطای 409 را به پاسخ conflict تبدیل می‌کنند:

- `PATCH /api/v1/grades/:id`
- `PATCH /api/v1/attendance/:id`

## 9. محدودیت‌های شناخته‌شده

| مورد | وضعیت |
|---|---|
| PostgreSQL-only شدن production | مربوط به Wave 1 است و در این Wave کامل نمی‌شود. |
| اجرای migration روی دیتابیس واقعی | در این محیط انجام نشد؛ تست‌ها بدون PG واقعی و با pool جعلی هستند. |
| rollback تولید | فایل‌های down وجود دارند، اما rollback مخرب `001_initial.down.sql` فقط پیش از داده واقعی/تولید قابل استفاده است. |
| DML قدیمی در `server/schema.sql` | فایل legacy همچنان شامل داده seed نیز هست؛ migration `001_initial.sql` فقط بخش DDL را تثبیت می‌کند. |
| بازگرداندن mutation حافظه پس از conflict PG | مسیر JSON/memory برای سازگاری باقی است؛ منبع حقیقت production پس از Wave 1 باید فقط PostgreSQL باشد. |

برای rollback این Wave:

1. revert کامیت Wave 2.
2. در دیتابیس آزمایشی، در صورت اجرای migrationها:

```text
migrations/003_constraints.down.sql
migrations/002_indexes.down.sql
migrations/001_initial.down.sql
```

3. اجرای دوباره تست‌ها:

```bash
node tests/db-engineering.js
node tests/db-engineering-mutations.js
node tests/run.js
node --expose-gc --max-old-space-size=2048 tests/smoke.js
node tools/check-authz.js
node tests/secret-scan.js
```

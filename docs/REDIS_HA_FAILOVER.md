# Redis — دسترس‌پذیری بالا (HA) و فیل‌اُوور برای استقرار ملی

> فاز ۲ چت ۴ — سندِ عملیاتی و قابل‌اجرا (۲۰۲۶-۰۹-۰۹)
> کد: `server/redis.js` (پشتیبانی سنتینل + مهلتِ اتصال) · تست: `tests/redis-sentinel-failover.js`
> پیش‌نیازها: پی۰-۱۳ (فال‌بک ممنوع در تولید) و ممیزی کلیدها (`docs/REDIS_KEY_OPTIMIZATION.md`)

---

## ۱.۱ انتخاب معماری

| گزینه | کاربرد | مزیت | هزینه |
|---|---|---|---|
| **Redis Sentinel** | دسترس‌پذیری بالا با یک مجموعهٔ مستر/کپی | ساده، بالغ، بدون تغییر مدل داده؛ فیل‌اُوور خودکار | مقیاس‌پذیری افقی ندارد (یک مستر فعال) |
| **Redis Cluster** | مقیاس افقی + HA | توزیع داده روی چند مستر (شاردینگ) | پیچیدگی کلاینت/عملیات؛ چند کلیدِ چندقسمتیِ ما باید هم‌شارد شوند |

**پیشنهاد رسمی:** برای شروعِ استقرار ملی **Sentinel** (ساده‌تر و کافی — بار
کش/قفل/نرخِ ما با یک مسترِ ۴–۸ گیگی به‌راحتی جمع می‌شود) و **Cluster فقط برای
آینده** اگر حجم کلیدها یا توانِ نوشت از ظرفیت یک مستر فراتر رفت. کلیدهای فعلی
(فهرست `REDIS_KEY_OPTIMIZATION.md`) همگی کوچک و کوتاه‌عمرند؛ گلوگاه بعید است.

**چرا برای ما حیاتی است؟** پی۰-۱۳ فال‌بک حافظه را در تولید ممنوع کرده —
سرور بدون ردیسِ زنده اصلاً سرویس نمی‌دهد. پس در دسترس بودن ردیس = در دسترس
بودن محصول. یک مسترِ تنها یعنی یک نقطهٔ شکست؛ سنتینل آن را حذف می‌کند.

## ۱.۲ معماری Sentinel (هدفِ استقرار ملی)

```text
┌─────────────────────────────────────────────────────────────┐
│                    Redis Sentinel Architecture               │
├─────────────────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │  Sentinel 1 │  │  Sentinel 2 │  │  Sentinel 3 │         │
│  │  :26379     │  │  :26379     │  │  :26379     │         │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘         │
│         │                │                │                 │
│         │  پایش + رأی‌گیری برای فیل‌اُوور   │                 │
│         ▼                ▼                ▼                 │
│  ┌────────────────────────────────────────────────┐         │
│  │          Redis Master (Primary) :6379          │         │
│  └──────────────────┬─────────────────────────────┘         │
│              replication (async)                            │
│  ┌─────────────────┴──┐  ┌─────────────────────┐            │
│  │  Redis Replica 1   │  │  Redis Replica 2    │            │
│  │  :6380             │  │  :6381              │            │
│  └────────────────────┘  └─────────────────────┘            │
└─────────────────────────────────────────────────────────────┘
   اپلیکیشن (نمونه‌های سرور) ── فقط با نگهبان‌ها حرف می‌زنند:
   REDIS_SENTINELS="s1:26379,s2:26379,s3:26379"
```

قواعد چیدمان:
- **۳ نگهبان** روی **۳ میزبانِ جدا** (اکثریت برای رأی‌گیری؛ با ۲ نگهبان، مرگ یک
  میزبان = از دست رفتن اکثریت = بدون فیل‌اُوور).
- نگهبان‌ها بهتر است روی میزبان‌های اپ یا میزبان‌های مستقل باشند، نه لزوماً
  کنار خود ردیس (تا مرگ میزبانِ ردیس، نگهبان را هم نبرد).
- کپی‌ها با `replicaof` مستر را دنبال می‌کنند؛ در فیل‌اُوور یکی از آن‌ها مستر می‌شود.
- حداقل یک کپی، ترجیحاً دو کپی (یکی برای خواندن/پشتیبان، یکی نامزد فیل‌اُوور).

## ۱.۳ استراتژی فیل‌اُوور

۱. **تشخیص:** نگهبان‌ها هر ثانیه مستر را پینگ می‌کنند. عدم پاسخ برای
   `down-after-milliseconds` (پیشنهاد: ۵۰۰۰) → وضعیت *subjectively down*.
   وقتی اکثریت نگهبان‌ها هم‌نظر شدند → *objectively down*.
۲. **انتخاب کپی:** نگهبانِ راهبر (که با رأی انتخاب می‌شود) یکی از کپی‌ها را
   بر اساس اولویت، مقدار کپی‌سازی (replication offset) و شناسه برمی‌گزیند.
۳. **ارتقا:** کپی انتخاب‌شده `REPLICAOF NO ONE` می‌گیرد و مستر می‌شود؛ بقیهٔ
   کپی‌ها به آن وصل می‌شوند.
۴. **اطلاع‌رسانی به اپلیکیشن:** نیازی به تغییر DNS یا دخالت اپ نیست —
   `ioredis` در حالت سنتینل خودش از نگهبان‌ها آدرس مسترِ جدید را می‌پرسد
   (`failoverDetector` در `server/redis.js` تغییر را ظرف ~۱ ثانیه کشف می‌کند)
   و اتصال را بازسازی می‌سازد. رفت‌وبرگشت‌های در جریان، خطا می‌گیرند و لایه‌های
   بالاتر (کش/قفل) خطا را تحمل می‌کنند: کش می‌سازد، قفل ناموفق → تلاش بعد.
۵. **رفتار اپ هنگام بحران:** قرارداد پی۰-۱۳ پابرجاست — اگر در لحظهٔ بوت ردیس
   در دسترس نباشد سرور بالا نمی‌آید (شکستِ ریدی). حین کار، افت موقت ردیس =
   خطای عملیات کش (نه کرش) و هلث ۵۰۳ برای پروب‌ها.

**بازه‌های هدف:** تشخیص ≤ ۵ ثانیه + ارتقا ≤ ۱۰–۳۰ ثانیه ⇒ کل فیل‌اُوور معمولاً
زیر ۴۰ ثانیه؛ در این پنجره نوشت‌های کش ناموفق‌اند ولی هستهٔ فروشگاه/پستگرس
آسیب نمی‌بیند.

**تضمین‌های داده:** ردیسِ ما فقط کش/قفل/شمارنده/حالت ورود است (منبع حقیقتِ
داده پستگرس و اسنپ‌شات فروشگاه است). کپی‌سازی ناهمزگام یعنی در فیل‌اُوور ممکن
است چند ثانیه از حالتِ ورود بپرد — برای همین `payesh:otp:state` فلاشِ زیر قفل
دارد و کدها پس از فیل‌اُوور نهایتاً یک‌بار دیگر ارسال می‌شوند. هیچ دادهٔ
کسب‌وکاری در ردیس نیست؛ `AOF everysec` برای کاهش همین پنجره توصیه می‌شود.

## ۱.۴ تنظیمات پیشنهادی `redis-sentinel.conf`

برای هر سه نگهبان (روی میزبان‌های جدا؛ فقط پورت/آدرس میزبان فرق می‌کند):

```conf
port 26379
# هر نگهبان به بقیه هم نیاز ندارد تا شروع کند؛ خودشان همدیگر را کشف می‌کنند
sentinel monitor mymaster <IP-MASTER> 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
# در استقرار واقعی حتماً رمز بگذارید (هم ردیس، هم نگهبان):
# requirepass <STRONG_SECRET>          (روی خود ردیس)
# sentinel auth-pass mymaster <STRONG_SECRET>
# sentinel sentinel-pass <STRONG_SECRET>
```

و حداقل‌های سمت ردیس (مستر و هر کپی):

```conf
# redis.conf (روی کپی‌ها)
replicaof <IP-MASTER> 6379
# پایداری بیشتر حالت ورود در فیل‌اُوور:
appendonly yes
appendfsync everysec
# اگر رمز دارید:
# masterauth <STRONG_SECRET>
# requirepass <STRONG_SECRET>
```

نکات عملیاتی:
- `quorum = 2` با ۳ نگهبان: تحملِ مرگِ یک نگهبان بدون از دست رفتن فیل‌اُوور.
- `parallel-syncs 1`: بعد از فیل‌اُوور کپی‌ها یکی‌یکی به مستر جدید وصل شوند
  (جلوگیری از افت توان در لحظهٔ بحران).
- `failover-timeout 60000`: اگر فیل‌اُوور ناکام ماند، ۶۰ ثانیه بعد دوباره
  مجاز است (جلوگیری از چرخهٔ فیل‌اُوور).
- فایروال: نگهبان‌ها ↔ ردیس‌ها روی 6379/6380/6381 و 26379 باز باشد؛ اپ ↔
  نگهبان‌ها (26379) و اپ ↔ **مسترِ جاری** (پورت ردیس، نه فقط یک آی‌پی ثابت —
  چون مستر جابه‌جا می‌شود).

## ۱.۵ یکپارچه‌سازی با `server/redis.js` — انجام شد

پشتیبانی سنتینل در کد پیاده است (بدون تغییر رفتارِ پیش‌فرض — فقط با متغیرهای
محیطی فعال می‌شود):

```bash
# استقرار ملی با سنتینل:
NODE_ENV=production \
REDIS_SENTINELS="10.0.0.1:26379,10.0.0.2:26379,10.0.0.3:26379" \
REDIS_MASTER_NAME="mymaster" \
node server/index.js

# توسعه یا استقرار تک‌گره (رفتار قدیمی، بدون تغییر):
REDIS_URL="redis://127.0.0.1:6379" node server/index.js
```

جزئیات پیاده‌سازی:
- `buildSentinelConfig(csv, name)` فهرست `هاست:پورت` را به کانفیگ آیورِدیس
  تبدیل می‌کند (پورت پیش‌فرض 26379؛ تابع خالص و تست‌پذیر).
- در حالت سنتینل، کلاینت اصلی و کلاینتِ اشتراک هر دو با `{name, sentinels}`
  ساخته می‌شوند؛ `sentinelReconnectInterval: 2000` و `failoverDetector: 1000`
  یعنی پس از فیل‌اُوور، مسترِ تازه ظرف ~۱–۲ ثانیه کشف می‌شود.
- **مهلتِ اتصال ۸ ثانیه** (`CONNECT_DEADLINE_MS`): اگر ردیس/نگهبان‌ها در بوت
  پاسخ ندهند، اتصال برای همیشه آویزان نمی‌ماند — شکست قطعی می‌خورد و قرارداد
  پی۰-۱۳ اجرا می‌شود (تولید: خروج با شکستِ ریدی؛ توسعه: حافظه).
- اشتراک‌ها (کانال بی‌اعتبارسازی کش) پس از بازسازی اتصال توسط آیورِدیس دوباره
  ثبت می‌شوند؛ نیازی به کد اضافه نیست.

## ۲. پایش و هشدار

| متریک | آستانهٔ هشدار |
|---|---|
| `redis_up{job="master"}` | ۰ برای بیش از ۱۰ ثانیه |
| تعداد نگهبان‌های زنده | کمتر از ۳ → هشدار؛ کمتر از ۲ → بحرانی (اکثریت از دست رفته) |
| `connected_slaves` روی مستر | کمتر از ۱ |
| تأخیر کپی‌سازی (`master_link_status`) | `down` |
| `/api/health` سرورهای اپ | `cache: unavailable` یا ۵۰۳ |

دستورهای سریع:
```bash
redis-cli -h <sentinel> -p 26379 sentinel master mymaster    # وضعیت مستر
redis-cli -h <sentinel> -p 26379 sentinel replicas mymaster  # وضعیت کپی‌ها
redis-cli -p 6379 info replication                           # روی خود ردیس
node tools/redis-audit.js                                    # سلامت کلیدها و TTL
```

## ۳. ران‌بوکِ کوتاه (وقتی هشدار آمد)

1. `sentinel get-master-addr-by-name mymaster` — مسترِ جاری کیست؟
2. اگر نگهبان‌ها بین خود اختلاف دارند (`known-sentinels` قدیمی): نگهبان معیوب
   را ری‌استارت کنید؛ `SENTINEL RESET mymaster` فقط با دستور سرپرست.
3. اگر فیل‌اُوور خودکار انجام نشد (اکثریت از دست رفته): **دستی** —
   روی کپیِ سالم: `redis-cli -p 6380 replicaof no one`، سپس بقیهٔ کپی‌ها:
   `replicaof <IP-مستر-جدید> 6379`؛ نگهبان‌ها را ری‌استارت تا توپولوژی روز شود.
4. میزبانِ مرده که برگشت، حتماً به‌عنوان **کپی** اضافه شود
   (`replicaof <مستر-جدید> 6379`) — وگرنه مسترِ دوگانه و شکافتگی داده.
5. بعد از هر مانور: `node tools/redis-audit.js` و `/api/health` همهٔ نمونه‌ها.

## ۴. مسیر آینده (در صورت نیاز)

- **مهاجرت به Redis Cluster** فقط وقتی: بیش از ~۵۰ گیگ دادهٔ داغ یا بیش از
  ~۱۰۰هزار نوشت بر ثانیه. پیش‌نیاز: بررسی هم‌شاردی کلیدها (هیچ‌کدام از
  کلیدهای فعلی چندکلیدی تراکنشی ندارند؛ `payesh:otp:state` یک سند واحد است).
- **ردیسِ مدیریت‌شدهٔ ابری** (با سنتینلِ داخلی) اگر تیم عملیات نخواهد
  نگهبان‌ها را خودش نگه دارد — قرارداد اپ (`REDIS_SENTINELS` یا `REDIS_URL`)
  تغییر نمی‌کند.

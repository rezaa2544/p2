## فاز ۱ — تشخیص (۰ تا ۵ دقیقه)

| گام | اقدام | خروجی |
|---|---|---|
| ۱٫۱ | آلارم را ack کن (آلارتمنجر → کانال آن‌کال)؛ اگر گزارش انسانی است، `trace_id` بساز و ثبت کن | حضور اعلام‌شده |
| ۱٫۲ | شدت اولیه را با [کانن §۱](INCIDENT_RESPONSE.md) تعیین کن؛ در شک (داده/امنیت) ← **P0** | شدت اعلام‌شده در کانال |
| ۱٫۳ | فرماندهٔ حادثه (IC) را اعلام کن (پیش‌فرض: خودت)؛ برای P0 بکاپ را page کن | `IC: <نام> · شدت: <P0..P3>` در کانال |
| ۱٫۴ | دو شاهد جمع کن: لاگ (Loki/`trace_id`) + متریک (Grafana/alert-rules) — بدون دو شاهد، rollback ممنوع | خط زمانی شروع‌شده |
| ۱٫۵ | اگر P0: ذی‌نفعان را با قالب §۴ مطلع کن؛ تایمر ۱۵ دقیقه‌ای به‌روزرسانی را روشن کن | اولین اطلاع‌رسانی |

**ضدالگو:** حدس‌زدن و دست‌کاری تولید قبل از ۱٫۴. مشاهده اول، اقدام بعد.

## فاز ۲ — مهار (۵ تا ۳۰ دقیقه)

### ۲٫۱ درخت تصمیم rollback

```text
آیا حادثه در ≤ ۶۰ دقیقه پس از یک دیپلوی شروع شد؟
├─ بله → آیا دو شاهد (لاگ + متریک) دیپلوی را متهم می‌کنند؟
│   ├─ بله → IC تأیید کند → ROLLBACK (مطابق DEPLOYMENT_GUIDE §بازگشت) → فاز ۳
│   └─ نه  → rollback ممنوع؛ ادامهٔ مهار در ۲٫۲
└─ نه  → آیا فیچرفلاگ/کانفیگِ تازه‌تغییر مقصر است؟
    ├─ بله → IC تأیید کند → برگرداندن فلگ/کانفیگ (اثر < rollback کامل) → فاز ۳
    └─ نه  → rollback ممنوع؛ ادامهٔ مهار در ۲٫۲
```

### ۲٫۲ مهار بدون rollback

| سناریو | اقدام | runbook |
|---|---|---|
| Primary پستگرس مرده | promote دستی تأییدشده (≈ ۴ دقیقه) | [DR_RUNBOOK §۱](DR_RUNBOOK.md) |
| Redis master مرده | انتظار failover خودکار ≤ ۳۰s؛ وگرنه دستی ≤ ۲ دقیقه | [DR_RUNBOOK §۲](DR_RUNBOOK.md) |
| فساد/حذف داده | ایزولهٔ مسیر نویسنده → PITR در محیط جدا | [DR_RUNBOOK §۴](DR_RUNBOOK.md) |
| ازدحام/اشباع (p95 > ۳۰۰ms، صف رشد) | مقیاس افقی تا سقف مصوب؛ کش «درمان» نیست — ریشه در [CAPACITY_MODEL](CAPACITY_MODEL.md) | [CAPACITY_MODEL](CAPACITY_MODEL.md) §۵ |
| حادثهٔ امنیتی (نشت/IDOR/ورود مشکوک) | ایزوله → چرخش راز → شواهد نگه‌داشته شود (لاگ پاک نشود) | §۵ همین سند + [THREAT_MODEL](THREAT_MODEL.md) |
| طوفان تعارض sync | مهار سمت سرور (dedupe/OCC فعال بماند)؛ داوری انسانی، نه LWW | §۶ همین سند |

### ۲٫۳ پایان مهار

مهار کامل است وقتی: (الف) گسترش متوقف شده (متریک صاف/نزولی ۵ دقیقه) و (ب) IC آن را در کانال اعلام کرده.
مهار ≠ رفع کامل؛ رفع کامل در فاز ۳.

---

## فاز ۳ — رفع (۳۰ دقیقه تا ۴ ساعت)

| گام | اقدام |
|---|---|
| ۳٫۱ | ریشه‌یابی روی دادهٔ واقعی (trace + لاگ + متریک)؛ فرضیه‌ها را یکی‌یکی با شاهد رد/تأیید کن |
| ۳٫۲ | فیکس را در staging اعتبارسنجی کن (حداقل: سوئیت مرتبط + smoke)؛ دیپلوی مستقیمِ تست‌نشده به تولید ممنوع |
| ۳٫۳ | دیپلوی با نظارت IC؛ بودجهٔ خطای مصرف‌شده را محاسبه و ثبت کن ([OPERATIONAL_READINESS §۲](OPERATIONAL_READINESS.md)) |
| ۳٫۴ | اعتبارسنجی پس از رفع: آلارم‌ها سبز ۱۵ دقیقه + سنجهٔ کاربرمحور (SLO مربوطه) برگشته |
| ۳٫۵ | اعلام `all-clear` در کانال + خلاصهٔ ۵ خطی (چه شد / چه کردیم / اثر کاربر / بودجهٔ مصرفی / قدم بعد) |

## فاز ۴ — پست‌مورتم (۴ ساعت تا ۴۸ ساعت)

- فرایند و قالب کانن: [INCIDENT_RESPONSE §۵](INCIDENT_RESPONSE.md)؛ فرم قابل‌پرکردن: `templates/POSTMORTEM_TEMPLATE.md`.
- مهلت: P0 ← ۴۸ ساعت؛ P1 ← ۱ هفته؛ P2 ← اختیاری؛ شکست SLO بدون حادثه ← اجباری ([OPERATIONAL_READINESS §۲](OPERATIONAL_READINESS.md)).
- هر action item: مالک + مهلت + ردیف در [RISK_REGISTER](RISK_REGISTER.md). پست‌مورتم بدون action itemِ رهگیری‌شده = تئاتر مستندسازی، مردود.
- بازسازی خط زمانی از سه منبع: لاگ (Loki) + متریک (Prometheus) + پیام‌های کانال حادثه.

## §۵ شاخهٔ حادثهٔ امنیتی (Security Incidents)

1. شدت اولیه **P0** (قاعدهٔ سفت کانن) تا اثبات خلاف.
2. اولویت اول: **نگه‌داشت شواهد** — لاگ‌ها/متریک‌های بازه فریز شوند؛ هیچ‌چیز پاک/rotate نشود.
3. ایزوله: بستن مسیر آسیب‌دیده (WAF rule / revoke توکن / غیرفعال‌سازی حساب) قبل از ریشه‌یابی کامل.
4. رازها: اگر احتمال نشت هست، چرخش فوری طبق `docs/RUNBOOK_CARDS/JWT_SECRET_ROTATION.md` + [SECRETS_MANAGEMENT](SECRETS_MANAGEMENT.md). **هیچ توکنی در کانال حادثه، پست‌مورتم یا کامیت.**
5. ثبت در [SECURITY_INCIDENT_LOG](SECURITY_INCIDENT_LOG.md) + اطلاع‌رسانی انطباق طبق [THREAT_MODEL](THREAT_MODEL.md).
6. پست‌مورتم امنیتی ۴۸ ساعته اجباری، حتی اگر اثر کاربری صفر بود.

## §۶ حالت‌های خرابی پرتکرار + لینک runbook

| حالت خرابی | نشانهٔ اول | runbook |
|---|---|---|
| مرگ primary پستگرس | `/api/health` قرمز 503 + `connection refused` | [DR_RUNBOOK §۱](DR_RUNBOOK.md) |
| مرگ master ردیس | `lag` صف + آلارم Redis | [DR_RUNBOOK §۲](DR_RUNBOOK.md) |
| فاجعهٔ منطقه‌ای | همه‌چیز قرمز یک منطقه | [DR_RUNBOOK §۳](DR_RUNBOOK.md) |
| فساد داده / مهاجرت خراب | مغایرت integrity + خطای validates | [DR_RUNBOOK §۴](DR_RUNBOOK.md) |
| اشباع ظرفیت (صبح مهر) | p95 > ۳۰۰ms + رشد صف + CPU نودها | [CAPACITY_MODEL](CAPACITY_MODEL.md) + [BOTTLENECK_MAP](BOTTLENECK_MAP.md) |
| طوفان تعارض sync | رشد `conflicts` + retry storm | شواهد: `tests/sync-conflict-storm-drill.js`؛ سیاست: preserve-همه/apply-هیچ، داوری انسانی |
| قطع observability | سکوت آلارم‌ها (خطرناک‌ترین حالت) | [OBSERVABILITY_DEPLOYMENT](OBSERVABILITY_DEPLOYMENT.md) §بازیابی؛ تا بازگشت، پایش دستی هر ۱۵ دقیقه |

**قاعدهٔ سکوت:** اگر آلارم‌ها ساکت‌اند ولی گزارش کاربری هست، اول سلامت خودِ استک رصد را چک کن — «سبزِ دروغین» بدتر از «قرمز» است.

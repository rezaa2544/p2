## ۲. معماری دسترسی‌پذیری بالا (High Availability Architecture)

معماری پایش به صورت چندلایه‌ای و کاملاً بدون نقطه شکست منفرد (No Single Point of Failure - SPoF) طراحی‌شده است:

```
                               ┌────────────────────────────────┐
                               │  DNS Anycast / Geo-DNS Router  │
                               └───────────────┬────────────────┘
                                               │
                 ┌─────────────────────────────┴─────────────────────────────┐
                 │ (منطقه اصلی: تهران - Active)                               │ (منطقه پشتیبان: تبریز - Standby)
                 ▼                                                           ▼
       ┌───────────────────┐                                       ┌───────────────────┐
       │ HAProxy / Ingress │                                       │ HAProxy / Ingress │
       │ (Keepalived VRRP) │                                       │ (Keepalived VRRP) │
       └─────────┬─────────┘                                       └─────────┬─────────┘
                 │                                                           │
        ┌────────┴────────┐                                         ┌────────┴────────┐
        ▼                 ▼                                         ▼                 ▼
   ┌─────────┐       ┌─────────┐                               ┌─────────┐       ┌─────────┐
   │ Pod A1  │  ...  │ Pod An  │                               │ Pod B1  │  ...  │ Pod Bn  │
   └────┬────┘       └────┬────┘                               └────┬────┘       └────┬────┘
        │                 │                                         │                 │
        └────────┬────────┘                                         └────────┬────────┘
                 │                                                           │
   ┌─────────────┴─────────────┐                               ┌─────────────┴─────────────┐
   ▼                           ▼                               ▼                           ▼
┌──────────────────┐   ┌───────────────┐                   ┌──────────────────┐   ┌───────────────┐
│ PostgreSQL Master│   │ Redis Master  │                   │ PostgreSQL Standby│  │ Redis Replica │
│ (Patroni Raft)   │   │ (Sentinel Q.) │                   │ (Async Streaming)│   │ (Sentinel Q.) │
└────────┬─────────┘   └───────┬───────┘                   └──────────────────┘   └───────────────┘
         │ (WAL Streaming)     │ (Cross-Region Sync)
         └─────────────────────┼───────────────────────────────────────►
                               ▼
                   ┌───────────────────────┐
                   │  Geo-Replicated S3    │
                   │ (ArvanCloud Storage)  │
                   └───────────────────────┘
```

### ۲.۱. افزونگی در لایه‌های مختلف:
1. **لایه وب و هدایت بار (Load Balancing):** دو سرور HAProxy با پروتکل VRRP و IP مجازی مشترک؛ در صورت سقوط نود اول، ترافیک بدون تاخیر روی نود دوم سوئیچ می‌شود.
2. **لایه سرورهای برنامه (Stateless Application Pods):** توزیع پادها در حداقل ۳ Availability Zone با قانون `podAntiAffinity` در Kubernetes.
3. **لایه پایگاه‌داده (PostgreSQL HA via Patroni):** کلاستر Patroni با همگام‌سازی جریانی (Streaming Replication) و الگوریتم اجماع Raft/Etcd جهت ارتقای خودکار Standby به Master در کمتر از ۱۰ ثانیه.
4. **لایه حافظه سریع (Redis Sentinel):** کلاستر ردیس با ۳ گره سنتینل جهت نظارت دائمی و مدیریت Failover.

## ۳. راهبرد خودکار پشتیبان‌گیری چندسطحی (Automated Backup Strategy)

برای دستیابی به RPO زیر ۵ دقیقه، سیستم پشتیبان‌گیری در ۳ سطح مکمل پیاده‌سازی می‌شود:

```
┌─────────┬──────────────────────┬─────────────┬─────────────┬───────────────────────────────────────────┐
│ سطح     │ نوع پشتیبان          │ تناوب اجرا  │ محل ذخیره   │ کاربرد و بازه بازگشت                      │
├─────────┼──────────────────────┼─────────────┼─────────────┼───────────────────────────────────────────┤
│ سطح ۱   │ Continuous WAL (PITR)│ بلادرنگ     │ S3 Object   │ بازگشت به ثانیه مشخص (Point-in-Time)      │
│         │ (pgBackRest / WAL-G) │ (هر ۵ دقیقه)│ Storage     │ بازیابی خطاهای انسانی یا باگ‌های داده‌ای  │
├─────────┼──────────────────────┼─────────────┼─────────────┼───────────────────────────────────────────┤
│ سطح ۲   │ اسنپ‌شات کامل (Full) │ روزانه      │ S3 Encrypted│ کپی کامل پایگاه‌داده با رمزنگاری AES-256  │
│         │ (Physical Snapshot)  │ (ساعت ۲ بامداد)│ باکت ایزوله│ نگهداری ۳۰ نسخه آخر                      │
├─────────┼──────────────────────┼─────────────┼─────────────┼───────────────────────────────────────────┤
│ سطح ۳   │ پشتیبان منطقی (Dump) │ هفتگی       │ دیتاسنتر ثانویه│ فایل مستقل JSON/SQL برای مهاجرت یا تست │
│         │ (Logical Database)   │ (جمعه‌ها)   │ (Cold Vault)│ نگهداری ۱۲ ماهه                           │
└─────────┴──────────────────────┴─────────────┴─────────────┴───────────────────────────────────────────┘
```

### ۳.۱. تایید خودکار سلامت فایل‌های پشتیبان (Automated Verification Drill)
پشتیبان‌گیری بدون راستی‌آزمایی، غیرقابل اعتماد است. هر شب در ساعت ۳:۰۰ بامداد:
1. یک کانتینر موقت ایزوله (Ephemeral Sandbox) آخرین فایل پشتیبان را از S3 دانلود می‌کند.
2. پایگاه‌داده آزمایشی Restore‌شده و چک‌سام SHA-256 جدول‌ها تایید می‌گردد.
3. یک سوئیت تست دود (Smoke Test) روی دیتای بازیابی‌شده اجرا می‌شود.
4. گزارش موفقیت یا هشدار خطا به کانال مانیتورینگ ارسال می‌شود.

## ۴. مانورهای دوره‌ای بازیابی (Restore Drills & SLA Validation)

برای اطمینان از آمادگی تیم فنی و کارکرد درست اسکریپت‌ها در شرایط واقعی:

* **مانور فصلی انسانی (Quarterly GameDay):** قطع عمدی یکی از دیتاسنترها در ایام تعطیل با حضور تیم DevOps و سنجش زمان واکنش به بحران.

## ۵. پایش‌پذیری سراسری سیستم (Full-Stack Observability)

زیرساخت پایش‌پذیری پایش بر پایه سه ستون اصلی معماری ابری بنا‌شده است:

```
                               ┌────────────────────────────────┐
                               │     پایش‌پذیری جامع پایش       │
                               └───────────────┬────────────────┘
                                               │
                 ┌─────────────────────────────┼─────────────────────────────┐
                 │                             │                             │
                 ▼                             ▼                             ▼
       ┌───────────────────┐         ┌───────────────────┐         ┌───────────────────┐
       │  سنجه‌ها (Metrics) │         │   لاگ‌ها (Logs)   │         │  ردگیری (Tracing) │
       │Prometheus/Grafana │         │Grafana Loki / ELK │         │OpenTelemetry/Jaeger│
       └───────────────────┘         └───────────────────┘         └───────────────────┘
```

### ۵.۱. سنجه‌های کلیدی (Metrics):
* **متد RED برای وب‌سرویس‌ها:** نرخ درخواست (Rate)، نرخ خطاها (Errors: 5xx, 4xx)، زمان پاسخ‌دهی (Duration: p50, p95, p99).
* **متد USE برای زیرساخت:** درصد اشغال پردازنده و رم (Utilization)، طول صف ورودی (Saturation)، خطاهای دیسک و شبکه (Errors).

### ۵.۲. مدیریت لاگ‌ها (Structured Logging):
* لاگ‌ها با فرمت استاندارد JSON ذخیره‌شده و شناسه یکتای درخواست (`trace_id` / `request_id`) در تمام لایه‌ها از فرانت‌اند تا دیتابیس تزریق می‌شود.

## ۷. دستورالعمل اجرایی بازگشت از بحران (Disaster Recovery Runbook)

چهار سناریوی بحرانی محتمل و گام‌های اجرایی رفع آن‌ها:

---

### سناریو ۱: سقوط یا خرابی فیزیکی سرور اصلی پایگاه‌داده (RTO: ۴ دقیقه)
* **علائم:** هشدار P0 خطای اتصال دیتابیس، افزایش خطای ۵۰۰ در APIها.
* **اقدامات اجرایی:**
  1. بررسی وضعیت کلاستر Patroni:
     ```bash
     patronictl -c /etc/patroni/db.yml topology
     ```
  2. در صورت عدم اجرای خودکار Failover، ارتقای دستی رپلیکا به مستر:
     ```bash
     patronictl -c /etc/patroni/db.yml failover --candidate db-replica-1 --force
     ```
  3. بازتنظیم آدرس اتصال در HAProxy / PgBouncer.
  4. بررسی لاگ‌های اپلیکیشن و اعتبارسنجی تداوم همگام‌سازی.

---

### سناریو ۲: قطعی کامل شبکه دیتاسنتر تهران (RTO: ۸ دقیقه)
* **علائم:** قطعی ارتباط کلیه سرورهای منطقه تهران، هشدار Blackout در مانیتورینگ.
* **اقدامات اجرایی:**
  1. تغییر مسیر ترافیک در سطح DNS Anycast / کلودفلر به دیتاسنتر پشتیبان (تبریز):
     ```bash
     curl -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE/dns_records/$REC" \
          -d '{"content": "185.x.x.tabriz_lb"}'
     ```
  2. ارتقای رپلیکای استندبای تبریز به عنوان پایگاه‌داده فعال اصلی.
  3. مقیاس‌دهی خودکار تعداد پادهای سرور برنامه در دیتاسنتر تبریز (HPA Scale Up).
  4. انتشار اطلاعیه پایداری به مدارس.

---

### سناریو ۳: حمله سایبری، نشت کلیدها یا تخریب عمدی داده‌ها (RTO: ۱۴ دقیقه)
* **علائم:** ثبت رکوردهای مخدوش در لاگ ممیزی، هشدار سرقت توکن‌ها.
* **اقدامات اجرایی:**
  1. قطع فوری دسترسی عمومی و فعال‌سازی صفحه تعمیرات (Maintenance Mode):
     ```bash
     kubectl scale deployment payesh-gateway --replicas=0
     ```
  2. ابطال و چرخش کلیه کلیدهای JWT، رمز دیتابیس و توکن‌های S3 (`PAYESH_KEY`).
  3. بازگردانی پایگاه‌داده به وضعیت امن قبل از حمله با استفاده از Point-in-Time Recovery (PITR):
     ```bash
     pgbackrest --stanza=payesh --type=time "--target=2026-09-08 09:15:00" restore
     ```
  4. راه‌اندازی مجدد سرورها با کلیدهای امن تازه و رفع حالت تعمیرات.

---

### سناریو ۴: دوپارگی شبکه در کلاستر ردیس (Split-Brain / Partition - RTO: ۲ دقیقه)
* **علائم:** ناهماهنگی در سقف‌های ریت‌لیمیتر و هشدارهای Sentinel.
* **اقدامات اجرایی:**
  1. ایزوله‌سازی نود اقلیت با فایروال محلی.
  2. فعال‌سازی Circuit Breaker محلی در سرورهای برنامه جهت اعتبارسنجی خودکفای JWT.
  3. اجرای دستور همگام‌سازی مجدد کلاستر:
     ```bash
     redis-cli -p 26379 SENTINEL reset payesh-master
     ```
  4. اتصال مجدد و عادی‌سازی ترافیک.

## ۸. جمع‌بندی شاخص‌های پایداری

| قابلیت زیرساختی | قبل از طرح | پس از اجرای طرح Reliability & DR |
|---|---|---|
| **سطح تحمل قطعی** | آسیب‌پذیر در برابر قطعی سرور | **تحمل سقوط کامل یک دیتاسنتر بدون قطعی سرویس** |
| **میزان از دست رفتن داده (RPO)** | تا ۲۴ ساعت (پشتیبان روزانه) | **کمتر از ۵ دقیقه (پشتیبان‌گیری پیوسته WAL)** |
| **زمان بازگشت به کار (RTO)** | چندین ساعت | **کمتر از ۱۵ دقیقه با فرآیندهای کاملاً خودکار** |
| **پایش و هشدار** | متکی به گزارش دستی کاربران | **کشف بلادرنگ حوادث با تریکرهای P0 و تماس خودکار** |

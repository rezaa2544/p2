## ۱) اهداف سطح سرویس (SLO) — به‌تفکیک زیرسیستم حیاتی

| # | زیرسیستم | SLO | پنجره | منبع (مصوب) |
|---|---|---|---|---|
| S1 | دسترس‌پذیری API | **≥ ۹۹٫۹۵٪** (سقف قطعی ≈ ۲۱٫۶ دقیقه/ماه) | ماهانه غلتان | [RELIABILITY_DR_PLAN](RELIABILITY_DR_PLAN.md) §۱ + [DR_RUNBOOK](DR_RUNBOOK.md) §۰ |
| S2 | موفقیت همگام‌سازی (sync push/pull بدون دادهٔ گم‌شده) | **≥ ۹۹٫۵٪** | ماهانه غلتان | [CAPACITY_MODEL](CAPACITY_MODEL.md) §۴ |
| S3 | دسترس‌پذیری ورود (OTP) در ساعات مدرسه (۰۶:۰۰–۱۴:۰۰) | **≥ ۹۹٫۹٪** | ماهانه غلتان | [CAPACITY_MODEL](CAPACITY_MODEL.md) §۴ |
| S4 | تأخیر API — p95 | **< ۳۰۰ms** | ۵ دقیقه‌ای (آلارم `HighLatency`) | [CAPACITY_MODEL](CAPACITY_MODEL.md) §۴ + `infra/observability/alert-rules.yml` |
| S5 | تأخیر API — p99 | **< ۱s** | ۵ دقیقه‌ای | [CAPACITY_MODEL](CAPACITY_MODEL.md) §۴ |
| S6 | بازیابی فاجعه — RTO | **≤ ۱۵ دقیقه** | هر حادثهٔ P0 | [DR_RUNBOOK](DR_RUNBOOK.md) §۰ |
| S7 | بازیابی فاجعه — RPO | **≤ ۵ دقیقه** | هر حادثهٔ P0 | [DR_RUNBOOK](DR_RUNBOOK.md) §۰ |
| S8 | تخلیهٔ صف (۱۰۰۰ پیام) — *پیشنهاد چت ۱۰، نیازمند ACCEPT* | **< ۵ دقیقه** | هر drill فصلی | بدون منبع مصوب — مبنای پیشنهادی: drill فصلی §۷ |

**یادداشت‌های صداقت:**
- بریف اولیه «API ‏99.9%» و «sync ‏99.95%» پیشنهاد داده بود؛ هر دو **عمداً** با اعداد مصوب
  (۹۹٫۹۵٪ SLA و ۹۹٫۵٪ sync) جایگزین شدند تا سند واحدِ حقیقت بماند. تغییر این اعداد فقط با کامیت مستقل روی سند مصوب.
- S8 تنها SLO پیشنهادیِ بدون منبع است؛ تا ACCEPT ناظر، لازم‌الاجرا نیست و در drill فصلی اول کالیبره می‌شود.
- شواهد sync امروز در `tests/sync-conflict-storm-drill.js` (‏18/18) و `tests/offline-e2e.js` (‏23/23) است؛
  فایل `SYNC_RELIABILITY_EVIDENCE.md` در ریپو **وجود ندارد** — SLO ‏S2 با همین شواهد موجود هم‌خوان شده، نه با سند موهوم.

## ۲) سیاست بودجهٔ خطا (Error Budget)

| وضعیت بودجهٔ ماهانه | اقدام لازم‌الاجرا |
|---|---|
| مصرف < ۵۰٪ | عادی؛ دیپلوی طبق روال |
| ۵۰٪ ≤ مصرف < ۹۰٪ | هشدار به آن‌کال + بررسی هفتگی در هندآف؛ فیچرهای پرریسک نیازمند تأیید IC |
| مصرف ≥ ۹۰٪ (باقی‌مانده < ۱۰٪) | **فریز دیپلوی** — فقط هات‌فیکس/امنیتی با تأیید Incident Commander |
| بودجه تمام شد (SLO شکست) | فریز + پست‌مورتم اجباری (حتی اگر حادثه P2 بود) + اقدام اصلاحی در [RISK_REGISTER](RISK_REGISTER.md) |

- محاسبه: `(۱ − SLO) × درخواست‌های پنجره`. مثال S1: بودجهٔ ماهانه ≈ ۲۱٫۶ دقیقه قطعی مجاز.
- نرخ مصرف (burn rate): آلارم `HighErrorRate` در `alert-rules.yml` معادل burn-rate سریع است؛
  burn-rate کند (۲× در ۶ ساعت) در drill فصلی اول کالیبره می‌شود — **NOT-RUN**.
- هر شکست SLO یک ردیف در گزارش روزانه + (برای P0/P1) پست‌مورتم دارد؛ بدون استثنا.

## ۳) آن‌کال (خلاصه — جزئیات در [ONCALL_SCHEDULE](ONCALL_SCHEDULE.md))

- چرخش **هفتگی** primary/secondary؛ تحویل شیفت فقط با چک‌لیست handoff (قالب: `templates/ONCALL_HANDOFF_TEMPLATE.md`).
- زمان پاسخ: P0 ‏≤ ۵ دقیقه · P1 ‏≤ ۱۵ دقیقه · P2 ‏≤ ۱ ساعت · P3 روز کاری بعد.
- تشدید (escalation): ماتریس کامل در `templates/ESCALATION_MATRIX.md`.
- **NOT-RUN:** انتساب واقعی افراد (نام/تلفن) — نیازمند تیم انسانی و ACCEPT ناظر. تا آن روز، primary = «آن‌کالِ پاسخ‌دهنده» طبق [INCIDENT_RESPONSE](INCIDENT_RESPONSE.md).

## ۴) شدت حادثه (Severity) — کانن واحد

کانن شدت، [INCIDENT_RESPONSE §۱](INCIDENT_RESPONSE.md) است (**P0 تا P3**). این سند طبقه‌بندی موازی نمی‌سازد؛
فقط نگاشت به زبان رایج صنعت (SEV) برای ارتباط با ذی‌نفع بیرونی:

| کانن ریپو | معادل SEV | پاسخ اولیه | پست‌مورتم |
|---|---|---|---|
| **P0** — قطعی کامل / ازدست‌رفتن داده / نقض امنیتی | SEV1 | ≤ ۵ دقیقه، all-hands | اجباری ۴۸ ساعته |
| **P1** — اختلال گسترده / قطعی بخشی | SEV2 | ≤ ۱۵ دقیقه، آن‌کال + بکاپ | اجباری ۱ هفته‌ای |
| **P2** — یک ویژگی خراب، بقیه سالم | SEV3 | ≤ ۱ ساعت، آن‌کال | اختیاری |
| **P3** — ظاهری/جزئی | SEV4 | روز کاری بعد | ندارد |

قاعدهٔ سفت (نقل از کانن): هر شک به «ازدست‌رفتن داده» یا «دسترسی غیرمجاز» تا اثبات خلاف **P0** است.

## ۵) فرماندهٔ حادثه (Incident Commander)

| بُعد | شرح |
|---|---|
| چه کسی | پیش‌فرض: آن‌کالِ پاسخ‌دهنده. P0: باتجربه‌ترین فرد حاضر (با اعلام صریح در کانال حادثه). |
| اختیار | تأیید rollback/failover · ارتقای/تنزل شدت (تنزل فقط با IC) · فریز دیپلوی · فراخوان all-hands · توقف drill در صورت اثر تولیدی |
| ممنوعه | کدنویسی حین فرماندهی (مگر تنها نیروی فنی) · تصمیم rollback بدون دو شاهد (لاگ + متریک) |
| ارتباطات | به‌روزرسانی ذی‌نفعان هر ۱۵ دقیقه در P0 (قالب در [INCIDENT_PLAYBOOK §۴](INCIDENT_PLAYBOOK.md)) · اعلام پایان رسمی «all-clear» |
| پس از حادثه | مالک پست‌مورتم (مهلت §۴) · ثبت action itemها در [RISK_REGISTER](RISK_REGISTER.md) · ورودی `incident:` در HANDOFF |

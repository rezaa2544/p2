# طرح: حالت‌های زمان‌دار حضور و غیاب و اصلاح گزارش

> **وضعیت: ✅ پیاده شد (دور ۶۶)** — حالت‌های زمان‌دار: تأخیر/خروج با ساعت و دقیقه از زنگ مدرسه
> (`attTimeFields`)، ردپایِ موجه‌سازیِ مدیرانه پس از ثبت، الگوی «خروج مکرر» + پیامکِ خروج.
> آزمون: `tests/att2.js` ۶/۶ + جهش‌ها. متنِ زیر = مرجعِ طراحی (دور ۶۰).

## ۱. پرسش نخست — ویرایش مشخصات کاربران توسط مدیر

### ✅ پاسخ: بله، آزاد است. سنجیده شد.

| کنش | مجوز |
|---|---|
| ویرایش کاربر | مدیر · مدیر کل ✅ |
| حذف کاربر | مدیر · مدیر کل ✅ |
| فعال و غیرفعال کردن | مدیر · مدیر کل ✅ |
| بازنشانی رمز | مدیر · مدیر کل ✅ |

**و محدودهٔ مدرسه رعایت می‌شود** — سنجش اجرایی: مدیر مدرسهٔ یک،
۲۴۳ کاربر مدرسهٔ خودش را می‌بیند و کاربران مدرسهٔ دو در فهرستش
**دیده نمی‌شوند**.

### 🔴 ولی یک استثنا لازم است

طبق تصمیم دور ۵۹، مدیر باید بتواند **شمارهٔ موبایل** را عوض کند
ولی **کد ملی نه** — چون کد ملی کلید هویت است. امروز هر دو
آزادند.

⚠️ اگر مدیر بتواند کد ملی را آزادانه عوض کند، می‌تواند کد ملی
خودش را روی حساب دیگری بگذارد و از احراز هویت رد شود.

## ۲. تبدیل غیبت به تأخیر با زمان

### سناریو

```
۰۸:۰۰  کلاس شروع · دبیر حضور و غیاب می‌کند · علی غایب
۰۸:۳۰  علی می‌رسد
        ↓
دبیر غیبت را برمی‌دارد ⇒ باید «تأخیر ۳۰ دقیقه» شود
```

### 🔴 مشکل امروز

رکورد حضور و غیاب **هیچ فیلد زمانی ندارد**:

```
school_id · class_id · student_id · date · status · note · id
```

«تأخیر» فقط یک برچسب است — نمی‌دانیم پنج دقیقه بوده یا پنجاه.

### راه‌حل پیشنهادی

```js
/* افزوده به رکورد حضور و غیاب */
late_minutes    // ۳۰
arrived_at      // '08:30'
```

**محاسبهٔ خودکار:** ساعت شروع زنگ از زمان‌بندی مدرسه گرفته
می‌شود (از دور ۴۱ موجود است) و اختلافش با «اکنون» تأخیر است.

⚠️ **دام:** اگر دبیر ساعت ۱۱ یادش بیفتد که علی ۸:۳۰ آمده،
محاسبهٔ خودکار «۱۸۰ دقیقه» می‌دهد. پس **میدان ساعت ورود باید
قابل ویرایش باشد** با پیش‌فرض «اکنون».

### اثر بر پروندهٔ انضباطی

**خواستهٔ شما:** «از زمان تشکیل کلاس تا آمدن علی در پروندهٔ
انضباطی لحاظ شود».

🔴 **پیشنهاد من: خودکار ثبت نشود.**

| اگر خودکار باشد | مشکل |
|---|---|
| هر تأخیر ⇒ رکورد انضباطی | پرونده پر از رکورد کم‌اهمیت |
| تأخیر ۳ دقیقه‌ای هم ثبت | تفاوتی با ۴۰ دقیقه ندارد |
| دبیر نمی‌تواند قضاوت کند | شاید دلیل موجه داشته |

**جایگزین — دو لایه:**

۱. **تأخیر همیشه در رکورد حضور ثبت شود** (با دقیقه) — دادهٔ خام
   همیشه در دسترس.
۲. **رکورد انضباطی با آستانه و تأیید:** اگر تأخیر از حدی بیشتر
   بود (مثلاً ۱۵ دقیقه)، به دبیر **پیشنهاد** داده شود، نه
   خودکار.

⚠️ **آستانه را مدیر تعیین کند** — هر مدرسه سیاست متفاوتی دارد.

🟢 **گزارش تجمیعی مفیدتر است:** «علی این ماه ۷ بار تأخیر داشته،
جمعاً ۹۵ دقیقه» — بهتر از هفت رکورد جدا.

## ۳. خروج موقت از کلاس

### سناریو

```
دانش‌آموز اجازه می‌گیرد ⇒ دبیر «خروج از کلاس» را می‌زند
                              ↓
                        تایمر شروع می‌شود
                              ↓
              برمی‌گردد ⇒ دبیر «بازگشت» را می‌زند
                              ↓
                    مدت غیبت از کلاس ثبت می‌شود
```

### مدل داده

```js
/* جدول تازه: class_exits */
{
  id, school_id, class_id, student_id,
  date, period,
  out_at,         // '09:35'
  back_at,        // '09:48' یا null
  minutes,        // ۱۳
  reason,         // اختیاری
  by_teacher_id, created_at
}
```

⚠️ **چرا جدول جدا؟** یک دانش‌آموز ممکن است در یک روز **چند بار**
خارج شود. رکورد حضور یکی است، خروج‌ها چندتا.

### 🔴 سه حالت مرزی

**۱. برنگشت و زنگ تمام شد.** هنگام پایان زنگ، خروج‌های باز باید
**خودکار بسته شوند** با نشان «تا پایان زنگ برنگشت» — وگرنه
تایمر تا فردا می‌شمارد.

**۲. دبیر یادش رفت «بازگشت» را بزند.** هنگام ثبت حضور زنگ بعد،
اگر خروج بازی هست به دبیر یادآوری شود.

**۳. زنگ تفریح وسط خروج.** اگر دانش‌آموز پنج دقیقه مانده به
تفریح خارج شود و پنج دقیقه پس از تفریح برگردد، آیا ۲۵ دقیقه
غیبت داشته؟ 🔴 **نه** — زمان تفریح باید کسر شود.

## ۴. 🔴 اصلاح و حذف گزارش‌های ارسالی

### چرا مهم است

شما گفتید «همه‌چیز باید آنلاین باشد و سریع اعمال شود». پیامد
ناخواسته: **خطای دبیر هم سریع منتشر می‌شود.**

### 🟢 آنچه از قبل هست — سنجیده شد

از دور ۴۲ چهار لایهٔ دفاعی هست:

| لایه | چه می‌کند |
|---|---|
| پیش‌نویس | تیک‌ها تا «ثبت نهایی» ذخیره نمی‌شوند |
| مرور نهایی | خلاصهٔ تغییرات پیش از ثبت |
| پنجرهٔ ۲۰ دقیقه | اصلاح دبیر ⇒ پیام معلق خاموش لغو می‌شود |
| اصلاحیهٔ خودکار | اگر پیام رفته، پیام اصلاحی ساخته می‌شود |

و سابقهٔ تغییرات هم هست (چه کسی، کِی، از چه به چه).

### 🔴 آنچه کم است

**الف) صفحهٔ «گزارش‌های من» برای دبیر.** امروز دبیر می‌تواند
حضور و غیاب را عوض کند، ولی **جای متمرکزی ندارد** که ببیند
امروز چه ثبت کرده.

```
📋 گزارش‌های امروز من

دانش‌آموز    نوع        زمان    وضعیت        اقدام
علی رضایی    غیبت       ۰۸:۰۵   ✅ پیامک رفت  [اصلاح]
مریم احمدی   تأخیر ۱۵د  ۰۸:۲۰   ⏳ در صف      [اصلاح]
حسن کریمی    خروج ۱۳د   ۰۹:۳۵   —            [حذف]
```

**ب) تفکیک «حذف» از «اصلاح».**

| اقدام | چه وقت مجاز | اثر بر پیامک |
|---|---|---|
| **اصلاح** | همیشه | معلق ⇒ به‌روز · رفته ⇒ اصلاحیه |
| **حذف** | 🔴 فقط اگر پیامی نرفته | پیام معلق لغو می‌شود |

🔴 **چرا حذف پس از ارسال ممنوع است؟** اگر خانواده پیامک «غیبت»
گرفته و بعد رکورد پاک شود، هیچ ردی نمی‌ماند که چرا آن پیام رفت.
**اصلاحیه باید فرستاده شود، نه پاک‌کردن تاریخ.**

**ج) پنجرهٔ مهلت برای خروج از کلاس** — امروز فقط برای حضور و
غیاب است.

## ۴.۵ موجه کردن تأخیر پس از ثبت (خواستهٔ دور ۶۲)

**خواستهٔ کاربر:** «امکانش هست بعد از ثبت، مثلاً بعد از یک هفته،
این تأخیر با توجیه اولیا موجه بشه. در این صورت مدیر می‌تواند آن
را در پروندهٔ انضباطی موجه کند و به‌عنوان امتیاز منفی برایش
لحاظ نشود.»

### طراحی

```
تأخیر ثبت شد (۳۰ دقیقه، امتیاز −۳)
        ↓
   یک هفته بعد، ولی توضیح می‌دهد
        ↓
مدیر «موجه» می‌کند ⇒ امتیاز منفی برداشته می‌شود
        ↓
   🔴 ولی رکورد **پاک نمی‌شود** — فقط وضعیتش عوض می‌شود
```

🔴 **چرا رکورد پاک نمی‌شود؟** اگر دانش‌آموزی ده بار تأخیر داشته
و همه موجه‌شده‌اند، این خودش الگویی است که مدیر باید ببیند —
حتی اگر هیچ‌کدام امتیاز منفی نداشته باشد.

### مدل

```js
/* افزوده به رکورد انضباطی */
excused          // 0 | 1
excused_at
excused_by       // شناسهٔ مدیر
excuse_reason    // متن توضیح ولی
```

**محاسبهٔ امتیاز:** رکوردهای موجه‌شده در جمع امتیاز **شمرده
نمی‌شوند**، ولی در فهرست **دیده می‌شوند** با نشان «موجه».

⚠️ **دام محاسباتی:** هر جا امتیاز انضباطی جمع می‌شود، باید
`excused` را کنار بگذارد. اگر یک جا فراموش شود، دو عدد متفاوت
در دو صفحه دیده می‌شود.

### چه کسی می‌تواند موجه کند؟

| نقش | اختیار |
|---|---|
| مدیر | ✅ موجه کردن و برگرداندن |
| دبیر | ❌ فقط ثبت اولیه |
| ولی | ❌ فقط درخواست می‌دهد |

⚠️ **مسیر درخواست ولی:** ولی از پنل خودش «درخواست بررسی» می‌زند
با توضیح. مدیر می‌بیند و تصمیم می‌گیرد. بدون این مسیر، ولی باید
تلفن بزند.

## ۴.۷ 🔴 الگوی تکرار — مهم‌ترین بخش

**خواستهٔ کاربر:** «بعضی دانش‌آموزان عمداً برای فرار از کلاس به
بهانه‌های مختلف خارج می‌شوند. اگر این خروج از حدی بیشتر بود
باید پیگیری شود… یا دانش‌آموزی به کرات تأخیر می‌کند. این‌ها
خیلی مهم‌اند در نظم مدرسه و باید پیگیری شوند و اولیا هم در
جریان باشند.»

### چرا این از خودِ ثبت مهم‌تر است

یک تأخیر ۱۰ دقیقه‌ای چیزی نیست. **ده تأخیر در ماه** یک الگوست.
سامانه باید الگو را ببیند، نه فقط رویداد را.

### سه شمارندهٔ الگو

```js
patternCheck(studentId, days) → {
  late:    { count, totalMinutes, trend },
  exits:   { count, totalMinutes, trend },
  absent:  { count, unexcused }
}
```

**`trend` سه حالت دارد:** رو به افزایش · ثابت · رو به کاهش —
با مقایسهٔ نیمهٔ اول بازه با نیمهٔ دوم (همان روش نمودار روند
نمرات در دور ۴۳).

### آستانه‌ها — قابل تنظیم توسط مدیر

| الگو | پیش‌فرض | چرا این عدد |
|---|---|---|
| تأخیر در ماه | ۴ بار | هفته‌ای یک بار = الگو |
| خروج از کلاس در هفته | ۳ بار | بیش از این یعنی بهانه |
| مجموع دقیقهٔ خروج در هفته | ۴۵ دقیقه | یک زنگ کامل |
| غیبت غیرموجه در ماه | ۳ بار | |

⚠️ **آستانه‌ها باید قابل تنظیم باشند.** مدرسهٔ روستایی که
دانش‌آموزانش با سرویس می‌آیند، تأخیر بیشتری طبیعی دارد.

### چه رخ می‌دهد وقتی آستانه رد شد

```
دانش‌آموز به آستانه رسید
        ↓
۱. نشان هشدار در پروندهٔ دانش‌آموز (همهٔ نقش‌های مجاز می‌بینند)
۲. رکورد در صف پیگیری مدیر
۳. اعلان به ولی  ← 🔴 خودکار نه، با تأیید مدیر
```

🔴 **چرا اعلان به ولی خودکار نباشد؟** ممکن است دانش‌آموز مشکل
خانوادگی یا پزشکی داشته باشد که مدیر می‌داند و دبیر نه. پیام
خودکار «فرزند شما ۵ بار تأخیر داشته» در چنین شرایطی آسیب‌زننده
است.

⚠️ **ولی اگر مدیر تأیید کرد**، از همان سامانهٔ پیام‌رسانی موجود
(دور ۴۲) استفاده می‌شود — با صف تأیید و سقف روزانه.

### نمای الگو برای مدیر

```
📊 الگوهای نیازمند پیگیری — این ماه

┌──────────────┬────────┬──────────┬─────────┬────────┐
│ دانش‌آموز    │ تأخیر  │ خروج     │ روند    │ اقدام  │
├──────────────┼────────┼──────────┼─────────┼────────┤
│ علی رضایی    │ ۷ بار  │ ۲ بار    │ 📈 بیشتر│ [بررسی]│
│              │ ۹۵ دقیقه│ ۲۰ دقیقه │         │        │
│ مریم احمدی   │ ۲ بار  │ ۹ بار    │ 📈 بیشتر│ [بررسی]│
│              │ ۱۵ دقیقه│ ۱۳۰ دقیقه│         │        │
└──────────────┴────────┴──────────┴─────────┴────────┘
```

⚠️ **مریم نمونهٔ خوبی است:** تأخیرش کم است ولی خروجش زیاد —
دقیقاً همان «فرار از کلاس» که کاربر گفت. بدون شمارندهٔ جدا،
این الگو دیده نمی‌شد.

### 🔴 دام: موجه‌شده‌ها در الگو شمرده شوند یا نه؟

**پیشنهاد من: بله، ولی جدا.**

```
علی رضایی: ۷ تأخیر (۳ موجه · ۴ غیرموجه)
```

دانش‌آموزی که هفت بار دیر آمده — حتی اگر همه موجه باشند — مشکلی
دارد که باید دیده شود. شاید سرویسش مشکل دارد یا مسیرش دور است.

## ۵. مدل داده — جمع‌بندی

```js
/* افزوده به attendance */
late_minutes     // عدد یا null
arrived_at       // 'HH:MM' یا null

/* جدول تازه: class_exits */
{ id, school_id, class_id, student_id, date, period,
  out_at, back_at, minutes, reason, by_teacher_id, created_at }

/* افزوده به discipline — موجه کردن پس از ثبت (بخش ۴.۵) */
excused          // 0 | 1
excused_at
excused_by       // شناسهٔ مدیر
excuse_reason    // توضیح ولی

/* جدول تازه: excuse_requests — درخواست ولی */
{ id, school_id, student_id, discipline_id,
  parent_id, reason, status,      // 'pending'|'approved'|'rejected'
  created_at, decided_at, decided_by }

/* افزوده به schools.discipline_rules */
{ late_threshold_min: 15,        // آستانهٔ پیشنهاد رکورد انضباطی
  exit_threshold_min: 20,
  auto_discipline: false,        // 🔴 پیش‌فرض خاموش

  /* آستانه‌های الگو (بخش ۴.۷) — همه قابل تنظیم */
  pattern_late_month:  4,        // تأخیر در ماه
  pattern_exit_week:   3,        // خروج در هفته
  pattern_exit_min:    45,       // مجموع دقیقهٔ خروج در هفته
  pattern_absent_month: 3,       // غیبت غیرموجه در ماه
  pattern_notify_parent: false } // 🔴 اعلان به ولی فقط با تأیید مدیر
```

⚠️ **چرا `pattern_notify_parent` پیش‌فرض خاموش است؟** ممکن است
دانش‌آموز مشکل خانوادگی یا پزشکی داشته باشد که مدیر می‌داند و
سامانه نه. پیام خودکار در چنین شرایطی آسیب‌زننده است.

## ۷. 🔴 هشدارها

| ریسک | توضیح |
|---|---|
| ثبت خودکار انضباطی | پرونده پر از رکورد کم‌اهمیت |
| تایمر خروج بی‌پایان | هنگام پایان زنگ خودکار بسته شود |
| کسر زمان تفریح | وگرنه خروج ۵ دقیقه‌ای ۲۵ دقیقه محاسبه می‌شود |
| حذف پس از ارسال پیامک | 🔴 ممنوع — اصلاحیه باید برود |
| ساعت دستگاه | همان محدودیت دورهای پیشین |

⚠️ **یک نکتهٔ انسانی:** ثبت دقیقه‌به‌دقیقهٔ خروج دانش‌آموز، حس
نظارت شدید می‌دهد. پیشنهاد می‌کنم دلیل خروج **اختیاری** بماند و
در پروندهٔ دائمی ثبت نشود مگر با تصمیم دبیر.

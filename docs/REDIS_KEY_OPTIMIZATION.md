# بهینه‌سازی کلیدهای Redis و TTL — پایش و قراردادها

> فاز ۲ چت ۴ — ممیزی کلیدها، تضمین انقضا و ابزار پایش (۲۰۲۶-۰۹-۰۹)
> ابزار: `tools/redis-audit.js` · تست: `tests/redis-key-audit.js`

## ۱. فهرست کامل کلیدها

| الگوی کلید | مالک | TTL | وضعیت |
|---|---|---|---|
| `payesh:cache:bootstrap:<userId>` | `server/cache.js` (بوت‌استرپ) | ۳۰۰ ثانیه | ✅ |
| `payesh:rl:<action>:<identifier>` | `server/cache.js` + `server/waf.js` | به‌اندازهٔ پنجره (60–900 ثانیه) | ✅ |
| `payesh:rl:waf:ip:<ip>` | `server/waf.js` | ۶۰ ثانیه (۱۰۰ درخواست/دقیقه) | ✅ |
| `payesh:rl:waf:audit:<rule>` | `server/waf.js` | ۶۰ ثانیه (۵ ممیزی/دقیقه) | ✅ |
| `payesh:idempotency:<uid>` | `server/cache.js` ← `server/sync.js` | ۲۴ ساعت | ✅ |
| `payesh:lock:<name>` | `server/cache.js` (قفل پی۰-۱۴) | ۵–۱۰ ثانیه (به‌اندازهٔ بحرانی) | ✅ |
| `payesh:otp:state` | `server/otp-store.js` | **دائمیِ مجاز** | ✅ (عمدی) |
| `rate:otp:send:phone:day:<phone>` | `server/rate-limit.js` | ۲۴ ساعت | ✅ |
| `rate:otp:send:ip:<ip>` / `rate:otp:send:phone:<phone>` | `server/rate-limit.js` | ۹۰۰ ثانیه | ✅ |
| `rate:otp:login:ip:<ip>` | `server/rate-limit.js` | ۹۰۰ ثانیه | ✅ |

کانالِ `payesh:pubsub:inval` هم وجود دارد که کلید نیست (Pub/Sub برای بی‌اعتبارسازی کش).

## ۲. تصمیم‌های ممیزی

- **`payesh:otp:state` چرا دائمی است؟** این سند شامل کدهای ورود (۵ دقیقه)،
  کول‌داون ارسال و تأخیر تصاعدی ورود است. اگر ۵ دقیقه منقضی می‌شد، شمارندهٔ
  تأخیرِ بروت‌فورس بعد از هر انقضا صفر می‌شد — **ضعف امنیتی**. اندازهٔ سند با
  هرسِ درون‌سندی (افق ۲۵ ساعت + عمر کد) کراندار است، پس نشتی در کار نیست.
- **کلیدهای `rate:*` و نشتِ پنجرهٔ کرش:** الگوی قدیمی `INCR` سپس `EXPIRE`
  بود؛ اگر فرایند میان این دو می‌مُرد، کلید برای همیشه بی‌TTL می‌ماند
  (نشت حافظه در مقیاس ملی). حالا `redis.incrWithTtl` با یک اسکریپت لوآ
  اینکریمِنت + تضمین انقضا را اتمیک انجام می‌دهد و هر کلید یتیمِ مانده، در
  اولین برخوردِ بعدی خوددرمانی می‌شود.
- **قفل‌ها:** TTL کوتاه و به‌اندازهٔ بحرانی (۵ ثانیه برای شناسه‌ها، ۱۰ ثانیه
  برای فلاش حالت ورود). افزایش بی‌دلیل یعنی ماندگاری بیشترِ قفلِ مرده.
- **کلیدهای `revoked:*` / `id:seq:*`** که در برخی جدول‌های مروری ذکر شده‌اند،
  در این مخزن وجود ندارند: ابطال نشست در `store.__revoked_jti` نگهداری می‌شود
  و دنباله‌های شناسه سمت پستگرس‌اند (پی۰-۱۶)، نه ردیس.

## ۳. دستورالعمل پایش

```bash
# گزارش کامل (با محیط واقعی سرور؛ بدون REDIS_URL روی درایور حافظه کار می‌کند)
REDIS_URL=redis://… node tools/redis-audit.js

# خروجی: فهرست کلیدها با TTL و مالک + پرچمِ:
#   ⚠️  کلید بی‌انقضای غیرمجاز (یتیم)
#   ❓ کلید ناشناخته (باید در KEY_SPECS ثبت شود)
# کد خروجی: ۰ سالم، ۲ نیازمند رسیدگی
```

پیشنهاد اجرا: بعد از هر استقرار، و به‌صورت دوره‌ای (کرون) روی هر نمونه.
اگر کلید تازه‌ای به پروژه اضافه شد، ابتدا در `KEY_SPECS` ابزار ثبتش کنید
تا ممیزی آن را «ناشناخته» نداند.

## ۴. قواعد قراردادی برای کلیدهای آینده

1. هر کلید یا باید انقضا داشته باشد، یا در فهرست «دائمیِ مجاز» ثبت شود.
2. شمارنده‌ها فقط با `redis.incrWithTtl` ساخته شوند (تضمین انقضا اتمیک).
3. قفل‌ها فقط از `cache.acquireLock/releaseLock` (توکن‌دار) گرفته شوند.
4. هیچ‌گاه از `KEYS *` استفاده نشود — فقط `redis.scan` (SCAN با مکان‌نما).

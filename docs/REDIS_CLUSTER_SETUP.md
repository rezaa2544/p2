# راهنمای کامل استقرار ردیس — پایش (فاز ۲.۱)

> مرجع استقرار تولید: توپولوژی سنیتنل ۳ نودی (وضعیت پشتیبانی‌شدهٔ
> فعلی)، پایداری RDB+AOF، پشتیبان‌گیری خودکار، و نقشهٔ ارتقا به
> Redis Cluster برای مقیاس ملی.
>
> فایل‌های پیکربندی: `ops/redis/` · پشتیبان: `tools/redis-backup.sh` ·
> بازیابی: `docs/REDIS_RESTORE_PROCEDURE.md` · آزمون: `tests/redis-cluster.js`

---

## ۱) معماری انتخاب‌شده و چرا

| حالت | کی؟ | وضعیت در پایش |
|---|---|---|
| **۳ نود + ۳ سنیتنل** (مستر + ۲ تکثیر) | حجم داده در گنجایش یک نود است؛ نیاز به شکست‌خورد خودکار | ✅ استقرار پیش‌فرض فاز ۲.۱ |
| **Redis Cluster** (≥۳ مستر + ≥۳ تکثیر) | داده از گنجایش یک مستر فراتر رفت یا افق افقی لازم شد | 📋 نقشهٔ ارتقا — بخش ۶ |

تحلیل مقیاس ملی: بار پایش عمدتاً کلیدهای کوچک با طول عمر کوتاه است
(شمارنده‌های نرخ، کش، قفل نشست) — الگویی که سنیتنل با یک مستر به‌خوبی
پاسخ می‌دهد؛ کلاستر زمانی لازم می‌شود که **حجم ماندگار** یا **توان
نوشتن تک‌نود** گلوگاه شود.

## ۲) پیش‌نیازهای میزبان

- ۳ میزبان مستقل (ترجیحاً در رک/زون متفاوت) — هر میزبان: یک نود داده
  + یک سنیتنل.
- پورت‌های باز بین میزبان‌ها: `6379` (داده) و `26379` (سنیتنل)؛ برای
  کلاستر آینده `16379` (گفت‌وگوی کلاستر) هم باز خواهد شد.
- `maxmemory` متناسب با حافظهٔ آزاد؛ سیاست پایش `noeviction` است
  (دادهٔ نشست/شمارنده هرگز نباید بیرون انداخته شود) — کمبود حافظه
  باید با هشدار قبل از بحران دیده شود.
- دیسک ماندگار برای `/var/lib/redis/*` (ترجیحاً حجم جدا؛ حداقل
  ۲× اندازهٔ داده برای RDB+AOF هم‌زمان).

## ۳) استقرار توپولوژی سنیتنل

### ۳.۱) پیکربندی

الگوها در `ops/redis/` — دو جای‌دار دارند که در زمان استقرار پر می‌شود:

| جای‌دار | مقدار |
|---|---|
| `{{REDIS_PASSWORD}}` | رمز ردیس — فقط از مخزن اسرار محیط، هرگز در گیت |
| `{{REDIS_NODE1_HOST}}` | نشانی میزبان نود ۱ (مستر اولیه) |

```bash
# میزبان A (نود ۱ = مستر + سنیتنل ۱)
sed -e "s/{{REDIS_PASSWORD}}/${REDIS_PASSWORD:?}/" \
    -e "s/{{REDIS_NODE1_HOST}}/${NODE1_HOST:?}/" \
    ops/redis/redis-node-1.conf > /etc/redis/redis.conf
sed -e "s/{{REDIS_PASSWORD}}/${REDIS_PASSWORD:?}/" \
    -e "s/{{REDIS_NODE1_HOST}}/${NODE1_HOST:?}/" \
    ops/redis/sentinel-1.conf > /etc/redis/sentinel.conf
systemctl enable --now redis redis-sentinel
```

همین دو فرمان را روی میزبان‌های B و C با `redis-node-2.conf` /
`redis-node-3.conf` و `sentinel-2/3.conf` تکرار کنید (نودهای ۲ و ۳ در
خود الگو `replicaof {{REDIS_NODE1_HOST}} 6379` دارند).

### ۳.۲) اتصال پایش

```bash
REDIS_SENTINELS=<A>:26379,<B>:26379,<C>:26379
REDIS_SENTINEL_NAME=payesh-master
REDIS_PASSWORD=<از مخزن اسرار>
```

`server/redis.js` در بالاآمدن، کشف مستر را از سنیتنل‌ها می‌گیرد و در
قطعی، پس از شکست‌خورد سنیتنل، خودکار به مستر تازه وصل می‌شود. بدون
هیچ‌کدام از این متغیرها، سرور با فال‌بک درون‌حافظه‌ای بالا می‌آید —
این حالت **فقط برای توسعه** است (تک‌پروسه، بدون اشتراک بین نمونه‌ها).

### ۳.۳) تأیید استقرار

```bash
# یک مستر واحد از دید هر سه سنیتنل
for h in <A> <B> <C>; do
  redis-cli -h $h -p 26379 SENTINEL get-master-addr-by-name payesh-master
done

# دو تکثیر متصل
redis-cli -a "$REDIS_PASSWORD" INFO replication | head

# پایداری فعال است؟
redis-cli -a "$REDIS_PASSWORD" INFO persistence | grep -E 'aof_enabled|rdb_last_bgsave_status'
# انتظار: aof_enabled:1 و rdb_last_bgsave_status:ok

# آزمون خودکار اتصال (با همان متغیرهای محیط بالا)
node tests/redis-cluster.js
```

## ۴) پایداری داده (خلاصهٔ مصوبه)

| مورد | مقدار | چرا |
|---|---|---|
| `save 900 1 / 300 10 / 60 10000` | عکس فوری سه‌آستانه | نقطهٔ بازیابی دوره‌ای |
| `appendonly yes` + `appendfsync everysec` | AOF هر ثانیه | حداکثر زیان = ۱ ثانیه |
| `auto-aof-rewrite-percentage 100` + `min-size 64mb` | بازنویسی خودکار | کنترل اندازهٔ فایل |
| `stop-writes-on-bgsave-error yes` | توقف نوشتن در شکست ذخیره | خرابی ذخیره‌سازی پنهان نمی‌ماند |
| `maxmemory-policy noeviction` | بدون بیرون‌اندازی | نشست‌ها/شمارنده‌ها هرگز گم نشوند |

جزئیات در `ops/redis/redis-node-*.conf` و `ops/redis/README.md`.

## ۵) پشتیبان و بازیابی

- **پشتیبان خودکار:** `tools/redis-backup.sh` — کرون هر ۶ ساعت،
  نگهداری ۷ روز، خروجی `dump-<TS>.rdb` + `appendonly-<TS>.aof` +
  مانیفست؛ در صورت تنظیم `BACKUP_S3` نسخه‌ها در فضای شیئی هم می‌رود.

  ```cron
  0 */6 * * * /opt/payesh/tools/redis-backup.sh >> /var/log/redis/backup.log 2>&1
  ```

- **بازیابی:** `docs/REDIS_RESTORE_PROCEDURE.md` — اولویت با AOF؛ تمرین
  در محیط جدا پیش از هر مهاجرت الزامی است.

## ۶) نقشهٔ ارتقا به Redis Cluster

پیش‌شرط‌ها: کد کلاینت آماده است (`REDIS_CLUSTER_NODES` در
`server/redis.js`)؛ پیکربندی الگو در `ops/redis/README.md`.

1. **ظرفیت‌سنجی:** اگر `INFO memory` نشان داد `used_memory` به ~۶۰٪
   حافظهٔ نود رسید یا نرخ نوشتن به سقف تک‌نود نزدیک شد، مهاجرت را شروع کنید.
2. **شش نود:** روی همان سه میزبان (یا سه میزبان جدید) نودهای
   `7000..7005` را با `cluster-enabled yes` بالا بیاورید:
   ```bash
   redis-cli --cluster create \
     <A>:7000 <B>:7000 <C>:7000 <A>:7001 <B>:7001 <C>:7001 \
     --cluster-replicas 1
   ```
3. **بررسی کلیدها:** کلیدهای چندکلیدی پایش باید هم‌اسلات شوند —
   هر جا چند کلید با هم خوانده/نوشته می‌شوند، هش‌تگ `{…}` بگیرند
   (مثل `rate:{login}:ip`). کلیدهای تکی نیاز به تغییر ندارند.
4. **سوییچ:** متغیر محیط پایش را به `REDIS_CLUSTER_NODES` تغییر دهید —
   کد برنامه تغییری نمی‌خواهد. یک دور کامل آزمون (`tests/redis-cluster.js`
   + تست بازیابی در محیط جدا) پیش از سوییچ اجرا شود.
5. **نگهبانی پس از سوییچ:** حداقل ۴۸ ساعت `cluster_state:ok`، بدون
   اسلات مهاجرتِ باز، و پشتیبان‌گیری موفق — سپس سنیتنل‌ها بازنشسته
   می‌شوند (در کلاستر، خود کلاستر مسئول شکست‌خورد است).

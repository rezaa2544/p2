## ۱. خلاصهٔ یک‌خطی

امروز «رئیس اداره» **یک نقش** (`edu_office`) با **سه سطحِ واقعی** (استان / شهرستان / منطقه)
است که سطحش روی **رکوردِ اداره** نشسته، نه روی حساب. پیشنهاد: افزودنِ
`office_level` به **حساب** (`users.office_level ∈ {district, province}`) به‌عنوان
کلیدِ تشخیص، با یک **نگاشتِ رسمی و صریح** برای سطحِ سوم (شهرستان)، و تفکیکِ
تدریجیِ ناوبری/داشبورد/دامنه بر اساس آن.

## ۳. مسئله (چرا وضعیتِ فعلی کافی نیست)

1. **ابهامِ مرجع:** سطح روی اداره است؛ هرجا که به `office` دسترسی نباشد
   (مثلاً در `canRoute` که فقط `role` می‌گیرد، یا در JWT) سطح گم می‌شود.
2. **یک UI برای سه مقیاس:** کارتِ «پراکندگی به تفکیک شهرستان» برای ادارهٔ
   **منطقه** بی‌معناست (یک شهرستان بیشتر ندارد) و برای ادارهٔ **استان** بیش‌ازحد
   درشت است (باید بتواند به شهرستان/منطقه سفر کند).
3. **نامحدود بودنِ سمت سرور (#۹):** وقتی دو سطح داشته باشیم، ادارهٔ استانِ تهران
   با همین قانون می‌تواند روی مدرسه‌ای در کردستان بنویسد. تفکیکِ سطح **اگر سمت
   سرور اجرا نشود، فقط تزئین است.**
4. **حسابرسی:** نمی‌توان گفت «کدام سطح این بخشنامه را ابلاغ کرد» چون در رکورد
   فقط `created_by` هست و سطح باید از اداره استخراج شود (و اداره ممکن است بعداً
   تغییر کند).

## ۴. پیشنهادِ طراحی

### ۴.۱ کلیدِ تشخیص: `office_level` روی حساب

```
users.office_level  ∈  'district' | 'province'
```

* **تک‌منبعِ حقیقت همچنان `offices.level` است**؛ `users.office_level` یک
  **برآیندِ کَش‌شده** است که هنگام ساخت/ویرایشِ حساب و هنگام تغییرِ سطحِ اداره
  بازنویسی می‌شود (یک تابع، یک نقطهٔ تعریف).
* نگاشتِ رسمی برای سطحِ سوم (شهرستان) — تصمیمِ پیشنهادی:

  | `offices.level` | `users.office_level` | توضیح |
  |---|---|---|
  | `district` | `district` | ادارهٔ ناحیه/منطقه |
  | `county`   | `district` | **شهرستان در این فاز «سطحِ منطقه» دیده می‌شود** (دامنه = کلِ شهرستان) |
  | `province` | `province` | اداره کل استان |

  > چرا شهرستان ⇐ منطقه؟ چون تفاوتِ این دو در **دامنه** است (شهرستان شامل چند
  > منطقه است)، نه در **جنسِ کار**؛ هر دو «دیدِ مدرسه‌به‌مدرسه» دارند. سطحِ
  > استان جنسِ کارش فرق می‌کند: تجمیع و پایشِ اداراتِ زیرمجموعه.

### ۴.۲ نگاشتِ سطح (fail-closed)

```js
function effectiveOfficeLevel(u){
  if(!u || u.role !== 'edu_office') return null;          // نقشِ دیگر: بی‌معنا
  if(u.office_level === 'province' || u.office_level === 'district') return u.office_level;
  var o = officeOf(u);                                     // از روی اداره استخراج
  if(o && o.level === 'province') return 'province';
  if(o && (o.level === 'district' || o.level === 'county')) return 'district';
  return 'district';   // 🔴 پیش‌فرض = کم‌دسترسی‌ترین سطح (fail-closed)
}
```

* پیش‌فرض عمداً **`district`** است: اگر سطح نامعلوم بود، کاربر دیدِ محدود
  می‌گیرد تا این‌که ناگهان دیدِ استانی پیدا کند.
* ناهماهنگیِ حساب/اداره (مثلاً حساب `province` ولی اداره `district`) یک
  **هشدارِ حسابرسی** می‌سازد و برآیند را **باریک‌تر** می‌گیرد
  (`intersection`): هر دو باید `province` باشند تا استان داده شود.

### ۴.۳ روت‌ها و ناوبری

| روت | `district` | `province` | توضیح |
|---|:--:|:--:|---|
| `officedash` | ✅ | ✅ | سطحِ منطقه: مدارسِ محدوده؛ سطحِ استان: تجمیعِ مناطق + دریل‌داون |
| `officeschools` | ✅ | ✅ | فهرستِ مدارسِ محدوده (استان: با فیلترِ شهرستان/منطقه) |
| `provincedash` *(جدید)* | ❌ | ✅ | کارتِ امتیازیِ استان: مقایسهٔ مناطق با هم |
| `officescore` *(جدید — D.2)* | ✅ | ✅ | کارتِ امتیازیِ محدوده |
| `staffneeds` *(جدید — D.4)* | ✅ (خواندن) | ✅ (خواندن) | مدیر اعلام می‌کند، اداره می‌بیند |
| `announcements` | ✅ | ✅ | D.3 نوعِ فوری/بحرانی |

قاعدهٔ ناوبری پیشنهادی: **منو از `NAV` استخراج می‌شود، سپس با سطح پالایش
می‌شود** — یعنی `navRoutesOf(role)` + `levelFilter(role, level)`. این کار
نیاز به `NAV.edu_office_province` ی جدا ندارد و تک‌منبعِ حقیقت (`NAV`) را
حفظ می‌کند.

### ۴.۴ مجوزدهی

**کلاینت (فازِ دمو — می‌دانیم که سدِ نهایی نیست):**

```js
canRoute(route, role, level)
// علاوه بر allowedRoutes(role)، برای روت‌هایِ استانی
// شرطِ level === 'province' هم لازم است.
```

**سرور (ضروری — بند ۳.۳ بالا):**

1. `office_level` به **ادعاهای JWT** افزوده شود (`server/auth.js`)؛
2. `server/sync.js:447` از «بازگشتِ همیشگیِ true» به **بررسیِ محدوده** تغییر کند:
   * `district` → فقط مدارسی که در `province/county/district` ادارهٔ کاربرند؛
   * `province` → فقط مدارسی که در استانِ ادارهٔ کاربرند؛
   * نامعلوم → **رد** (fail-closed).
3. این تغییر باید **پیش از** فعال‌سازیِ سطحِ استان در تولید انجام شود،
   وگرنه «تفکیک سطح» فقط یک برچسبِ رابط است.
4. نیازمندِ آزمونِ ویژه: «ادارهٔ استانِ تهران نمی‌تواند روی مدرسهٔ کردستان
   بنویسد» (آزمونِ سروری + آزمونِ جهشی).

### ۴.۵ مدلِ داده و مهاجرت

* `authz/model.json` → `users.fields` += `office_level`
  (بدون تغییر در `ins/upd/del`: همان manager/superadmin که امروز حسابِ اداره
  را می‌سازند).
* `server/schema.sql` → ستونِ `office_level VARCHAR(16)` روی `users`.
* مهاجرتِ داده: برای هر `users.role === 'edu_office'` مقدار از
  `offices.level` با نگاشتِ §۴.۱ پُر می‌شود؛ رکوردهای بی‌`office_id`
  مقدارِ `district` می‌گیرند + یک گزارشِ حسابرسی از مواردِ نامعلوم.
* **سازگاری با عقب:** تا وقتی `office_level` پر نشده، `effectiveOfficeLevel`
  از اداره استخراج می‌کند ⇒ نیازی به توقفِ سرویس نیست.

## ۱) نمای معماری (Architecture Overview)

```text
Internet
  ↓
DNS → CDN → WAF/DDoS → LB (nginx edge: nginx/nginx.conf)
  ↓
API #1 … API #N  ← Node بدون وضعیت (هر نمونه یک پروسه؛ سرور داخلی)
  ├─→ PgBouncer :6432 (txn pooling)
  │      ├─ payesh          → pg-primary  (تنها منبع نوشتن) ──→ آرشیو WAL/بکاپ (S3/MinIO، pgbackrest)
  │      └─ payesh-readonly → pg-standby  (hot standby؛ گزارش‌های سنگین)
  ├─→ Redis (master + 2 replica / 3 sentinel — نام: mymaster)
  │      ← OTP · rate-limit · idempotency · نشست/ابطال · کش
  └─→ outbox (در PostgreSQL) → ورکرهای ناهمگام (SMS/گزارش/پشتیبان)

پایش: Prometheus ← /metrics (دروازهٔ METRICS_TOKEN؛ لبه هرگز روت نمی‌کند)
      → Grafana / Loki / Jaeger / Alertmanager (infra/observability/)
```

### مسیرهای حیاتی

| مسیر | روت‌ها | وابستگی‌ها | رفتار در خرابی |
|---|---|---|---|
| **ورود (login)** | `POST /api/auth/send-code` → `POST /api/auth/login` → `GET /api/auth/me` | Redis (هش OTP، ریت‌لیمیت) + کاربران در PG | ردیابی‌پذیر با `trace_id`؛ ریت‌لیمیت توزیع‌شده جلوی طوفان را می‌گیرد |
| **همگام‌سازی (sync)** | `POST /api/sync` + پولِ صفحه‌بندی‌شدهٔ دلتا | تراکنش PG + کلید توان‌دهی (Redis) + OCC | شکست = 503/409 تمیز؛ کلاینت با صف آفلاین + صف مرده محافظت می‌شود |
| **حضور (attendance)** | روت‌های `attendance` (بوتهای کلاس‌محور) | نوشتن تراکنشی + `server/routes/attendance.js` (گاردهای scope زنده؛ middleware قدیمی حذف شده) + `server/policy.js` | هرگز دادهٔ مدرسهٔ دیگر نشت نمی‌کند (تطبیق `tools/check-authz.js`) |
| **نمره (grades)** | روت‌های `grades` | PG + `base_version` (تعارض → 409) | بازنویسی هم‌زمان غیرممکن است؛ تعارض‌ها در `sync_conflicts` ثبت می‌شوند |

### منابع مشترک بین نمونه‌ها (و آنچه مشترک نیست)

| منبع | مشترک؟ | قرارداد |
|---|---|---|
| PostgreSQL | ✅ | **تنها** منبع حقیقت (§2 نقشه راه)؛ همهٔ نمونه‌ها از یک استخر می‌خوانند/می‌نویسند |
| Redis | ✅ | حالت توزیع‌شدهٔ گذرا (نرخ/نشست/توان‌دهی/کش)؛ «ردیس مرده = نمونه آماده نیست» (P0-13) |
| outbox/صف | ✅ | ردیف‌های `server_outbox` با `status='pending'` — عمقش سنجهٔ `payesh_sync_queue_depth` است |
| کش L1 هر نمونه | ❌ | محلی، محدود، با TTL — بی‌خطر چون لایهٔ بالاسری‌اش مشترک است |
| لاگ ممیزی هر نمونه | ❌ | چرخش ۱۰ مگابایتی `server/audit.js`؛ همبستگی با `trace_id` |

> ⚠️ **وضعیت فعلی مقیاس افقی:** تا ادغام کامل موج ۱ (شاخهٔ چت ۳)،
> `memoryStore` هر نمونه جداست و حالت فایلیِ `server/otp-store.js` باقی است ⇒
> **تولیدِ چند‌نمونه‌ای امن نیست** (چک‌لیست آمادگی، محور توزیع‌شدگی). افزودن نمونه
> فقط پس از آن ادغام مجاز است — رویهٔ §۵ همین‌جا آماده است.

## ۲) راه‌اندازی و خاموشی (Startup / Shutdown)

### چک‌لیست پیش‌پرواز (قبل از هر بوت/استقرار)

- [ ] درخت کاری تمیز + `node tests/secret-scan.js` سبز (هیچ رازی در تغییرات نیست)
- [ ] فایل‌های محیط (`.env`) موجود، با دسترسی `0600` و بیرون از ریپو
- [ ] `PAYESH_JWT_SECRET` حداقل ۲۵۶ بیت (کمتر = بوت **نمی‌شود** — شکست‌بستهٔ R96)
- [ ] مهاجرت‌های `migrations/` روی مقصد اعمال شده‌اند (`psql -c '\dt'` با جداول مورد انتظار)
- [ ] آخرین بکاپ سبز: `pgbackrest --stanza=payesh info` (خطای بدون backup = توقف)
- [ ] استک پایش بالا و آمادهٔ اسکراپ (`docs/OBSERVABILITY_DEPLOYMENT.md` §۳)
- [ ] دروازهٔ انتشار: `node tools/release-gate.js` سبز

### ترتیب بوت — هرگز جابه‌جا نشود

1. **PostgreSQL**: بالاآوردن استک (`infra/postgres/docker-compose.ha.yml`) →
   `bash infra/postgres/post-checks.sh` باید **سبز** شود (ارسال‌کنندهٔ WAL، آرشیو، لاگ).
2. **Redis**: بالاآوردن استک (`infra/redis/docker-compose.sentinel.yml`) →
   `bash infra/redis/redis-checks.sh` باید سبز شود (نقش‌ها + دید سنتینل‌ها).
3. **گره‌های API**: بوت هر نمونه. بوت **شکست‌بسته** است: نبودِ کشِ توزیع‌شدهٔ سالم =
   خروج `FATAL` از پروسه (`server/index.js`) — هرگز با ری‌استارتِ پشت‌سرهم «درستش نکنید»؛
   ابتدا بند ۲ همین فهرست را سبز کنید. تأیید هر نمونه:
   `curl -sf <node>/api/health` ⇒ `{"ok":true,...}` (و اسکرپ `/metrics`).
4. **لبه (LB)**: افزودن نمونه‌ها به `upstream` در `nginx/nginx.conf` + بارگذاری مجدد +
   تأیید از بیرون: `curl -sf https://<دامنه>/api/health`.

### ترتیب خاموشی — دقیقاً برعکس

1. **لبه (LB)**: نمونهٔ هدف از `upstream` خارج و بارگذاری مجدد شود؛ ترافیک تازه‌ای نگیرد.
2. **گره‌های API**: `SIGTERM` به پروسه ⇒ توالی درینِ موج ۱۵ (`server/index.js`):
   درین ⇒ توقف پذیرش اتصال تازه ← انتظارِ درخواست‌های درحال‌پرواز ← ذخیرهٔ پایانی ←
   بستن اتصال‌های دیتابیس و ردیس ← خروج با کد `0`. جزئیات: بندِ راستی‌آزمایی.
3. **Redis**: فقط پس از آنکه هیچ نمونه‌ای به آن نیاز ندارد (در عمل: خاموشی کامل استک).
4. **PostgreSQL**: آخرین جزء؛ پیش از آن `pg_stat_archiver` بدون خطا (آرشیوِ قطع‌شده یعنی
   از‌دست‌رفتن پنجرهٔ بازیابی نقطه‌ای).

### راستی‌آزمایی خاموشیِ آرام

- کد خروج هر نمونه `0` است؛ لاگ `FATAL`/پشتهٔ خطا ندارد.
- `SHOW POERS` نیست — در عمل: `pgbouncer` اتصالِ بازِ مرتبط با نمونهٔ مرده ندارد
  (`psql` به پورت ۶۴۳۲ → `SHOW CLIENTS` بدون ردیف‌های آن نمونه).
- عمق `server_outbox` (pending) ثابت مانده یا کاهش یافته — رشد یعنی ورکرها نرفته‌اند.
- **تخلیهٔ درحال‌پرواز (موج ۱۵، مرج‌شده در `main`):** بلافاصله پس از `SIGTERM` نمونه
  درین می‌شود ⇒ `/api/readiness` فوراً ۵۰۳ می‌دهد (لبه ترافیک تازه نمی‌فرستد) ⇒
  درخواست‌های درحال‌پرواز تا مهلت `PAYESH_SHUTDOWN_TIMEOUT_MS` (پیش‌فرض ۱۰ ثانیه)
  فرصت پایان دارند. کد خروج `0` فقط برای ختمِ تمیز است؛ عبور از مهلت = خروجِ
  اجباری با کد `1` (غیرصفر = قابل مشاهده در مانیتورینگ؛ با «ری‌استارت بیشتر» حلش نکنید).

## ۳) پایش و سلامت (Monitoring & Health)

### پایان‌گرهای سلامت

| پایان‌گر | وضعیت فعلی | قرارداد |
|---|---|---|
| `GET /api/health` | ✅ زنده | `200 {ok:true}` فقط وقتی کشِ توزیع‌شده آماده است؛ وگرنه `503` (شکست‌بستهٔ P0-13). در حالت PG زنده، وضعیت استخرها (`db_pools`) هم دارد |
| `GET /metrics` | ✅ زنده | اکسپوزیشنِ پرومتئوس؛ پشت دروازهٔ `METRICS_TOKEN` (401 بدون هدر)؛ لبه **هرگز** روتش نمی‌کند (در فهرست مجازِ دبلیو‌ای‌اف) |
| `GET /api/liveness` | ✅ زنده (موج ۱۵) | همیشه ۲۰۰ — عمداً وابستگی‌ها را چک نمی‌کند تا خرابیِ دیتابیس/ردیس، ارکستراتور را به ری‌استارتِ طوفانی وادار نکند؛ حتی در حالِ درین هم ۲۰۰ است |
| `GET /api/readiness` | ✅ زنده (موج ۱۵) | ۲۰۰ فقط وقتی دیتابیس و کش زنده‌اند و نمونه درین نیست؛ در `PAYESH_ENV=production` زنده‌بودنِ ردیس الزامی است (شکست‌بستهٔ پی‌۰-۱۳) ⇒ ۵۰۳ یعنی «ترافیک نفرست» |

### سنجه‌های کلیدی برای پایش مستمر (همه در `server/metrics.js`)

| سنجه | معنی | آستانهٔ توجه |
|---|---|---|
| `payesh_http_requests_total` / `..._duration_seconds` | توان و تأخیر (p50/p95/p99 از هیستوگرام) | مطابق اهداف `CAPACITY_MODEL.md` §۵ |
| `payesh_redis_up` · `payesh_redis_ping_latency_ms` | دسترس‌پذیری کش توزیع‌شده | `0` بیش از ۱ دقیقه ⇒ بحرانی |
| `payesh_db_up` · `payesh_db_query_latency_ms` | دیتابیس + تأخیر نمونه‌ای | بیش از ۵۰ میلی‌ثانیه پایدار ⇒ هشدار |
| `payesh_db_pool_{total,idle,waiting}` | اشباع استخر اتصال | `waiting>0` پایدار ⇒ پولر/ظرفیت |
| `payesh_sync_queue_depth` | عمق صف ناهمگام | بیش از ۱۰۰۰ ⇒ پلی‌بوک ۱۰ |
| `payesh_cache_hits_total` / `..._misses_total` | نرخ اصابت هدف: بالای ۸۰٪ | افت پایدار ⇒ بار دیتابیس چند برابر می‌شود |

| `payesh_process_heap_bytes` / `rss` / `gc_total` | حافظه و نشتی | بالای ۸۰٪ سقف = هشدار؛ روند صعودی = پلی‌بوک ۵ |

## ۴) عملیات روتین (Routine Operations)

| عملیات | دوره | دستور / معیار سبز |
|---|---|---|
| **راستی‌آزمایی بکاپ** | روزانه | `pgbackrest --stanza=payesh info` + بررسی لاگِ کرونِ میزبان (طرح: یکشنبه‌ها کامل، بقیهٔ روزها تفاضلی — `HA_POSTGRES.md` §۵). هر خطا = حادثهٔ سطح ۲ |
| **دریل بازیابی** | ماهانه | `tools/pitr-restore.sh --latest` + `tools/pitr-verify.sh` در محیط ایزوله → ثبت در جدولِ تمرینِ `DR_RUNBOOK.md` §۶. «بکاپِ بی‌آزمون، بکاپ نیست» |
| **چرخش لاگ** | خودکار/هفتگی | ممیزی با چرخش ۱۰ مگابایتی در `server/audit.js`؛ هفتگی: فضای پوشهٔ لاگ + نگهداری ۳۰روزهٔ لوکی/پرومتئوس (`OBSERVABILITY_DEPLOYMENT.md` §۵) |
| **حافظهٔ ردیس** | هفتگی | `redis-cli INFO memory` در برابر سقف ۲۴ گیگابایت؛ سیاست `noeviction` یعنی پُری **بلند** شکست می‌خورد نه بی‌صدا؛ بررسی بی‌کلیدِ بی‌انقضا (`redis-audit.js`) |
| **تورم/وکیوم پستگرس** | هفتگی | `SELECT relname, n_dead_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 20;` — رشد پایدار = `VACUUM (ANALYZE)` دستی؛ ماهانه: `REINDEX CONCURRENTLY` روی جداول داغ در پنجرهٔ کم‌ترافیک |
| **تازه‌سازی گواهی** | پایش ۳۰ روز قبل از انقضا | `openssl s_client -connect <دامنه>:443 | openssl x509 -noout -dates`؛ تمدید + بارگذاری مجدد لبه؛ گواهی‌های لبهٔ سی‌دی‌ان جداگانه (`docs/CDN_INTEGRATION_SETUP.md`). انقضا = پلی‌بوک ۷ حادثه |
| **بکاپ ردیس** | طبق برنامهٔ میزبان | `tools/redis-backup.sh` + رویهٔ `docs/REDIS_RESTORE_PROCEDURE.md` (کش بی‌خطر است؛ نرخ‌ها/توان‌دهی‌ها گرم می‌شوند) |

## ۵) عملیات مقیاس (Scaling Operations)

### ۵.۱ افزودن نمونهٔ افقیِ اپ (پس از آزادسازی موج ۱)

1. نود تازه را با همان تصویرِ تغییرناپذیر آماده کن (کانفیگ بیرون کد).
2. محیط یکسان: `DATABASE_URL` از مسیر پولر + `READ_DATABASE_URL` + `REDIS_SENTINELS`/`REDIS_SENTINEL_NAME` + **همان** `PAYESH_JWT_SECRET` (نشست‌ها بین نمونه‌ها مشترک‌اند).
3. بوت و تأیید: `/api/health` سبز + اسکراپ `/metrics` + دودِ سریع (چند روت حضور/نمره).
4. افزودن به `upstream` لبه + بارگذاری مجدد؛ ۱۵ دقیقه پایش (استخر، خطا، تأخیر).
5. معیار بازگشت: هر نمونهٔ تازه نباید `payesh_db_pool_waiting` را به‌طور پایدار مثبت کند.

### ۵.۲ مقیاس عمودی (تغییر منابع یک جزء)

- فقط با پنجرهٔ تعمیرات: حذف از لبه → خاموشی آرام (§۲) → تغییر منابع → بوت → راستی‌آزمایی.
- یادآوری ضدالگو (§28 نقشه راه): «افزایش منابع به‌جای مقیاس افقی» راه‌حل نیست؛
  ابتدا گلوگاهِ اثبات‌شده در `docs/BOTTLENECK_MAP.md` / خروجی تست بار را ببینید.

### ۵.۳ توسعهٔ ردیس

- افزایش ظرفیت حافظه: بالابردن `maxmemory` هر گره یا افزودن شارد — با مانورِ
  بدون قطعی از مسیر سنتینل (`HA_REDIS.md` §۴). هرگز دو هم‌زمان زنده نماند.

### ۵.۴ افزودن رپلیکای خواندنِ پستگرس

1. `pg_basebackup -R` از primary → بوت به‌عنوان `pg-standby` تازه.
2. `post-checks.sh` سبز (جریان استریمینگ) → اتصال مسیر `payesh-readonly` در پولر.
3. مسیریابی گزارش‌های سنگین به `READ_DATABASE_URL` (موج ۱۰).

|---|---|---|
| `DATABASE_URL` / `READ_DATABASE_URL` | اتصال نوشتن/خواندن از پولر | هیچ نمونه‌ای مستقیم به پستگرس وصل نشود |
| `PG_POOL_MIN` / `PG_POOL_MAX` / `PG_TIMEOUT_MS` | اندازهٔ استخر هر نمونه | جمعِ `PG_POOL_MAX` نمونه‌ها ≤ استخر پولر (سهم هر نود ≤ ۲۵ — مدل ظرفیت §۳.۲) |
| `REDIS_SENTINELS` / `REDIS_SENTINEL_NAME` / `REDIS_PASSWORD` | حالت سنتینل | مهاجرت خودکار پس از فیلاور، بدون ری‌بوت (`server/redis.js`) |
| `PAYESH_JWT_SECRET` / `PAYESH_JWT_SECRET_PREV` | امضای نشست | چرخش = §۶.۳ |
| `METRICS_TOKEN` | دروازهٔ اسکرپ | پرومتئوس هدر می‌فرستد؛ لبه هرگز روت نمی‌کند |
| `TRACING_ENABLED` / `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | ردیابی | خرابی کالکتور بی‌اثر است (باز-رو به بالا) |
| `PAYESH_AUDIT_ASYNC` | ممیزی ناهمگام | پیش‌فرض سنکرون؛ فعال‌سازی با احتیاط و پایش |
| `PAYESH_SMS_*` | سقف‌های ضد سوءاستفادهٔ پیامک | تغییر = بازبینی هم‌زمان `docs/RATE_LIMITING_DESIGN.md` |

### ۶.۲ قوانین تغییر

- هر تغییر پیکربندی = ویرایش قالبِ مورد تأیید در ریپو + کامیت مستقل `docs(config)`/`chore(config)` + استقرار مجدد تصویر تغییرناپذیر.
- رازها هرگز در ریپو نمی‌نشینند (`0600`، بیرون از گیت؛ نگهبان: اسکن مخفی‌ها).
- پرچم‌های ویژگی فقط محیطی‌اند و **پیش‌فرض‌شان شکست‌بسته** است؛ افزودن پرچم تازه بدون تست = مرج نمی‌شود.

### ۶.۳ چرخش رمز نشست (JWT)

1. `PAYESH_JWT_SECRET` = کلید تازهٔ حداقل ۲۵۶بیتی + `PAYESH_JWT_SECRET_PREV` = کلید فعلی.
2. ری‌استارت غلتان نمونه‌ها (یکی‌یکی، با تأیید سلامت بین هرکدام).
3. پس از گذشت بیشینهٔ عمر نشست، `PREV` حذف و دوباره ری‌استارت شود.
- کلید زیر ۲۵۶ بیت بوت را می‌کُشد (شکست‌بستهٔ آراس‌۹۶) — این خطا را با «ری‌استارت بیشتر» حل نکنید؛ کلید را درست کنید.

## ۷) رویه‌های بازگشت (Rollback Procedures)

- **استقرار:** رویهٔ کامل در `docs/DEPLOY.md`؛ بازگشت = **استقرار مجددِ تصویر/بیلد قبلی**
  (خروجی `node build.js` هرگز دستی ویرایش نمی‌شود — قرارداد تک‌فایلی، `SKILLS_MASTER` §۱).
- **داده/اسکیما:** مهاجرت‌ها تغییرناپذیرند؛ بازگشت اسکیما فقط با فایل‌های بازگشتِ
  نسخه‌دار (`migrations/*_rollback`) و تصمیم کتبی — طرح کامل در `docs/DATABASE_ARCHITECTURE.md` §۲.
- **فاجعهٔ داده:** بازیابی نقطه‌ای (پی‌آی‌تی‌آر) در `docs/DR_RUNBOOK.md` §۴.
- **دروازهٔ باز-انتشار:** قبل از هر بازگشت/پیش‌روی مجدد، `node tools/release-gate.js`
  و سه گیت همیشگی (اسمود ۵۴۷/۵۴۷ · تطبیق مجوزها · اسکن مخفی‌ها).

# پرامپت جامع پروژه «پایش»
### سند انتقال کامل بافتار (Context Handover) برای هر مدل هوش مصنوعی

> **نحوه استفاده:** کل این سند را در ابتدای گفتگو به مدل بدهید. پس از خواندن، مدل باید بدون نیاز به هیچ سؤال اضافه‌ای بتواند روی پروژه کار کند.

## ۰. دستور نقش (Role Instruction)

```
تو یک مهندس ارشد نرم‌افزار هستی که روی پروژه‌ی «پایش» کار می‌کنی — یک سامانه‌ی
مدیریت مدرسه‌ی فارسی/RTL که به‌صورت تک‌فایلی و آفلاین‌محور توسعه یافته است.

قواعد الزامی:
۱. هرگز index.html را مستقیم ویرایش نکن — آن خروجی build است. فقط در src/ تغییر بده.
۲. هیچ فریم‌ورک، کتابخانه یا وابستگی خارجی (CDN، npm در زمان اجرا) اضافه نکن.
۳. هر متن قابل مشاهده باید فارسی باشد؛ هر ورودی کاربر باید با esc() فرار داده شود.
۴. تاریخ‌ها داخلی ISO میلادی ذخیره و فقط هنگام نمایش به شمسی تبدیل می‌شوند.
۵. تغییر داده فقط از طریق insert/update/remove — نه دستکاری مستقیم db.
۶. پس از هر تغییر: npm run build && npm test — هر دو باید سبز باشند.
۷. پاسخ‌ها به فارسی، مستقیم و بدون تعارف. اگر چیزی را نمی‌دانی، حدس نزن؛ کد را بخوان.
۸. هرگز الگوی جستجوی خطی در مسیر رندر ننویس. اگر داخل map/forEach به find نیاز
   داری، اول با idxGroup/idxUnique ایندکس بساز. این قاعده مقیاس ملی را ممکن می‌کند.
۹. هر داده‌ای که نقش کاربر اجازهٔ دیدنش را ندارد، نباید اصلاً به مرورگر برسد.
   محدوده را در 29-scope.js تعریف کن، نه با فیلتر سمت نمایش.
۱۰. ⭐ قاعدهٔ دائمی کاربر: پس از **هر** تغییر در برنامه، همین سند
    (docs/AI_PROMPT.md) را به‌روز کن و نسخهٔ به‌روزشده را در ورک‌اسپیس بگذار.
    این کار اختیاری نیست و باید در همان نوبت انجام شود.
۱۱. قاعدهٔ دو نسخه: هر قابلیت جدید باید هم در نسخهٔ تک‌فایلی و هم در نسخهٔ
    سروری پیاده و تست شود.
۱۲. ⭐⭐ **دو اصل همیشگی که هرگز نباید فراموش شوند:**

    **اصل یکم — همگامی مستندات:**
    با **هر** تغییری در برنامه، همین سند (`docs/AI_PROMPT.md`) و راهنمای
    برنامه‌نویس (`CONTRIBUTING.md`) باید **در همان نوبت** به‌روز شوند.
    نه بعداً، نه در نوبت بعد. جزئیات ریز هم باید نوشته شود: چرا آن
    تصمیم گرفته شد، چه عددی سنجیده شد، چه دامی وجود دارد.

    **اصل دوم — تفکیک اصولی کد:**
    ساختار کد باید طوری بماند که برنامه‌نویس تازه‌وارد **بدون پرسیدن**
    بخش موردنظرش را پیدا کند. نام فایل محتوایش را بگوید، هر صفحه یک
    تابع `view` داشته باشد، و هر ماژول سرفصل فارسی داشته باشد.

۱۳. ⭐ قاعدهٔ نگارش: همهٔ توضیح‌ها به کاربر و همهٔ متن این سند باید **فارسی**
    باشد. نام‌های انگلیسی فقط داخل قطعه‌کد، مسیر فایل یا سلول جدول بیایند و
    هرگز وسط جملهٔ فارسی قرار نگیرند، چون متن درهم و ناخوانا می‌شود.
    ✅ درست: «تابع ساخت کیف پول در ماژول `33-forms-sms.js` است.»
    ❌ نادرست: «تابع smsWalletOf در ماژول forms-sms هست که wallet را create می‌کند.»
```

## ۱. هویت پروژه

| ویژگی | مقدار |
|---|---|
| **نام** | پایش (Payesh) — سامانه هوشمند مدیریت مدرسه |
| **مخاطب** | مدارس ایران، ادارات آموزش‌وپرورش، دبیران، دانش‌آموزان، اولیا |
| **زبان/جهت** | فارسی، RTL، تقویم شمسی (جلالی) |
| **وضعیت فعلی** | **نسخه دمو** — بدون بک‌اند؛ سرور بعداً وصل می‌شود |
| **پشته** | Vanilla JS، صفر وابستگی زمان اجرا، بدون فریم‌ورک |
| **خروجی** | یک فایل `index.html` (~۴۹۹KB) شامل همه‌چیز |
| **حجم کد منبع** | ~۸٬۰۰۰ خط جاوااسکریپت در **۳۸ ماژول** + ۳ فایل شیوه‌نامه |
| **داده نمونه** | ۳۲٬۱۵۷ رکورد در ۳۰ مجموعه (~۴.۶MB JSON در حافظه) |

### دو معنای متفاوت «آفلاین» — مهم است اشتباه نشود

| اصطلاح | معنی در این پروژه |
|---|---|
| **تک‌فایلی / بدون وابستگی** | فونت، لوگو، CSS و JS همه داخل فایل جاسازی شده‌اند؛ هیچ درخواست CDN وجود ندارد |
| **Offline-first** ⭐ | **قابلیت اصلی محصول:** دبیری که در مدرسه اینترنت ندارد، حضور و غیاب می‌زند؛ داده روی دستگاه می‌ماند و به‌محض وصل شدن اینترنت خودکار به سرور می‌رود |

مورد دوم دلیل وجودی لایه‌ی `27-sync.js` است.

## ۲. معماری

### ۲.۱ توسعه ماژولار، توزیع تک‌فایلی

```
src/head.html  ─┐
src/styles/*.css├─→  node build.js  ─→  index.html  (تک‌فایلی، قابل توزیع)
src/js/*.js    ─┤                        └─→ dist/payesh.html
src/body.html  ─┘
```

`build.js` فقط **الحاق (concatenation)** انجام می‌دهد — نه ترنسپایل، نه باندلر، نه minify.
به همین دلیل `node build.js --check` می‌تواند تضمین کند خروجی **بیت‌به‌بیت** با نسخه‌ی توزیعی یکسان است.

⚠️ همه‌ی ماژول‌ها در **یک scope مشترک** اجرا می‌شوند (نه ES modules). پس:
- ترتیب در `src/js/_order.json` **حیاتی** است
- نام متغیرها سراسری‌اند — خطر تصادم نام وجود دارد
- `const`/`let` سطح‌بالا روی `window` نمی‌نشینند (نکته‌ی مهم برای تست)

### ۲.۳ جریان اجرا

```
بارگذاری صفحه
      │
      ├─ generate()        ← داده پایه با SEED ثابت (قابل بازتولید)
      ├─ generateExtras()  ← مالی، تقویم، پیام
      ├─ generateP8()      ← امتحانات، کد ملی، چندمدرسه‌ای
      ├─ generateP9()      ← تقسیمات کشوری، ادارات
      ├─ generateP10()     ← اشتراک‌ها
      ├─ loadLog()         ← خواندن تغییرات کاربر از localStorage
      ├─ applyLog()        ← بازپخش روی داده پایه  (SYNC_MUTED=true)
      ├─ initSync()        ← بارگذاری صف ارسال + شنود online/offline
      └─ render()
              │
     ┌────────┴────────┐
 renderLogin      renderShell
                       │
                  renderRoute()   ← switch روی S.route
                       │
                  viewXxx()       ← رشته HTML برمی‌گرداند
                       │
                 کلیک کاربر
                       │
        event delegation روی [data-act]
                       │
                  insert/update/remove
                       │
              applyOp() ──┬─→ log  → localStorage
                          └─→ enqueueOp() → صف همگام‌سازی
                       │
                    render()
```

### ۲.۴ الگوی رندر

رشته‌محور، بدون Virtual DOM:
- هر `viewXxx()` یک رشته HTML برمی‌گرداند
- `$('#root').innerHTML = ...` کل صفحه را بازنویسی می‌کند
- رویدادها با **event delegation** روی `document` مدیریت می‌شوند (`data-act`)
- پس نیازی به اتصال مجدد listener بعد از رندر نیست

**استثنا:** `refreshSyncBadge()` فقط نشانگر همگام‌سازی را جایگزین می‌کند تا رندر کامل لازم نشود.

### ۴.۴ سازوکارهای ویژه‌ی ارتباطی

**۱. جعل هویت (Impersonation)**
سوپرادمین می‌تواند وارد پنل مدیر یک مدرسه شود:
```js
S.boss = S.user;  S.user = mgr;   // نوار هشدار بالای صفحه نمایش داده می‌شود
// بازگشت با 'stop-imp'
```

**۲. چندنقشی (Multi-role)**
یک شخص می‌تواند همزمان دبیر و ولی باشد:
```js
panelsOf(u)        // فهرست پنل‌های در دسترس
activePersona()    // S.persona || S.user.role
panelPicker()      // صفحه انتخاب پنل هنگام ورود
```
اتصال با **کد ملی** انجام می‌شود: اگر `student.father_nid === user.national_id`
آن شخص خودکار پنل اولیا هم می‌گیرد (`linkAsParent`).

**۳. تأیید فرزندان (Parent Gate)**
پس از اتصال خودکار، ولی باید تأیید کند:
```
pending → ولی «بله فرزند من است» → confirmed
        → ولی «فرزند من نیست»   → rejected + ثبت در corrections → مدیر مدرسه
```

**۴. دبیر مشترک بین مدارس**
`teacher_schools` — دبیر می‌تواند در چند مدرسه تدریس کند.
سیستم **تداخل زمانی** را تشخیص می‌دهد (`overlapP`) و مانع ابلاغ متناقض می‌شود.

**۵. Paywall اولیا**
```js
parentLocked()  // فقط اگر persona==='parent' && paywall فعال && اشتراک منقضی
// در renderRoute:
if(parentLocked() && !['subscription','notifications','announcements'].includes(S.route))
  return viewLocked();
```
اولین ورود → مهلت تست رایگان خودکار (پیش‌فرض ۲۱ روز، قابل تنظیم در پنل سوپرادمین).

## ۵.۵ چرخهٔ تحصیلی (ماژول `31-student-lifecycle.js`) ⭐

پنج تب در روت `lifecycle` (فقط مدیر و سوپرادمین):

| تب | کار |
|---|---|
| `promotion` | نمای پایان سال هر کلاس + دکمهٔ اجرای ارتقا |
| `transfers` | درخواست‌های انتقال ورودی/ارسالی + سابقه |
| `conflicts` | کد ملی‌هایی که در مدرسهٔ دیگری فعال‌اند |
| `incomplete` | پرونده‌های ناقص با درجهٔ اهمیت |
| `archive` | بایگانی فارغ‌التحصیلان به تفکیک سال |

### قواعد نظام آموزشی ایران
```
ابتدایی ۱–۶ · متوسطه اول ۷–۹ · متوسطه دوم ۱۰–۱۲
پایه ۶ و ۹  = پایان مقطع  ⇒ status='awaiting_transfer'
پایه ۱۲     = فارغ‌التحصیلی ⇒ بایگانی + active=0
سایر پایه‌ها = grade_level+1
```

### API
```js
yearCode()                    // '1404-1405' (سال از مهر شروع می‌شود)
yearTitle()                   // '۱۴۰۴-۱۴۰۵'
isTerminal(g)                 // ۶/۹/۱۲ ⇒ true
gradeFromName('نهم ۲')        // 9 — استنتاج پایه از نام کلاس
levelOfLC(9)                  // 'متوسطه اول'
activeStudentsOfClass(cid)    // از ایندکس، فقط دانش‌آموزان فعال
graduateStudent(s,sid,cls)    // بایگانی + status + حذف ثبت‌نام + اعلان به ولی
moveStudent(st,to,classId,r)  // انتقال با کل پرونده ⇒ {grades,attendance,discipline}
recordConflict(sid,nid,...)   // ثبت تعارض بدون تکرار
incompleteUsers(sid)          // فهرست مرتب‌شده بر اساس شدت
```

### ۴ مجموعهٔ داده
```

transfer_requests   درخواست‌ها (pending/approved/rejected)
student_archive     کارنامهٔ فارغ‌التحصیلان (معدل، درصد حضور، انضباط)
nid_conflicts       تعارض کد ملی (open/resolved/dismissed)
```

### ⚠️ نکتهٔ مهم انتقال
`moveStudent` علاوه بر `users.school_id`، فیلد `school_id` رکوردهای
`grades`/`attendance`/`discipline` را هم به‌روز می‌کند. بدون این کار پرونده در
مدرسهٔ جدید دیده نمی‌شد (چون کوئری‌ها بر اساس `school_id` مرزبندی می‌کنند).

### ⚠️ عملیات انبوه حتماً در `batchWrites` بپیچید
```js
batchWrites(()=>{ /* هزاران insert/update */ });
```
`promote-run` و `tr-ok` این کار را می‌کنند. بدون آن ارتقای یک مدرسهٔ ۵۰۰ نفره
**۳٬۲۰۰ms** طول می‌کشید؛ با آن **۱۸۷ms** (۱۷ برابر سریع‌تر).

## ۵.۸ ویزارد ورود اکسل (`34-excel-import.js`) ⭐

چهار مرحله: انتخاب فایل ← نگاشت ستون‌ها ← بررسی خطاها ← ثبت نهایی.
فقط مدیر و سوپرادمین. وضعیت ویزارد در `S.imp` نگه داشته می‌شود.

### چرا خوانندهٔ اکسل از صفر نوشته شد؟
پروژه هیچ وابستگی بیرونی ندارد، پس آوردن کتابخانه ممکن نبود. فایل `xlsx`
در واقع یک بایگانی فشرده است؛ ساختار آن مستقیم خوانده می‌شود و محتوای
فشرده با `DecompressionStream` مرورگر باز می‌گردد. اگر مرورگر این توانایی
را نداشته باشد، پیام روشن داده می‌شود و ورود از `csv` همچنان کار می‌کند
(تابع `canReadXlsx`).

### اصل طراحی
مدرسه نباید فایلش را با قالب ما تطبیق دهد؛ سامانه باید فایل موجود مدرسه را
با هر ترتیب ستونی بفهمد. برای همین:

- **ردیف تیتر خودکار پیدا می‌شود** — پرمحتواترین ردیف میان پنج ردیف نخست،
  پس فایل‌هایی که سطر توضیح یا لوگو دارند هم درست خوانده می‌شوند.
- **نگاشت ستون‌ها هوشمند است** — هر عنوان با فهرست مترادف‌ها سنجیده می‌شود
  و امتیاز می‌گیرد؛ امتیاز ۷۰ به بالا پذیرفته می‌شود.
- **نویسه‌های عربی یکسان‌سازی می‌شوند** (`normHdr`)، پس «كدملي» با «کد ملی»
  یکی شمرده می‌شود.
- **ارقام فارسی و عربی** به لاتین تبدیل می‌شوند (`toLatinDigits`).

### اعتبارسنجی پیش از ثبت
`validateImport` هیچ داده‌ای نمی‌نویسد جز ثبت تعارض کد ملی. برای هر ردیف
خطاها و هشدارها جدا گزارش می‌شوند:

| وضعیت | نمونه |
|---|---|
| خطا (ردیف ثبت نمی‌شود) | نام کوتاه‌تر از سه نویسه · کد ملی نامعتبر · تکرار در همان فایل · کد ملی متعلق به مدرسهٔ دیگر |
| هشدار (ردیف ثبت می‌شود) | بدون کد ملی · بدون کلاس · شمارهٔ نامعتبر · تاریخ تولد خوانده نشد |
| به‌روزرسانی | کد ملی از قبل در همین مدرسه هست ⇒ رکورد موجود ویرایش می‌شود، نه ساخت تکراری |

اگر کد ملی متعلق به دانش‌آموزی در مدرسهٔ دیگر باشد، ردیف رد شده و به‌طور
خودکار در `nid_conflicts` ثبت می‌شود تا مدیر از تب «انتقالی‌ها» درخواست
انتقال بدهد. این پل میان ویزارد ورود و چرخهٔ تحصیلی است.

### ثبت نهایی
`commitImport` همهٔ نوشتن‌ها را در یک `batchWrites` انجام می‌دهد و علاوه بر
دانش‌آموز، **کلاس‌های تازه** و **حساب ولی** را هم می‌سازد و پیوند ولی به
دانش‌آموز را برقرار می‌کند. نام کاربری یکتا تضمین می‌شود.

سنجش: ثبت **۱۰۰۰ دانش‌آموز در ۲۹۷ میلی‌ثانیه**.

> برگرداندنش نبود** — یعنی عملاً بی‌فایده. حالا هر دو سو کامل است.

`validateBackup` شش بررسی دارد: قالب فایل · آرایه بودن عملیات · شمارهٔ
نسخه · نوع هر عمل · وجود مجموعهٔ مقصد در این نسخه. **اگر فایل خراب باشد
هیچ تغییری اعمال نمی‌شود** — با آزمون تأیید شد که داده دست‌نخورده می‌ماند.

## ۶. لایه Offline-First (ماژول `27-sync.js`) ⭐

**سناریوی هدف:** دبیر در کلاس، بدون اینترنت، حضور و غیاب می‌زند.

```
ثبت حضور  →  applyOp()  →  ┬→ db (فوری در UI دیده می‌شود)
                            ├→ log → localStorage
                            └→ enqueueOp() → صف ارسال → localStorage
                                     │
                          ┌──────────┴──────────┐
                     آفلاین؟                 آنلاین؟
                          │                     │
                  در صف می‌ماند          ارسال + حذف از صف
                          │                     │
              رویداد 'online' ────────→ ارسال خودکار
                                                │
                                     خطا؟ → backoff نمایی
                                            ۲s→۴→۸→…→۵min
```

**وضعیت‌های عملیات:** `pending` → `sending` → `synced` (حذف) / `failed` (تلاش مجدد) / `conflict`

**نشانگر نوار بالا:**

| حالت | نمایش |
|---|---|
| 🟢 | همگام |
| 🟡 | در صف ‹تعداد› |
| ⚫ | آفلاین ‹تعداد› |
| 🔵 | همگام‌سازی… |
| 🔴 | تعارض ‹تعداد› |

**اتصال به سرور واقعی — فقط دو خط:**
```js
SYNC.demoMode  = false;
SYNC.serverUrl = '/api/sync';
```

**قرارداد API مورد انتظار:**
```jsonc
// درخواست
POST /api/sync
{ "ops": [ {"uid":"op_...", "t":"ins", "c":"attendance", "data":{...}} ] }

// پاسخ
{ "results": [
    {"uid":"op_...", "ok": true},
    {"uid":"op_...", "conflict": true, "server": {...}, "message":"..."},
    {"uid":"op_...", "ok": false, "message": "خطا"}
] }
```

### ۷.۱ وضعیت — راستی‌آزمایی‌شده با حمله واقعی، نه بازبینی چشمی

| مورد | روش سنجش | نتیجه |
|---|---|---|
| XSS | ۴ payload (تگ، شکستن attribute، نقل‌قول، `javascript:`) تزریق در ۱۶ مجموعه × ۵۰ فیلد، سپس **بررسی DOM واقعی** در ۱۷۴ ترکیب نقش×روت | ✅ صفر عنصر تزریقی ساخته شد |
| مرز چندمستأجری | مدیر مدرسه A دنبال نام دانش‌آموز مدرسه B در ۲۹ روت | ✅ نشتی ندارد |
| اداره | جستجوی نام دانش‌آموز در همه روت‌ها | ✅ فقط داده تجمیعی |
| paywall | باز کردن ۱۲ روت قفل‌شده با تغییر مستقیم `S.route` | ✅ همه مسدود |
| ارتقای امتیاز | تغییر `S.route` به روت‌های مدیریتی با نقش پایین | ✅ مسدود (پس از رفع باگ زیر) |
| جانشینی | سوپرادمین → مدیر، سپس تلاش برای روت سوپرادمین | ✅ درست |

> ⚠️ نکتهٔ روش‌شناختی: تشخیص XSS با جستجوی متنی در رشتهٔ خروجی **غلط** است —
> فرم escape‌شدهٔ payload (`&lt;img...`) را مثبت کاذب می‌شمارد. سنجش درست:
> `innerHTML` را ست کن و با `querySelectorAll` ببین آیا عنصر واقعاً ساخته شد.

### ۷.۲ 🔴 باگ بحرانی که یافت و رفع شد (ممیزی دور ۵)

**مسئله:** `renderRoute()` هیچ بررسی مجوزی نداشت و فقط روی `S.route` سوییچ می‌کرد.
`NAV` تعیین می‌کرد چه چیزی در **منو** دیده شود، اما هیچ‌چیز جلوی تغییر مستقیم
`S.route` (یا hash آدرس) را نمی‌گرفت.

**شدت: بحرانی.** فقط نشت اطلاعات نبود — **تغییر داده** هم ممکن بود:

```
دانش‌آموز → S.route='attendance' → کل لیست کلاس + دکمه‌های فعال «ثبت وضعیت»
         → کلیک att-set روی هم‌کلاسی
         → غیبت جعلی ثبت شد و وارد صف ارسال به سرور شد ❌
دانش‌آموز → S.route='adminsubs' → ۵۱ کیلوبایت پنل مدیریت اشتراک سوپرادمین ❌
```

**رفع:** ماژول `30-authz.js` با دو گارد:

```js
// در renderRoute() — پیش از switch
if(typeof canRoute==='function' && !canRoute(S.route)) return viewForbidden();

// در دیسپچر کلیک 19-actions.js — پیش از اجرای اکشن
if(S.user && typeof canAction==='function' && !canAction(a)){
  toast('شما اجازهٔ انجام این عملیات را ندارید','err'); return;
}
```

**اصل طراحی:** مجوز روت از خودِ `NAV` استخراج می‌شود (تک‌منبع حقیقت) به‌علاوهٔ
`EXTRA_ROUTES` برای زیرصفحه‌هایی که در منو نیستند. پس افزودن آیتم منو خودکار
مجوز می‌دهد و امکان ناهماهنگی بین منو و مجوز از بین می‌رود.

**API ماژول `30-authz.js`:**
```js
navRoutesOf(role)      // روت‌های موجود در منوی نقش
allowedRoutes(role)    // مجموعهٔ کامل مجاز (NAV + EXTRA + COMMON) با کش
canRoute(route, role)  // آیا این روت مجاز است؟
canAction(act, role)   // آیا این اکشن مجاز است؟
homeRoute(role)        // روت خانه
viewForbidden()        // صفحهٔ «دسترسی مجاز نیست»
EXTRA_ROUTES           // روت‌های خارج از منو، به تفکیک نقش
COMMON_ROUTES          // باز برای همهٔ واردشده‌ها
ACTION_ROLES           // نگاشت اکشن → نقش‌های مجاز (۳۰ اکشن حساس)
```

**راستی‌آزمایی:** ۱۰ دسترسی غیرمجاز مسدود شد، ۱۹ دسترسی مجاز دست‌نخورده ماند
(صفر رگرسیون)، جانشینی و پرسونای دوم درست کار کردند. ۱۰ تست دائمی افزوده شد.

### ۷.۳ مهم‌ترین تصمیم امنیتی: محدودسازی داده

اگر سرور کل دیتابیس را به مرورگر بفرستد، یک دانش‌آموز با کنسول می‌تواند نمرات و
کد ملی **همهٔ** کاربران را بخواند. **هیچ فیلتر سمت کلاینتی این را حل نمی‌کند.**

| نقش | آنچه سرور مجاز است بفرستد |
|---|---|
| دانش‌آموز | فقط رکوردهای خودش (~۸KB) |
| ولی | فقط فرزندان تأییدشده |
| دبیر | فقط کلاس‌های خودش، پنجرهٔ ۴۵ روزه (~۳۵۶KB) |
| مدیر | فقط مدرسهٔ خودش (~۱MB) |
| اداره | 🔒 فقط آمار تجمیعی — هیچ رکورد فردی |
| سوپرادمین | آمار ملی + فهرست صفحه‌بندی‌شده |

### ۷.۴ محدودیت‌های ذاتی نسخهٔ دمو — تصمیم آگاهانه، نه باگ

```
❌ رمز عبور متن ساده در db (همه: '123456')
❌ احراز هویت فقط سمت کلاینت — با کنسول قابل دور زدن
❌ کل داده در حافظهٔ مرورگر
❌ بدون CSRF / rate-limit / audit trail
```

**لایهٔ مجوزدهی سمت کلاینت، سد نهایی نیست** — تجربهٔ کاربری درست و دفاع لایه‌ای
است. سرور موظف است **مستقلاً** همین قواعد را اعمال کند:

```
• رمز با bcrypt/argon2 (۱۲ round)
• JWT کوتاه‌عمر + refresh چرخشی
• محدوده از توکن تعیین شود، نه از پارامتر کلاینت
• هر عملیات ورودی از صف sync مجدداً اعتبارسنجی شود
• paywall در لایهٔ API
• audit_log برای عملیات حساس
```

## ۹.۵ نوشتن دسته‌ای (`batchWrites`) ⭐

**مسئله‌ای که حل می‌کند:** `saveLog()` و `saveQueue()` هر بار **کل** لاگ/صف را
`JSON.stringify` می‌کنند. در عملیات انبوه این رفتار **درجه‌دوم** می‌شود:

| طول لاگ | ۱۰۰ insert |
|---|---|
| ۱۰۶ | ۲۰ms |
| ۱٬۱۰۰ | ۱۰۶ms |
| ۴٬۱۰۰ | ۴۶۰ms |

**قاعده:** هر عملیاتی که بیش از ~۵۰ نوشتن دارد باید در `batchWrites` بپیچد.

```js
batchWrites(() => {
  students.forEach(s => update('users', s.id, { grade_level: g + 1 }));
});
// یک saveLog + یک saveQueue در پایان، نه هزاران بار
```

**ویژگی‌ها:** تودرتو امن است (شمارندهٔ عمق)، در برابر استثنا امن است
(`finally`)، و هیچ عملیاتی گم نمی‌شود — لاگ و صف در پایان کاملاً همگام‌اند.

**بهینه‌سازی مرتبط در `applyOp`:** ترتیب باطل‌سازی ایندکس مهم است — ابتدا با
ایندکسِ معتبر جستجو کن، **سپس** باطل کن. در غیر این صورت `idxById` بلافاصله کل
مجموعه را بازمی‌سازد و هر نوشتن از درجهٔ n می‌شود.

## ۱۲.۶ زمان‌بندی ساخت سرور — تصمیم ثبت‌شده

**پرسش کاربر:** «هنوز باید خیلی جاها را ویرایش کنیم؛ صبر کنیم یا الان سرور لازم است؟»

**تصمیم: فعلاً سرور ساخته نمی‌شود.** دلیل، با شواهد:

| شاهد | یافته |
|---|---|
| رشد مدل داده | سه دور اخیر هر کدام مجموعهٔ دادهٔ تازه آوردند (اکنون ۳۹ مجموعه) |
| نقاط نوشتن | ۵۲ فراخوانی درج/ویرایش/حذف که منطقشان هنوز در حال تغییر است |
| هزینهٔ تأخیر | تقریباً صفر، چون قالب همگام‌سازی **عمومی** است |

**چرا هزینهٔ تأخیر صفر است؟** قالب عملیات به نام مجموعه گره نخورده:
`{t, c, data}` که `t` نوع عمل و `c` نام مجموعه است. افزودن مجموعهٔ جدید
هیچ تغییری در لایهٔ همگام‌سازی لازم ندارد.

### سه قراردادی که قفل شده‌اند و نباید عوض شوند
۱. قالب `POST /api/sync` با `{ops:[...]}` و پاسخ `{results:[...]}`
۲. قرارداد `GET /api/bootstrap` با محدوده از توکن سرور
۳. جدول نقش‌ها در `30-authz.js` به‌عنوان تک‌منبع حقیقت

### شرط‌های شروع ساخت سرور
دو دور پیاپی بدون مجموعهٔ دادهٔ جدید · تثبیت فیلدهای رکوردهای اصلی ·
پایان ویرایش‌های ظاهری · **بازخورد یک مدرسهٔ واقعی**

جزئیات کامل: `docs/SERVER_TIMING.md`

## ۱۴. اشتباهات رایجی که نباید تکرار شوند

| ❌ اشتباه | ✅ درست |
|---|---|
| ویرایش `index.html` | ویرایش `src/` سپس `npm run build` |
| افزودن ماژول بدون ثبت در `_order.json` | همیشه ثبت شود، در جای درست ترتیب |
| `fa()` روی رشته | `faD()` برای رشته، `fa()` برای عدد |
| `db.x.push()` | `insert('x', {...})` |
| فرض «آفلاین = بدون CDN» | آفلاین = **کار بدون اینترنت + همگام‌سازی بعدی** |
| افزودن CDN/کتابخانه | صفر وابستگی — دستی بنویس |
| نام متغیر عمومی مثل `f`, `s`, `t` در ماژول جدید | تصادم با helperهای موجود — پیشوند بگذار |
| `find` خطی داخل `map` در مسیر رندر | ابتدا ایندکس بساز (`idxGroup`/`idxUnique`) |
| فرستادن کل دیتابیس به مرورگر | فقط برش نقش — `scopeDescriptor` |
| بلعیدن خطای `localStorage` | کاربر باید از پرشدن حافظه باخبر شود |
| افزودن ایندکس بدون باطل‌سازی | `applyOp` خودکار انجام می‌دهد؛ دستکاری نکن |
| افزودن روت بدون ثبت در `NAV`/`EXTRA_ROUTES` | گارد مجوز آن را مسدود می‌کند |
| عملیات انبوه بدون `batchWrites` | رفتار درجه‌دوم؛ رابط چند ثانیه قفل می‌شود |
| باطل‌کردن ایندکس پیش از جستجو در `applyOp` | باعث بازسازی کامل در هر نوشتن می‌شود |
| انتقال دانش‌آموز بدون به‌روزرسانی `school_id` رکوردهای پرونده | پرونده در مدرسهٔ جدید دیده نمی‌شود |
| نوشتن `\n` داخل رشتهٔ آزمون در `tests/smoke.js` | به خط جدید تبدیل نمی‌شود؛ از `String.fromCharCode(10)` استفاده کن |
| جستجوی کاربر با نام در آزمون | دادهٔ نمونه نام تکراری دارد؛ با کد ملی یا شناسه جستجو کن |
| نام‌گذاری متغیر محلی `f` داخل تابع نما | تابع سراسری سازندهٔ فیلد را می‌پوشاند؛ نام دیگری بگذار |
| فرض اینکه فایل مدرسه با قالب ما یکی است | فایل واقعی «نام» و «نام خانوادگی» جدا دارد و معدل را با اسلش می‌نویسد |
| ساخت قابلیت پشتیبان‌گیری بدون بازیابی | نیمی از کار بی‌فایده است؛ همیشه هر دو سو را بساز |
| ساخت csv بدون پیشوند BOM | اکسل فارسی را به‌هم‌ریخته نشان می‌دهد |
| ساخت csv بدون خنثی‌سازی `=` و `+` | تزریق فرمول در اکسل قربانی ممکن می‌شود |

## ۱۵. خلاصه‌ی یک‌پاراگرافی

> «پایش» یک سامانه‌ی مدیریت مدرسه‌ی فارسی/RTL است که با Vanilla JS و صفر وابستگی
> نوشته شده و به‌صورت یک فایل HTML تک‌فایلی (~۵۰۰KB) توزیع می‌شود، اما ماژولار در
> `src/` (۳۰ ماژول) توسعه می‌یابد و با یک اسکریپت الحاق ساده build می‌شود که
> یکسانی بیت‌به‌بیت خروجی را تضمین می‌کند. شش نقش (سوپرادمین، اداره، مدیر، دبیر،
> دانش‌آموز، ولی) با **سه** لایه جدا شده‌اند: منو (`NAV`)، مجوز (`30-authz.js`) و
> فیلتر داده (`04-queries.js`). داده در ۳۰ مجموعه با الگوی event-log روی
> localStorage نگه داشته می‌شود. مهم‌ترین قابلیت محصول **offline-first** است:
> دبیر بدون اینترنت حضور و غیاب می‌زند و تغییرات با backoff نمایی به سرور می‌روند.
> سامانه برای **مقیاس ملی** طراحی شده (۱۰ میلیون دانش‌آموز، ۵ میلیون کاربر همزمان)
> بر پایهٔ این اصل که **بار هر مرورگر ثابت و مستقل از اندازهٔ کشور بماند**:
> لایهٔ ایندکس (`28-indexes.js`) جستجوی خطی را از مسیرهای داغ حذف کرده و لایهٔ
> محدوده (`29-scope.js`) تضمین می‌کند سرور فقط برش مجاز هر نقش را بفرستد.
> در ممیزی امنیتی دور ۵ یک **باگ بحرانی** یافت و رفع شد: `renderRoute()` هیچ
> بررسی مجوزی نداشت و دانش‌آموز می‌توانست با تغییر `S.route` صفحهٔ حضور و غیاب را
> باز کند و برای هم‌کلاسی‌اش غیبت جعلی ثبت کند که وارد صف سرور هم می‌شد.
> پروژه فعلاً **نسخهٔ دمو بدون بک‌اند** است؛ امنیت واقعی (هش رمز، احراز هویت،
> اعمال مستقل مجوز و محدوده سمت سرور) باید هنگام اتصال سرور پیاده شود.
> بنچمارک: بزرگ‌ترین مدرسهٔ ایران (۱٬۵۲۰ نفر، ۲۷۳ هزار رکورد حضور) = ۵۴ms کل رندر؛
> ۱٬۵۰۰ رندر پیاپی = ۰ خطا و ۱.۳MB رشد حافظه. آزمون: ۳۱ ایستا + ۱۹۳ رفتاری.

# 🛡️ DISASTER RECOVERY — معماری کلان بازیابی از فاجعه

**نسخه:** ۱.۰.۰ | **تاریخ:** ۲۰۲۶-۰۹-۱۰ | **مالک:** چت ۶ (مستندات و انتشار)
**وضعیت:** سند اجباری §30 نقشه راه — سندِ «معماری و سیاست» بازیابی
**مرجع‌ها:** `docs/RELIABILITY_DR_PLAN.md` (اهداف مصوب) · `docs/DR_RUNBOOK.md` (بازوی اجرایی) · `docs/HA_POSTGRES.md` · `docs/HA_REDIS.md` · `docs/PRODUCTION_RUNBOOK.md` · `docs/INCIDENT_RESPONSE.md`

> تقسیم کار: **این سند** = سیاست، معماری و چرخهٔ آزمون. **ران‌بوک بازیابی** =
> دستورهای لحظهٔ حادثه. هیچ شماره‌ای در این سند نباید از اهداف مصوبِ
> «برنامهٔ پایایی» شل‌تر خوانده شود؛ اعداد اینجا سقفِ تضمین‌شدهٔ سیاست‌اند.

## ۱) سیاست آر‌پی‌او / آر‌تی‌او (RPO/RTO Policy)

| سناریو | آر‌پی‌او (حداکثر اتلاف داده) | آر‌تی‌او (حداکثر زمان بازگشت) | مسئول |
|---|---|---|---|
| خرابی پستگرسِ اصلی | ≤ ۵ دقیقه | ≤ ۱۵ دقیقه | دی‌بی‌ای (چت ۱) |
| خرابی ردیس | ≤ ۱ دقیقه | ≤ ۵ دقیقه | زیرساخت (چت ۲) |
| خرابی مرکز داده (منطقه‌ای) | ≤ ۳۰ دقیقه | ≤ ۴ ساعت | ناظر + زیرساخت |
| فساد/تخریب داده | هر نقطهٔ قابل انتخاب (بازیابی نقطه‌ای) | ≤ ۱ ساعت | دی‌بی‌ای + امنیت |

**اهداف عملیاتی (سخت‌گیرانه‌تر — مصوبِ برنامهٔ پایایی و ران‌بوک بازیابی):**
اتلافِ واقعیِ پستگرس با آرشیوِ پیوسته عملاً ثانیه‌هاست؛ فیلاورِ ردیس خودکار
زیر ۳۰ ثانیه؛ سرویسِ منطقهٔ دوم در حدود ۸ تا ۱۵ دقیقه. اعدادِ جدولِ بالا
**سقفِ سیاست‌گذاری** برای طراحی ظرفیت و قراردادِ گزارش‌دهی‌اند — دستیابی
بهتر از آن‌ها الزامی، بدتر از آن‌ها حادثهٔ رسمی است.

## ۲) راهبرد پشتیبان (Backup Strategy)

| منبع | روش | زمان‌بندی | نگهداری |
|---|---|---|---|
| پستگرس | پشتیبانِ فیزیکی + آرشیوِ پیوستهٔ لاگ‌های تراکنش (ابزار پشتیبان → فضای شیئی) | کامل: هفتگی · تفاضلی: روزانه · آرشیو: پیوسته | هدف سیاست: **۳۰ روز** (وضعیت فعلی استک: ۷ نسخهٔ کامل — ارتقا در برنامهٔ استقرار) |
| ردیس | پایاییِ لحظه‌ای + تصویرِ دوره‌ای (`tools/redis-backup.sh` + `docs/REDIS_RESTORE_PROCEDURE.md`) | روزانه | **۷ روز** |
| فضای شیئی (پیوست‌ها/خروجی‌ها) | نسخه‌بندیِ اشیاء + تکثیرِ بین‌منطقه‌ای | پیوسته | **۱ سال** |

اصول:
- پشتیبان بیرونِ میزبانِ اصلی و بیرونِ دسترسیِ مستقیمِ برنامه نگه‌داری می‌شود.
- رمزنگاری در حالِ انتقال و سکون برای هر نسخهٔ پشتیبان الزامی است.
- «پشتیبانِ بی‌آزمون، پشتیبان نیست» — چرخهٔ آزمون در §۵.

## ۳) توپولوژی تکثیر (Replication Topology)

```text
منطقهٔ اصلی (تهران)                              منطقهٔ پشتیبان (تبریز / منطقهٔ ابری دوم)
┌───────────────────────────────┐               ┌───────────────────────────────┐
│ پستگرس اصلی ──استریمینگ──► آمادهٔ داغ          │ آماده از فضای مشترک (آرشیوِ تکثیرشده) │
│      │            └─ مسیر فقط‌خواندنی           │ بوت با بوت‌استرپِ آرشیو هنگامِ فاجعه     │
│      └─► آرشیوِ پیوسته ──────────────────────────────────────────►                │
│ ردیس: اصلی + ۲ کپی + ۳ نگهبان (اتفاق‌نظر ۲ از ۳)│ ردیسِ مستقلِ منطقهٔ دوم                 │
└───────────────────────────────┘               └───────────────────────────────┘
```

| جزء | قرارداد |
|---|---|
| پستگرس | اصلی + آمادهٔ داغِ استریمینگ؛ مسیر فقط‌خواندنیِ گزارش‌ها روی آماده (پیکربندی `infra/postgres/docker-compose.ha.yml`) |
| ردیس | اصلی + ۲ کپی + ۳ نگهبان؛ تشخیصِ مرگ پس از ۵ ثانیه، فیلاورِ خودکار با اتفاق‌نظرِ ۲ از ۳ (`infra/redis/docker-compose.sentinel.yml`) |
| بین‌منطقه | تکثیرِ سطلِ آرشیو بین دو منطقه؛ فاصلهٔ تکثیر ≤ پنجرهٔ آر‌پی‌اوی منطقه‌ای (سناریوی ۳ ران‌بوک بازیابی) |

## ۴) رویه‌های فیلاور (خلاصه — اجرا در ران‌بوک بازیابی)

### خرابی پستگرس اصلی
```text
تشخیص (پایش/سلامت قرمز) ← تصمیم (سه نمونهٔ مرگِ تأییدشده؟ شبکه یا خودِ گره؟)
← اقدام (ابزار فیلاورِ پستگرس با گاردهای دو‌مغزی/واگذاری) ← تأیید (خروج از حالت بازیابی + سلامت سبز)
```

### خرابی ردیس
```text
تشخیص (اتصال‌های مجددِ پیاپی) ← تصمیم (نگهبانان خودکار عمل کردند؟)
← اقدام (در صورت سکوت: ابزار فیلاورِ ردیس) ← تأیید (نقش‌ها + مهاجرتِ برنامه بدون ری‌بوت)
```

### فاجعهٔ منطقه‌ای
```text
تشخیص (مرگِ هم‌زمانِ اجزای منطقه) ← تصمیم (ناظر: اعلامِ فاجعهٔ رسمی)
← اقدام (بوتِ منطقهٔ دوم از آرشیو + فیلاور + سوییچِ لبه) ← تأیید (سلامت از لبه + آرشیو روی اصلیِ جدید)
```

### فساد داده
```text
تشخیص (آمار غیرمنطقی/گزارش حذف انبوه) ← تصمیم (نقطهٔ پیش از فساد کِی بوده؟)
← اقدام (بازیابی نقطه‌ای در محیط ایزوله + راستی‌آزمایی + ترویج یا ادغامِ انتخابی) ← تأیید (چک‌سام + سلامت)
```

> دستورهای دقیق، گاردها و ثبتِ مانور: `docs/DR_RUNBOOK.md` — این بخش فقط
> نقشهٔ تصمیم است.

## ۵) آزمون بازیابی (Recovery Testing)

| مانور | دوره | ابزار | خروجی |
|---|---|---|---|
| دریلِ ری‌استور | **ماهانه** | ابزار بازیابی نقطه‌ای + راستی‌آزمایی خودکار (پروموت/جداول حیاتی/چک‌سام ۲۰۰ ردیفی) | ثبت در جدولِ مانورِ ران‌بوک |
| دریلِ فیلاور | **فصلی** | فیلاورِ پستگرس/ردیس با شبیه‌سازیِ مرگ روی استیجینگ | آر‌تی‌اوی اندازه‌گرفته + امضا |
| مانورِ تمام‌منطقه | **سالانه** | سناریوی ۳ ران‌بوک (منطقهٔ دوم) | گزارشِ رسمی به ناظر |

قاعده: نتیجهٔ هر مانور (آر‌پی‌او/آر‌تی‌اوی واقعی، گاردهای ردشده، اقدام اصلاحی)
در §۶ ران‌بوک بازیابی ثبت می‌شود؛ مانورِ بی‌ثبت = انجام‌نشده.

## ۶) برنامهٔ ارتباطات

- **داخلی:** آن‌کال ← مسئول بحران (ناظر/مدیر فنی) ← مدیریت ارشد؛ برای هر
  سطحِ شدت زمان‌بندیِ اعلام در سند پاسخ حادثه §۲ آمده است.
- **خارجی — کاربران:** صفحهٔ وضعیت با چهار فیلدِ ثابت (شناسهٔ حادثه، شدت،
  وضعیت فعلی، زمانِ به‌روزرسانی بعدی)؛ به‌روزرسانی در فواصلِ اعلام‌شده، حتی
  وقتی خبر تازه‌ای نیست.
- **خارجی — نهاد بالادستی:** وزارت آموزش‌وپرورش به‌عنوان کارفرمای ملی؛ در
  حوادثِ سطحِ بحرانی، اطلاع‌رسانی رسمی با متنِ تأییدشدهٔ ناظر.
- **رگولاتوری:** در صورت نقض داده/نفوذ، اطلاع به مراجع ذی‌صلاح در پنجرهٔ
  قانونی با هماهنگی حقوقی — فرایند فنی آن: پلی‌بوک ۸ سند حادثه (مهار +
  حفظ شواهد + چرخش رازها).

## ۷) راستی‌آزمایی پس از بازیابی (قبل از اعلام «تمام شد»)

1. **سلامت داده:** شمارش جداولِ حیاتی + چک‌سامِ نمونه‌ای (خروجی ابزار
   راستی‌آزمایی بازیابی) در برابر پیش از حادثه.
2. **دودِ برنامه:** سه گیتِ همیشگی (دودی ۵۴۷ · تطبیق مجوزها · اسکن رازها) +
   چند مسیرِ واقعی (ورود، همگام‌سازی، حضور) — فهرست دقیق در §۵ ران‌بوک بازیابی.
3. **اعتبار نشست‌ها:** اگر رمز نشست نچرخیده، نشست‌های موجود معتبرند؛ اگر
   چرخیده، کاربران ورود مجدد می‌خواهند — هر دو حالت باید آگاهانه انتخاب شده باشد.
4. **گرم‌شدن کش:** نرخ‌ها/توان‌دهی‌ها/قفل‌ها تهی‌اند؛ چند دقیقهٔ نخست ترافیک
   عادی است و نباید با «خرابی نرخ‌ها» اشتباه گرفته شود.
5. **سلامت کامل:** سلامتِ ای‌پی‌آی + هر دو چکِ زیرساخت (پستگرس/ردیس) سبز +
   آرشیوِ لاگِ تراکنش روی اصلیِ جدید فعال (وگرنه بازیابیِ بعدی می‌میرد).

## ۸) محدودیت‌های صادقانه

| مورد | وضعیت |
|---|---|
| استکِ آماده‌به‌کار | زیرساخت به‌صورت کد (کامپوز/قالب‌ها/ابزارها) کامل و تست‌شده است؛ **اجرای واقعی روی میزبانِ استقرار هنوز انجام نشده** |
| مانورها | هیچ مانورِ واقعی اجرا نشده — جدولِ ثبتِ ران‌بوک خالی است؛ چرخهٔ §۵ باید با استقرار آغاز شود |
| تکثیر بین‌منطقه | طراحیِ دومنطقه‌ای مستند است؛ سطلِ تکثیرشده و منطقهٔ دوم هنوز تأمین نشده |
| نگهداریِ ۳۰روزهٔ پشتیبان | تنظیمِ فعلی استک ۷ نسخهٔ کامل است؛ ارتقا به هدفِ سیاست = تغییر تنظیم + ظرفیت |
| صفحهٔ وضعیت و مخاطبان رسمی | قراردادشان در این سند آمده؛ خودِ صفحه و فهرست مخاطبان/توافق‌های نهادی هنوز برپا نیست |
| سند «راه‌اندازی زنده» | ندارد — مراجع واقعی: `docs/HA_POSTGRES.md` + `docs/HA_REDIS.md` + `docs/DR_RUNBOOK.md` |

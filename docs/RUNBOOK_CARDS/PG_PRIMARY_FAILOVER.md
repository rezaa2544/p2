# کارت ران‌بورد — فیلاور اولیهٔ پستگرس (PG Primary Failover)

| | |
|---|---|
| شناسه | RC-002 |
| بودجهٔ زمانی | ≤۱۵ دقیقه |
| مرجع | [HA پستگرس](../HA_POSTGRES.md) · [ران‌بورد بازیابی §۱](../DR_RUNBOOK.md) · `tools/failover-postgres.sh` |

**Trigger (محرک):** هشدار «پرایمری غیرقابل‌دسترسی» (`pg_up=0` روی پرایمری) یا قطع کامل نوشتن‌ها.
**Impact (تأثیر):** همهٔ نوشتن‌ها متوقف؛ خواندن‌ها ممکن است از ریپلیکا ادامه یابد. هدف: آر‌پی‌او ۰.

## Steps (گام‌ها)

1. **تشخیص سه‌باره:** پرایمری واقعاً مرده است؟ سه بار با فاصلهٔ ۵ ثانیه تست اتصال بزنید (گاردهای اسکریپت هم همین را می‌خواهند).
   `pg_isready -h <primary> -p 5432` — سه بار.
   **تأیید:** هر سه خطا ⇒ ادامه؛ اگر یکی وصل شد ⇒ مشکل شبکه/پول است، فیلاور **نکنید**.
2. **سنجش عقب‌ماندگی:** روی استندبای تأخیر ریکاوری را ببینید.
   `psql -h <standby> -c "SELECT now() - pg_last_xact_replay_timestamp();"`
   **تأیید:** تأخیر کم است ⇒ آر‌پی‌او ≈۰؛ اگر زیاد است فقط با پذیرش آر‌پی‌او ادامه دهید (اسکریپت `--force` می‌خواهد).
3. **فیلاور رسمی:** اسکریپت را اجرا کنید (پروموت + بازتنظیم پی‌جی‌باندسر).
   `bash tools/failover-postgres.sh --live`
   **تأیید:** خروجی اسکریپت «پروموت موفق + چک‌لیست پس از اقدام» را چاپ می‌کند.
4. **حصارکشی (fence):** پرایمری قدیمی هرگز نباید زنده برگردد و دو پرایمری شود.
   نمونهٔ قدیمی را دان/جداسازی کنید یا با نقش **ریپلیکا** به اولیهٔ تازه بپیوندید.
   **تأیید:** `SELECT count(*) FROM pg_stat_replication;` روی اولیهٔ تازه ≥۱ و هیچ «دو پرایمری» در مانیتورینگ نیست.
5. **سلامت برنامه:** اتصال اپ به اولیهٔ تازه.
   **تأیید:** `GET /health` ⇒ 200 و یک نوشتن آزمایشی کوچک موفق.

## Rollback (اگر رفع جواب نداد)

- پروموت نیمه‌کاره ماند یا استندبای سالم نیست ⇒ اسکریپت گارد دارد (اسپلیت-برین ⇒ ابورت). **دستی پروموت نکنید**؛ به سطح ۲ تشدید کنید.
- اگر اولیهٔ قدیمی زنده برگشت، آن را فقط به‌عنوان ریپلیکا بپیوندید — بازگشت به عقب با «سوییچ نقش» رسمی است، نه پروموت دوباره.

## Escalation (چه زمانی)

- اگر تا دقیقهٔ ۱۰ اولیهٔ سالم ندارید ⇒ سطح ۲ (مسئول فنی) + سطح ۳ (مالک سامانه).
- مشاهدهٔ هر نشانهٔ اسپلیت-برین ⇒ فوراً سطح ۳ + توقف هر اقدام خودکار.

# کارت ران‌بورد — بازگشت سرویس پس از استقرار خراب (Service Rollback)

| | |
|---|---|
| شناسه | RC-004 |
| بودجهٔ زمانی | ≤۱۰ دقیقه |
| مرجع | [راهنمای استقرار §۵](../DEPLOYMENT_GUIDE.md) · [بستهٔ انتشار](../GO_LIVE_PACKAGE.md) |

**Trigger (محرک):** پس از استقرار: نقطهٔ سلامت 200 نمی‌دهد، نرخ خطا/تأخیر از آستانه گذشته، یا رفتار امنیتی مشکوک.
**Impact (تأثیر):** کاربران خطا می‌بینند یا سرویس ناپایدار است؛ بازگشت کد، داده را برنمی‌گرداند (بند ۳ مرجع را ببینید).

## Steps (گام‌ها)

1. **تأیید مشکل از استقرار است:** قبل از بازگشت، همبستگی زمانی با آخرین استقرار را چک کنید.
   داشبورد: شروع افزایش خطا ≈ زمان استقرار؟
   **تأیید:** همبستگی هست ⇒ ادامه؛ نیست ⇒ کارت دیگری (مثلاً دیتابیس/ردیس).
2. **بازگشت غلتان (مسیر اصلی):** نسخهٔ قبلی را برگردانید.
   `kubectl rollout undo deployment/payesh` — در صورت نیاز به نسخهٔ مشخص: `kubectl rollout history` سپس `--to-revision=N`.
   **تأیید:** `kubectl rollout status deployment/payesh` ⇒ کامل؛ پادها ریدی.
3. **بازگشت آبی-سبز/قناری (اگر مسیر استقرار شما این است):** ترافیک را به نسخهٔ قبلی سوئیچ کنید.
   روتر/سرویس را به گروه سالم (آبی) برگردانید؛ گروه خراب (سبز/قناری) را از روتر خارج کنید.
   **تأیید:** ۱۰۰٪ ترافیک روی نسخهٔ قبلی + نبود نسخهٔ خراب در مسیر.
4. **سلامت پس از بازگشت:** تأیید سرتاسری.
   `GET /health` و `readiness` ⇒ 200 + یک smoke سریع روی استیجینگ (`node tests/smoke.js`).
   **تأیید:** هر دو سبز.
5. **بررسی داده (فقط اگر مهاجرت تخریبی داشت):** این پروژه مهاجرت تخریبی ندارد؛ اگر استثناً داشتید، `.down.sql` مربوطه: `node tools/migrate-to-pg.js down <n>`.

## Rollback (اگر رفع جواب نداد)

- بازگشت نسخه هم خطا داد ⇒ مشکل از کد نیست؛ کارت‌های دیتابیس/ردیس/دیسک را بررسی کنید.
- هرگز دو بازگشت پشت‌هم بدون تشخیص نزنید — ابتدا لاگ نسخهٔ قبلی را ببینید.

## Escalation (چه زمانی)

- اگر پس از دقیقهٔ ۱۰ هنوز نسخهٔ سالم بالا نیامده ⇒ سطح ۲.
- هر مشکل داده/مهاجرتی ⇒ فوراً سطح ۲ + کارت بازیابی (نه بازگشت کد).

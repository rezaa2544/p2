## ۱. مقدمه و پارامترهای مقیاس ملی (National Scale Parameters)

سامانه **پایش** به عنوان بستر یکپارچه و هوشمند مدیریت مدارس کشور، برای پاسخگویی به الزامات زیرساختی سطح ملی با مشخصات زیر طراحی می‌شود:

```

│                     شاخص‌های کلیدی مقیاس ملی (KPIs)                     │
├────────────────────────────────┬────────────────────────────────────────┤
│ جامعه دانش‌آموزی کل کشور       │ ۱۰,۰۰۰,۰۰۰ دانش‌آموز                   │
│ کاربران فعال هم‌زمان (Peak Concurrency)│ ۵,۰۰۰,۰۰۰ کاربر (دبیران، اولیا، کادر)  │
│ تعداد واحدهای آموزشی (مدارس)   │ ۱۰۵,۰۰۰ مدرسه در سراسر کشور            │
│ متوسط عملیات همگام‌سازی روزانه │ بیش از ۱۲۰,۰۰۰,۰۰۰ جهش (Mutations/Day) │
│ رفتار اتصال شبکه               │ Offline-First با سناریوهای قطع طولانی   │
│ سقف تأخیر پردازش در سرور       │ کمتر از ۵۰ میلی‌ثانیه برای هر Batch     │
└────────────────────────────────┴────────────────────────────────────────┘
```

### چالش‌های بنیادین محیط Offline-First در مقیاس کشوری
1. **تولید مستقل داده در کلاینت‌های ایزوله:** مدارس در مناطق روستایی یا نقاط با قطعی اینترنت باید بتوانند روزها بدون دسترسی به سرور، انواع رکوردهای جدید (حضور و غیاب، نمرات، کارنامه، ثبت‌نام، دریافت شهریه) ایجاد کنند.
2. **غیرممکن بودن قفل توزیع‌شده سراسری (Distributed Locks Failure):** ایجاد قفل‌های توزیع‌شده سنتی (مثل Redis Redlock یا Two-Phase Commit) در شبکه‌های با تأخیر بالا و ناپایدار کلاینت-سرور موجب توقف کل سامانه و فریز شدن رابط کاربری می‌شود.
3. **تعارضات ناشی از هم‌زمانی (Concurrency & Split-Brain):** ثبت همزمان نمره توسط دو دبیر، پرداخت همزمان یک قسط توسط پدر و مادر، یا تغییر همزمان وضعیت تحصیلی دانش‌آموز در حالت آفلاین باید بدون از دست رفتن داده (Zero Data Loss) حل و فصل شود.

## ۲. معماری شناسه: گذار بنیادین از ID عددی به ULID

### ۲.۱. چرا شناسه‌های عددی (Auto-Increment Integer) در مقیاس ملی شکست می‌خورند؟

| شاخص | شناسه عددی خودافزاینده (Auto-Increment) | شناسه جهان‌شمول ترتیبی (ULID) |
|---|---|---|
| **تولید در حالت آفلاین** | ❌ **غیرممکن** (نیاز به هماهنگی با سرور جهت دریافت ID بعدی) | ✅ **۱۰۰٪ مستقل در کلاینت** بدون نیاز به شبکه |
| **خطر تصادم شناسه‌های محلی** | 🔴 بسیار بالا (کلاینت‌ها شناسه مشترک مثلاً `id: 105` تولید می‌کنند) | 🟢 **صفر مطلق** بر پایه زمان و ۸۰ بیت آنتروپی |
| **امنیت و نفوذناپذیری (IDOR)** | ❌ قابل حدس و پیمایش ترتیبی (Insecure by design) | ✅ مقاوم در برابر حدس و پیمایش شناسه |
| **عملکرد ایندکس دیتابیس** | 🟡 خوب در سرور تکی، فاجعه در شاردینگ و توزیع | 🟢 فوق‌العاده سریع به دلیل حفظ ترتیب زمانی (B-Tree friendly) |
| **مهاجرت و ادغام پایگاه‌داده** | ❌ نیازمند بازسازی کلیدهای خارجی در مهاجرت | ✅ ادغام بدون تداخل جداول از ۱۰۰ هزار مدرسه |

### ۲.۲. مشخصات ساختار فنی ULID

یک **ULID (Universally Unique Lexicographically Sortable Identifier)** یک شناسه ۱۲۸ بیتی است که در قالب ۲۶ نویسه استاندارد **Crockford's Base32** (بدون حروف شبهه‌ناک I, L, O, U) کدگذاری می‌شود:

$$\text{ULID} = \underbrace{\text{Timestamp (48 bits)}}_{\text{۱۰ نویسه — دقت میلی‌ثانیه}} + \underbrace{\text{CSPRNG Randomness (80 bits)}}_{\text{۱۶ نویسه — آنتروپی رمزنگاری}}$$

```
 01AN4Z07BY      79KA1307SR9X4MV3
|----------|    |----------------|
  Timestamp         Randomness
   48 bits            80 bits
  (Base32)           (Base32)
```

#### ویژگی‌های ریاضی و فنی:
1. **مرتب‌پذیری الفبایی-زمانی (Lexicographically Sortable):** رکوردهایی که زودتر ثبت‌شده‌اند همواره بر اساس رشته کد ULID قبل از رکوردهای جدیدتر قرار می‌گیرند.
2. **طول عمر زمانی:** ۴۸ بیت زمان تا سال ۱۰۸۸۹ میلادی با دقت ۱ میلی‌ثانیه پاسخگو است.
3. **احتمال برخورد (Collision Probability):** با ۸۰ بیت تصادفی در هر میلی‌ثانیه، برای رسیدن به ۵۰٪ احتمال تصادم در یک میلی‌ثانیه مشخص، باید بیش از $1.2 \times 10^{12}$ (۱.۲ تریلیون) شناسه در همان یک میلی‌ثانیه تولید شود.

### ۲.۳. الگوریتم تولید ULID در کلاینت (Pure Vanilla JS - Zero Dependency)

پیاده‌سازی بهینه و سبک جهت ادغام در کلاینت تک‌فایلی پایش بدون نیاز به پکیج‌های npm:

```javascript
/* ==========================================================================
   ULID Generator — Pure Vanilla JS (Crockford Base32 + Monotonic Clock)
   سازگار با مرورگرهای موبایل، وب و محیط Node.js
   ========================================================================== */
(function(global){
  const ENCODING = "0123456789ABCDEFGHJKMNPQRSTVWXYZ";
  const ENCODING_LEN = 32;
  const TIME_LEN = 10;
  const RANDOM_LEN = 16;

  let lastTime = 0;
  let lastRandom = new Uint8Array(RANDOM_LEN);

  function getCryptoRandom(buffer) {
    if (typeof crypto !== 'undefined' && crypto.getRandomValues) {
      return crypto.getRandomValues(buffer);
    }
    // محیط تست یا فال‌بک امن Node.js
    const cryptoNode = require('crypto');
    return cryptoNode.randomFillSync(buffer);
  }

  function encodeTime(now, len) {
    let str = "";
    for (let i = len - 1; i >= 0; i--) {
      const mod = now % ENCODING_LEN;
      str = ENCODING.charAt(mod) + str;
      now = (now - mod) / ENCODING_LEN;
    }
    return str;
  }

  function encodeRandom(bytes) {
    let str = "";
    for (let i = 0; i < bytes.length; i++) {
      str += ENCODING.charAt(bytes[i] % ENCODING_LEN);
    }
    return str;
  }

  function generateUlid(seedTime) {
    const now = typeof seedTime === 'number' ? seedTime : Date.now();
    const timePart = encodeTime(now, TIME_LEN);

    // تضمین ترتیب یکنواخت (Monotonic Increment) در یک میلی‌ثانیه مشترک
    if (now === lastTime) {
      for (let i = RANDOM_LEN - 1; i >= 0; i--) {
        if (lastRandom[i] < 255) {
          lastRandom[i]++;
          break;
        }
        lastRandom[i] = 0;
      }
    } else {
      lastTime = now;
      getCryptoRandom(lastRandom);
    }

    const randomPart = encodeRandom(lastRandom);
    return timePart + randomPart;
  }

  global.ulid = generateUlid;
})(typeof window !== 'undefined' ? window : global);
```

## ۳. مدل نسخه‌گذاری و پروتکل همگام‌سازی (Optimistic Versioning Model)

### ۳.۱. آناتومی آبجکت جهش (Mutation Envelope)

تمامی تغییرات در کلاینت در قالب ساختار استاندارد زیر بسته‌بندی‌شده و در صف `sync_queue` قرار می‌گیرند:

```typescript
interface MutationOp {
  uid: string;             // شناسه یکتای عملیات (ULID) — برای Idempotency
  id: string;              // شناسه یکتای موجودیت هدف (ULID)
  c: string;               // نام مجموعه داده (Collection) e.g., 'grades', 'attendance'
  t: 'ins' | 'upd' | 'del';// نوع عملیات
  base_version: number;    // شماره نسخه پیش از اعمال تغییر (Optimistic Lock)
  client_time: string;     // برچسب زمان ایجاد عملیات در کلاینت (ISO 8601)
  data: Record<string, any>;// فیلدهای جدید یا تغییریافته
}
```

## ۴. ماتریس سیاست‌های حل تعارض به تفکیک حوزه‌ها (Domain Conflict Policies)

در مقیاس ملی، اعمال یک سیاست واحد (مانند صرفاً LWW یا صرفاً Reject) منجر به خرابی داده یا قفل شدن فرآیندهای مدرسه می‌شود. بنابراین سامانه پایش از **۵ سیاست تخصصی مبتنی بر دامنه (Domain-Driven Conflict Policies)** استفاده می‌کند:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        ماتریس جامع سیاست‌های حل تعارض داده                        │
├─────────────────┬───────────────────┬──────────────────────┬───────────────────────────┤
│ حوزه کاری       │ مجموعه‌های داده   │ استراتژی حل تعارض    │ رفتار و قواعد اعتبارسنجی  │
├─────────────────┼───────────────────┼──────────────────────┼───────────────────────────┤
│ حضور و غیاب     │ attendance        │ Conditional LWW      │ آخرین ثبت برنده است؛      │
│                 │ att_records       │ (بر پایه زمان سرور)  │ اعتبارسنجی تقاطع روز/کلاس  │
├─────────────────┼───────────────────┼──────────────────────┼───────────────────────────┤
│ نمرات و کارنامه │ grades, exams     │ Version-Preserved    │ عدم بازنویسی خاموش؛ ثبت   │
│                 │ corrections       │ Arbitration          │ در تعارضات + داوری مدیر   │
├─────────────────┼───────────────────┼──────────────────────┼───────────────────────────┤
│ مالی و شهریه    │ tuitions, payments│ Strict Transactional │ اتمیک (ACID) + قفل ردیف   │
│                 │ installments      │ (Row-Lock on Student)│ روی شناسه دانش‌آموز       │
├─────────────────┼───────────────────┼──────────────────────┼───────────────────────────┤
│ ثبت‌نام و ظرفیت │ enrollments       │ Capacity-Guarded     │ انحصاری مدیر + کنترل سقف  │
│                 │ classes, students │ Management Authority │ ظرفیت اسمی کلاس           │
├─────────────────┼───────────────────┼──────────────────────┼───────────────────────────┤
│ هویت و دسترسی   │ users, roles      │ Unique Constraint    │ یکتایی ملی تلفن/کد ملی    │
│                 │ permissions       │ Fail-Closed          │ در سرور + خطای 409        │
└─────────────────┴───────────────────┴──────────────────────┴───────────────────────────┘
```

### ۴.۱. حوزه ۱: حضور و غیاب (Attendance Policy)

* **استراتژی:** `Conditional Last-Write-Wins (CLWW)`
* **منطق کسب‌وکار:** حضور و غیاب یک رویداد برخط روزانه است. اگر دبیری در زنگ اول دانش‌آموز را غایب بزند و ناظم مدرسه نیم ساعت بعد وضعیت را به «حاضر با تأخیر» تغییر دهد، وضعیت ناظم ارجحیت دارد.
* **قواعد و شروط نگهبان (Guards):**
  1. **بررسی تقاطع روز و ساعت (Time-Window Guard):** ثبت حضور فقط برای همان روز مجاز است؛ ثبت وضعیت برای روزهای گذشته نیازمند سطح دسترسی مدیر است.
  2. **گارد روز غیرحضوری (Virtual Day Guard):** در صورتی که سرور مدرسه را در آن تاریخ «غیرحضوری» اعلام کرده باشد، هرگونه درج وضعیت غیبت عادی رد می‌شود (`virtual_day_blocked`).
  3. **حفظ سابقه اصلاح (Audit Trace):** هر بازنویسی LWW وضعیت قبلی را در آرایه تاریخچه رکورد نگه‌می‌دارد.

---

### ۴.۲. حوزه ۲: نمرات و کارنامه (Grades Policy)

* **استراتژی:** `Optimistic Versioning with Conflict Preservation & Arbitration`
* **منطق کسب‌وکار:** نمره سند حقوقی و سرنوشت‌ساز دانش‌آموز است. بازنویسی خاموش با LWW می‌تواند موجب تغییر غیرعمدی یا مخرب نمره نهایی شود.
* **الگوریتم حل تعارض:**
  1. اگر `op.base_version === server_rec.version`: نمره اعمال‌شده و `version` یک واحد افزایش می‌یابد.
  2. اگر `op.base_version !== server_rec.version`:
     - عملیات مستقیماً اعمال **نمی‌شود**.
     - رکورد تعارض در مجموعه `sync_conflicts` ذخیره می‌شود:
       $$\text{Conflict} = \{ \text{id}, \text{record\_id}, \text{base\_version}, \text{server\_version}, \text{server\_val}, \text{incoming\_val}, \text{by}, \text{status: 'open'} \}$$
     - اعلان فوری با اولویت بالا برای مدیر مدرسه ارسال می‌شود (`conflict_notification`).
     - مدیر از طریق پنل داوری تعارضات (`POST /api/sync/resolve-conflict`) یکی از دو نسخه را انتخاب می‌کند.
  3. **اعتبارسنجی دامنه نمره (Range Validation):** نمره عددی باید در بازه $[0, 20]$ با حداکثر دو رقم اعشار باشد؛ نمرات کیفی ابتدایی باید دقیقاً منطبق بر مقادیر معتبر (`خیلی خوب`, `خوب`, `قابل قبول`, `نیاز به آموزش`) باشند.

---

### ۴.۳. حوزه ۳: مالی، شهریه و تراکنش‌ها (Finance & Tuition Policy)

* **استراتژی:** `Strict Transactional Isolation (Pessimistic Row-Locking per Student)`
* **منطق کسب‌وکار:** جلوگیری از پرداخت تکراری (Double Payment) و مغایرت مانده حساب بدهکاری/بستانکاری دانش‌آموز.
* **الگوریتم پردازش:**
  1. شروع تراکنش اتمیک روی پایگاه‌داده.
  2. اخذ قفل انحصاری روی ردیف شهریه دانش‌آموز (`SELECT * FROM tuitions WHERE student_id = ? FOR UPDATE`).
  3. اعتبارسنجی مجدد مانده بدهی؛ اگر مبلغ پرداختی بیش از مانده باشد، تراکنش لغو و وجه در حساب کیف پول منظور می‌شود.
  4. اعمال همزمان ۳ جهش در یک تراکنش واحد:
     - ثبت رکورد در `transactions`
     - به‌روزرسانی وضعیت قسط در `installments`
     - کسر از مانده کل در `tuitions`
  5. آزادسازی قفل و انتشار لاگ تراکنش به ممیزی (`audit`).

---

### ۴.۴. حوزه ۴: ثبت‌نام، کلاس‌بندی و ظرفیت (Enrollment Policy)

* **استراتژی:** `Capacity-Guarded Management Authority`
* **منطق کسب‌وکار:** تخصیص دانش‌آموز به کلاس منحصراً در صلاحیت مدیر مدرسه یا سوپرادمین است و باید سقف مصوب آموزش و پرورش رعایت شود.
* **قواعد اعتبارسنجی:**
  1. شمارش بلادرنگ دانش‌آموزان فعال کلاس:
     $$\text{CurrentCount} = \text{Count}(\text{enrollments where class\_id} = C \text{ and status} = \text{'active'})$$
  2. شرط پذیرش: $\text{CurrentCount} + 1 \le \text{Class.capacity}$
  3. در صورت تکمیل ظرفیت، خطا با کد `capacity_exceeded` بازگردانده‌شده و درخواست به صف «پیش‌ثبت‌نام و انتظار» منتقل می‌شود.

---

### ۴.۵. حوزه ۵: هویت و اطلاعات پایه کاربری (Identity Policy)

* **استراتژی:** `Server-Enforced Global Unique Constraint`
* **منطق کسب‌وکار:** هر شماره همراه و هر کد ملی در کل کشور باید منحصر‌به‌فرد باشد.
* **الگوریتم اعتبارسنجی:**
  1. بررسی صحت الگوریتم ده‌رقمی چک‌سام کد ملی ایران:
     $$(\sum_{i=1}^{9} \text{Digit}_i \times (11 - i)) \pmod{11} = \text{CheckDigit}$$
  2. جستجوی سراسری روی ایندکس `idx_users_nid` و `idx_users_phone`.
  3. در صورت وجود رکورد مغایر، عملیات رد‌شده و خطای `409 Conflict (identity_duplicate)` صادر می‌گردد.

## ۵. سناریوهای جامع آزمون و شرایط مرزی (Comprehensive Test Scenarios)

### سناریو ۱: مسابقه ویرایش نمره در حالت آفلاین (Concurrent Offline Grade Race)

### سناریو ۲: پرداخت هم‌زمان اقساط توسط پدر و مادر (Concurrent Dual Payment)
* **شرایط اولیه:** مانده بدهی قسط شهریه: ۱,۰۰۰,۰۰۰ تومان.
* **رخداد:** پدر و مادر همزمان در دو اپلیکیشن جداگانه دکمه پرداخت آنلاین قسط را می‌زنند.
* **نتیجه مورد انتظار:**
  - درخواست پدر با قفل ردیف وارد دیتابیس‌شده، قسط تسویه می‌شود و مانده به صفر می‌رسد.
  - درخواست مادر به دلیل رسیدن مانده به صفر با پیام «این قسط قبلاً پرداخت‌شده است» متوقف‌شده و مبلغ پرداختی مادر به عنوان بستانکاری در کیف پول دانش‌آموز شارژ می‌شود (عدم ایجاد بالانس منفی).

---

### سناریو ۳: انحراف زمانی ساعت دستگاه کلاینت (Clock Skew Tolerance)
* **شرایط:** ساعت گوشی دبیر به اشتباه ۲ روز به جلو یا عقب تنظیم‌شده است.
* **نتیجه مورد انتظار:**
  - سرور عملیات را به دلیل خطای ساعت رد نمی‌کند (تا سقف ۲۴ ساعت مجاز).
  - در گزارش ممیزی رخداد `sync_clock_skew` ثبت می‌شود.
  - زمان قطعی ثبت رکورد در دیتابیس همواره بر مبنای ساعت اتمی هماهنگ‌شده سرور (NTP Server Time) اعمال می‌گردد.

## ۶. نقشه راه مهاجرت از ID عددی به ULID (Zero-Downtime Migration Plan)

برای جلوگیری از هرگونه توقف در کارکرد مدارس کشور، فرآیند مهاجرت در ۴ فاز زمان‌بندی‌شده اجرا می‌شود:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    مراحل ۴ گانه مهاجرت ساختار شناسه‌ها                  │
├─────────────────────────────────────────────────────────────────────────┤
│ فاز ۱: پشتیبانی دوگانه (Dual-ID Support)                               │
│       - افزودن ستون ulid به تمامی جداول پایگاه‌داده                    │
│       - پذیرش هم‌زمان id عددی و ulid در API سرور                       │
│       - تولید ULID برای تمام رکوردهای جدید کلاینت                      │
├─────────────────────────────────────────────────────────────────────────┤
│ فاز ۲: نگاشت و انتقال داده‌های گذشته (Data Backfill Migration)          │
│       - اجرای اسکریپت tools/migrate-to-ulid.js                         │
│       - تولید ULID معادل زمانی برای رکوردهای قدیمی بر اساس created_at  │
│       - ساخت جدول نگاشت id_map(legacy_id, ulid, collection)            │
├─────────────────────────────────────────────────────────────────────────┤
│ فاز ۳: به‌روزرسانی کلیدهای خارجی و ایندکس‌ها (Foreign Key Cutover)      │
│       - جایگزینی school_id, student_id, class_id با شناسه‌های ULID      │
│       - بازسازی ایندکس‌های B-Tree در SQLite / PostgreSQL               │
│       - اجرای آزمون‌های یکپارچگی ارجاعی (Referential Integrity Check)   │
├─────────────────────────────────────────────────────────────────────────┤
│ فاز ۴: سوئیچ نهایی و حذف ستون‌های عددی (Final Deprecation)              │
│       - غیرفعال‌سازی ستون‌های عددی Auto-Increment                      │
│       - انتشار نسخه نهایی کلاینت تک‌فایلی                              │
└─────────────────────────────────────────────────────────────────────────┘
```

### نمونه اسکریپت نگاشت و تولید ULID برای داده‌های قدیمی:

```javascript
/* tools/migrate-to-ulid.js — ابزار تبدیل شناسه‌های قدیمی */
function migrateRecordToUlid(record, collectionName) {
  if (record.ulid) return record; // قبلاً مهاجرت‌شده
  
  const createdTime = record.created_at ? new Date(record.created_at).getTime() : Date.now();
  const newUlid = ulid(createdTime);
  
  return {
    ...record,
    ulid: newUlid,
    legacy_id: record.id
  };
}
```

## ۷. جمع‌بندی و الزامات استقرار

با استقرار این مدل معماری:
1. **استقلال ۱۰۰٪ کلاینت‌های آفلاین** در سراسر کشور تضمین می‌شود.
2. **هیچ داده‌ای در اثر هم‌زمانی و تداخل پاک یا بازنویسی ناخواسته نخواهد شد** (Zero Data Loss).
3. عملکرد پایگاه‌داده سرور به دلیل خاصیت مرتب‌بودن زمانی ULID در مقیاس ۱۰ میلیون دانش‌آموز در بالاترین سطح بهینگی (Sub-millisecond Index Lookup) باقی می‌ماند.

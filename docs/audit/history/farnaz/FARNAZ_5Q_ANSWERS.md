## سؤال ۴ — شیم موقت jsdom و اعتبار تست‌ها

### پاسخ کوتاه

شیم **موقت و فقط-محیط-تست** بود؛ روی هیچ محیط واقعی اجرا نمی‌شود/نشده؛ و **اعتبار اعداد سبز را کم نمی‌کند** — چون اعداد از اجراهای واقعی (نه ردشده) آمده‌اند. جزئیات با مدرک:

### ۱. شیم چه بود و کجا بود؟

- تک‌خط در `/tmp/node-shim.js` (بیرون مخزن، هرگز کامیت نشد): اگر `worker_threads.markAsUncloneable` نبود، یک no-op می‌گذاشت؛ اجراها با `node --require /tmp/node-shim.js` انجام شدند.
- ریشهٔ نیاز: `jsdom@30` (مرج PR #16) ← `undici@8.10.2` که در `lib/web/webidl/index.js:5` به `markAsUncloneable` از `node:worker_threads` نیاز دارد؛ این API در Node این سندباکس (`v20.20.2` — اثبات: `typeof … === 'undefined'`) نیست ⇒ `require('jsdom')` می‌ترکید و سوئیت‌ها به شاخهٔ «نصب نیست» می‌افتادند.

### ۲. چرا اعتبار سبزها خدشه‌دار نمی‌شود؟

- تابع وصله‌شده فقط در سازندهٔ `CacheStorage` کتابخانهٔ undici (API کشِ ServiceWorker) صدا می‌شود؛ تست‌های دودی تک‌ریسه‌ای jsdom هرگز از cloning بین workerها استفاده نمی‌کنند ⇒ اثر رفتاری وصله بر assertionها **تهی** است.
- مهم‌تر: خطاهای «رد شد» با پیام متمایز خارج می‌شوند (`tests/smoke.js:15`)؛ همهٔ اعداد گزارش‌شده (۵۴۷/۵۴۷ و…) از مسیر اجرای کامل با شمارش assertion آمده‌اند، نه مسیر رد. (شاهد معکوس: وقتی شیم نبود، خروجی «⏭️ رد شد» بود، نه عدد.)

### ۳. آیا CI/پایلوت واقعی هم به وصله نیاز دارند؟

- **پایلوت/تولید: خیر، قطعاً.** `jsdom` در `devDependencies` است (`package.json` — ران‌تایم فقط `ioredis`+`pg`)؛ هیچ مسیر اجرایی واقعی jsdom را load نمی‌کند.
- **CI: احتمالاً خیر، ولی یک حفرهٔ واقعی هست.** ورک‌فلو `.github/workflows/node.js.yml` روی 18.x/20.x/22.x دستور `npm test` (= `run.js` + `smoke.js`) را می‌دواند و سبز بوده (نمونه: ۴ چک PR #22) — پس Nodeهای گیت‌هاب یا جدیدترند (بک‌پورت API) یا… نکتهٔ دوم مهم‌تر است:
- **یافتهٔ جنبی (مهم):** شاخهٔ catch در `smoke.js:14-15` بین «jsdom نصب نیست» و «jsdom خراب است» فرق نمی‌گذارد و با **exit(0)** خارج می‌شود ⇒ اگر روزی jsdom در CI بشکند، پایپ‌لاین **سبزِ کاذب با صفر تست اجراشده** می‌دهد. این خلاف اصل fail-closed (SKILLS §۱) است. توصیه (بدون اقدام، چون دستور جاری فقط-سند است): تفکیک خطا (نبود ⇒ exit 2 با پیام؛ خرابی ⇒ exit 1) یا assertion روی «۵۴۷/۵۴۷» در خروجی CI.

## سؤال ۵ — بند B.3: ارزشیابی ناشناس معلم (طرح کامل، با ناشناسی کامل)

> دامنه: **طرح** (کد منوط به تأیید صریح ناظر است — اصل هشتم). این بند حساس است: ناشناسی باید در برابر مدیر مدرسه، سوپرادمین و حتی خوانندهٔ مستقیم دیتابیس پایدار بماند.

### ۱. مدل تهدید (چه چیزی را پنهان می‌کنیم؟)

- **سوژه (آشکار، لازم):** معلمِ ارزشیابی‌شونده + مدرسه + دورهٔ زمانی — این‌ها شناسهٔ عادی دارند.
- **راز (پنهان مطلق):** هویت ارزشیاب (کدام دانش‌آموز/ولی، چه رأیی داد). مهاجم: مدیر کنجکاو، ادمین دیتابیس، خوانندهٔ لاگ/بکاپ.
- **نکتهٔ طراحی:** رأی‌دادنِ دوباره باید بدون شناخت رأی‌دهنده مهار شود ⇒ **توکن‌های بی‌نام یک‌بارمصرف** (الگو: کد OTP موجود در `server/auth.js`، ولی بدون اتصال به هویت).

### ۲. معماری پیشنهادی

**الف) صدور توکن (تنها نقطهٔ تماس هویت — و بلافاصله فراموشی):**

- برای هر (مدرسه، معلم، دوره، کلاسِ واجد)، سرور N توکن تصادفی (`crypto.randomInt` + `sha256`، الگوی OTP در SKILLS §۲) می‌سازد و **فقط هش** را در جدولِ فقط-سروری `eval_tokens{token_hash, school_id, teacher_id, period, consumed}` نگه می‌دارد — **هیچ ستون هویت/کلاسِ تکی/زمانِ دقیقی**.
- متن توکن یک‌بار از کانال امن خود کاربر (صندوق داخلی ولی/دانش‌آموز واجد) نمایش داده می‌شود و دیگر هرگز قابل‌بازیابی نیست. توکن‌ها درون استخر (معلم، دوره) **تعویض‌پذیر**‌اند: دانستن «کدام توکن مصرف شد» هیچ ربطی به «چه کسی» نمی‌دهد.

**ب) ثبت رأی (کالکشن `teacher_evals` — عمداً بدون هویت):**

```
teacher_evals { id, school_id, teacher_id, period, day_bucket,
                answers(JSON: پنج سؤال ثابت ۱–۵), comment?(≤۳۰۰ نویسه) }
```

- ممنوعه‌ها (با گیت fail-closed در `server/validate.js` + تست قفل): هر فیلد هویتی (`student_id/parent_id/user_id/token/ip/user_agent`) ⇒ `validation_failed`؛ `created_at` دقیق ذخیره نمی‌شود (فقط `day_bucket` — انحراف آگاهانه و مستند از سنت `created_at`) تا همبستگی زمانی ناممکن شود.
- ثبت = ارائهٔ توکن معتبرِ مصرف‌نشده ⇒ علامت `consumed` + درج رأی **بدون هیچ پیوندی** بین سطر توکن و سطر رأی (دو تراکنش جدا؛ حتی ترتیب درج، ربط را لو نمی‌دهد چون انتشار تجمیعی پس از بستن دوره است).

**ج) گزارش (فقط تجمیعی + حد نصاب — الگوی `dropStats` در AD 76.1):**

- خروجی فقط: تعداد، میانگین/توزیع هر سؤال. **قاعدهٔ سرکوب:** گروه با `n < 5` ⇒ «کمتر از حد نصاب» (بدون عدد)؛ نظرهای متنی فقط وقتی `n ≥ 10` و با ترتیب تصادفی نمایش.
- نقش‌ها: ثبت = دارندهٔ توکن (بدون احراز هویت هویتی در لحظهٔ ثبت، فقط اعتبار توکن)؛ مشاهدهٔ تجمیعی = مدیر مدرسهٔ خود + سوپرادمین؛ معلم = فقط تجمیعیِ خودش. هیچ نمایی سطر خام نشان نمی‌دهد.
- لاگ حسابرسی (`server/audit.js`) فقط شمارش ثبت می‌کند («۱ رأی در دورهٔ X») — هرگز توکن/هویت/متن.

**د) همگام‌سازی و PG:** رأی‌ها چون PII ندارند با همان write-perms (نقش `eval-submit` مجازی؟ — نه: ثبت از مسیر API ناشناس جدا، بیرون از sync، تا `op.by` هویت ننویسد)؛ جدول PG آینهٔ همان سفیدفهرست؛ جدول توکن‌ها **فقط-سرور** (هرگز sync نمی‌شود).

### ۳. تست‌ها (طبق SKILLS §۵ — هرکدام با جهش‌کشی)

- دامنه (`eval2`): واجد/ناواجد، مصرف دوبارهٔ توکن (رد)، حد نصاب ۵/۱۰، دامنهٔ مدیر/معلم.
- حریم (`eval-privacy`): **پویش استاتیک** (هیچ فیلد هویتی در مدل/اسکیما/نماها) + **دینامیک** (ثبت واقعی ⇒ بازخوانی سطر ⇒ کلیدها دقیقاً همان سفیدفهرست).
- جهش‌ها: حذف سرکوب ⇒ باید بمیرد؛ افزودن ستون هویت ⇒ باید بمیرد؛ دورزدن `consumed` ⇒ باید بمیرد.

### ۴. زمان تخمینی (تک‌چت، با دروازه‌های کامل)

| فاز | کار | زمان |
|---|---|---|
| ۱ | مدل + `eval_tokens` + API ناشناس + سفیدفهرست validate + PG | ۱ روز |
| ۲ | UI ثبت (فرم بی‌نام) + UI تجمیعی + حد نصاب + نقش‌ها | ۱ روز |
| ۳ | `eval2` + `eval-privacy` + جهش‌ها + `secret-scan`/`check-authz` | ۱–۱.۵ روز |
| ۴ | بازبینی ناظر + رفع + رگرسیون (`smoke` ۵۴۷/۵۴۷) | ۰.۵ روز |
| **جمع** | | **≈ ۴ روز کاری** (+ بافر پایلوت) |

### ۵. تصمیم‌های لازم از ناظر/کارفرما پیش از پیاده‌سازی

1. پنج سؤال ثابت ارزشیابی (متن دقیق) + دوره‌ها (ترمی/سالیانه)؛ ۲. آستانه‌های ۵/۱۰ تأیید شود؛ ۳. آیا نظر متنی اصلاً لازم است (ریسک سبک‌نگارشی) یا فقط نمره؟

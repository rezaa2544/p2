# دور ۸۹ — بازِ‌سازیِ جریان‌هایِ همگام‌سازیِ نقش‌هایِ غیرمدیر (chat/تکلیف/نشان/ردِ فرزند)

**تاریخ:** ۲۰۲۶-۰۹-۰۸ · **مبنایِ شروع:** باقی‌ماندهٔ شمارهٔ ۱ گزارشِ دور ۸۸ («شکافِ سیستماتیکِ اعلان»)
**کامیت‌ها:** `186a4e9` (رفع) · `ebc355c` (سازگاری S20) · `264748c` (محافظِ قرمزِ کاذب) — همه روی main و پوش‌شده
**گیت نهایی:** رجیسیون **125/125** (458s) · smoke 546/546 · check-authz 0 · server1 31/31 · server12 **41/41**

## چه پیدا شد (ماتریسِ پروبِ زنده، پیش از هر تغییری)

پروبِ ۳۱ موردی روی سرورِ واقعی (چهار نشستِ زنده: والد/دبیر/دانش‌آموز/مدیر) نشان داد که
`inScope` برایِ عملیاتِ **ins** فقط رکوردهایی را می‌شناسد که «مالکیت» را روی `student_id`
(یا `parent_id` روی رکوردِ موجود) سوار کنند. نتیجه:

| جریان | نقش | وضعیتِ قبل |
|---|---|---|
| چت (`ins messages`) | والد/دبیر/دانش‌آموز | **403 — کلِ چتِ غیرمدیر در حالتِ سرور کار نمی‌کرد** (پیام، نه فقط نشان) |
| نشانِ «خوانده شد» (`upd notifications`) | والد/دانش‌آموز | **403** — نشانِ قرمز هیچ‌وقت پاک نمی‌شد (والد out_of_scope، دانش‌آموز role_denied) |
| تکلیف/جنگی (`ins hw_assignments`/`vclass_sessions`) | دبیر | **403** — رکوردِ کلاسی بدونِ student_id |
| نوبتِ مشاوره (`ins meeting_slots`) | دبیر | **403** — رکورد با `parent_id:null, student_id:null` |
| ردِ فرزند (`kid-reject`) | والد | **3 شکست**: `corrections` و `parent_links` اصلاً در `WRITE_PERMS`ِ والد نبودند (role_denied) — گزارش به مدرسه نمی‌رسید |
| موجه/مرخصی | والد | ins خوب بود؛ اعلانِ مدیر را دور ۸۸ پوشش داده بود (کلمه‌گذاری فقط «موجه» بود) |

## رفع‌ها (همه در `server/sync.js` — صفر تغییرِ کلاینت)

1. **`WRITE_PERMS`:** والد + `corrections` + `parent_links` · دانش‌آموز + `notifications`
   (هر دو محدودِ `inScope` می‌مانند — اجازهٔ خام نمی‌دهد).
2. **مالکیتِ پیام (chat):** برایِ سه نقشِ رکوردی (student/parent/teacher)، `messages` فقط
   با `from_id === u.id` (ins) یا `rec.from_id === u.id` (upd/del)؛ بدونِ `from_id` = fail-closed.
   **مدیر/edu_office مسیرِ قدیمیِ سطحِ مدرسه را نگه می‌دارند** — قراردادِ تستِ موجود
   (server1 S20: پیامِ مدیر بدونِ `from_id`) شکست و در رجیسیون رد شد؛ محدودسازی نقش،
   رفعِ درست بود (کامیت `ebc355c`).
3. **نشانِ خوانده‌شدن:** هر کاربر `upd` رکوردِ اعلانِ **خودش** (`rec.user_id===u.id`) —
   فقط برایِ نقش‌هایی که قبلاً هیچ مسیری نداشتند (والد/دانش‌آموز)؛ مدیر/دبیر/مشاور قبلاً
   از مسیرِ مدرسه رد می‌شدند (بدونِ تغییر).
4. **دامنهٔ کلاسیِ دبیر:** `hw_assignments`/`vclass_sessions` فقط برایِ کلاسی که دبیر
   سرپرستِ پایهٔ آن است یا در برنامهٔ تدریسش دارد — برایِ کلاسِ دیگر **fail-closed**
   (حتی همان مدرسه) · `meeting_slots` فقط نوبتِ خودش.
5. **گاردِ `parent_links`:** ins جدید فقط با `parent_id === u.id` (ساختِ لینکِ جعلی برای
   فرزندِ خود، با parent_idِ دیگران، مسدود) — و خودِ لینک همچنان فقط فرزندِ فعلی.
6. **هُک‌هایِ اعلانِ سمتِ سرور** (کنارِ هوکِ دور ۸۸؛ کلاینت نمی‌تواند اعلان بسازد، پس
   سرور برایِ عملِ خودش می‌سازد):
   - `ins messages` (نقشِ غیرمدیر) → اعلانِ chat برایِ گیرنده
   - `ins corrections` (status open) → اعلانِ «درخواست اصلاح اطلاعات ولی» برایِ مدیر
   - هوکِ مرخصی: کلمه‌گذاری **عمومی** شد («درخواست مرخصی جدید … از X تا Y») تا برای
     هر دو جریان (موجهِ سریع + مرخصیِ استاندارد) درست بخواند
   - **جلوگیری از تکرار:** هوک‌ها نقش‌هایِ مدیر/سوپرادمین را رد می‌کنند — اعلانِ کلاینتیِ
     مدیر apply می‌شود و هوک تکرار نمی‌کند (پروب: «دقیقاً یک»).

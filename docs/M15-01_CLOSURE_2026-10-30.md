Five consecutive passes recorded the same sentence — *no PostgreSQL, no Redis, no Docker, no
Chromium* — and it is the reason 63 real verdicts had to be filed as environment reds. It is no
longer true, and none of it needed a repository change:

| service | version | how it was obtained | CI baseline |
|---|---|---|---|
| PostgreSQL | **18.4** | npm `@embedded-postgres/linux-x64@18.4.0-beta.17` — a real server with `initdb`/`pg_ctl`; cluster `/tmp/pgdata`, DSN `postgres://payesh:payesh@127.0.0.1:5432/payesh_ci` | `postgres:17` service container |
| Redis | **6.2.14** | `redislite` wheel from PyPI (a real `redis-server` binary) on `127.0.0.1:6379` | `redis:8` service container |
| Chromium | **153.0.8010.0** | npm `@sparticuz/chromium` + its AL2023 libraries, driven by `playwright`, exported as `CHROMIUM_PATH` — the same hook `.github/workflows/node.js.yml` uses | `playwright install chromium` |

Two details are part of the evidence rather than setup trivia:

* **`PGDATA=/tmp/pgdata` is load-bearing.** `tests/pg-outage-control.js` stops and starts "the
  PostgreSQL that `DATABASE_URL` actually talks to" through Docker, `pg_ctlcluster` or
  `pg_ctl -D $PGDATA`. With no Docker and no Debian cluster, only the third path exists — so
  without `PGDATA` the suites that must *really* stop the database (`phase65-runtime-truth`
  RT-06, `chaos-suite` S2) cannot, and report a failure that look like a product defect. With it,
  RT-06 passes (37/37) and S2 passes (19/19).
* **`sudo` is available, and that changed the verdict on two drills.** `sudo -n mount -t tmpfs`
  works here, so `chaos-drill-disk-pressure` could fill a real 96 MB tmpfs after the `createdb`
  fix (§5.3) — it now passes with 16 real checks and `ENOSPC`/`PANIC` lines in the PostgreSQL log.
  What is still impossible is `wal-disk-full`: it needs a cluster directory **owned by the OS user
  `postgres`**, and without root `chown` is refused, so `sudo -u postgres initdb` cannot prepare one.
  That drill therefore stays NOT-RUN and says so (exit 2), which is its own honest verdict.
* **`/var/tmp/local-services` must exist.** `chaos-suite` restarts PostgreSQL with a hardcoded
  `-l /var/tmp/local-services/pg.log`; in a sandbox where that directory does not exist the
  restart silently fails and the suite then dies one step later with `ECONNREFUSED 5432`. Creating
  the directory is environment provisioning; changing the suite to write somewhere else would have
  been a change to a test that CI does not need.

Still absent, and therefore still a hard boundary: **Docker** (C-03/C-04/C-05 cannot run),
the PostgreSQL **client package** (`psql`, `createdb` are now replaced by shims; `pg_dump`,
`pg_isready` and `pg_basebackup` are not), a **`postgres`-owned cluster directory** (root `chown`
is not available), and any **second host** (E4).

Versions differ from CI (PG 18 vs 17, Redis 6.2 vs 8). Every claim below was executed here, not
inferred across the gap, but a behaviour that differs *only* on PG 17 or Redis 8 would not be
caught by these runs — that limitation is repeated in §9.

## 5. Three repository-controlled defects, found only because a database now exists

### 5.1 `tools/psql-min.js` refused the surface the live suites actually use

The shim's reason to exist is *"suites that shell out to `psql` work on a machine without the real
binary"*. Measured, it did not:

| invocation that exists in the repository | shim's answer | consequence |
|---|---|---|
| `psql -h … -p … -U … -d … -tA -c …` (`n21`, `n22`, `chaos-drill-lib`) | `-h` refused | suite dies in its fixture step |
| `psql <url> -t -A -c …` (`a35-regression`) | `-t` refused | dies before its first assertion |
| `psql <url> -v ON_ERROR_STOP=1 -q -f -` (`wave23-norm-edge-mutations`) | `-f -` treated as a file named `-` | `ENOENT … open '/home/user/p2/-'` |
| `psql <url> -v … -q` with the script on **stdin** (`migration-012`; psql's documented default) | `nothing to execute` | fixture step dies |
| URL with `sslmode=prefer` against a server without TLS (`phase2-occ-*`, `chaos-suite`) | `The server does not support SSL connections` | NOT-RUN against a reachable database |

Fix: psql's own argument shapes (`-h/-p/-U/-d` and long forms, clustered `-tAq`, a cluster ending
in a value flag, `-d` accepting a conninfo string, `--version`, `-w`/`-X` as documented no-ops),
`-f -` and "neither `-f` nor `-c`" read stdin, an explicit TLS policy (`require`/`verify-*` force
TLS, `disable`/`allow` never, `prefer` connects and retries once with TLS), and psql-shaped row
output so `-tA -c 'SELECT count(*)'` prints a bare number.

Guards did not move: unknown option, unknown letter in a cluster, unsupported `--sslmode`,
non-numeric `-p`, missing target, unknown meta-command, unresolved `:var`, and a `-f` path escaping
the base directory are all still hard failures. `--selftest` **33/33 → 48/48** (`+P22..P31`,
`+N13..N17`). The one deviation from real psql — `prefer` connects plaintext first and retries with
TLS — is written into `tools/PSQL_SHIM_GUIDE.md` §4a instead of being left implicit.

### 5.2 `migration-012-crash-recovery-live` mutated the shared database and depended on its contents

The suite rolled the **shared** database down to `011` and left it there. Two measured
consequences:

* **it fails on a seeded database.** Migration `025` widens `bell_schedules.days` to `TEXT`
  precisely because a real school week stringifies to ~1.3 KB, and `025…down.sql` is deliberately
  fail-closed. On a database any earlier suite has seeded, the rollback dies with `value too long
  for type character varying(255)` — the migration behaving correctly, the test's precondition
  being wrong;
* **it destroys shared state.** Every later suite expects the shared database at head.

Fix: the same real chain (`migrateUp` to head, roll down to `011`, the crash window, the recovery,
the checksum assertion) now runs on its own scratch database `payesh_m012_crash`, dropped
afterwards. No assertion changed; only which database they apply to.

## 7. Registry: 66 failures → 0 failures, and the blocker that was *not* removed

The registry was bound to `bf263bf2` while the tree is elsewhere, so the gate's 66 failures were
all **one** class — `V-02` (artifact/SHA binding) ×33 and `G9` (per-item binding) ×32 — and nothing
else. The gate was not saying "the work is wrong"; it was saying "this evidence describes a tree
that no longer exists".

The protocol in `docs/STRICT_VERIFICATION_GATE.md` (two-phase binding) says: produce evidence on an
immutable source SHA, commit it, then land a **single-parent** commit that changes exactly the
registry emitted against that SHA. Done with the repository's own builder, not by editing JSON:

| step | command | result |
|---|---|---|
| collect | `node tools/m15-01-build-registry.js --collect` | 4/4 evidence runs exit 0, zero failing checks |
| emit | `node tools/m15-01-build-registry.js --emit --head 590a5c6eb4624112a51a9b1acc3114c5bcd1fcb2` | 32 items, `head_bound=590a5c6eb4624112a51a9b1acc3114c5bcd1fcb2` |
| land | a single-parent registry-only commit whose parent is `590a5c6e` and which changes exactly one path | the shape measured above |

After: `node tools/strict-verification-gate.js` → ****697 OK / 1 FAIL** — and the failure is `V-06` alone (HEAD must be contained in `origin/main`; a branch tip can never satisfy it, owner decision OD-2). **VERDICT NOT VERIFIED**, `VERIFIED_ITEMS 3/32`, blocked by `V-15`/`V-16`.**.

Measured on the rebinding commit (dry-run of the exact landing shape, then reverted so the real
registry-only commit could be produced from the documentation commit):

```
==== PAYESH STRICT VERIFICATION GATE ====
  OK G1 current HEAD known — <registry-only commit>
  OK V-02 evidence binding mode explicit — single-parent registry-only metadata commit; evidence binds parent 590a5c6e
  OK V-02 registry head_bound matches immutable evidence SHA — head_bound=590a5c6e evidence_sha=590a5c6e [metadata-only]
  OK V-02 A-01 evidence binds immutable SHA+artifact+hash+exit0
  OK G9 A-01 binds immutable evidence SHA — item=590a5c6e evidence_sha=590a5c6e
  OK V-15 registry status is bounded by its weakest item — top=UNKNOWN(0) weakest_item_rank=0
  OK V-15b blocked items cap the registry below the verifying band — blocked_items=29 top=UNKNOWN
  FAIL V-06 HEAD contained in origin/main (not a local-only line)
CONTRACT FAIL
VERIFIED_ITEMS 3/32 at registry status UNKNOWN
VERDICT NOT VERIFIED
```

697 checks pass, one fails, and the one that fails is not about this work at all: `V-06` requires
the gate's HEAD to be an ancestor of `origin/main`, which is impossible for a branch tip and is
recorded as an open owner decision (OD-2) in the registry itself. Before the rebind the same file
produced **66** failures (`V-02` ×33, `G9` ×32) because the evidence pointed at `bf263bf2`.

**This is not promotion and not closure.** Re-binding says the evidence describes this tree; it does
not say the 29 legacy carry-over items are verified. They remain `UNKNOWN`/`blocked` with their
Atria-era text quoted verbatim, and the gate correctly refuses to call a registry green that
verifies nothing (`V-16`), with the headline capped at its weakest item (`V-15`). Clearing that
requires verifying A-01…A-29 — the programme itself — not a metadata edit. Inventing statuses is the
one thing this repository's gate exists to prevent, and it was not done.

## 9. Limitations (explicit, not buried)

1. **Version deltas.** PG 18.4 / Redis 6.2.14 / Chromium 153 — not the CI baseline (17 / 8 / pinned
   Playwright). Everything claimed was executed here, but a regression specific to those CI versions
   would not be caught by these runs.
2. **No Docker, no sudo, no client package.** C-03/C-04/C-05, the two disk-pressure drills and the
   E4 subsets cannot run here; their verdict is "not demonstrated in this environment", never
   "passing".
3. **The final run precedes the documentation commit.** A commit cannot contain its own run; the

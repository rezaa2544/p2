## ۱. هدف و چرایی

در نسخه‌های اولیه کلاینت، تمام داده‌ها به صورت محلی در حافظه مرورگر تولید و نگهداری می‌شدند و همگام‌سازی صرفاً از طریق صف ارسال یک‌طرفه (Push-only / `POST /api/sync`) انجام می‌پذیرفت. برای حرکت به سمت یک معماری داده‌محور و چندکاربره سازمانی، کلاینت نیازمند سازوکاری استاندارد جهت:
1. **دریافت اولیه داده‌ها در زمان ورود (Bootstrap / Full Snapshot)**
2. **دریافت دوره‌ای تغییرات سرور به صورت تفاضلی (Delta Pull / Incremental Sync)**
3. **ادغام ایمن با داده‌های محلی و تغییرات معلق صف آفلاین (Offline-aware Merge)**
4. **اعمال مرزهای امنیتی و دسترسی نقش‌ها (Role-based Scope & Projection)**

## ۲. مشخصات قرارداد API

### نقطه پایانی (Endpoint):
`GET /api/v1/pull`

### پارامترهای پرس‌وجو (Query Parameters):
| پارامتر | نوع | اجباری | توضیحات |
| :--- | :---: | :---: | :--- |
| `since` | رشته (ISO) یا عدد | خیر | مُهر زمان آخرین دریافت کلاینت. در صورت خالی بودن، اسنپ‌شات کامل ارسال می‌شود. |
| `collections` | رشته | خیر | فهرست نام کالکشن‌ها با کاما (مثلاً `grades,attendance,classes`). در صورت عدم ارسال، همه مجموعه‌های مجاز واکشی می‌شوند. |
| `school_id` | عدد | خیر | شناسه مدرسه (صرفاً برای سوپرادمین و ادارات کل؛ برای سایر نقش‌ها از نشست استخراج می‌شود). |

### پاسخ سرور (Response Format):
```json
{
  "ok": true,
  "server_time": "2026-09-08T12:00:00.000Z",
  "since": "2026-09-08T10:00:00.000Z",
  "full_snapshot": false,
  "server_version": 142,
  "collections": {
    "classes": [
      { "id": 1, "school_id": 1, "name": "کلاس ۱۰۱", "grade": 10, "version": 2, "updated_at": "2026-09-08T11:30:00.000Z" }
    ],
    "grades": [
      { "id": 501, "school_id": 1, "student_id": 101, "subject_id": 2, "score": 19, "version": 3, "updated_at": "2026-09-08T11:45:00.000Z" }
    ]
  },
  "deleted": [
    { "c": "grades", "id": 490, "at": "2026-09-08T11:20:00.000Z" }
  ]
}
```

## ۳. مدل دسترسی و محدوده داده‌ها (Scope & Security Policy)

سرور در زمان پاسخ به `GET /api/v1/pull` قواعد امنیتی زیر را به ازای نقش اعمال می‌کند:

1. **مدیر مدرسه (`manager`):**
   - دسترسی کامل به تمامی مجموعه‌های مدرسه خودش (`school_id`).
   - عدم دسترسی به داده‌های سایر مدارس.

2. **معلم (`teacher`):**
   - دسترسی به برنامه درسی خودش (`schedule`).
   - دسترسی به کلاس‌های تحت تدریس یا سرپرستی.
   - دسترسی به رکوردهای حضور و غیاب و نمرات کلاس‌های خودش.
   - اطلاعیه‌ها، تقویم و اعلانات مربوط به مدرسه.

3. **دانش‌آموز و اولیا (`student` / `parent`):**
   - دسترسی دقیق و محدود به رکوردهای ثبت‌نامی و کارنامه فردی (`student_id`).
   - عدم مشاهده نمرات، یادداشت‌ها و موارد انضباطی سایر دانش‌آموزان.

4. **سوپرادمین (`superadmin`):**
   - دسترسی نامحدود به سراسر مدارس و مجموعه‌ها.

## ۴. سازوکار نسخه‌گذاری و ردیابی حذفیات در سرور

1. **افزایش نسخه در هر نوشتن (`version`):**
   - هر عملیات درج (`ins`) رکورد را با `version: 1` و `updated_at: nowIso` ذخیره می‌کند.
   - هر عملیات ویرایش (`upd`) نسخه را به `version + 1` افزایش داده و `updated_at` را به‌روز می‌نماید.
2. **ثبت لاگ حذفیات (`__deleted_records` / Tombstones):**
   - هنگام حذف یک رکورد (`del`)، ورودی `{ c, id, school_id, at }` در بافر حذفیات سرور ثبت می‌شود تا کلاینت‌های دارای `since` از حذف رکورد مطلع شوند و آن را از دیتابیس محلی پاک کنند.

## ۵. سازوکار ادغام کلاینت (Client Merge Engine)

ماژول کلاینت `src/js/29-pull.js` مراحل زیر را طی می‌کند:

1. **بررسی وضعیت آنلاین/آفلاین:** در صورت قطع شبکه، فرآیند بدون شکستن برنامه به داده‌های محلی رجوع می‌کند.
2. **دریافت دلتا:** ارسال آخرین `last_pull_time` ذخیره‌شده در متادیتای `offlineStorage`.
3. **ادغام هوشمند با صف محلی:**
   - اگر رکوردی در صف آفلاین کلاینت (`sync_queue`) دارای عملیات معلق (`pending`) باشد، دلتای سرور روی آن رکورد رونویسی نمی‌شود تا از بین رفتن تغییرات محلی جلوگیری شود.
   - رکوردهای جدید و ویرایش‌شده سرور در `db[c]` و `offlineStorage` ثبت می‌شوند.
   - رکوردهای موجود در بخش `deleted` از `db[c]` و `offlineStorage` حذف می‌گردند.
4. **به‌روزرسانی پرچم مهاجرت:** ثبت پرچم `payesh_pull_migrated = 'true'`.

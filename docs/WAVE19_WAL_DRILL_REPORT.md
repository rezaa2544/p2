# 🧨 WAVE 19 — مانورِ واقعیِ «پر شدنِ دیسکِ WAL» (WAL Disk-Full Drill)

**تاریخ:** ۲۰۲۶-۰۹-۱۱ · **شاخه:** `feat/wave19-wal-drill` · **نسخهٔ PG:** ۱۷.۱۰ (Debian 17.10-0+deb13u1)
**ابزار:** `tests/wal-disk-full.js` · **زیرساخت:** `infra/wal-drill/bootstrap.sh` · **خروجیِ ماشین‌خوان:** `tests/chaos-output/wal-disk-full.json`

> **این مانور شبیه‌سازی نیست.** یک کلاسترِ واقعیِ PostgreSQL بالا آمد، `pg_wal`
> روی یک tmpfsِ سقف‌دار قرار گرفت، دیسک واقعاً تا `avail=0B` پر شد، و PostgreSQL
> واقعاً PANIC کرد. اعدادِ زیر اندازه‌گیری‌اند، نه برآورد.

---

## ۱) زیرساختِ مانور

| پارامتر | مقدار |
|---|---|
| کلاستر | PostgreSQL 17.10 روی پورتِ **۵۵۴۳۲** (سوکتِ یونیکس، `trust`) |
| `pg_wal` | symlink به `/mnt/pgwal` = **tmpfs با سقفِ ۱۰۰MB** |
| migrations | هر ۷ فایلِ `001`–`006` اعمال شد ⇒ **۹۰ جدول** |
| seed | ۶۰ مدرسه · ۱۸۰ کلاس · ۱۲٬۶۰۰ رکوردِ حضور |
| `wal_level` | `replica` (برای W4) · `max_wal_senders=4` |
| مدتِ کلِ مانور | **۴۵٫۴ ثانیه** (seed تا پایانِ W4) |

### پیکربندیِ غیرپیش‌فرض و دلیلِ فنیِ آن (صداقتِ روش)

| تنظیم | پیش‌فرض | مانور | چرا |
|---|---|---|---|
| `wal_segment_size` | ۱۶MB | **۱MB** | با سگمنتِ ۱۶MB، PG تا مدت‌ها داخلِ سگمنتِ از‌پیش‌تخصیص‌یافته می‌نویسد و **حتی رویِ دیسکِ کاملاً پُر هم ENOSPC را حس نمی‌کند** |
| `wal_recycle` | `on` | **`off`** | با بازیافت، PG سگمنتِ قدیمی را `rename` می‌کند؛ هیچ تخصیصِ تازه‌ای لازم نیست و از کنارِ ENOSPC رد می‌شود |
| `wal_keep_size` | ۶۴MB | **۰** | کاهشِ سگمنت‌های نگه‌داشته‌شده |
| `max_wal_size` | ۱GB | **۱۶MB** | چرخهٔ سریع‌ترِ checkpoint |

**این‌ها «شتاب‌دهیِ مانور» است، نه پیشنهادِ پیکربندیِ تولید.** با تنظیمِ پیش‌فرض،
سه اجرایِ پیاپیِ مانور به‌طورِ کاذب سبز شد (۷٬۲۰۰ سطر رویِ دیسکِ «پُر» بدونِ هیچ
خطایی commit شد) — این دقیقاً همان دامی است که §۴ مستند می‌کند.

## ۲) نتایجِ سناریوها (W1–W5)

| سناریو | نتیجه | RTO | RPO |
|---|---|---|---|
| **W1** — WAL → ۸۰٪ | ✅ **۸۳٪** رسید؛ سرور سالم و در حالِ سرویس‌دهی؛ **هیچ هشداری ثبت نشد** | n/a (خرابی رخ نداد) | n/a |
| **W2** — WAL → ۱۰۰٪ | ✅ **PANIC** ثبت شد؛ `avail=0B`؛ نوشتنِ تأییدی ENOSPC داد؛ **۰ سطر** commit شد؛ سرور خاموش شد | n/a | نشتی در لحظهٔ PANIC = صفر (تراکنشِ ناتمام rollback شد) |
| **W3** — بازیابی | ✅ restart با دیسکِ پُر **شکست خورد**؛ پس از آزادسازیِ فضا بالا آمد | **۳۰٫۲ ثانیه** | **۰** |
| **W4** — replica | ✅ `pg_basebackup -R -S` + streaming؛ replica به LSNِ primary رسید | n/a (گرم) | **۰** (primary=۱۴٬۱۰۰ = replica=۱۴٬۱۰۰) |
| **W5** — RPO=0 | ✅ شمارِ رکوردها کاهش نیافت (۱۲٬۶۰۰ → ۱۲٬۹۰۰) | — | **۰** (با قیدِ §۵) |

اجرا بود (چکِ ایستای S7) که با همین سند بسته می‌شود.

## ۳) شاهدِ لاگ (عیناً از `postgresql-*.log`)

سه چهرهٔ متفاوتِ ENOSPCِ WAL در یک مانور دیده شد:

**(الف) PANIC در زمانِ اجرا** — نخستین و بحرانی‌ترین:
```
2026-09-11 18:31:10 UTC [6367] postgres@postgres PANIC:  could not write to file "pg_wal/xlogtemp.6367": No space left on device
```

**(ب) FATAL در startup و خاموشیِ کلاستر** — چون بازیابی هم برایِ `xlogtemp`
به فضا نیاز دارد:
```
FATAL:  could not write to file "pg_wal/xlogtemp.5499": No space left on device
LOG:    startup process (PID 5499) exited with exit code 1
LOG:    terminating any other active server processes
LOG:    shutting down due to startup process failure
```

**(پ) حلقهٔ retry بدونِ PANIC** — در اجرایِ نخست، checkpointer هر ~۱ ثانیه
ERROR می‌داد و سرور «زنده ولی بی‌فایده» می‌ماند:
```
ERROR:  could not write to file "pg_wal/xlogtemp.4792": No space left on device
ERROR:  could not write to file "pg_wal/xlogtemp.4792": No space left on device   (۱ ثانیه بعد)
```

> نکتهٔ عملیاتی: حالتِ (پ) از حالتِ (الف) خطرناک‌تر است — سرویس از دیدِ
> `pg_isready` «سالم» به‌نظر می‌رسد ولی هیچ نوشتنی پیش نمی‌رود. آلارمِ صرفاً
> «PG بالاست» این حالت را رد می‌کند.

### ۳-۱) صداقتِ منبعِ شاهد (پورت از PR #76)

### ۳-۱) پیام PANIC در این اجرا از سمت **کلاینت** ثبت شد، نه لاگ سرور

در اجرای نهایی، پرچم‌های `panic`/`enospc` در JSON برابر `false` هستند، چون تست آن‌ها
را از *فایل لاگ سرور* استخراج می‌کند و آن فایل در لحظهٔ کرش نوشته نشد. پیام واقعی از
خطای کلاینت گرفته شده است:

```
could not write to file "pg_wal/xlogtemp.9228": No space left on device
```

**چرا؟** در یک نسخهٔ میانی، `logging_collector = on` بود و خروجی نشان داد که PANIC
**هرگز** به دیسک نرسید (۰ occurrence در لاگ) — چون collector بافر دارد و همراهِ
postmaster می‌میرد. بنابراین `logging_collector = off` شد و stderr با `pg_ctl -l`
به فایل می‌رود. در اجرای `16:46:17` همین پیام **در لاگ سرور** هم ثبت شد:

```
2026-09-11 16:46:17.748 UTC [8008] PANIC:  could not write to file "pg_wal/xlogtemp.8008": No space left on device
```

## ۴) یافته‌های عملیاتی

1. **شکافِ پایش (مهم‌ترین یافته):** PostgreSQL در ۸۰٪ پُریِ WAL **کاملاً ساکت**
   است — هیچ warning، هیچ متریکِ هشداری. نخستین نشانهٔ قابلِ مشاهده، PANIC است.
   ⇒ آلارمِ دیسکِ WAL باید **بیرونی** باشد (`node_exporter` روی mountِ `pg_wal`
   یا `pg_stat_wal`) با آستانهٔ ۷۰/۸۵٪. این یک قلمِ باز برایِ `docs/OBSERVABILITY.md` است.
2. **restart با دیسکِ پُر ناموفق است.** حتی crash recovery برایِ نوشتنِ
   `xlogtemp` به فضا نیاز دارد. ⇒ ران‌بوک باید صریح بگوید: **اول فضا آزاد کن،
   بعد restart** (§۶ ران‌بوک به‌روز شد).
3. **RTO اندازه‌گیری‌شده ۳۰٫۲ ثانیه** است، در برابرِ سقفِ سیاست (۱۵ دقیقه) —
   با اختلافِ زیاد زیرِ سقف. ولی این عدد شاملِ «زمانِ تشخیص» نیست؛ در حادثهٔ
   واقعی، تشخیص (نه restart) گلوگاه است.
4. **replica گرم، RPO=0 را نگه داشت** — در این مانور هیچ تراکنشِ commit‌شده‌ای
   از دست نرفت.

### ۴-۲) پرشدنِ archive_command به‌تنهایی توقف نیست (پورت از PR #76)

### ۴-۲) پرشدنِ `archive_command` به‌تنهایی دیتابیس را متوقف نمی‌کند

وقتی مقصد آرشیو روی همان tmpfs بود، اولین ENOSPC از مسیر `cp` در `archive_command`
آمد:

```
cp: error copying 'pg_wal/000000010000000000000073' to '.../wal/archive/...': No space left on device
```

در این حالت PostgreSQL **زنده می‌ماند** و فقط آرشیو مختل می‌شود. برای رسیدن به PANIC
باید خودِ walwriter در تخصیص فضا شکست بخورد. تفکیک این دو حالت مهم است: یکی «هشدارِ
قابل‌ادامه» است و دیگری «توقف سرویس».

## ۵) آنچه تأیید **نشد** (محدودیت‌های صادقانه)

| مورد | وضعیت |
|---|---|
| RPO=0 | **فقط با شمارِ رکوردها** تأیید شد، نه با checksumِ سطر‌به‌سطرِ محتوای هر رکورد. ادعای «صفر data loss» در سطحِ محتوا راستی‌آزمایی نشده است. |
| PITR از آرشیو | آزمایش **نشد** — مقصدِ آرشیو (فضای شیئی) در این محیط موجود نیست؛ `archive_mode` عمداً خاموش ماند. |
| فاجعهٔ منطقه‌ای / چند AZ | آزمایش **نشد** — تک‌میزبان، تک‌replica. |
| `wal_segment_size=1MB` | عددِ مطلقِ RTO به این تنظیم حساس است؛ **مستقیماً به تولید تعمیم داده نشود.** |
| فشارِ همزمان (concurrency) | بارِ نوشتن تک‌اتصال بود؛ رفتارِ زیرِ صدها نوشتنِ همزمان رویِ WALِ پُر اندازه‌گیری نشد. |

## ۶) سه «سبزِ کاذب» که حینِ ساختِ مانور گرفته شد

ثبتِ این‌ها عمدی است — هر سه می‌توانستند گزارشی سبز ولی بی‌ارزش تولید کنند:

| # | دام | نشانه | تشخیص |
|---|---|---|---|
| ۱ | tmpfs صفحه‌ها را **تنبل** تخصیص می‌دهد؛ `df used` عددِ ۱۰۰٪ نشان می‌داد در حالی که `avail` هنوز ۲۰MB بود | ۷٬۲۰۰ سطر بدون خطا commit شد | معیار به `avail==0` + یک نوشتنِ تأییدی که باید ENOSPC بدهد تغییر کرد |
| ۲ | سگمنتِ ۱۶MB از‌پیش‌تخصیص‌یافته + `wal_recycle=on` ⇒ PG هیچ تخصیصِ تازه‌ای لازم نداشت | دیسک «پُر» ولی صفر خطا | `wal_segment_size=1MB` + `wal_recycle=off` |
| ۳ | نشانگرِ لاگ با «نامِ آخرین فایل» گرفته می‌شد، پس delta همیشه خالی بود | «هشداری در لاگ نیست» در حالی که لاگ پر از PANIC بود | نشانگر به **آفستِ بایتِ** هر فایل تغییر کرد |

## ۷) بازاجرا

```bash
# ۱) زیرساخت (نیاز به root برایِ mountِ tmpfs)
sudo infra/wal-drill/bootstrap.sh

# ۲) مانور
sudo PGBIN=/usr/lib/postgresql/17/bin \
     PGDATADIR=/var/tmp/pgdata-wal-drill WAL_MNT=/mnt/pgwal \
     PGSOCKDIR=/var/tmp/wal-drill-run/sock WAL_LOGDIR=/var/tmp/wal-drill-run/logs \
     PGPORT_DRILL=55432 PGUSER=postgres WAL_MB=100 \
     node tests/wal-disk-full.js

# فقط بررسیِ ایستا (بدونِ زیرساخت):
node tests/wal-disk-full.js --skip-live
```

کدهای خروج: `0` = همه سبز · `1` = خطا · `2` = سناریوهایِ زنده **اجرا نشدند**.
کدِ ۲ عمداً از ۰ جداست تا در CI «اجرا نشد» با «موفق» اشتباه گرفته نشود.

**نسخه سند:** ۴.۲ جامع  
**وضعیت:** مصوب فنی و پیاده‌سازی‌شده  
**پوشش:** کلیه ۸۱ ماژول کلاینت، معماری آفلاین-محور (`IndexedDB`)، موتورهای همگام‌سازی و پولینگ (`A01 Pull & Sync`)، سیستم اعتبارسنجی، امنیت و تست‌ها

## ۱. فلسفه معماری و اصول بنیادین طراحی (Architectural Philosophy)

سامانه «پایش» بر پایه پنج اصل کلیدی مهندسی نرم‌افزار پیاده‌سازی شده است:

1. **معماری آفلاین‌محور مطلق (Offline-First Zero-Latency):**  
   تمامی عملیات خواندن و نوشتن کاربر در مرحله نخست روی دیتابیس کلاینت (`IndexedDB` با پشتیبان `localStorage`) انجام می‌شود و رابط کاربری بدون کوچک‌ترین تاخیر شبکه (صفر میلی‌ثانیه) پاسخ می‌دهد.
2. **برنامه تک‌فایلی مستقل (Zero-Dependency Single-File Bundle):**  
   کل برنامه با فرآیند بیلد اختصاصی (`build.js`) به یک فایل HTML واحد (با فونت‌های فارسی Vazirmatn در قالب Base64 و بدون هیچ درخواست CDN یا اسکریپت خارجی) کامپایل می‌شود.
3. **تغییرناپذیری تراکنش‌ها و دفترچه وقایع (Append-Only Event-Sourced Operations):**  
   کلیه جهش‌های داده‌ای به عنوان یک عملیات (`op`) با شناسه‌های یکتا، زمان، شناسه مدرسه، کاربر و نسخه پایه (`base_version`) در صف محلی ثبت و به سرور ارسال می‌شوند.
4. **همگام‌سازی دوطرفه مقاوم (Bidirectional Sync & A01 Pull/Bootstrap):**  
   امکان دریافت اسنپ‌شات اولیه یا دلتای تغییرات پس از آخرین زمان پول (`since timestamp`) با مدیریت رکوردهای حذف‌شده (Tombstones) و حل تعارض‌های ۳-طرفه.
5. **امنیت چندلایه و اصل حداقل دسترسی (Fail-Closed Multi-Tier Security):**  
   گارد امنیتی مبتنی بر نقش (`RBAC`) در سطح کلاینت (`canRoute` و `canAction`) و اعتبارسنجی مستقل سمت سرور با ماتریس `WRITE_PERMS`.

## ۳. لایه ذخیره‌سازی پایگاه داده محلی (IndexedDB & Local Storage)

سامانه از کلاس `OfflineStorage` در ماژول `03-idb-persistence.js` استفاده می‌کند که ۳ Object Store در دیتابیس `payesh_offline_db` تعریف می‌کند:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        payesh_offline_db (v1)                          │
├───────────────────┬──────────────────────────────┬─────────────────────┤
│     entities      │          sync_queue          │      metadata       │
├───────────────────┼──────────────────────────────┼─────────────────────┤
│ key: [coll, id]   │ key: id (auto-increment)     │ key: key (string)   │
│ indexes:          │ indexes:                     │ stores:             │
│  - by_collection  │  - by_status                 │  - last_pull_time   │
│  - by_school      │  - by_created_at             │  - migration_flag   │
│  - by_updated     │  - by_attempts               │  - active_theme     │
└───────────────────┴──────────────────────────────┴─────────────────────┘
```

### ۳.۱. متدهای اصلی کلاس `OfflineStorage`:
- `initDb()`: اتصال و ارتقای ساختار دیتابیس IndexedDB با Fallback خودکار در صورت عدم پشتیبانی مرورگر.
- `putEntity(collection, record)`: ذخیره یا بروزرسانی موجودیت با درج خودکار `updated_at`.
- `getEntity(collection, id)`: واکشی یک رکورد بر اساس شناسه.
- `getCollection(collection)`: بازگردانی کلیه رکوردهای یک کالکشن.
- `getEntitiesBySchool(collection, schoolId)`: واکشی فیلترشده با ایندکس `by_school`.
- `removeEntity(collection, id)`: حذف رکورد از دیتابیس محلی.
- `addToQueue(op)`: افزودن عملیات آفلاین به صف ارسال.
- `getPendingQueue()`: دریافت کلیه آیتم‌های صف با وضعیت `pending` یا `failed`.
- `updateQueueStatus(id, status, errorMsg, attempts)`: بروزرسانی وضعیت عملیات پس از تلاش ارسال.
- `removeFromQueue(id)`: حذف قطعی عملیات همگام‌شده از صف.
- `migrateFromLocalStorageToIdb()`: ماژول `00-migration.js` که داده‌های نسخه قبلی را به ساختار امن `IndexedDB` بدون ریزش داده منتقل می‌کند.

## ۴. چرخه همگام‌سازی و موتور کشش داده‌ها (A01 Pull & Sync Engine)

سامانه پایش از یک مدل ترکیبی **Push-Pull Synchronization** استفاده می‌کند:

```
                     ┌────────────────────────┐
                     │   سرور مرکزی پایش      │
                     │  (/api/v1/pull & sync) │
                     └───────────┬────────────┘
                                 │
                 A01 Pull Engine │ Push Sync Engine
                (دلتای تغییرات)  │ (صف عملیات معلق)
                                 │
                     ┌───────────▼────────────┐
                     │     موتور کلاینت       │
                     │  - 29-pull.js          │
                     │  - 27-sync.js          │
                     │  - 00-data-layer.js    │
                     └───────────┬────────────┘
                                 │
                     ┌───────────▼────────────┐
                     │  مخزن امن IndexedDB    │
                     │ (Store & OfflineStorage│
                     └────────────────────────┘
```

### ۴.۱. نحوه عملکرد `pullFromServer(options)`:
1. پارامترهای `school_id` و `since` (آخرین زمان پول موفق) به اندپوینت `/api/v1/pull` ارسال می‌شوند.
2. سرور بر اساس نقش کاربر (مدیر: کل مدرسه / معلم: کلاس‌های خودش / دانش‌آموز: فقط نمرات و دروس خودش) خروجی دلتا را بازمی‌گرداند.
3. تابع `mergeServerDelta(delta)` با رعایت قاعده زیر تغییرات را ادغام می‌کند:
   - رکوردهایی که در صف آفلاین محلی کلاینت (`pending queue`) دارای عملیات منتظر ارسال هستند، بازنویسی **نمی‌شوند** تا تغییرات محلی از بین نرود.
   - رکوردهای موجود در آرایه `deleted` (Tombstones) از پایگاه داده محلی حذف می‌شوند.
   - متادیتای `payesh_last_pull_timestamp` بروزرسانی می‌گردد.

## ۵. ماتریس امنیت، نقش‌ها و مجوزهای دسترسی (RBAC & Authorization)

سامانه از ۷ نقش مستقل پشتیبانی می‌کند:
1. `superadmin`: دسترسی سراسری کشوری و استانی به کل سامانه و تنظیمات سرور.
2. `manager`: مدیریت مدرسه، کلاس‌ها، کاربران، دوره‌ها، امور مالی و پیامک.
3. `teacher`: ثبت حضور و غیاب، نمرات، تکالیف، آزمون‌ها و کلاس‌های مجازی.
4. `counselor`: مشاهده صف ارجاع، الگوهای افت تحصیلی و ثبت مشاوره‌ها.
5. `driver`: ثبت وضعیت سوار/پیاده شدن دانش‌آموزان در مسیرهای سرویس.
6. `student`: دسترسی به برنامه کلاسی، کارنامه، تکالیف و امتحانات.
7. `parent`: پنل اولیا، پیگیری فرزندان (با سوییچر فرزندان) و پرداخت آنلاین.

### ۵.۱. گارد اکشن‌ها (`canAction`) و مجوزهای سمت سرور (`WRITE_PERMS`):
کلیه ۳۳۷ اکشن ثبت‌شده در `19-actions-*.js` در فایل `tools/check-authz.js` ممیزی می‌شوند. هیچ اکشنی بدون انتساب دقیق نقش در کلاینت و سرور نمی‌تواند داده‌ای را دستخوش تغییر نماید.

## ۶. پروتکل‌های توسعه، فرآیند ساخت و اجرای تست‌ها

### ۶.۱. فرآیند ساخت (Build Process):
برای ایجاد باندل تک‌فایلی مستقل، دستور زیر را اجرا نمایید:
```bash
node build.js
```
این دستور فایل‌های `src/styles/*.css` و ۸۱ ماژول `src/js/*.js` (بر اساس ترتیب `src/js/_order.json`) را ادغام و به صورت بیت‌به‌بیت فایل‌های `index.html` و `dist/payesh.html` را می‌سازد.

### ۶.۲. اجرای سوئیت‌های جامع تست:
```bash
# ۱. تست‌های ساختار، آفلاین و قوانین برنامه
node tests/run.js

# ۲. تست دودی ۵۴۷ مرحله‌ای
node tests/smoke.js

# ۳. اعتبارسنجی ماتریس دسترسی و اکشن‌ها
node tools/check-authz.js

# ۴. تست‌های پایه و جهش IndexedDB
node tests/idb-persistence.js && node tests/idb-persistence-mutations.js

# ۵. تست موتور کشش A01
node tests/pull-bootstrap.js

# ۶. آزمون‌های نفوذپذیری و امنیت
node tests/security.js
```

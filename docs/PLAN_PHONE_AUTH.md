## ۱. جریان — همان‌طور که کاربر توصیف کرد

```
۱. کاربر شمارهٔ موبایل می‌دهد
۲. کد پیامکی می‌رود        ← بعداً به پنل پیامکی وصل می‌شود
۳. ⏱️ تایمر یک‌دقیقه‌ای آغاز می‌شود · دکمهٔ «ارسال مجدد» غیرفعال
۴. کاربر کد را وارد می‌کند
۵. 🔴 بار اول: کد ملی ⇒ سامانهٔ شاهکار  ← دروازهٔ ورود
   ├─ تأیید شد   ⇒ احراز هویت سالم ✅ ادامه به مرحلهٔ ۶
   └─ تأیید نشد ⇒ ⛔ **پایان کار.** کاربر وارد نمی‌شود.
                    تنها راه: مراجعهٔ حضوری به مدرسه
۶. نقش دارد؟
   ├─ بله ⇒ نقش‌هایش نمایش داده می‌شود (می‌تواند چند نقش /
   │        چند دانش‌آموز باشد)
   └─ نه  ⇒ «هیچ نقشی برای شما تعریف نشده» + دکمهٔ [پیگیری]
```

### مسیر پیگیری

```
⚠️ **این مسیر فقط برای کاربری است که احراز هویتش تأیید شده**
ولی نقشی برایش تعریف نشده. کسی که شاهکار ردش کرده، اصلاً به
اینجا نمی‌رسد.

[پیگیری] ⇒ «نقش شما چیست؟»
           زیرنویس: «اگر چند نقش دارید، فقط یکی را بزنید»
              │
              ├─ دبیر · دانش‌آموز · ولی   ⇒ به مدیر مدرسه
              └─ مدیر · رئیس اداره        ⇒ به سوپرادمین
              │

              │

      └───────┬────────┘
              │
   فهرست مدارس منطبق ⇒ کشویی + جست‌وجو
              │
   پیام کامل به مدیر (یا سوپرادمین) برای پیگیری
```

## ۲. ✅ تناقض حل شد — مرحلهٔ شاهکار می‌ماند

**تصمیم قطعی کاربر (دور ۵۶):**

> اگر شاهکار تأیید کرد ⇒ **احراز هویت سالم است**
> اگر تأیید نکرد ⇒ **احراز هویت ناقص است** و به کاربر گفته
> می‌شود: «شمارهٔ شما با کد ملی مطابقت ندارد»

پس مرحلهٔ کد ملی و شاهکار **سر جایش می‌ماند** (حالت «ب» که در
نسخهٔ پیشین پیشنهاد شده بود). ابهام دور ۵۳ بسته شد.

### جایگاه دقیق در جریان

```
۱. شماره  →  ۲. کد پیامکی  →  ۳. تأیید کد
                                    ↓
                      🔹 بار اول: کد ملی خواسته می‌شود
                                    ↓
                            سامانهٔ شاهکار
                        ┌───────────┴───────────┐
                     تأیید کرد              تأیید نکرد
                        ↓                        ↓
              احراز هویت سالم ✅        احراز هویت ناقص 🔴
                   وارد می‌شود          «شمارهٔ شما با کد ملی
                                          مطابقت ندارد»
```

### 🔴 احراز هویت پیش از هر چیز دیگر

**ترتیب مطلق است:**

```
احراز هویت  ⇒  اگر تأیید نشد، هیچ‌چیز دیگری رخ نمی‌دهد
```

نه صفحهٔ «نقشی تعریف نشده»، نه مسیر پیگیری، نه دیدن نقش‌ها.
کاربر **اصلاً وارد نمی‌شود**.

### پیام به کاربر

```
┌────────────────────────────────────────────┐
│  ⛔ ورود امکان‌پذیر نیست                     │
│                                            │
│  شمارهٔ موبایل شما با کد ملی واردشده        │
│  مطابقت ندارد.                              │
│                                            │
│  سیم‌کارت باید به نام خودتان ثبت شده باشد.  │
│                                            │
│  ─────────────────────────────────────     │
│  اگر کد ملی شما در سامانهٔ مدرسه هست ولی    │
│  با شمارهٔ دیگری ثبت شده، باید حضوراً به     │
│  مدرسه مراجعه کنید و شمارهٔ جدید خود را     │
│  به مدیر اعلام نمایید.                      │
│                                            │
│           [ تلاش دوباره ]                  │
└────────────────────────────────────────────┘
```

⚠️ **متن عمداً صریح است.** کاربری که سیم‌کارت به نامش نیست باید
دقیقاً بفهمد چرا رد شد و **چه کاری باید بکند** — نه پیام مبهم
«خطایی رخ داد».

⚠️ **نام مالک واقعی گفته نمی‌شود** — نشت اطلاعات است.

### 🔴 تصحیح دور ۵۹ — تنها راه، مراجعهٔ حضوری است

نسخهٔ پیشین این طرح دکمهٔ «ویرایش کد ملی» داشت. **حذف شد.**

**چرا؟** اگر کاربر بتواند کد ملی را عوض کند و دوباره بیازماید،
دقیقاً همان حمله‌ای رخ می‌دهد که می‌خواستیم جلویش را بگیریم:
کسی با سیم‌کارت خودش، کد ملی‌های مختلف را آزمون می‌کند تا
ببیند کدام «تطابق دارد».

**سناریوی واقعی که کاربر مطرح کرد:**

> شخصی کد ملی‌اش در سامانه هست، ولی با شماره‌ای که به نام خودش
> نیست می‌خواهد وارد شود.

| راه | چرا رد شد |
|---|---|
| ورود مشروط | 🔴 هویت تأیید نشده — دادهٔ کودکان است |
| تأیید مدیر از راه دور | 🔴 مدیر نمی‌تواند مالکیت سیم‌کارت را بسنجد |
| پرسش امنیتی جایگزین | 🔴 ضعیف‌تر از شاهکار — قابل حدس |
| **مراجعهٔ حضوری** | ✅ **تنها راه امن** |

🔴 **تصمیم قطعی: هیچ راه نرم‌افزاری وجود ندارد.** شخص باید
حضوراً به مدرسه برود، شماره‌ای که **واقعاً به نام خودش است**
اعلام کند، مدیر آن را در سامانه ثبت کند، و سپس شاهکار تأییدش
کند.

⚠️ **این محدودیت عمدی است، نه نقص.** هر راه دیگری یعنی کسی
می‌تواند با سیم‌کارت شخص دیگری به پروندهٔ تحصیلی کودکان دسترسی
پیدا کند.

### آنچه پس از عدم تطابق **نمی‌شود**

| ❌ نمی‌شود | چرا |
|---|---|
| ورود با پرچم «تأییدنشده» | تصمیم دور ۵۲: کاربر غیرقانونی است |
| اعلان به مدیر مدرسه | به مدیر ربطی ندارد؛ مسئلهٔ کاربر و اپراتور است |
| ذخیرهٔ کد ملی ردشده | دادهٔ شخصی بی‌استفاده نگه داشته نمی‌شود |
| شمارش نامحدود تلاش | سقف ۳ بار (بخش ۴.۷) وگرنه می‌شود کد ملی‌ها را آزمود |

🔴 **سقف تلاش کد ملی مهم است:** بدون آن، مهاجم می‌تواند با یک
شمارهٔ معتبر، کد ملی‌های مختلف را آزمون کند تا مالک واقعی را
بیابد. **۳ تلاش، سپس قفل ۲۴ ساعته برای آن شماره.**

## ۲.۵ چرخهٔ اصلاح شماره — کار مدیر

وقتی کاربر حضوراً به مدرسه می‌رود، مدیر باید بتواند شماره را
عوض کند. این چرخه باید کامل باشد وگرنه بن‌بست می‌شود.

```
کاربر حضوراً می‌رود  →  مدیر شمارهٔ جدید را ثبت می‌کند
                              ↓
                     کاربر دوباره تلاش می‌کند
                              ↓
                        شاهکار تأیید می‌کند ✅
                              ↓
                          وارد می‌شود
```

### آنچه در سامانه لازم است

🟢 **ویرایش کاربر از قبل هست** — مدیر در صفحهٔ کاربران می‌تواند
شمارهٔ تلفن را عوض کند (کنش `user-save`).

🔴 **ولی سه چیز کم است:**

**۱. هشدار هنگام تغییر شماره.** مدیر باید بداند که شمارهٔ جدید
هم باید **به نام همان شخص** باشد، وگرنه کاربر باز هم نمی‌تواند
وارد شود.

```
⚠️ شمارهٔ جدید باید به نام خودِ این شخص ثبت شده باشد.
   در غیر این صورت، سامانهٔ شاهکار ورود او را رد می‌کند.
```

**۲. آزمون پیشاپیش (اختیاری ولی ارزشمند).** دکمه‌ای کنار میدان
تلفن که همان‌جا از شاهکار بپرسد «آیا این شماره با کد ملی این
شخص می‌خواند؟» — پیش از اینکه کاربر به خانه برود و بفهمد باز
هم رد شد.

⚠️ **هزینه دارد** (هر استعلام پولی است)، ولی از رفت‌وآمد دوبارهٔ
کاربر ارزان‌تر است.

**۳. باز شدن قفل ۲۴ ساعته.** اگر کاربر سه بار تلاش کرده و قفل
شده، تغییر شماره توسط مدیر باید قفل را **بردارد** — وگرنه باید
یک شبانه‌روز صبر کند.

### 🔴 دام: کد ملی نباید توسط مدیر عوض شود

مدیر می‌تواند **شماره** را عوض کند، ولی 🔴 **کد ملی نه** —
دست‌کم نه بدون سند.

**چرا؟** اگر مدیر بتواند کد ملی را آزادانه عوض کند، می‌تواند کد
ملی خودش را روی حساب دیگری بگذارد و وارد شود. کد ملی **کلید
هویت** است، نه یک میدان معمولی.

⚠️ **پیشنهاد:** تغییر کد ملی توسط مدیر ثبت شود در سابقهٔ
تغییرات و به مدیر کل سامانه اعلان برود.

## ۴.۵ ماندگاری نشست — 🟢 از قبل کار می‌کند

**خواستهٔ کاربر (دور ۵۲):** «بعد از احراز هویت دیگر خارج نشود
مگر خودش دکمهٔ خروج را بزند.»

سنجش کد نشان داد **از پیش پیاده است**:

```js
Store.set(SESSION_KEY, u.username);   // 19-actions.js:39 — ورود
Store.remove(SESSION_KEY);            // 19-actions.js:42 — فقط logout
const su = Store.get(SESSION_KEY);    // 24-edu-office.js:788 — بوت
```

`localStorage` انقضا ندارد و با بستن مرورگر نمی‌پرد. **کار تازه‌ای
لازم نیست**، فقط کلید جدا برای احراز هویت:

`AUTH_KEY = 'sms_auth_v1'` ⇒ `{phone, nid, verified_at}`

⚠️ **جدا از `SESSION_KEY`:** اگر کاربر خروج بزند، نشست پاک
می‌شود ولی **احراز هویت** می‌ماند — بار بعد فقط کد پیامکی، نه
کد ملی دوباره.

🔴 **در تولید:** نشست باید انقضا داشته باشد
(`Max-Age=28800` طبق قرارداد سرور). «هرگز خارج نشدن» فقط برای
دموی بدون سرور قابل قبول است.

## ۴.۷ ⏱️ تایمر و ارسال مجدد کد

### رفتار

```
┌────────────────────────────────────────┐
│  کد پیامک‌شده را وارد کنید              │
│  ارسال‌شده به ۰۹۱۲***۴۵۶۷              │
│                                        │
│      [ _ _ _ _ _ _ ]                   │
│                                        │
│  ⏱️ ۰۰:۴۷ تا امکان ارسال مجدد           │
│  ─────────────  (پس از پایان)          │
│  [ ارسال مجدد کد ]   [ تغییر شماره ]   │
└────────────────────────────────────────┘
```

**دو تایمر جدا** — و این تمایز مهم است:

| تایمر | مدت | کارش |
|---|---|---|
| **ارسال مجدد** | ۶۰ ثانیه | تا پایانش دکمهٔ «ارسال مجدد» خاموش است |
| **اعتبار کد** | ۳ دقیقه | پس از آن کد باطل می‌شود حتی اگر درست باشد |

⚠️ **چرا اعتبار کد بلندتر از تایمر ارسال مجدد است؟** اگر هر دو
۶۰ ثانیه باشند، کاربری که پیامکش با تأخیر می‌رسد کدِ باطل وارد
می‌کند و گیج می‌شود. سه دقیقه فرصت معقولی است.

### 🔴 دام: `render()` تایمر را می‌کشد

`render()` کل `#root` را با `innerHTML` بازمی‌سازد
(`24-edu-office.js:760`). هر `setInterval` که به عنصر DOM وابسته
باشد، با نخستین رندر مرجعش را از دست می‌دهد و به عنصر مرده
می‌نویسد.

**راه‌حل: زمان پایان در `Store` نگه داشته شود، نه در تایمر.**

```js
/* ✅ درست — مقاوم در برابر رندر و بستن مرورگر */
Store.setJSON(OTP_KEY, { phone, code, sentAt, resendAt, expiresAt });
/* هر رندر از روی اختلاف زمان دوباره می‌سازد */
var left = Math.max(0, Math.ceil((otp.resendAt - Date.now()) / 1000));

/* ❌ غلط — با رندر می‌پرد */
let sec = 60;
setInterval(() => { sec--; el.textContent = sec; }, 1000);
```

⚠️ **مزیت جانبی:** اگر کاربر صفحه را ببندد و برگردد، تایمر از
جایی که بود ادامه می‌دهد — نه از صفر. یعنی نمی‌شود با
بارگذاری دوباره محدودیت را دور زد.

⚠️ **یک `setInterval` سبک لازم است** فقط برای به‌روزرسانی عدد
روی صفحه (هر ثانیه). ولی **منبع حقیقت `Store` است** نه شمارنده.
هنگام ترک صفحهٔ ورود باید `clearInterval` شود وگرنه نشت حافظه
می‌دهد.

### محدودسازی نرخ — سه لایه

| قاعده | مقدار | چرا |
|---|---|---|
| فاصلهٔ دو ارسال | ۶۰ ثانیه | جلوی اسپم پیامکی |
| سقف ارسال | ۳ بار در ۱۰ دقیقه | جلوی هزینهٔ پیامک |
| سقف تلاش کد غلط | ۵ بار | جلوی حدس زدن ۶ رقم |
| 🔴 سقف تلاش کد ملی | ۳ بار سپس قفل ۲۴ ساعته | جلوی آزمون کد ملی‌های مختلف با یک شماره |

🔴 **پس از ۵ تلاش غلط، کد باطل می‌شود** و کاربر باید از نو
شروع کند. بدون این، ۱۰۰۰٬۰۰۰ حالت با تلاش پیاپی شکستنی است.

⚠️ **در دمو هم اعمال شود.** اگر عادت درست از حالا جا نیفتد، روز
تولید یادمان می‌رود. ولی 🔴 **این محدودیت محلی دور زدنی است**
(پاک‌کردن `localStorage`) — روز سرور باید سمت سرور برود.

### هزینه

هر «ارسال مجدد» یک پیامک واقعی است. با سقف ۳ بار، بدترین حالت
برای هر کاربر ۳ پیامک است. برای مدرسهٔ ۵۰۰ نفره با اولیا (~۱۰۰۰
کاربر) در بدترین حالت ۳۰۰۰ پیامک — که با کیف اعتبار موجود
(`sms_wallet`) باید سنجیده شود.

⚠️ **پیشنهاد:** کد تأیید از کیف اعتبار **مدرسه** کم نشود.
احراز هویت هزینهٔ سامانه است نه مدرسه. جدول جدا یا شمارندهٔ
سراسری لازم است.

```
│                                     │
│  اگر باید در سامانه حسابی داشته      │
│  باشید، پیگیری کنید.                 │
│                                     │
│           [ پیگیری ]                │
└─────────────────────────────────────┘
```

**پس از زدن «پیگیری»:**

```
نقش شما چیست؟
اگر چند نقش دارید، فقط کافی است یکی را بزنید.

  [ دبیر ]  [ دانش‌آموز ]  [ ولی ]
  [ مدیر مدرسه ]  [ رئیس اداره ]
```

### فرم بر پایهٔ نقش

| میدان | ولی / دانش‌آموز | دبیر | مدیر / رئیس اداره |
|---|---|---|---|
| استان · شهرستان · منطقه | ✅ | ✅ | ✅ |
| مقطع تحصیلی | ✅ | ❌ | ❌ |
| پایه | ✅ | ❌ | ❌ |
| جنسیت | ✅ | ❌ | ❌ |
| نام دانش‌آموز | ✅ **الزامی** | ❌ | ❌ |
| فهرست مدارس | ✅ فیلترشده | ✅ همهٔ منطقه | ✅ |
| زیرنویس ویژه | — | «اگر در چند مدرسه درس می‌دهید، یکی کافی است» | — |

**فهرست مدارس:** کشویی + جعبهٔ جست‌وجو. با هر تغییر فیلتر،
فهرست خودکار به‌روز می‌شود.

⚠️ **چرا نام دانش‌آموز برای ولی الزامی است؟** شما نوشتید «بگه
اسم دانش‌آموزش چیه و همه‌چیزش برای مدیر شفاف باشه». بدون آن مدیر
نمی‌داند دنبال چه کسی بگردد.

## ۶. 🔴 شمارهٔ اشتباه در مدرسهٔ دیگر — سناریوی ویژه

**خواستهٔ صریح شما:** «امکان دارد یک شماره اشتباهی در مدرسهٔ
دیگری ثبت شده باشد. باید بگردی پیدا کنی در کدام مدرسه ثبت شده و
به مدیر اطلاع بدهی تا اصلاح کند.»

### چه وقت رخ می‌دهد؟

```
کد ملی کاربر در پایگاه داده نیست
   ولی شمارهٔ موبایلش روی کاربر دیگری ثبت است
        ⇓
یعنی مدرسه‌ای این شماره را برای شخص اشتباهی وارد کرده
```

### رفتار پیشنهادی

**به کاربر:**
> این شماره در سامانه برای شخص دیگری ثبت شده است. موضوع به
> مدرسهٔ مربوطه اطلاع داده شد تا بررسی کند.

🔴 **نام آن شخص به کاربر گفته نمی‌شود** — نشت اطلاعات است.

**به مدیرِ آن مدرسه:**
> ⚠️ شمارهٔ `0912***4567` برای «علی رضایی» (دانش‌آموز، کلاس دهم
> تجربی) ثبت شده، ولی شخص دیگری با کد ملی `007***1234` با همین
> شماره تلاش کرد وارد شود. لطفاً بررسی کنید شمارهٔ ثبت‌شده درست
> است یا نه.

⚠️ **این حالت با «نقشی تعریف نشده» فرق دارد** و باید جدا مدیریت
شود — چون یک **خطای دادهٔ موجود** را نشان می‌دهد، نه نبودِ
حساب.

⚠️ **اگر شماره در چند مدرسه ثبت شده باشد**، به **همهٔ** مدیرانش
اطلاع می‌رود.

## ۷. پنل رسیدگی — دو صف جدا

**خواستهٔ شما:** «در پنل‌ها هم باید همچین قابلیتی برای رسیدگی
باشد.»

| نقشِ درخواست‌شده | صف | صفحهٔ تازه |
|---|---|---|
| دبیر · دانش‌آموز · ولی | مدیر مدرسه | `idreq` در منوی مدیر |
| مدیر · رئیس اداره | سوپرادمین | `idreq` در منوی سوپرادمین |

**در هر ردیف:** شماره (ماسک‌شده) · کد ملی · نقش ادعایی · مدرسه ·
نام دانش‌آموز (اگر ولی) · تاریخ · وضعیت

**کنش‌ها:** ✅ ایجاد/تصحیح حساب · ❌ رد با دلیل · ⏸️ در دست بررسی

🟢 **پس از تصحیح مدیر:** کاربر با همان شماره وارد می‌شود و پنل
خودکار بالا می‌آید — چون `SESSION_KEY` می‌ماند و نقش تازه در
`panelsOf()` دیده می‌شود. **کار اضافه‌ای لازم نیست.**

## ۸. مدل داده

```js
/* جدول تازه: identity_requests */
{
  id, phone, national_id,
  claimed_role,          // 'teacher'|'student'|'parent'|'manager'|'edu_office'
  province_id, county_id, district_id,
  level, grade, gender,  // فقط برای ولی/دانش‌آموز
  student_name,          // فقط برای ولی
  school_id,             // مدرسهٔ انتخابی
  routed_to,             // 'manager'|'superadmin'
  status,                // 'pending'|'in-review'|'approved'|'rejected'
  created_at, decided_at, decided_by, note
}

/* جدول تازه: phone_conflicts — سناریوی بخش ۶ */
{
  id, phone, claimed_nid,
  existing_user_id, school_id,
  status,                // 'open'|'resolved'
  created_at, resolved_at, resolved_by
}

/* افزوده به users */
phone_verified_at
nid_verified           // 0|1

/* افزوده به app_settings */
auth_mode              // 'password'|'phone' — سوییچ امن
otp_ttl_sec            // 180 — اعتبار کد
otp_resend_sec         // 60  — فاصلهٔ ارسال مجدد
otp_max_send           // 3   — سقف ارسال در ۱۰ دقیقه
otp_max_attempt        // 5   — سقف تلاش کد غلط
nid_max_attempt        // 3   — سقف تلاش کد ملی
nid_lock_hours         // 24  — قفل پس از سقف

/* کلید Store (نه جدول db — موقتی است) */
OTP_KEY = 'sms_otp_v1'
// { phone, codeHash, sentAt, resendAt, expiresAt, sendCount, attempts }
```

⚠️ **`auth_mode` حیاتی است:** ورود فعلی نباید حذف شود. دمو با
۱۱۳۶ کاربر نمونه کار می‌کند و حساب‌های آزمایشی لازمند.

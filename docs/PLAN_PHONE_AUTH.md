## ۳. سامانهٔ شاهکار — تطبیق مالکیت سیم‌کارت

### 🔴 قاعدهٔ بنیادی: عدم تطابق یعنی رد قطعی

**تصحیح مهم (دور ۵۲):** نسخهٔ نخست این طرح می‌گفت «رد + اعلام به
مدیر». **غلط بود.** درست این است:

> اگر کد ملی با شمارهٔ موبایل نخواند، یعنی **سیم‌کارت به نام آن
> شخص نیست**. این کاربر غیرقانونی است و **اصلاً نباید وارد
> سامانه شود** — نه با پرچم، نه با نقش موقت، نه با اعلام به مدیر.

**چرا این‌قدر مهم است؟** سامانه دادهٔ کودکان دارد. اگر کسی با
سیم‌کارت دیگری وارد شود، هیچ راهی برای پاسخ‌گویی نمی‌ماند —
نه می‌دانیم واقعاً کیست، نه می‌توانیم ردش را بگیریم.

⚠️ **پس هیچ اعلانی هم به مدیر نمی‌رود.** اعلام «شمارهٔ X با کد
ملی Y نخواند» خودش نشت اطلاعات است و به مدیر هم ربطی ندارد؛
مسئلهٔ بین کاربر و اپراتور تلفن است.

### سرویس‌شناسی

پشت همهٔ این سرویس‌ها **سامانهٔ شاهکار** (سازمان تنظیم مقررات و
ارتباطات رادیویی) است. ارائه‌دهندگان واسط:

| ارائه‌دهنده | نکته |
|---|---|
| **فینوتک** (انتخاب کاربر) | `apibeta.finnotech.ir` · OAuth با `Bearer` · سرویس «تطبیق کدملی و موبایل» |
| ↳ نکتهٔ فینوتک | دو سرویس جدا دارد: **تطبیق** (شاهکار) و **صحت‌سنجی کد ملی** (ثبت احوال، درصد تطابق نام). ما به **اولی** نیاز داریم |
| کاوشک · زحل · یوآیدی · api.ir | جایگزین‌های شناخته‌شده — پاسخ `true/false` |

**الگوی مشترک پاسخ:**
```json
{ "status": 200,
  "data": { "isValid": true, "nationalCode": "001******9",
            "mobile": "0912*******", "match": true } }
```

🟢 **نکتهٔ خوب:** خودِ سرویس‌ها هم کد ملی و موبایل را در پاسخ
**ماسک** می‌کنند — همان الگویی که ما هم باید رعایت کنیم.

⚠️ **هزینه:** همهٔ این سرویس‌ها **پولی**اند (به‌ازای هر استعلام).
چون احراز هویت **فقط بار اول** انجام می‌شود، هزینه با تعداد
کاربران رشد می‌کند نه با تعداد ورودها. برای مدرسهٔ ۵۰۰ نفره با
اولیا، حدود ۱۰۰۰ استعلام یک‌باره.

⚠️ **پیش از انتخاب نهایی ارائه‌دهنده، این‌ها را بسنجید:** قیمت
هر استعلام · محدودیت نرخ · زمان پاسخ (زحل ۴۰۰ms اعلام کرده) ·
پشتیبانی از محیط تست (فینوتک `apibeta` دارد ✅).

### قرارداد پیاده‌سازی

```js
/* src/js/47-phone-auth.js */
var SHAHKAR = {
  /* 🔴 روز اتصال فقط این سه خط پر می‌شود */
  provider: 'finnotech',
  endpoint: null,          // https://apibeta.finnotech.ir/...
  token:    null,          // Bearer — 🔴 هرگز در کد مخزن!
  timeout:  8000,
  mode:     'demo'         // 'demo' | 'live'
};

/**
 * @returns {Promise<{ok:boolean, reason:string}>}
 *   reason: 'match' | 'mismatch' | 'unreachable' | 'invalid-nid'
 */
async function verifyNidPhone(nid, phone){ … }
```

### 🔴 سه حالت خطا — همه ورود را می‌بندند

| حالت | رفتار | چرا |
|---|---|---|
| `mismatch` | **رد قطعی** | سیم‌کارت به نام کاربر نیست |
| `unreachable` | **رد با پیام «بعداً تلاش کنید»** | 🔴 تصحیح‌شده در دور ۵۲ |
| `invalid-nid` | رد محلی، بدون تماس با سرویس | رقم کنترل غلط است |

🔴 **چرا `unreachable` هم ورود را می‌بندد؟** نسخهٔ نخست پیشنهاد
داده بود «ورود مشروط تا سرویس برگردد». **این یک رخنهٔ امنیتی
بود:** مهاجم می‌توانست با ایجاد اختلال شبکه (یا صرفاً آفلاین
شدن) از احراز هویت رد شود. وقتی سرویس در دسترس نیست، **هیچ‌کس**
نباید وارد شود.

⚠️ **پیامد عملیاتی که باید بدانید:** اگر شاهکار قطع شود،
کاربران **تازه** نمی‌توانند ثبت‌نام کنند. ولی کاربرانی که یک بار
احراز شده‌اند همچنان وارد می‌شوند (بخش ۴). پس قطعی سرویس مدرسه
را فلج نمی‌کند، فقط ثبت‌نام تازه را متوقف می‌کند.

⚠️ **توکن هرگز در مخزن نباشد.** الگوی موجود پروژه را دنبال
می‌کنیم: مثل `~/.payesh_gh_token` بیرون از مخزن. گیت‌هاب با
`GH013` جلوی کامیت شدنش را می‌گیرد، ولی نباید به آن تکیه کرد.

## ۴. مدل داده — سه افزودنی کوچک

```js
/* جدول تازه: identity_requests */
{
  id, phone, national_id,
  claimed_role,        // 'teacher'|'student'|'parent'|'manager'|'edu_office'
  province_id, county_id, school_id,
  status,              // 'pending'|'approved'|'rejected'
  routed_to,           // 'manager'|'superadmin'  ← تعیین‌کنندهٔ گیرنده
  created_at, decided_at, decided_by, note
}

/* افزوده به users */
phone_verified_at    // ISO — لحظهٔ احراز هویت موفق
nid_verified         // 0|1  ← هیچ حالت سومی نیست (دور ۵۲)

/* افزوده به app_settings */
auth_mode            // 'password' | 'phone'  ← سوییچ امن
```

⚠️ **`auth_mode` مهم است:** ورود فعلی (نام‌کاربری/رمز) نباید
حذف شود. دمو با ۱۱۳۶ کاربر نمونه کار می‌کند و حساب‌های آزمایشی
لازمند. سوییچ اجازه می‌دهد هر دو کنار هم باشند.

## ۴.۵ ماندگاری نشست — 🟢 از قبل کار می‌کند

**خواستهٔ کاربر:** «بعد از احراز هویت دیگر خارج نشود مگر خودش
دکمهٔ خروج را بزند.»

سنجش کد نشان داد این **از پیش پیاده است**:

```js
Store.set(SESSION_KEY, u.username);        // 19-actions.js:39 — هنگام ورود
Store.remove(SESSION_KEY);                 // 19-actions.js:42 — فقط در logout
const su = Store.get(SESSION_KEY);         // 24-edu-office.js:788 — هنگام بوت
if(su){ … S.user = u; }                    // نشست بازمی‌گردد
```

`localStorage` تا وقتی کاربر پاکش نکند می‌ماند — نه با بستن
مرورگر می‌پرد، نه انقضا دارد.

**پس کار تازه‌ای لازم نیست**، فقط دو افزوده:

۱. **کلید تازه برای احراز هویت تلفنی:** `AUTH_KEY = 'sms_auth_v1'`
   که `{phone, nid, verified_at}` را نگه دارد — تا بار دوم
   مرحلهٔ کد ملی تکرار نشود.
۲. **جدایی از `SESSION_KEY`:** اگر کاربر خروج بزند، نشست پاک
   می‌شود ولی **احراز هویت** می‌ماند. یعنی بار بعد فقط کد پیامکی
   می‌خواهد، نه کد ملی دوباره.

⚠️ **یک تصمیم امنیتی که باید بگیرید:** آیا خروج باید احراز هویت
را هم پاک کند؟

| گزینه | مزیت | ریسک |
|---|---|---|
| **الف) احراز بماند** (پیشنهاد من) | کاربر بار دوم فقط کد پیامکی می‌دهد | اگر گوشی دست دیگری بیفتد، فقط کد پیامکی مانع است |
| ب) احراز هم پاک شود | امن‌تر | هر بار کد ملی — آزاردهنده |

پیشنهاد من **الف** است، چون کد پیامکی خودش به همان سیم‌کارت
می‌رود و مالکیتش قبلاً تأیید شده.

🔴 **ولی در تولید:** نشست باید انقضا داشته باشد (قرارداد سرور:
`Max-Age=28800` یعنی ۸ ساعت). «هرگز خارج نشدن» فقط برای دموی
بدون سرور قابل قبول است.

## ۵. کد تأیید پیامکی — در دمو چه کنیم؟

🔴 **در دمو کد واقعی نمی‌فرستیم** (اعتبار پیامک مصرف می‌شود و
شمارهٔ نمونه `0999…` واقعی نیست).

**پیشنهاد:** کد شش‌رقمی تولید و **روی صفحه نمایش داده شود** با
برچسب صریح:

```
🔧 حالت نمایشی — کد تأیید: ۱۲۳۴۵۶
در نسخهٔ واقعی این کد پیامک می‌شود.
```

⚠️ **و یک نگهبان:** آزمونی که مطمئن شود این نمایش فقط وقتی
`NID_VERIFY.mode === 'demo'` است رخ می‌دهد. اگر روزی `live` شد و
کد روی صفحه ماند، **هر کسی می‌تواند با هر شماره‌ای وارد شود**.

**محدودسازی نرخ حتی در دمو:** حداکثر ۳ تلاش در ۱۰ دقیقه برای هر
شماره. الگویش ساده است و از همین حالا عادت درست را جا می‌اندازد.

## ۷. 🔴 هشدارهای امنیتی که باید ثبت شوند

طبق اصل پنجم، این تغییر **سطح حملهٔ تازه‌ای** می‌سازد:

| ریسک | در دمو | روز تولید |
|---|---|---|
| کد تأیید روی صفحه | عمدی و برچسب‌دار | 🔴 **باید حذف شود** |
| تصمیم ورود در مرورگر | مثل امروز | 🔴 باید سمت سرور برود |
| محدودسازی نرخ | محلی، دور زدنی | 🔴 باید سمت سرور |
| شمارش کد ملی | `nidOwner` همه را می‌بیند | 🔴 پاسخ باید یکسان باشد (نه «این کد ملی نیست») |
| نشست بی‌انقضا | عمدی (خواستهٔ کاربر) | 🔴 `Max-Age=28800` طبق قرارداد سرور |
| توکن شاهکار | `null` است | 🔴 بیرون از مخزن، مثل `~/.payesh_gh_token` |

⚠️ **نشت اطلاعات از پیام خطا:** اگر بگوییم «این کد ملی در سامانه
نیست»، مهاجم می‌تواند کد ملی‌ها را بشمارد. پیام باید **یکسان**
باشد: «اطلاعات با سوابق نمی‌خواند».

⚠️ **اعلان به مدیر خودش نشت است:** «شمارهٔ X با کد ملی Y نخواند»
یعنی مدیر می‌فهمد چه کسی تلاش کرده. باید فقط شمارهٔ **ماسک‌شده**
(`0912***4567`) نمایش داده شود.

## ۸. پرسش‌هایی که پیش از کد باید پاسخ بگیرند

۱. **`auth_mode` پیش‌فرض کدام باشد؟** پیشنهاد من: `password`
   بماند تا دمو نشکند، و ورود تلفنی گزینهٔ دوم باشد.

۰. **خروج، احراز هویت را هم پاک کند؟** (بخش ۴.۵) پیشنهاد من:
   نه — بار دوم فقط کد پیامکی.
۲. **اگر کد ملی به **چند** کاربر بخورد چه؟** (مثلاً یک نفر هم
   دبیر مدرسهٔ الف و هم ولی در مدرسهٔ ب). پیشنهاد من: همه نمایش
   داده شوند — `panelsOf` از قبل این را می‌کند.
۳. **درخواست تکراری:** اگر کاربری دو بار درخواست نقش داد، دومی
   رد شود یا اولی به‌روز؟ پیشنهاد من: **به‌روزرسانی**، تا صف
   مدیر پر از تکرار نشود.
۴. **مهلت درخواست:** درخواستی که ۳۰ روز بی‌پاسخ ماند چه شود؟
   پیشنهاد من: خودکار `expired` با اعلان به کاربر.

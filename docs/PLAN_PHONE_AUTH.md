## ۱. جریان کامل — آنچه توصیف شد

```
۱. کاربر شمارهٔ موبایل می‌دهد
۲. کد تأیید پیامکی می‌گیرد و وارد می‌کند
۳. 🔹 بار اول: کد ملی می‌خواهد
۴. 🔹 سامانهٔ بیرونی: آیا این کد ملی با این شماره می‌خواند؟
      ├─ نه ⇒ رد + اعلام به مدیرِ مدرسه‌ای که این شماره در آن ثبت است
      └─ بله ⇒ ادامه
۵. جست‌وجوی کد ملی در پایگاه دادهٔ ما
      ├─ پیدا شد ⇒ همهٔ نقش‌هایش نمایش داده می‌شود (دبیر + ولی)
      └─ پیدا نشد ⇒ صفحهٔ «نقشی تعریف نشده» + مسیر درخواست
۶. بارهای بعد: فقط مرحلهٔ ۱ و ۲
```

**مسیر درخواست نقش (وقتی کاربر می‌گوید «من کاربر دارم»):**

```
نقش را انتخاب کن
   ├─ دبیر / دانش‌آموز / ولی  ⇒ ارجاع به مدیر مدرسه
   └─ مدیر / رئیس اداره       ⇒ ارجاع به سوپرادمین
سپس: استان → شهرستان → مدرسه
   ├─ مدرسه در پایگاه داده هست ⇒ اعلان به مدیرش
   └─ نیست ⇒ ارجاع به سوپرادمین
پس از تصحیح مدیر ⇒ کاربر با همان شماره وارد می‌شود و پنل بالا می‌آید
```

## ۳. سامانهٔ بیرونی — جای خالی با قرارداد روشن

آدرسش را نمی‌دانیم، پس **رابط را تعریف می‌کنیم و پیاده‌سازی را
جدا نگه می‌داریم**:

```js
/* src/js/47-phone-auth.js */
var NID_VERIFY = {
  /* 🔴 روز اتصال فقط این آدرس پر می‌شود — بقیهٔ کد دست نمی‌خورد */
  endpoint: null,              // مثلاً 'https://api.example.ir/verify'
  timeout:  8000,
  /* در دمو: شبیه‌ساز محلی. در تولید: fetch واقعی */
  mode: 'demo'                 // 'demo' | 'live'
};

/**
 * @returns {Promise<{ok:boolean, reason:string}>}
 *   reason: 'match' | 'mismatch' | 'unreachable' | 'invalid-nid'
 */
async function verifyNidPhone(nid, phone){ … }
```

⚠️ **قرارداد صریح برای سه حالت خطا:**

| حالت | رفتار |
|---|---|
| `mismatch` | 🔴 رد ورود + اعلان به مدیر مدرسهٔ آن شماره |
| `unreachable` | ⚠️ **ورود را قطع نکن** — با پرچم «تأییدنشده» ادامه بده و به مدیر اطلاع بده |
| `invalid-nid` | پیام محلی، بدون تماس با سرویس |

🔴 **چرا `unreachable` نباید ورود را ببندد؟** اگر سرویس دولتی
قطع باشد، کل مدارس کشور از سامانه بیرون می‌مانند. تصمیم بهتر:
ورود مشروط + نشان «احراز هویت ناتمام» که مدیر ببیند.

## ۴. مدل داده — سه افزودنی کوچک

```js
/* جدول تازه: identity_requests */
{
  id, phone, national_id,
  claimed_role,        // 'teacher'|'student'|'parent'|'manager'|'edu_office'
  province_id, county_id, school_id,
  status,              // 'pending'|'approved'|'rejected'
  routed_to,           // 'manager'|'superadmin'  ← تعیین‌کنندهٔ گیرنده
  created_at, decided_at, decided_by, note
}

/* افزوده به users */
phone_verified_at    // ISO — بار اول احراز هویت
nid_verified         // 0|1|null(سرویس در دسترس نبود)

/* افزوده به app_settings */
auth_mode            // 'password' | 'phone'  ← سوییچ امن
```

⚠️ **`auth_mode` مهم است:** ورود فعلی (نام‌کاربری/رمز) نباید
حذف شود. دمو با ۱۱۳۶ کاربر نمونه کار می‌کند و حساب‌های آزمایشی
لازمند. سوییچ اجازه می‌دهد هر دو کنار هم باشند.

## ۵. کد تأیید پیامکی — در دمو چه کنیم؟

🔴 **در دمو کد واقعی نمی‌فرستیم** (اعتبار پیامک مصرف می‌شود و
شمارهٔ نمونه `0999…` واقعی نیست).

**پیشنهاد:** کد شش‌رقمی تولید و **روی صفحه نمایش داده شود** با
برچسب صریح:

```
🔧 حالت نمایشی — کد تأیید: ۱۲۳۴۵۶
در نسخهٔ واقعی این کد پیامک می‌شود.
```

⚠️ **و یک نگهبان:** آزمونی که مطمئن شود این نمایش فقط وقتی
`NID_VERIFY.mode === 'demo'` است رخ می‌دهد. اگر روزی `live` شد و
کد روی صفحه ماند، **هر کسی می‌تواند با هر شماره‌ای وارد شود**.

**محدودسازی نرخ حتی در دمو:** حداکثر ۳ تلاش در ۱۰ دقیقه برای هر
شماره. الگویش ساده است و از همین حالا عادت درست را جا می‌اندازد.

## ۷. 🔴 هشدارهای امنیتی که باید ثبت شوند

طبق اصل پنجم، این تغییر **سطح حملهٔ تازه‌ای** می‌سازد:

| ریسک | در دمو | روز تولید |
|---|---|---|
| کد تأیید روی صفحه | عمدی و برچسب‌دار | 🔴 **باید حذف شود** |
| تصمیم ورود در مرورگر | مثل امروز | 🔴 باید سمت سرور برود |
| محدودسازی نرخ | محلی، دور زدنی | 🔴 باید سمت سرور |
| شمارش کد ملی | `nidOwner` همه را می‌بیند | 🔴 پاسخ باید یکسان باشد (نه «این کد ملی نیست») |

⚠️ **نشت اطلاعات از پیام خطا:** اگر بگوییم «این کد ملی در سامانه
نیست»، مهاجم می‌تواند کد ملی‌ها را بشمارد. پیام باید **یکسان**
باشد: «اطلاعات با سوابق نمی‌خواند».

⚠️ **اعلان به مدیر خودش نشت است:** «شمارهٔ X با کد ملی Y نخواند»
یعنی مدیر می‌فهمد چه کسی تلاش کرده. باید فقط شمارهٔ **ماسک‌شده**
(`0912***4567`) نمایش داده شود.

## ۸. پرسش‌هایی که پیش از کد باید پاسخ بگیرند

۱. **`auth_mode` پیش‌فرض کدام باشد؟** پیشنهاد من: `password`
   بماند تا دمو نشکند، و ورود تلفنی گزینهٔ دوم باشد.
۲. **اگر کد ملی به **چند** کاربر بخورد چه؟** (مثلاً یک نفر هم
   دبیر مدرسهٔ الف و هم ولی در مدرسهٔ ب). پیشنهاد من: همه نمایش
   داده شوند — `panelsOf` از قبل این را می‌کند.
۳. **درخواست تکراری:** اگر کاربری دو بار درخواست نقش داد، دومی
   رد شود یا اولی به‌روز؟ پیشنهاد من: **به‌روزرسانی**، تا صف
   مدیر پر از تکرار نشود.
۴. **مهلت درخواست:** درخواستی که ۳۰ روز بی‌پاسخ ماند چه شود؟
   پیشنهاد من: خودکار `expired` با اعلان به کاربر.

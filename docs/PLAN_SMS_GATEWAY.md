# قراردادِ اتصالِ درگاهِ پیامک — طراحیِ قفل‌شده (دور ۸۱ بند ۳)

> **وضعیت:** طراحی قفل شد، کدِ سمتِ درگاه **عمداً هنوز نوشته نشده** — چون
> شکلِ دقیقِ سازگارِ درگاه (برنامهٔ ارسال، قیمتِ قطعه، رسیدِ تحویل) به
> **قراردادِ خارجی** وابسته است. این سند می‌گوید وقتی قرارداد امضا شد،
> دقیقاً چه کاری (چه کدی، چه تستی، چه ترتیبی) انجام می‌شود.
>
> **سمتِ کلاینت (نسخهٔ تک‌فایلی) دست نمی‌خورد:** صفِ پیام، کیفِ اعتبار، شمارشِ
> قطعه و `sms_log` همه در کلاینت واقعی و قفل‌شده با آزمون‌اند؛ آنچه
> «شبیه‌سازی» است فقط **پایهٔ آخر** است: نوشتنِ `sms_log` با وضعیت
> «sent» به‌جای زنگ‌زدنِ درگاه.

---

## ۱. آنچه امروز واقعی و قفل‌شده است (سمتِ کلاینت)

| جزء | کجا | وضعیت |
|---|---|---|
| صفِ پیامِ اولیا (`notify_queue`): ساختِ خودکار (غیبت، نمره، ...) + بازبینی/تأییدِ مدیر + «رد» | `src/js/44-sms-notify.js` | ✅ واقعی + آزمون (بخشِ مربوط smoke + sim_full2) |
| شمارشِ قطعه (parts) و برآوردِ هزینه | همان فایل | ✅ واقعی + آزمون |
| کیفِ اعتبارِ هر مدرسه (`sms_wallet`) + سقفِ روزانه | همان فایل | ✅ واقعی + آزمون |
| لاگِ ارسال (`sms_log`: گیرنده، متن، قطعه، وضعیت) | همان فایل | ✅ واقعی (در حالتِ دمو، «sent» = شبیه‌سازی) |
| ورودِ تلفن+کد+کدملی | `server/auth.js` | ✅ واقعی + آزمون (server1–3) |

**مرزِ دقیقِ شبیه‌سازی:** در `notifyApprove`، پس از کسرِ اعتبار، برایِ هر
گیرنده فقط یک رکوردِ `sms_log` با `status:'sent'` نوشته می‌شود — هیچ HTTP
به بیرون نمی‌رود. **همین یک نقطه، تنها نقطهٔ اتصالِ درگاه است.**

## ۲. شکاف‌ها (برایِ حالتِ «اتصال به سرور») — با شواهد

| # | شکاف | شواهد |
|---|---|---|
| ۱ | صف/کیف/لاگ در **همگام‌سازی** نیستند: `WRITE_PERMS` در `server/sync.js` این سه مجموعه را نمی‌شناسد (fail-closed) — فقط superadmin با `'*'` می‌تواند بنویسد | `server/sync.js` (جدولِ WRITE_PERMS) |
| ۲ | **ندایِ ارسالِ سمتِ سرور** وجود ندارد (`/api/sms/*` نیست) | `server/index.js` (رایتر) |
| ۳ | کیفِ اعتبار در حالتِ واقعی باید **مالکیتِ سرور** داشته باشد (کلاینت فقط نمایش) — امروز مالکِ نوشتنِ کیف در دمو، خودِ کلاینت است | `44-sms-notify.js` (notifyApprove) |
| ۴ | **درگاهِ خارجی** (کاربر/رمز/برنامهٔ ارسال + قیمت + رسید) | قرارداد |

## ۳. معماریِ هدف (قفل شد)

```
 [کلاینت: صف + تأییدِ مدیر] --(syncِ معمولی)--> [سرور: store]
                                                      |
                      superadmin/اپراتور: POST /api/sms/send {queue_ids}
                                                      |
                              [server/sms.js] ── provider adapter ──> [درگاه]
                                                      |
                        sms_log (sent/failed + provider_msg) + کیف + آدیت
```

**تصمیماتِ قفل‌شده (هرکدام با دلیل):**

1. **ارسال فقط سمتِ سرور.** کلاینت هرگز مستقیم به درگاه نمی‌زند (رازِ درگاه
   سمتِ کلاینت نمی‌رود؛ اعتبار هم فقط سرور کسر می‌کند — وگرنه هر کلاینتی
   کیف را صفر می‌کرد).
2. **صف، با همگام‌سازیِ معمولی به سرور می‌رسد** (شکافِ ۱ بسته می‌شود):
   `notify_queue` به WRITE_PERMS اضافه می‌شود برایِ `manager` و `teacher`
   (سازندگانِ رکوردها) — `sms_wallet` و `sms_log` به **هیچ نقشه** داده
   نمی‌شوند (فقط سرور می‌نویسد؛ کلاینت فقط می‌خواند).
3. **منبعِ حقِ هزینه = کیفِ ما** (نه گزارشِ درگاه): کسرِ اعتبار با قطعهٔ
   اعلام‌شدهٔ درگاه (اگر درگاه قطعهٔ متفاوت گزارش کرد، اختلاف در آدیت
   ثبت می‌شود و هفتگی تراز می‌شود — §۶).
4. **ایدمپوتانس:** کلیدِ یکتا = `queue_id + parent_id`. اگر رکوردِ
   `sms_log` با آن کلیدِ `sent` وجود داشته باشد، دوباره ارسال/کسر نمی‌شود
   (ری‌ترِ اپراتور امن است).
5. **سیاستِ شکست:** شکست در یک گیرنده = کلِ آن آیتمِ صف **ثبتِ sent نمی‌شود**
   (بایدها: همگی برسند، یا هیچ — نصفه ارسال با هزینه، بدترین حالت است).
   رکوردِ `failed` + دلیل می‌ماند؛ **ری‌ارسالِ خودکار نیست** (کنترلِ
   هزینه) — اپراتور دکمهٔ «تلاشِ دوباره» را می‌زند.
6. **سقفِ روزانهٔ سمتِ سرور** (`PAYESH_SMS_MAX_PER_DAY`، پیش‌فرض ۲۰۰۰):
   شمارش از `sms_log`ِ همان روز؛ عبور = `429 daily_cap` برایِ کلِ دسته.
7. **آدیت بدونِ شماره** (قاعدهٔ موجود: بدونِ phone/nid): `sms_send {school, n, parts, credits}`
   و `sms_fail {school, n, code}` — هیچ phone در audit.log نمی‌آید.
8. **Dry-run:** `PAYESH_SMS_DRY_RUN=1` — همهٔ منطق (کیف، ایدمپوتانس، سقف)
   واقعی، فقط زنگِ درگاه نمی‌زند؛ پیامکِ «آزمایشی» برمی‌گردد. **پیش‌نیازِ
   گامِ ۳ِ switchover.**

## ۴. سازگارِ درگاه (پروتکلِ داخلی — سازگارِ واقعی بعد از قرارداد)

```js
// server/sms.js — adapter
send({ phone, body }) -> Promise<{ message_id: string, parts: number }>
// خطا = reject با { code: 'gateway_<reason>' } — هرگز promise خالی
```

- اعتبارنامه‌ها **فقط** در envِ سرور: `PAYESH_SMS_USERNAME` /
  `PAYESH_SMS_PASSWORD` (یا `PAYESH_SMS_API_KEY`) + `PAYESH_SMS_FROM`
  (شمارهٔ فرستنده/شناسه). هرگز در ریپازیتوری، هرگز در کلاینت.
- سازگارِ واقعی = یک `fetch` JSON (اکثرِ درگاه‌های ایرانی REST با
  همان فرم `to`/`message`‌اند) + **یک جدولِ نگاشتِ کوچک** برایِ هر
  درگاه (نامِ فیلدها، فرمِ اعتبار، کدِ خطاها) — ۲۰–۳۰ سطرِ
  درگاه‌بسته. **تا قرارداد امضا نشود، هیچ درگاهِ خاصی در کد نمی‌آید.**
- سازگارِ `mock` (برایِ تستِ server11) همین پروتکل را با
  `message_id='mock-…'` و `parts = max(1, ceil(len/66))` باز می‌گرداند.

## ۵. ترتیبِ switchover (وقتی قرارداد امضا شد)

| گام | کار | خروجی/درِ باز |
|---|---|---|
| ۰ | امضایِ قرارداد + دریافتِ اعتبارنامه + شمارهٔ فرستنده | — |
| ۱ | کد: `server/sms.js` (نهای + سازگارِ mock + سازگارِ درگاهِ قرارداد) + `notify_queue` در WRITE_PERMS (manager/teacher) + endpoint در index.js | آزمون‌هایِ §۶ سبز |
| ۲ | استقرار: env (بخشِ ۴) + `PAYESH_SMS_DRY_RUN=1` → ارسالِ واقعیِ ۵ پیام به شمارهٔ تیم | رسیدِ تحویلِ درگاه دیده شد |
| ۳ | `PAYESH_SMS_DRY_RUN=0` (live) → ۳۰ پیامِ واقعیِ کنترل‌شده (۳ مدرسهٔ دمو/پایلوت) | ۳۰/۳۰ تحویل + کیف درست کسر شد |
| ۴ | مانیتورِ ۴۸ ساعت: آدیت + سقف + ترازِ روزانه | صفرِ شکستِ توضیح‌نشده |
| ۵ | ترازِ هفتگیِ خودکار: `sms_log` در برابرِ گزارشِ درگاه (اختلاف > ۱٪ = هشدار به اپراتور) | گزارشِ تراز |

**نکتهٔ ترتیب:** این switchover **پس از** استقرارِ تولید (`docs/DEPLOY.md`)
و **پس از** انتخابِ مدرسهٔ پایلوت است — پیش‌نیازِ go-live در §۹ِ DEPLOY همین
درگاه است.

## ۶. تراز و هزینه

- هر `sms_log` رکوردِ `credits` (قطعه × ۱ واحد) دارد.
- گزارشِ هفتگی: `SUM(credits) GROUP BY school` در برابرِ پنلِ درگاه؛
  اختلاف → آدیتِ `sms_recon {school, ours, theirs, diff}`.
- افزایشِ کیف: فقط با تراکنش (ساختارِ موجودِ `transactions`) — دستِ
  اپراتور به کیفِ مستقیم نمی‌رود.

## ۷. آزمون (طراحیِ قفل‌شده — در گامِ ۱ نوشته می‌شود)

`tests/server11-sms.js` (همان الگویِ server1: HTTP واقعی، store جدا در tmp):

| # | آزمون | جهشِ هدف |
|---|---|---|
| S1 | بدونِ envِ درگاه → `503 sms_not_configured` (و کلاینتِ دمو دست‌نخورده) | حذفِ گاردِ تنظیم |
| S2 | ارسالِ واقعی (mock): ۲ آیتمِ صف → `sms_log` ۳ رکورد + کیف -۳ + صف sent | حذفِ نوشتنِ log / حذفِ کسر |
| S3 | **ایدمپوتانس:** همان `/send` دوباره → صفرِ کسر، صفرِ رکوردِ نو | حذفِ چکِ کلید |
| S4 | **شکستِ جزئی:** mock برایِ یک شماره fail → کلِ آیتم sent نمی‌شود + `failed` ثبت شد | تبدیلِ fail به sent |
| S5 | **سقف:** `MAX_PER_DAY=1` → درخواستِ دوم `429 daily_cap` | حذفِ سقف |
| S6 | **نقش:** مدیر (non-superadmin) → `403 forbidden` (فقط superadmin) | حذفِ چکِ نقش |
| S7 | **آدیت:** بعد از S2، در audit.log خطای `sms_send` هست و هیچ phone ندارد | نشتِ phone در آدیت |
| S8 | dry-run: `PAYESH_SMS_DRY_RUN=1` → همهٔ منطق سبز + `message_id='dry-…'` + زنگِ درگاه نرفته | در dry-run زنگِ واقعی |

جهش‌سنجی: `server11-mutations.js` (حداقل ۵ جهش — الگویِ server7/8).

## ۸. تصمیماتِ باز (به‌علاوهٔ قرارداد)

| پرسش | پیش‌فرضِ قفل‌شده | باز تا |
|---|---|---|
| قیمت/برنامهٔ درگاه (قطعه‌ای یا بسته) | ترازِ هفتگی (§۶) جبران می‌کند | امضای قرارداد |
| شناسهٔ فرستنده (shortcode vs شماره) | هرکدام که درگاه بدهد (`PAYESH_SMS_FROM`) | قرارداد |
| رسیدِ تحویل (webhook vs polling) | pollingِ سادهٔ ساعتی تا webhook در دسترس شود | قرارداد |
| ارسالِ «تأییدِ ورود» به اولیا در لحظهٔ فعال‌سازی | بله (از همین صف می‌گذرد) | — (قفل) |

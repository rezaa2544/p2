# ران‌بوردِ تمرینِ چرخشِ credentialها (SI-013-SIM) — ۲۰۲۶-۱۱-۲۶

> **فرمانِ مالک (۲۰۲۶-۱۱-۲۶):** تا خریدِ فیزیکی زیرساخت، هر مرحلهٔ نیازمندِ سرور با Docker/شبیه‌ساز روی ویندوز اجرا شود؛ «هیچ کاری جز تهیهٔ واقعی و فیزیکی زیرساخت‌ها باقی نماند.» این تمرین طبق همین فرمان، **رویهٔ چرخش** را کامل اثبات می‌کند؛ چرخشِ خودِ اعتبارنامهٔ افشاشدهٔ W18 (نشست) و تصمیمِ تاریخ، همچنان **اقدامِ انحصاریِ مالک** است (ردیف ۲ = BLOCKED-OWNER در آن بخش).
> کارتِ مرجع: `docs/RUNBOOK_CARDS/E4_SI013_STAGING_BOOTSTRAP.md` (گام ۳).

## ۱) چرخشِ رمزِ نقشِ PostgreSQL — دومرحله‌ای، دو نود (مسیرِ scram)
میزبان: استکِ `payesh-pg-ha` محلی. نقشِ تمرینی: `drill_rotate` (ساخته/انداخته‌شده در همان تمرین).
- گام‌های ۱–۳: نقش با رمزِ قدیمی ساخته شد؛ اتصال با قدیمی از دو نود (کانتینرِ primary فعلی و کانتینرِ PITR) = موفق (`select 1` → 1).
- گام ۴: `ALTER ROLE drill_rotate PASSWORD '<new>'`.
- گام‌های ۵–۸: قدیمی از نودِ مسیر-scram = **رد شد** (`FATAL: password authentication failed` — 28P01) و جدید از هر دو نود = پذیرفته شد.
- **یافتهٔ ثبت‌شده (خارج از scopeِ تمرین — برای bootstrap واقعی):** خطوطِ `trust` برای loopback در init محلی (dev-only) باعث شد اتصال از داخلِ خودِ کانتینرِ primary بدون رمز هم بپذیرد؛ در bootstrap واقعی (کارتِ RC-027-E4) pg_hba باید برای **همهٔ** خطوط host = `scram-sha-256` پین شود. مکانیزمِ چرخش روی مسیر scram کاملاً درست عمل کرد.

## ۲) چرخشِ `requirepass` Redis — دومرحله‌ای، دو نود
کانتینرِ تمرین: `e4sim-redis-drill` (image `redis:7.4.2-bookworm`، همان نسخهٔ استک)؛ نود دوم = کانتینرِ `sentinel-1`.
- قدیمی از هر دو نود = `PONG` ✓ → `CONFIG SET requirepass <new>` = `OK` ✓
- قدیمی پس از چرخش (اتصالِ جدید): نود۱ = `NOAUTH Authentication required`، نود۲ = `WRONGPASS invalid username-password pair` = **رد شد** ✓
- جدید از هر دو نود = `PONG` ✓. کانتینرِ تمرین = حذف شد؛ به استکِ HA دست نخورد.

## ۳) چرخشِ kid رمزنگاریِ فیلد (پاکت `payesh-fenc:v1:<kid>:…`) — پنجرهٔ هم‌پوشانی
مکانیزم: `server/field-crypto.js` (تحویلِ m15-09). تمرین سه‌فازی با env جدا در هر فاز (کلیدها فقط در حافظه، پس از تمرین پاک شدند):
- فاز ۱: رمز با `k1` (شکلِ پاکت ✓).
- فاز ۲ (پنجرهٔ هم‌پوشانی `k1,k2`، KID→k2): **پاکتِ قدیمیِ k1 همچنان بازشد** ✓ + مقدارِ جدید با `k2` نوشته شد ✓ — همان الگویِ «rotation-ready» سندِ m15-09.
- فاز ۳ (حذفِ k1 از نقشه): پاکتِ قدیمی = **بازنشد (اثباتِ از-دست‌رفتن)** ✓ و k2 باز شد ✓ → این است چراییِ اجباریِ «پنجرهٔ هم‌پوشانی» هنگام چرخش واقعی.

## ۴) باقی‌ماندهٔ مالک (تغییرنیافته)
- چرخش/ابطالِ خودِ اعتبارنامهٔ نشستِ W18 در محیطِ مستقر + تصمیمِ تاریخِ عمومی + ردِ حذف در `SECURITY_INCIDENT_LOG`.
- اجرای همین رویه‌ها روی سرورهای واقعی (بعد از خرید) — فقط اجرای همان گام‌ها، بدونِ اثباتِ جدید.

## نتیجه
رویهٔ چرخش در هر سه بستر (PG / Redis / field-crypto) به‌صورت دومرحله‌ای (قدیمی‌باطل/جدیدفعال) و از دو نود **SIM-VERIFIED** شد؛ یافتهٔ pg_hba برای bootstrap واقعی ثبت شد.

# ضمیمهٔ الف — مقیاس کشوری در برابر `localStorage`

> تحلیل معماری برای تصمیم‌گیری. دور ۴۶ · نویسنده: احمد
> **این سند کد نیست؛ سه مسیر را می‌سنجد تا انتخاب آگاهانه شود.**

## ۱. مسئله در یک جمله

هدف پروژه **سطح کشوری** است، ولی معماری امروز داده را در
`localStorage` **هر مرورگر** نگه می‌دارد. این دو با هم جمع
نمی‌شوند و مشکل در یک جا خودش را نشان می‌دهد: **داشبورد تجمیعی
رئیس اداره**.

## ۲. چرا معماری فعلی ذاتاً کافی نیست

امروز صفحهٔ `officedash` کار می‌کند و آمار چند مدرسه را نشان
می‌دهد — ولی **فقط چون همهٔ مدارس در یک `db` واحدِ نمونه‌اند**.

در استقرار واقعی این‌طور نیست:

```
مرورگر مدیر مدرسهٔ الف  →  localStorage الف  →  فقط دادهٔ الف
مرورگر مدیر مدرسهٔ ب   →  localStorage ب   →  فقط دادهٔ ب
مرورگر رئیس اداره      →  localStorage خودش →  ❓ هیچ
```

`localStorage` به **مبدأ (origin) + دستگاه** بسته است. مرورگر
رئیس اداره هیچ راهی به دادهٔ مدارس ندارد. یعنی:

🔴 **`officeScopeSchools()` در دمو درست کار می‌کند و در واقعیت
هیچ‌چیز برنمی‌گرداند.** این یک باگ نیست — محدودیت ذاتی معماری
است.

سه پیامد دیگر همین ریشه:
- **سقف ~۵MB** برای هر مرورگر. یک مدرسهٔ ۵۰۰ نفره امروز ۴٫۷MB
  می‌گیرد؛ اداره‌ای با ۵۰ مدرسه اصلاً جا نمی‌شود.
- **پاک‌کردن حافظهٔ مرورگر = نابودی کل دادهٔ مدرسه.**
- **کاربر دو دستگاهی** (مدیر در مدرسه و خانه) دو دادهٔ متفاوت
  می‌بیند.

## ۳. سه مسیر ممکن

### مسیر الف — لایهٔ سرور مرکزی از همین حالا

سرور + پایگاه‌دادهٔ واقعی؛ مرورگر فقط نما می‌شود و
`localStorage` به کش آفلاین تنزل می‌یابد.

| | |
|---|---|
| **حجم کار** | 🔴 بسیار زیاد — ۲ تا ۴ ماه |
| **ریسک فنی** | متوسط؛ مسیرش شناخته‌شده است |
| **ریسک پروژه** | 🔴 **بالا** — دمو ماه‌ها بلااستفاده می‌شود |
| **حل مسئله** | ✅ کامل |

⚠️ زیرساختش تا حد خوبی آماده است: `00-data-layer.js` تنها دروازهٔ
داده است و `Api`/`enqueueOp` نوشته‌شده‌اند. یعنی «فقط درونشان به
`fetch` تبدیل شود» — همان چیزی که در دور ۲۸ برایش طراحی شد.

🔴 **ولی چهار مسدودکنندهٔ `TODO_BEFORE_PRODUCTION.md` هم باید با
هم حل شوند** (bcrypt، احراز هویت سرور، پایگاه‌داده، بررسی نقش).
نمی‌شود سرور زد و امنیت را عقب انداخت.

### مسیر ب — `localStorage` بماند + استخراج دوره‌ای برای اداره

هر مدرسه محلی می‌ماند. یک «خروجی تجمیعی» می‌گیرد (فایل JSON
کوچک) و رئیس اداره واردشان می‌کند.

| | |
|---|---|
| **حجم کار** | 🟢 کم — ۱ تا ۲ هفته |
| **ریسک فنی** | کم |
| **ریسک پروژه** | 🟢 کم — چیزی خراب نمی‌شود |
| **حل مسئله** | ⚠️ **نیمه** |

**چه چیزی حل می‌شود:** رئیس اداره آمار می‌بیند. حجم مسئله‌ای نیست
چون فقط **خلاصه** منتقل می‌شود نه رکوردها (برآورد: هر مدرسه چند
کیلوبایت).

**چه چیزی حل نمی‌شود:**
- 🔴 داده **کهنه** است — به‌روزرسانی دستی و دوره‌ای
- 🔴 وابسته به **همکاری مدیر مدرسه**؛ اگر نفرستد، اداره کور است
- 🔴 مسائل بنیادی (پاک‌شدن حافظه، دو دستگاه، سقف ۵MB) دست‌نخورده
- 🔴 «مقیاس کشوری» با انتقال دستی فایل معنا ندارد

⚠️ **این مسیر یک پل است نه مقصد.** اگر انتخاب شود، باید صریح
گفته شود که موقت است — وگرنه سه سال بعد کسی می‌پرسد چرا سامانهٔ
ملی با ایمیل فایل رد و بدل می‌کند.

### مسیر ج — سرور فقط برای تجمیع، نه برای همه‌چیز

مسیر میانه: مدرسه محلی و آفلاین‌اول می‌ماند، ولی یک **سرویس
کوچک تجمیع** می‌گیرد که هر شب فقط **آمار خلاصه** را می‌فرستد
(نه رکورد دانش‌آموز).

```
مدرسه (localStorage)  ──[شبانه، خودکار]──▶  سرور آمار  ──▶  اداره
        دادهٔ کامل محلی می‌ماند              فقط شمارنده‌ها
```

| | |
|---|---|
| **حجم کار** | 🟡 متوسط — ۳ تا ۵ هفته |
| **ریسک فنی** | کم — سرور فقط `POST` می‌گیرد و جمع می‌زند |
| **ریسک پروژه** | 🟢 کم — دمو دست‌نخورده می‌ماند |
| **حل مسئله** | ✅ برای اداره کامل · ⚠️ بقیه نه |

**مزیت ویژه‌ای که دو مسیر دیگر ندارند:**

🟢 **بار امنیتی‌اش بسیار کمتر است.** چون هیچ دادهٔ فردی منتقل
نمی‌شود (نه نام، نه کد ملی، نه نمره — فقط «۴۲۰ دانش‌آموز، میانگین
حضور ۹۳٪»)، مسائل حریم خصوصی و رضایت والدین **اصلاً پیش
نمی‌آیند**. مسیر الف باید همهٔ آن‌ها را حل کند.

🟢 **پله‌ای است.** همان سرویس بعداً می‌تواند به سرور کامل رشد کند؛
کار دورریز نیست.

**چه چیزی حل نمی‌شود:** پاک‌شدن حافظهٔ مرورگر، دو دستگاه، سقف
۵MB — همه سر جایشان می‌مانند.

# ضمیمهٔ ب — مدل داده: تک‌مدرسه‌ای یا چندمدرسه‌ای؟

> پاسخ به سه پرسش مهندس ارشد امنیت · دور ۴۹
> **تحلیل، نه کد.** روش: خواندن ساختار جدول‌ها + اجرای واقعی jsdom.

## خلاصهٔ یک‌خطی

🟢 **مدل داده از همین حالا چندمدرسه‌ای است و هیچ فرض تک‌مدرسه‌ای در
آن قفل نشده.** محدودیت جای دیگری است: **لایهٔ ذخیره‌سازی**.

---

## پرسش ۱ — آیا مدل داده آمادهٔ «چند مدرسه زیر یک اداره» است؟

### پاسخ: بله. سنجیده شد.

**۳۲ جدول از ۴۳ جدول `school_id` دارند:**

```
users · classes · subjects · enrollments · schedule · attendance ·
grades · discipline · announcements · notifications · leaves ·
calendar · messages · tuitions · installments · transactions ·
exams · exam_duties · corrections · teacher_schools · sms_wallet ·
sms_log · notify_queue · meeting_slots · bell_schedules ·
teacher_notes · student_transfers · student_archive · …
```

**۱۱ جدول `school_id` ندارند — و هیچ‌کدام مشکل‌ساز نیستند:**

| جدول | چرا مشکلی نیست |
|---|---|
| `schools` | خودش تعریف مدرسه است |
| `provinces` · `counties` · `districts` · `offices` | **بالای** سطح مدرسه‌اند — عمداً |
| `parent_links` · `parent_verifications` | از راه `student_id` به مدرسه می‌رسند |
| `parent_subscriptions` · `subscription_payments` | اشتراک به **کاربر** تعلق دارد نه مدرسه (قاعدهٔ «پدر یا مادر») |
| `app_settings` · `school_years` | تنظیمات سراسری |

### سلسله‌مراتب از قبل وجود دارد

```
مدرسه → منطقه (district_id) → شهرستان (county_id) → استان (province_id)
```

هر رکورد `schools` این سه فیلد را دارد (سنجش: **۱۰۰٪ مدارس**).
جدول `offices` هم سه سطح دارد: `province` · `county` · `district`.

`officeScopeSchools()` همین زنجیره را فیلتر می‌کند و **کار می‌کند**:
ادارهٔ استان کردستان ⇒ ۳ مدرسه از ۶.

### شناسه‌ها سراسری‌اند، نه per-school

```
مدرسه ۱ → کلاس‌های ۱،۲،۳
مدرسه ۲ → کلاس‌های ۱۰،۱۱،۱۲
مدرسه ۳ → کلاس‌های ۱۹،۲۰،۲۱
```

🟢 **این مهم‌ترین یافته است.** اگر `nextId` per-school بود، دو
مدرسه هر دو `classes.id = 1` می‌ساختند و ادغامشان در یک پایگاه‌دادهٔ مرکزی **برخورد شناسه** می‌داد. اما شمارنده سراسری است، پس
ادغام بی‌دردسر است.

### کوئری‌ها school-scoped اند

`visibleClasses` · `schoolStudents` · `visibleSubjects` — هر سه
فیلتر `school_id` دارند. یعنی کد از همین حالا فرض نمی‌کند «فقط
یک مدرسه وجود دارد».

---

## پرسش ۲ — اگر جایی قفل‌شده، کجاست و چقدر کار می‌برد؟

### 🔴 نقطهٔ قفل واقعی: ذخیره‌سازی، نه مدل داده

```js
const LOG_KEY = 'sms_log_v1';        // ← یک کلید برای همهٔ مدارس
```

کل داده در **یک کلید `localStorage`** ذخیره می‌شود. این یعنی:

| در دمو | در استقرار واقعی |
|---|---|
| همهٔ مدارس در یک `db` ⇒ تجمیع کار می‌کند | هر مدرسه `localStorage` جدا ⇒ تجمیع **صفر** برمی‌گرداند |

⚠️ **این را در ضمیمهٔ الف هم نوشته بودیم، ولی حالا دقیق‌تر
می‌دانیم:** مشکل از مدل داده **نیست**. اگر فردا سروری بیاید و
همان ساختار جدول‌ها را در یک پایگاه‌دادهٔ مرکزی بریزد، هیچ
بازنویسی‌ای لازم نیست.

### دو نکتهٔ کوچک که ارزش دانستن دارند

**الف) `superadmin.school_id === null`.** کد باید `null` را تحمل
کند و می‌کند (سنجش: ۱۹ صفحهٔ سوپرادمین سالم رندر می‌شوند). این
نشانهٔ خوبی است — یعنی «کاربر بدون مدرسه» از قبل مفهوم معتبری
است.

**ب) `schoolStudents` گارد `null` صریح ندارد.** اگر `school_id`
تهی باشد، آرایهٔ خالی برمی‌گرداند نه خطا. رفتار قابل قبولی است
ولی بهتر است روزی صریح شود.

### برآورد کار برای آماده‌سازی مدل داده

**صفر.** مدل داده از قبل آماده است. کاری برای انجام نیست.

---

## پرسش ۳ — آیا شناسهٔ «سازمان» بالای مدرسه لازم است؟

### پاسخ: 🔴 نه. افزودنش **زیان** دارد نه سود.

سلسله‌مراتب موجود (`province_id / county_id / district_id`)
دقیقاً همان کاری را می‌کند که یک `org_id` می‌کرد — و با ساختار
واقعی آموزش‌وپرورش ایران هم می‌خواند.

**اگر `org_id` اضافه شود:**

| مشکل | چرا |
|---|---|
| **دو منبع حقیقت** | مدرسه هم `province_id` دارد هم `org_id` — کدام معتبر است؟ |
| **ناسازگاری خاموش** | اگر `org_id` با `district_id` نخواند، کدام برنده است؟ هیچ‌جا مشخص نیست |
| **حجم** | `db` الان ۴٫۷MB از سقف ۵MB است؛ فیلد تازه روی ۶ مدرسه ناچیز است ولی در مقیاس ملی نه |
| **کد مرده** | تا روز سرور هیچ مصرف‌کننده‌ای ندارد — و کد بی‌مصرف پوسیده می‌شود |

⚠️ **قاعدهٔ ضد مهندسی‌زدگی (اصل پنجم):** «نبودِ یک کنترل به‌خودی‌خود
ایراد نیست.» اینجا هم: نبودِ `org_id` ایراد نیست، چون کاری که
انتظار می‌رود از آن، **از قبل** با `province_id` انجام می‌شود.

### آنچه به‌جایش پیشنهاد می‌شود

اگر روزی سطحی بالاتر از استان لازم شد (مثلاً «وزارت» یا چند
کشور)، راه درست افزودن یک سطح به **همان زنجیرهٔ موجود** است:
`districts → counties → provinces → [ministries]`. الگویش از قبل
هست و تکرارش هزینه‌ای ندارد.

## تصمیمِ قفل‌شده (۱۴۵/۰۶/۱۵)

**سرویسِ ذخیره‌سازیِ فایل (تکالیف، فایل‌هایِ کلاسِ مجازی، تصویر/صوت/ویدیو/PDF)
وقتی لازم شد، **آروان‌کلاود Object Storage** باشد** — با بستهٔ پایهٔ
**همیشه‌رایگان (۵ گیگابایت فضا + ۲۰ گیگابایت ترافیک در ماه)**؛ مصرفِ
اضافه بر اساسِ مصرف (PAYG).

## چرا این انتخاب (خلاصهٔ موجه‌سازی)

| معیار | آروان‌کلاود | لیارا | MinIO خودمیزبان |
|---|---|---|---|
| هزینهٔ شروع | ✅ **صفر** (۵ گیگ رایگان دائمی) | ۲۰ گیگ ≈ ۳۵٬۰۰ تومان/ماه | صفر (ولی دیسک/سرور جدا) |
| پیچیدگیِ عملیاتی | ✅ پایین (مدیرشده، SSL/دامنه/CDN خودشان) | پایین | 🔴 بالا (دیسک، SSL، مانیتورینگ، SLA — همهٔ ما) |
| جابجاییِ آینده | S3-compatible — تعویض = endpoint/کلید | S3-compatible | S3-compatible |
| یکپارچگیِ CDN | ✅ بومیِ آروان | ✅ بومیِ لیارا | جدا |
| دوامِ داده روی دیسکِ واحد | ✅ مدیرشده | ✅ مدیرشده | 🔴 بدونِ erasure-coding = ریسکِ از دست رفتنِ کامل |

پایهٔ قفل: تا حجمِ واقعیِ پایلوت (چند مدرسه، چند گیگ فایل در ماه)
فرا رسد، **۵ گیگ رایگان کافی است و هزینهٔ صفر = کمتر وابستگیِ مالی
قبل از اولین مشتری**. سه‌تایِ گزینه S3-compatible‌اند، پس این قفل
**دستِ ما را نمی‌بندد**: اگر روزی گران/کم‌ظرفیت شود، جابه‌جایی
فقط تعویضِ endpoint و کلید است — نه بازنویسیِ کد.

## شرایطِ بازنگریِ صریح (قفلِ بازنگری‌پذیر)

این قفل بازنگری می‌شود **فقط** اگر یکی از این‌ها برقرار شود:
1. **حجم بیش از ۵ گیگ** یا **ترافیک بیش از ۲۰ گیگ در ماه** شود
   (آستانهٔ رایگان تمام‌شده)؛
2. هزینهٔ PAYGِ آروان برایِ حجمِ واقعی‌مان **گران‌تر از لیارا یا
   MinIO** شود (مقایسهٔ تازه با اعدادِ کنسول، نه اعدادِ ۱۴۵/۰۶/۱۵)؛
3. نیازِ فنیِ جدیدی (مثلاً SLAِ خاص، منطقهٔ جغرافیاییِ خاص) آروان
   را حذف کند.

تا آن‌وقت: هیچ کدِ دیگری برایِ ذخیره‌سازیِ فایل نوشته نمی‌شود
(امروز فایل‌ها در IndexedDBِ سمتِ کاربر‌اند و رکوردِ ارجاع در
پایگاهِ داده — درست مطابقِ وضعیتِ فعلی).

# ضمیمهٔ الف — مقیاس کشوری در برابر `localStorage`

> تحلیل معماری برای تصمیم‌گیری. دور ۴۶ · نویسنده: احمد
> **این سند کد نیست؛ سه مسیر را می‌سنجد تا انتخاب آگاهانه شود.**

## ۱. مسئله در یک جمله

هدف پروژه **سطح کشوری** است، ولی معماری امروز داده را در
`localStorage` **هر مرورگر** نگه می‌دارد. این دو با هم جمع
نمی‌شوند و مشکل در یک جا خودش را نشان می‌دهد: **داشبورد تجمیعی
رئیس اداره**.

## ۲. چرا معماری فعلی ذاتاً کافی نیست

امروز صفحهٔ `officedash` کار می‌کند و آمار چند مدرسه را نشان
می‌دهد — ولی **فقط چون همهٔ مدارس در یک `db` واحدِ نمونه‌اند**.

در استقرار واقعی این‌طور نیست:

```
مرورگر مدیر مدرسهٔ الف  →  localStorage الف  →  فقط دادهٔ الف
مرورگر مدیر مدرسهٔ ب   →  localStorage ب   →  فقط دادهٔ ب
مرورگر رئیس اداره      →  localStorage خودش →  ❓ هیچ
```

`localStorage` به **مبدأ (origin) + دستگاه** بسته است. مرورگر
رئیس اداره هیچ راهی به دادهٔ مدارس ندارد. یعنی:

🔴 **`officeScopeSchools()` در دمو درست کار می‌کند و در واقعیت
هیچ‌چیز برنمی‌گرداند.** این یک باگ نیست — محدودیت ذاتی معماری
است.

سه پیامد دیگر همین ریشه:
- **سقف ~۵MB** برای هر مرورگر. یک مدرسهٔ ۵۰۰ نفره امروز ۴٫۷MB
  می‌گیرد؛ اداره‌ای با ۵۰ مدرسه اصلاً جا نمی‌شود.
- **پاک‌کردن حافظهٔ مرورگر = نابودی کل دادهٔ مدرسه.**
- **کاربر دو دستگاهی** (مدیر در مدرسه و خانه) دو دادهٔ متفاوت
  می‌بیند.

## ۳. سه مسیر ممکن

### مسیر الف — لایهٔ سرور مرکزی از همین حالا

سرور + پایگاه دادهٔ واقعی؛ مرورگر فقط نما می‌شود و
`localStorage` به کش آفلاین تنزل می‌یابد.

| | |
|---|---|
| **حجم کار** | 🔴 بسیار زیاد — ۲ تا ۴ ماه |
| **ریسک فنی** | متوسط؛ مسیرش شناخته‌شده است |
| **ریسک پروژه** | 🔴 **بالا** — دمو ماه‌ها بلااستفاده می‌شود |
| **حل مسئله** | ✅ کامل |

⚠️ زیرساختش تا حد خوبی آماده است: `00-data-layer.js` تنها دروازهٔ
داده است و `Api`/`enqueueOp` نوشته شده‌اند. یعنی «فقط درونشان به
`fetch` تبدیل شود» — همان چیزی که در دور ۲۸ برایش طراحی شد.

🔴 **ولی چهار مسدودکنندهٔ `TODO_BEFORE_PRODUCTION.md` هم باید با
هم حل شوند** (bcrypt، احراز هویت سرور، پایگاه داده، بررسی نقش).
نمی‌شود سرور زد و امنیت را عقب انداخت.

### مسیر ب — `localStorage` بماند + استخراج دوره‌ای برای اداره

هر مدرسه محلی می‌ماند. یک «خروجی تجمیعی» می‌گیرد (فایل JSON
کوچک) و رئیس اداره واردشان می‌کند.

| | |
|---|---|
| **حجم کار** | 🟢 کم — ۱ تا ۲ هفته |
| **ریسک فنی** | کم |
| **ریسک پروژه** | 🟢 کم — چیزی خراب نمی‌شود |
| **حل مسئله** | ⚠️ **نیمه** |

**چه چیزی حل می‌شود:** رئیس اداره آمار می‌بیند. حجم مسئله‌ای نیست
چون فقط **خلاصه** منتقل می‌شود نه رکوردها (برآورد: هر مدرسه چند
کیلوبایت).

**چه چیزی حل نمی‌شود:**
- 🔴 داده **کهنه** است — به‌روزرسانی دستی و دوره‌ای
- 🔴 وابسته به **همکاری مدیر مدرسه**؛ اگر نفرستد، اداره کور است
- 🔴 مسائل بنیادی (پاک‌شدن حافظه، دو دستگاه، سقف ۵MB) دست‌نخورده
- 🔴 «مقیاس کشوری» با انتقال دستی فایل معنا ندارد

⚠️ **این مسیر یک پل است نه مقصد.** اگر انتخاب شود، باید صریح
گفته شود که موقت است — وگرنه سه سال بعد کسی می‌پرسد چرا سامانهٔ
ملی با ایمیل فایل رد و بدل می‌کند.

### مسیر ج — سرور فقط برای تجمیع، نه برای همه‌چیز

مسیر میانه: مدرسه محلی و آفلاین‌اول می‌ماند، ولی یک **سرویس
کوچک تجمیع** می‌گیرد که هر شب فقط **آمار خلاصه** را می‌فرستد
(نه رکورد دانش‌آموز).

```
مدرسه (localStorage)  ──[شبانه، خودکار]──▶  سرور آمار  ──▶  اداره
        دادهٔ کامل محلی می‌ماند              فقط شمارنده‌ها
```

| | |
|---|---|
| **حجم کار** | 🟡 متوسط — ۳ تا ۵ هفته |
| **ریسک فنی** | کم — سرور فقط `POST` می‌گیرد و جمع می‌زند |
| **ریسک پروژه** | 🟢 کم — دمو دست‌نخورده می‌ماند |
| **حل مسئله** | ✅ برای اداره کامل · ⚠️ بقیه نه |

**مزیت ویژه‌ای که دو مسیر دیگر ندارند:**

🟢 **بار امنیتی‌اش بسیار کمتر است.** چون هیچ دادهٔ فردی منتقل
نمی‌شود (نه نام، نه کد ملی، نه نمره — فقط «۴۲۰ دانش‌آموز، میانگین
حضور ۹۳٪»)، مسائل حریم خصوصی و رضایت والدین **اصلاً پیش
نمی‌آیند**. مسیر الف باید همهٔ آن‌ها را حل کند.

🟢 **پله‌ای است.** همان سرویس بعداً می‌تواند به سرور کامل رشد کند؛
کار دورریز نیست.

**چه چیزی حل نمی‌شود:** پاک‌شدن حافظهٔ مرورگر، دو دستگاه، سقف
۵MB — همه سر جایشان می‌مانند.

## ۵. جمع‌بندی تحلیلی

**هیچ‌کدام «درست» یا «غلط» نیستند؛ پاسخ به یک پرسش بیرونی بستگی
دارد:** آیا این پروژه در ۶ ماه آینده کاربر واقعی می‌گیرد یا
همچنان دمو می‌ماند؟

- **اگر دمو می‌ماند** ⇒ مسیر ب کافی است. پول و وقت را روی
  زیرساختی که کاربر ندارد خرج نکنید.
- **اگر کاربر واقعی می‌آید** ⇒ مسیر الف ناگزیر است، چون چهار
  مسدودکنندهٔ امنیتی هم همان موقع باید حل شوند.
- **اگر مطمئن نیستید** ⇒ مسیر ج. کمترین پشیمانی را دارد: مسئلهٔ
  فوری (اداره) را حل می‌کند، دمو را نمی‌شکند، بار حریم خصوصی
  ندارد، و اگر بعداً الف لازم شد دورریز نیست.

⚠️ **یک نکته که در هر سه مسیر صادق است:** تا وقتی رمزها متن ساده
و احراز هویت سمت مرورگر است، **هیچ داده‌ای نباید از دستگاه خارج
شود**. حتی آمار تجمیعیِ مسیر ج، پیش از رفتن به شبکه، به یک

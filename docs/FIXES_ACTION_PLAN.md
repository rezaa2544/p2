## ۴. شکاف‌های معماری (غیرفوری) — پیشنهاد برای هر مورد

> این‌ها «نقص» نیستند؛ مرزهای آگاهانه محصول‌اند. هر پیشنهاد در قالب: وضعیت فعلی ← پیشنهاد ← مراحل ← پیش‌نیاز/ریسک. ترتیب پیشنهادی اجرا در انتهای بخش.

### ۴.۱ pull/bootstrap عمومی (خواندن از سرور)

- **وضعیت فعلی:** نوشتن‌ها به سرور می‌روند (`/api/sync`) ولی خوانش‌های کلاینت از `db` محلی (دمو) است؛ `/api/v1/bootstrap` فقط بسته شروع نقش‌محور می‌دهد، نه pull عمومی؛ در بوتِ حالت سرور هم جهان دمو تولید می‌شود.
- **پیشنهاد:** pull افزایشی نسخه‌دار: سرور برای هر کالکشن `version` نگه می‌دارد؛ کلاینت با `since` (آخرین نسخه دیده‌شده) فقط دلتا می‌گیرد؛ بوت اول = snapshot کاملِ scope + سپس دلتا.
- **مراحل:** (۱) قرارداد `GET /api/v1/pull?since=&collections=` + نسخه‌گذاری سرور در `apply`؛ (۲) کلاینت: جایگزینی امن `db` (snapshot در `applySnapshot` موجود است — بازاستفاده شود) + ادغام دلتا بدون گم‌کردن opهای صف‌نشده؛ (۳) پرچم مهاجرت: تا pull کامل نشده، خوانش محلی می‌ماند (بدون قطعی)؛ (۴) تست: سناریوی دوموبایلی (ثبت در A ← pull در B).
- **پیش‌نیاز/ریسک:** بزرگ‌ترین تغییر معماری فهرست؛ ریسک اصلی «خواندنِ تازه + نوشتنِ در صفِ مبتنی بر خوانشِ کهنه» → نیازمند سیاست base_version در خوانش (ادامه R95). برآورد: ۲–۳ هفته.

### ۴.۲ بانک و پرداخت واقعی

- **وضعیت فعلی:** «پرداخت آنلاین» و `ref='SUB-'+ts` شبیه‌سازی کلاینتی است؛ ثبت واقعی فقط توسط مدیر؛ این همان **تنها تصمیم باز محصول** کل پروژه است.
- **پیشنهاد:** (الف) تصمیم محصول اول: کدام درگاه (شاپرک مستقیم/زرین‌پال/...) و برای کدام جریان (اشتراک ولی؟ شهریه آنلاین؟ هر دو؟). (ب) معماری: ساخت تراکنش سمت سرور → هدایت به درگاه → callback امن (امضای درگاه + idempotency روی `authority`) → نشستن روی `subscription_payments`/`installments` فقط از مسیر سرور؛ کلاینت هرگز وضعیت پرداخت را مستقیم ننویسد (گسترش `WRITE_PERMS`: این دو کالکشن برای ولی فقط‌خوان می‌ماند).
- **مراحل:** تصمیم محصول ← سند قرارداد درگاه ← sandbox درگاه ← پیاده‌سازی callback + مغایرت‌گیری روزانه ← تست نفوذ مسیر پرداخت (دستکاری مبلغ در کلاینت باید بی‌اثر باشد).
- **پیش‌نیاز/ریسک:** نیازمند قرارداد تجاری و نماد/مجوز؛ ریسک امنیتی بالا (مبلغ فقط سمت سرور). برآورد پس از تصمیم: ۱–۲ هفته.

### ۴.۳ SMS/OTP واقعی

- **وضعیت فعلی:** `server/sms.js` فقط `mock`/`dry-run` است (`PLAN_SMS_GATEWAY` گام‌های ۲–۵ باز)؛ OTP ورود هم کد دمو/حافظه است؛ ناهماهنگی برآورد قطعه (کلاینت ۷۰ / سرور ۶۶).
- **پیشنهاد:** تکمیل همان طرح قفل‌شده: adapter واقعی در نقطه تعویض `providerSend` + وب‌هوک تحویل (DLR) برای وضعیت واقعی `sent/failed` + یکسان‌سازی ثابت قطعه (تک‌منبع: پاسخ درگاه، با fallback مستند ۷۰) + سقف/هزینه واقعی کیف پول.
- **مراحل:** انتخاب ارائه‌دهنده ← پیاده‌سازی adapter + DLR ← مهاجرت `teacher_sms`/یادآورها روی همان مسیر ← تست E2E با شماره واقعی آزمایشی ← قطع `PAYESH_DEMO_CODE` در تولید (همین حالا پیش‌فرض خاموش است).
- **پیش‌نیاز/ریسک:** قرارداد پنل پیامکی؛ ریسک هزینه (سقف روزانه همین حالا هست). برآورد: ۱ هفته.

### ۴.۴ استعلام هویت بیرونی (شاهکار/ثبت‌احوال)

- **وضعیت فعلی:** تطبیق کد ملی + تلفن فقط در برابر داده محلی/سرور خودی است؛ `PLAN_PHONE_AUTH` جدایی «پنل پیامکی» از «سامانه تطبیق» را قفل کرده ولی اتصال بیرونی نیست.
- **پیشنهاد:** سرویس تطبیق سمت سرور: در `login` (پس از صحت OTP) و در ثبت‌نام/اصلاح، استعلام (کد ملی ↔ تلفن ↔ نام) از سرویس بیرونی؛ نتیجه فقط boolean + علت، بدون ذخیره پاسخ خام (حریم خصوصی)؛ fallback: حالت آفلاین/قطعی سرویس = پذیرش موقت با پرچم «راستی‌آزمایی‌نشده» + صف بازبینی مدیر.
- **مراحل:** قرارداد سرویس ← adapter + مدارشکن (circuit-breaker) + حالت fallback ← آدیت (بدون PII) ← تست قطعی/تأخیر سرویس.
- **پیش‌نیاز/ریسک:** قرارداد دولتی/تجاری؛ ریسک حریم خصوصی (ذخیره حداقلی). برآورد: ۱–۲ هفته.

### ۴.۵ فایل مشترک بین دستگاه‌ها

- **وضعیت فعلی:** فایل تکلیف/کلاس مجازی فقط Blob در IndexedDB همان دستگاه است (سقف نرم ۲۰۰MiB)؛ `file_key` در JSON بدون آپلود، برای دستگاه دیگر بی‌معناست؛ تصمیم قفل‌شده: آروان‌کلاود Object Storage (۵GB رایگان).
- **پیشنهاد:** آپلود/دانلود با URL امضاشده کوتاه‌مدت: کلاینت از سرور URL می‌گیرد، مستقیم به آبجکت‌استور می‌فرستد/می‌گیرد؛ سرور فقط `file_key` + مالکیت + سیاست نگهداری را نگه می‌دارد؛ IndexedDB می‌ماند به‌عنوان کش آفلاین (نه منبع حقیقت).
- **مراحل:** باکت + کلیدها ← endpoint صدور URL امضاشده (با scope مدرسه) ← مهاجرت: آپلود تنبل Blobهای موجود در اولین اتصال ← سیاست حذف (حذف رکورد = حذف فایل، با تأخیر امن) ← تست: آپلود در A، مشاهده در B + حالت آفلاین (کش).
- **پیش‌نیاز/ریسک:** حساب ابری + دامنه؛ ریسک هزینه ترافیک (سقف + فشرده‌سازی تصویر). برآورد: ۱–۲ هفته.

### ۴.۶ تولید خودکار برنامه هفتگی

- **وضعیت فعلی:** `suggestSlots` و جابه‌جایی تک‌جلسه + تشخیص تداخل وجود دارد، ولی **حل کامل زمان‌بندی** (تخصیص همه جلسات با همه قیود) پیاده نشده.
- **پیشنهاد:** موتور دومرحله‌ای: (الف) تخصیص حریصانه با مرتب‌سازی محدودکننده‌ترین‌اول (دبیر کم‌بازده/کلاس پرجلسه اول)؛ (ب) بهبود تکراری (جابه‌جایی محلی برای رفع تداخل باقی‌مانده)؛ ورودی = همان قیود موجود (بازده دبیر، ظرفیت/اتاق کلاس، زنگ‌ها، روزهای کاری) + قیود جدید (سقف جلسات پیاپی دبیر، ترجیح صبح/عصر)؛ خروجی = پیش‌نمایش قابل ویرایش دستی (انسان تصمیم‌گیر نهایی).
- **مراحل:** مدل قیود از داده موجود ← موتور خالص (بدون UI) + تست واحد سنگین ← UI پیش‌نمایش/اعمال ← بنچمارک مدرسه بزرگ (۲۰ کلاس × ۳۰ دبیر < چند ثانیه).
- **پیش‌نیاز/ریسک:** بدون وابستگی بیرونی؛ ریسک «برنامه غیرقابل‌اجرا در عمل» → همیشه پیش‌نمایش + ویرایش دستی + دکمه بازگشت. برآورد: ۲ هفته.

**ترتیب پیشنهادی شکاف‌ها:** ۴٫۳ (پیامک) ← ۴٫۵ (فایل) ← ۴٫۴ (هویت) ← ۴٫۲ (پرداخت، پس از تصمیم محصول) ← ۴٫۱ (pull، بزرگ‌ترین) ← ۴٫۶ (زمان‌بندی، مستقل و قابل‌موازی‌سازی با هر کدام).

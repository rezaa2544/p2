# طرح: کلاس مجازی — نسخهٔ سبک (در انتظار تأیید)

> **وضعیت:** 🟡 سنجش انجام شده، طرح آماده است — **پیاده‌سازی منتظر تأیید شماست.**
> **محدودهٔ سبک:** پایش میزبان ویدیوی زنده نمی‌شود؛ فقط دو حالت:
> (الف) نشست «شاد» با لینک/زمان + اطلاع‌رسانی، (ب) فایل/ویدیوی ضبط‌شده
> + توضیح (غیرهمزمان) + سؤالات متنی زیر آن.
> **سنجش:** `tests/idb-probe.js` (اجرا: `node tests/idb-probe.js`)

---

## ۱. نتیجهٔ سنجش سازگاری IndexedDB (واقعی، headless)

| سؤال | پاسخ |
|---|---|
| در مرورگر واقعی indexedDB هست؟ | بله — همهٔ مرورگرهای مدرن (کروم/فایرفاکس/اسارت/اپ‌های وب‌ویو اندروید) |
| در jsdom (محیط smoke) هست؟ | **خیر** — تعریف‌نشده است؛ تست‌ها با fake کوچک (سطح ۵ عضو: open/transaction/put/get/delete) بالا می‌روند — این fake در همان سنجش پیاده و سبز شد |
| سطح API مورد نیاز | ۵ عضو؛ wrapper روی Promise؛ یک ماژول تک‌فایلی ~۱۲۰ خط — بدون فریم‌ورک، سازگار با معماری فعلی |
| الگوی «فایل در IDB + متادیتا در db» | round-trip put/get/delete در سنجش سبز شد؛ متادیتای هر نشست < ۳۰۰ بایت ⇒ localStorage سالم می‌ماند |

**استنتاج:** مشکل فنی‌ای که جلوی کار را می‌گیرد نیست. تصمیم «فایل به IndexedDB»
درست است؛ فقط باید wrapper مستقل از بستر باشد تا smoke با fake بپیچد.

## ۲. چرا IndexedDB ضروری است (اعداد)

- سقف localStorage ~۵ مگابایت؛ دادهٔ فعلی دمو ~۴٫۷ مگابایت است (به
  ثبت در `03-persistence.js` و سنجش دور ۴۲). حتی ۵۰ کیلوبایت فضای
  باقی‌مانده برای فایل/ویدیو کافی نیست.
- IndexedDB سقف مستقل و بزرگ دارد (در عمل تا ۵۰٪ دیسک مرورگر)؛
  فایل/ویدیو آنجا می‌نشیند و در localStorage فقط کلید + متادیتا.

## ۳. ساختار داده

### ۳.۱ فایل — IndexedDB (دیتابیس `payesh`، استور `vclass_files`)
کلید: `vclass:<id>`. مقدار: `File`/`Blob` خالص.

### ۳.۲ نشست — جدول `vclass_sessions` در db فعلی (JSON/localStorage)
```js
{
  id, school_id, class_id,
  type: 'shad' | 'video',
  title,                    // «مرور فصل ۳ ریاضی»
  // حالت (الف):
  shad_url: 'https://shad... ',  shad_time: 'ISO با ساعت',
  // حالت (ب):
  file_key: 'vclass:<id>',  file_name: '...mp4', mime, size,
  description,              // توضیح متنی زیر فایل
  created_at, created_by
}
```

### ۳.۳ سؤال — جدول `vclass_questions` در db فعلی
```js
{ id, session_id, student_id, body, created_at, answer, answered_at, answered_by }
```
متنی و کوچک ⇒ localStorage کافی است (فایل نیست).

## ۴. نماها

| پنل | مسیر | محتوا |
|---|---|---|
| دبیر | `vclass` (منوی «کار آموزشی») | فهرست کلاس‌های من؛ برای هر کلاس: «نشست جدید» (فرم: نوع شاد/ویدیو + عنوان + لینک/ساعت یا آپلود فایل)؛ فهرست نشست‌های کلاس با حذف + شمار سؤالات |
| دانش‌آموز | تب تازه «کلاس مجازی» در پروندهٔ من (`record`) | نشست‌های کلاسش: (الف) دکمهٔ «ورود به شاد» + ساعت؛ (ب) پخش فایل + توضیح + جعبهٔ سؤال؛ پاسخ دبیر زیر سؤال |
| ولی | تب «کلاس مجازی» در پروندهٔ فرزند (`children`) | همان نمای دانش‌آموز ولی **بدون آپلود/پاسخ‌گویی** — فقط دیدن نشست + (تصمیم باز ۲) |

## ۵. اطلاع‌رسانی

- ساخت نشست شاد یا ویدیو ⇒ پیامک از صف پیام اولیا با نوع **`event`**
  موجود («اولیای گرامی، در کلاس X نشست «عنوان» (لینک/فایل) ثبت شد…»)
  — بدون نوع جدید؛ با کلید `kinds.event` فعلی کنترل می‌شود.
- پاسخ سؤال دبیر ⇒ اعلان درون‌برنامه‌ای (جدول `notifications`) +
  در صورت روشن بودن، پیامک `event` اختیاری (کلید جدا در آینده).

## ۶. محدودیت و حاشیهٔ امن

- **سقف نرم:** ۲۰۰ مگابایت برای هر فایل + نمایش «X مگابایت از Y» با
  `navigator.storage.estimate()` (در نبودش فرض ۴۰۰ مگابایت).
- **حذف:** حذف نشست ⇒ `idbDel` هم‌زمان با `remove('vclass_sessions',…)`؛
  اگر IDB خراب باشد، حذف فایل خطا نمی‌دهد (ورودیِ آگاهانهٔ try).
- **امنیت:** اکشن‌های ساخت/حذف فقط `teacher` (مالک کلاس) و `manager`
  (جدول مجوزها در `30-authz.js`)؛ سؤال فقط خودِ دانش‌آموز؛ نماها
  scope شده (دبیر فقط کلاس‌های خودش — همان قرارداد `29-scope.js`).
- **پشتیبان‌گیری:** فایل‌های IDB وارد `buildBackup()` نمی‌شوند
  (متادیتا وارد می‌شود + یادداشت در گزارش بازیابی). ⚠️ تصمیم: برای
  نسخهٔ دمو/آفلاین کافی است؛ در اتصال سروری، آپلود به سرور جایگزین
  می‌شود (بند ۳.۱ نقشه‌راه).

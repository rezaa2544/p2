> هرگاه مالک بخواهد، با یک پیام در چت هر امضای به-نیابتی را رد/تغییر می‌دهد؛

## (ب) طرحِ جداسازیِ multi-tenant — **تنها موردِ واقعاً باز**

**وضعیتِ موجود (de-facto):** schema مشترک؛ کلیدِ مستأجر = ستونِ `school_id`
روی همهٔ جداولِ tenant-scoped؛ دفاع در لایهٔ کاربرد: `inScope` (policy.js —
لنگرِ جهش‌شده در server-mutations M2) + دروازهٔ fieldGate/ABAC (M15-04، CI سبز)
+ قاعدهٔ ۴۰۴-به‌جای-۴۰۳ (ثبت ۲.۴).

**گزینه‌ها:**

| گزینه | شرح | هزینه | ریسک |
|---|---|---|---|
| **A — وضع موجود** | فقط دفاعِ لایهٔ کاربرد | صفر | یک باگِ دروازه = نشتِ cross-tenant |
| **B — RLS به‌عنوان دفاعِ عمق‌دار (توصیه‌شده)** | سیاست‌های `ROW LEVEL SECURITY` روی جداولِ tenant-scoped با `current_setting('payesh.tenant')`؛ SQL سخت‌گیرانه حتی در برابرِ باگِ لایهٔ کاربرد | یک migration + تستِ cross-tenant | منفی: اتصال‌هایِ بدونِ SET = fail-closed (باید migration/backfill ابزارها را پوشش دهد) |
| **C — schema-per-tenant** | یک schema جدا برای هر مدرسه | مهاجرتِ سنگینِ داده + تغییرِ کلِ لایهٔ db | بالا؛ برایِ مقیاسِ فعلی بی‌دلیل |

**توصیه:** **گزینهٔ B** — دقیقاً همان چیزی که ردیف ۲۰ (M15-03) می‌خواهد؛ با
معماریِ فعلی سازگار (هیچ داده‌ای جابه‌جا نمی‌شود)، fail-closed، و لایهٔ
کاربردِ موجود را بی‌تغییر می‌گذارد (RLS = دفاعِ دوم، نه جایگزین).

**معیارهای پذیرشِ M15-03 (در صورتِ امضای B):**
1. migration با `ENABLE ROW LEVEL SECURITY` + `CREATE POLICY` روی همهٔ
   جداولِ tenant-scoped (فهرست از schema واقعی) + `FORCE ROW LEVEL SECURITY`
   برای مالکِ جدول؛
2. اتصالِ بدونِ SETِ tenant = **هیچ سطری** (fail-closed) — تستِ منفی؛
3. خودکارِ cross-tenant: کاربرِ مدرسهٔ ۱ در هیچ مسیری سطرِ مدرسهٔ ۲ را
   نمی‌بیند/نمی‌نویسد (سوئیتِ تازه، R96-الگو)؛
4. مهاجرت‌ها/ابزارهایِ مدیریتی با نقشِ `payesh_admin` (BYPASSRLS) — مستند؛
5. gateِ کارایی: p99 روی لیست‌هایِ صفحه‌بندی‌شده ≤ +۱۰٪ پیش از RLS
   (مقیاسِ وگای م15)؛
6. rollback = `DROP POLICY`/`DISABLE` در down.sql.

**نیازِ مالک:** ☐ امضای گزینهٔ B (یا A/C) — سپس M15-03 (ردیف ۲۰) در همان
راندِ بعدی اجرا و راستی‌آزمایی می‌شود.

## ۱. پروفایل بار (Workload Profile)

ورودی‌های رسمی مقیاس ملی — مبنای تمام محاسبات بخش‌های بعد:

| سنجه | مقدار | منبع/مشتق |
|---|---:|---|
| Registered Users | **۱۰٬۰۰۰٬۰۰۰** | هدف نقشه راه (§1) |
| DAU (تخمین) | **۶٬۰۰۰٬۰۰۰** | ۶۰٪ کاربران ثبت‌شده فعال روزانه |
| Peak Concurrent | **۲٬۵۰۰٬۰۰۰** | اوج صبح مهر (زنگ اول) |
| RPS پیک (صبح مهر) | **۲۰٬۰۰۰** | سناریوی بدترین روز سال |
| Writes/sec پیک | **۲٬۵۰۰** | حضور + نمره + پروفایل + sync push |
| Login Rate پیک | **۸۳۳ ورود/ثانیه** | ≈ هر کاربر یک ورود روزانه متمرکز در ۲ ساعت |
| Sync Rate | **۶M × ۱ sync/day** | هر کاربر فعال حداقل یک همگام‌سازی روزانه |
| Attendance writes | **۵۰M رکورد/سال** | ثبت حضور کلاس‌محور |
| Grades writes | **۲۸۸M رکورد/سال** | ≈ ۴۰ رویداد نمره به ازای هر دانش‌آموز |

### ۱.۱ مشتقات زمانی پروفایل

| کمیت | مقدار | نحوه محاسبه |
|---|---:|---|
| درخواست کل روزانه | ≈ ۱۵۰ میلیون | ۶M DAU × ۲۵ درخواست/کاربر/روز |
| RPS میانگین | ≈ ۱٬۷۳۶ | ۱۵۰M ÷ ۸۶٬۴۰۰ ثانیه |
| ضریب پیک/میانگین | ≈ ۱۱.۵× | ۲۰٬۰۰۰ ÷ ۱٬۷۳۶ — الگوی کلاسی سامانهٔ مدرسه‌ای (تمرکز در ۰۷:۰۰ تا ۰۹:۰۰) |
| همگام‌سازی میانگین | ≈ ۶۹/ثانیه | ۶M ÷ ۸۶٬۴۰۰ |
| همگام‌سازی پیک | ≈ ۸۳۳/ثانیه | ۵۰٪ همگام‌سازی‌ها در پنجرهٔ یک‌ساعتهٔ صبح |
| رشد دادهٔ نوشتنی | ≈ ۳۳۸M رکورد/سال | ۵۰M حضور + ۲۸۸M نمره |

**فرض توزیع بار:** ۴۰٪ ترافیک روزانه در پنجرهٔ ۰۷:۰۰–۰۹:۰۰؛ «بدترین روز» اولین صبح مهر است
(ورود هم‌زمان مدارس کل کشور). سناریوی پس‌از قطعی (صف همگام‌سازی انباشتهٔ کلاینت‌ها) باید
در Wave 18 جداگانه به‌عنوان **Spike** تست شود.

## ۳. مدل ظرفیت — محاسبات (Capacity Math)

### ۳.۱ بار دیتابیس (qps)

```text
RPS پیک                        = ۲۰٬۰۰۰
خطاهای کش‌نشده (۲۰٪، فرض ۸۰٪ اصابت) × ~۱.۲ کوئری/درخواست   ≈  ۴٬۸۰۰
پول‌های همگام‌سازی پیک (۸۳۳/ثانیه × ~۳ کوئری صفحه‌بندی‌شده)   ≈  ۲٬۵۰۰
نوشتن‌ها (۲٬۵۰۰/ثانیه × ~۲ کوئری شامل ممیزی/outbox)          ≈  ۵٬۰۰۰
────────────────────────────────────────────────────────
مجموع بار روی PostgreSQL                                     ≈ ۱۲٬۳۰۰ qps
```

### ۳.۲ اتصال‌ها — قانون لیتل

```text
C = QPS × t_query
C = ۱۲٬۳۰۰ × ۰.۰۰۴s (میانگین کوئری ایندکس‌دار) ≈ ۵۰ اتصال فعال
دمِ کوئری‌های کند: ۱٪ کوئری در ۲۰۰ms ⇒ +~۲۵ اتصال
────────────────────────────────
هدف: ≤ ۸۰ اتصال فعال ⇒ استخر ۱۰۰ در PgBouncer، max_connections = ۲۵۶
```

**قرارداد اتصال (مطابق `server/db.js` و `infra/postgres/`):** اپلیکیشن فقط از مسیر
`payesh` (نوشتن+خواندن) و `payesh-readonly` (رپلیکا) با پولینگ تراکنشی وصل می‌شود؛
اتصال مستقیم نودها به Primary ممنوع است.

### ۳.۳ حجم ذخیره‌سازی (برآورد ۵ ساله)

اندازهٔ ردیف‌ها بر اساس برآورد از `server/schema.sql` (میانگین + سربار ایندکس ≈ ×۱.۸):

| جدول | ردیف/سال | اندازهٔ ردیف | حجم سالانه با ایندکس | ۵ سال |
|---|---:|---:|---:|---:|
| حضور (attendance) | ۵۰M | ~۰.۲KB | ≈ ۱۸GB | ≈ ۹۰GB |
| نمره (grades) | ۲۸۸M | ~۰.۲۵KB | ≈ ۱۳۰GB | ≈ ۶۵۰GB |
| ممیزی/رویدادها | ~۲۵۰M | ~۰.۴KB | ≈ ۱۸۰GB (با نمونه‌برداری) | ≈ ۵۰۰GB |
| کاربران/مدارس/کلاس‌ها/ثبت‌نام | رشد تجمعی | — | — | ≈ ۲۰GB |
| **جمع دادهٔ آنلاین** | | | | **≈ ۱.۲۵ ترابایت** |
| سربار عملیاتی (WAL، bloat، vacuum، temp) | | | | ×۲ تا ×۳ |
| **دیسک پیشنهادی هر گره** | | | | **۴ ترابایت NVMe** |

WAL در پیک: ۲٬۵۰۰ نوشتن × ~۸KB ≈ ۲۰MB/s (در بازهٔ ۲ ساعتهٔ پیک ≈ ۱۴۰ گیگابایت/روز)
⇒ نگهداری ۷ روز آرشیو WAL برای PITR ≈ ۱ ترابایت — در بودجهٔ آرشیو لحاظ شده است.

### ۳.۴ حافظهٔ PostgreSQL

```text
مجموعهٔ داغ (حدودی):
  کاربران + ثبت‌نام‌ها                     ≈ ۱۰GB
  نمره‌های ۶۰ روز اخیر (۲۸۸M/۱۸۰×۶۰ ≈ ۹۶M) ≈ ۴۳GB
  حضور سال جاری                            ≈ ۱۸GB
  ممیزی ۳۰ روز اخیر                        ≈ ۸GB
────────────────────────────────
مجموعهٔ داغ ≈ ۸۰ گیگابایت
```

با ۱۲۸ گیگابایت RAM:(shared_buffers ۴۸ گیگابایت + کش صفحهٔ سیستم‌عامل ~۴۸ گیگابایت)
پوشش مجموعهٔ داغ ≈ ۱۰۰٪ ⇒ هدف **نرخ اصابت بافر ≥ ۹۵٪**. اگر در تست واقعی کمتر شد،
ارتقا به ۲۵۶ گیگابایت (نه قبل از آن — ضدالگوی «افزایش RAM به‌جای مقیاس افقی» §28).

### ۳.۵ IOPS

```text
نوشتن‌ها: ۲٬۵۰۰ × ~۵ صفحهٔ ۸کیلوبایتی (داده + ایندکس + WAL تقریبی) ≈ ۱۲٬۵۰۰ نوشتن
خواندن از دیسک: خطای بافر ~۱٪ × ۱۰٬۰۰۰ × ۲ صفحه               ≈    ۲۰۰ خواندن
پس‌زمینه (autovacuum/analyze/checkpoint)                        ≈ +۲۰٪
────────────────────────────────
پیک ≈ ۱۵٬۰۰۰ تا ۱۶٬۰۰۰ IOPS ⇒ پیشنهاد ۲۵٬۰۰۰ با سربار
```

### ۳.۶ بار Redis

```text
اصابت کش روی ۲۰٬۰۰۰ RPS (نرخ ۸۰٪)                ≈ ۱۶٬۰۰۰ خواندن/ثانیه
بررسی نشست/ابطال برای هر درخواست                  ≈ ۲۰٬۰۰۰ عملیات/ثانیه
شمارندهٔ ریت‌لیمیت + نوشتن‌های نشست               ≈ ۵٬۰۰۰ نوشتن/ثانیه
چرخهٔ OTP (صدور + تأیید)                          ≈ ۲٬۰۰۰ عملیات/ثانیه
────────────────────────────────
پیک ≈ ۴۵٬۰۰۰ عملیات/ثانیه — یک شارد سالم ≥ ۱۰۰هزار را تحمل می‌کند ⇒ سربار > ۲×
```

### ۳.۷ گره‌های اپلیکیشن

```text
هزینهٔ پردازش هر درخواست (فرض): ~۰.۶ میلی‌ثانیه CPU (API JSON صفحه‌بندی‌شده، بدون سریال‌سازی کل فروشگاه)
پیک: ۲۰٬۰۰۰ × ۰.۶ms = ۱۲ هستهٔ فعال ⇒ با سربار ×۲ ≈ ۲۴ هسته
با توان فرضی ۲٬۰۰۰ RPS بر نود: ۲۰٬۰۰۰ ÷ ۲٬۰۰۰ = ۱۰ نود + ۲ تحمل خطا = ۱۲ نود
اسپایک ۲× کوتاه‌مدت: با مقیاس خودکار تا ۲۰ نود پوشش داده می‌شود
```

> ⚠️ توان ۲٬۰۰۰ RPS بر نود **فرض طراحی** است؛ عدد واقعی باید از آزمون بار
> `docs/LOAD_TEST_PLAN.md` (در دست ساخت) بیرون بیاید. اگر نصف شد، ۲۴ نود لازم است.

### ۳.۸ شبکه

```text
خروجی API: ۲۰٬۰۰۰ × ۴KB = ۸۰MB/s ≈ ۶۴۰Mbps ⇒ ۲× ۱Gbps با سربار
استاتیک: ۲.۱ مگابایت × فشرده‌سازی ~۵× ≈ ۳۶۰KB؛ ۶M کاربر ≈ ۲.۲ ترابایت/روز از لبه؛
با اصالت لبهٔ ۹۵٪، خروجی اورجین ≤ ۵۰ گیگابایت/روز
```

### ۳.۹ جدول فرض‌های رسمی (تغییر هر فرض = بازنگری سند)

| فرض | مقدار | حساسیت |
|---|---|---|
| نرخ اصابت کش (هدف) | ≥ ۸۰٪ | افت به ۶۰٪ ⇒ بار دیتابیس ~۲× — نخستین هشدار |
| تعریف کوئری کند | > ۲۰۰ms | دمِ ۱٪ کوئری کند اتصال‌ها را تا +۲۵ بالا می‌برد |
| اندازهٔ میانگین پاسخ | ۴ کیلوبایت (صفحه‌بندی واقعی) | هرگز پاسخ «کل فروشگاه» — ممنوعیت §25 |
| میانگین زمان کوئری ایندکس‌دار | ۴ میلی‌ثانیه | بدون ایندکس مناسب، کل مدل اتصال باطل می‌شود |
| درخواست روزانهٔ هر کاربر | ۲۵ | ضریب پیک/میانگین از این عدد مشتق می‌شود |
| تمرکز همگام‌سازی | ۵۰٪ در یک ساعت صبح | سناریوی صف انباشته پس از قطعی جداگانه تست شود |
| توان هر نود | ۲٬۰۰۰ RPS | فقط با آزمون بار معتبر می‌شود |

## ۴. نقاط اشباع (Bottlenecks) و توصیهٔ مقیاس

ترتیب اشباع با رشد بار (بر اساس این مدل — باید در تست‌های استرس تأیید شود):

| # | نقطه اشباع | در چه باری؟ | نشانهٔ زودهنگام | توصیه |
|---:|---|---|---|---|
| ۱ | **درگاه SMS/OTP (خارجی)** | ورود > ~۱٬۰۰۰/ثانیه | صف ارسال، خطای موقت فراهم‌کننده | صف + توان‌دهی تدریجی (backoff) + سقف نرخ فراهم‌کننده؛ خارج از کنترل ما، پس زودتر اشباع می‌شود |
| ۲ | **اتصال‌های دیتابیس** (بدون پولر) | هر اسپایک ناگهانی | افزایش `payesh_db_pool_wait` | PgBouncer تراکنشی اجباری؛ اتصال مستقیم نودها ممنوع |
| ۳ | **مسیر نوشتن PG (IOPS/WAL)** | ~۲× نوشتن پیک (۵٬۰۰۰/ثانیه) | افت طولانی‌تر نوشتن، رشد `wal_bytes` | پارتیشن‌بندی حضور/نمره/ممیزی (Wave 10)، دسته‌بندی نوشتن در ورکرهای outbox |
| ۴ | **CPU گره‌های اپ** وقتی اصابت کش < ۶۰٪ | دو برابر شدن خطای کش | افت p95، رشد RPS به سمت دیتابیس | مقیاس افقی نودها (تا سقف ۲۰) + بهبود استراتژی کش (نه افزایش هسته) |
| ۵ | **حافظهٔ Redis** با TTL نامحدود | رشد بی‌کران کلیدها | `used_memory` نزدیک `maxmemory` | TTL الزامی برای همهٔ کلیدها (۱۵ دقیقه برای idempotency؛ ممنوعیت کلید بدون انقضا) |
| ۶ | **طوفان همگام‌سازی پس از قطعی** | اتصال هم‌زمان ۶ میلیون کلاینت | جهش ناگهانی `sync_pull` | jitter/backoff سمت کلاینت + صف مرده (پیاده‌شده در `27-sync.js`) |

**اصل مقیاس (مطابق §13 و §28 نقشه راه):** اول مقیاس افقی و ساختاری (پولر → رپلیکای
خواندن → پارتیشن‌بندی → شارژینگ استانی **فقط با اثبات بنچمارک**)؛ «افزایش RAM/هسته به‌جای
مقیاس افقی» ضدالگوی ممنوع است.

## ۵. اهداف SLO

مطابق §29 نقشه راه — این اعداد هدف اولیهٔ بنچمارک‌اند و پس از آزمون‌های ملی نهایی می‌شوند:

| شاخص | هدف | نحوهٔ اندازه‌گیری |
|---|---|---|
| تأخیر — میانه | **p50 < ۱۰۰ms** | هیستوگرام `payesh_http_request_duration` (`server/metrics.js`) |
| تأخیر — دم | **p95 < ۳۰۰ms** | همان هیستوگرام + قانون آلارم `HighLatency` |
| تأخیر — دمِ دور | **p99 < ۱s** | همان هیستوگرام |
| خطای سرور | **5xx < ۰.۱٪** (بودجهٔ خطا ≈ ۴۳ دقیقه/ماه) | شمارنده‌های وضعیت + قانون `HighErrorRate` |
| نرخ اصابت کش | **> ۸۰٪** | `payesh_cache_hit_rate` |
| موفقیت همگام‌سازی | ≥ ۹۹.۵٪ (بدون دادهٔ گم‌شده) | صف همگام‌سازی + شمارندهٔ تعارض‌ها |
| دسترس‌پذیری ورود (OTP) | ≥ ۹۹.۹٪ در ساعات مدرسه | نرخ تأیید ورود در برابر صدور |

**قانون گزارش‌دهی:** هر اجرای بار واقعی (Wave 18) باید این پنج عدد را در
`docs/LOAD_TEST_RESULTS.md` ثبت کند؛ هر انحراف = یک آیتم باز در `docs/OPEN_ITEMS.md`.

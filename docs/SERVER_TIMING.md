# چه زمانی سرور را بسازیم؟

> پاسخ به پرسش: «هنوز باید خیلی جاها را ویرایش کنیم؛ صبر کنیم یا الان سرور لازم است؟»
> تاریخ بررسی: ۱۴۰۴/۰۶/۱۲

---

## پاسخ کوتاه

**الان سرور نسازید.** ویرایش‌ها را تمام کنید.
اما **همین حالا سه چیز را قفل کنید** تا وقتی سرور ساخته شد، دوباره‌کاری نشود.

---

## چرا الان زود است؟ (شواهد، نه حدس)

### شاهد یکم: مدل داده هنوز در حال رشد است

سه دور اخیر توسعه، هر کدام یک مجموعهٔ دادهٔ تازه آوردند:

| دور | مجموعه‌های افزوده‌شده |
|---|---|
| چرخهٔ تحصیلی | `student_transfers` · `transfer_requests` · `student_archive` · `nid_conflicts` |
| تعامل با خانواده | `meeting_slots` |
| فرم و پیامک | `sms_wallet` · `sms_log` |

جمعاً **۳۹ مجموعهٔ داده**. اگر سرور را دور پنجم ساخته بودیم، تا امروز
**سه بار** مهاجرت پایگاه داده لازم می‌شد. هر مهاجرت یعنی نوشتن اسکریپت،
آزمودن روی دادهٔ واقعی، و ریسک از دست رفتن داده.

> قاعدهٔ ساده: **تا وقتی جدول جدید اضافه می‌کنید، سرور نسازید.**

### شاهد دوم: ۵۲ نقطهٔ نوشتن داده وجود دارد

در فایل اکشن‌ها ۵۲ فراخوانی درج/ویرایش/حذف هست. هر کدام در سرور به یک
مسیر با اعتبارسنجی و مجوز نیاز دارد. اگر منطق‌شان هنوز تغییر می‌کند،
هر تغییر یعنی ویرایش هم‌زمان در دو جا.

### شاهد سوم: هزینهٔ تأخیر تقریباً صفر است

معماری فعلی طوری است که ساختن سرور **دیرتر** هیچ چیزی را دشوارتر نمی‌کند:

```
عملیاتی که به صف سرور می‌رود:
{
  "uid": "op_mtkjx1ic_yyl5n9",
  "op": { "t": "ins", "c": "attendance", "data": { ... } },
  "status": "pending", "tries": 0,
  "user_id": 4, "school_id": 1
}
```

این قالب **عمومی** است: `t` نوع عمل و `c` نام مجموعه است. لایهٔ همگام‌سازی
هیچ‌جا نام جدول خاصی را نمی‌داند. یعنی افزودن مجموعهٔ جدید **هیچ تغییری**
در لایهٔ همگام‌سازی لازم ندارد — همین حالا هم هر ۳۹ مجموعه را پشتیبانی می‌کند.

---

## اما این سه چیز را همین حالا قفل کنید

اگر این‌ها را رها کنیم، ساختن سرور در آینده گران می‌شود.

### ۱. قالب عملیات همگام‌سازی — ✅ قفل شده

```
POST /api/sync   { ops: [ {uid, op:{t,c,data}, user_id, school_id}, ... ] }
پاسخ            { results: [ {uid, ok} | {uid, conflict} ] }
```
این قرارداد نباید عوض شود. هر قابلیت جدید فقط `c` تازه می‌آورد، نه قالب تازه.

### ۲. قرارداد بارگذاری اولیه — ✅ قفل شده

`GET /api/bootstrap` که محدودهٔ داده را **از توکن سرور** می‌گیرد، نه از
پارامتر کلاینت. توصیف‌گر محدوده در `29-scope.js` آماده است.

### ۳. مرز مجوزدهی — ✅ قفل شده

جدول نقش‌ها در `30-authz.js` تک‌منبع حقیقت است. سرور باید **همین جدول** را
مستقل پیاده کند. چون از منوی برنامه استخراج می‌شود، ناهماهنگی ممکن نیست.

---

## نشانه‌هایی که می‌گویند «حالا وقتش است»

سرور را وقتی بسازید که **همهٔ** این‌ها درست باشد:

- [ ] دو دور توسعهٔ پیاپی **بدون** افزودن مجموعهٔ دادهٔ جدید بگذرد
- [ ] فیلدهای رکوردهای اصلی (کاربر، کلاس، نمره، حضور) تثبیت شده باشد
- [ ] ویرایش‌های ظاهری و جریان کاری تمام شده باشد
- [ ] یک مدرسهٔ واقعی نسخهٔ دمو را دیده و بازخورد داده باشد

آخرین مورد از همه مهم‌تر است: بازخورد یک مدرسهٔ واقعی معمولاً چند تغییر
در مدل داده می‌آورد. بهتر است آن تغییرها **پیش از** ساخت سرور بیایند.

---

## خطر واقعی که باید مراقبش باشیم

خطر این نیست که سرور دیر ساخته شود. خطر این است که **نسخهٔ دمو عادت‌هایی
پیدا کند که در سرور شدنی نیست.** سه نمونه که باید همیشه رعایت شود:

| عادت خطرناک | چرا در سرور کار نمی‌کند | راه درست |
|---|---|---|
| خواندن مستقیم کل یک مجموعه در نما | سرور هرگز کل جدول را نمی‌فرستد | از توابع محدودهٔ نقش استفاده کن |
| تکیه بر ترتیب شناسه‌های محلی | شناسه را سرور می‌دهد | کلید یکتای عملیات ملاک باشد |
| اعتبارسنجی فقط در نما | کاربر می‌تواند دور بزند | اعتبارسنجی در لایهٔ داده |

این سه مورد در ممیزی دور پنجم بررسی و رعایت شده‌اند.

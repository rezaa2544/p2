## ۱. مقدمه و ضرورت گذار به معماری چندنمونه‌ای (Architectural Motivation)

در معماری تک‌نمونه‌ای (Single-Instance)، متغیرهای نشست، سقف‌های ریت‌لیمیتر (`__auth`)، کدهای پردازش‌شده (`__processed_uids`) و فایل‌های پشتیبان همگی روی حافظه محلی و دیسک یک سرور قرار دارند. 

برای پاسخگویی به **۵ میلیون کاربر فعال هم‌زمان و مقیاس ۱۰ میلیون دانش‌آموز**، سرورهای پردازش برنامه باید **کاملاً بدون وضعیت (Stateless)** شوند تا بتوان آن‌ها را به صورت افقی (Horizontal Auto-Scaling) در قالب ده‌ها یا صدها نمونه در کلاسترهای Kubernetes مستقر کرد.

```
                               ┌────────────────────────────────┐
                               │  توزیع‌کننده بار (Load Balancer) │
                               │       (HAProxy / Nginx)        │
                               └───────────────┬────────────────┘
                                               │
                 ┌─────────────────────────────┼─────────────────────────────┐
                 │                             │                             │
                 ▼                             ▼                             ▼
       ┌───────────────────┐         ┌───────────────────┐         ┌───────────────────┐
       │ Payesh Instance 1 │         │ Payesh Instance 2 │         │ Payesh Instance N │
       │    (Stateless)    │         │    (Stateless)    │         │    (Stateless)    │
       └─────────┬─────────┘         └─────────┬─────────┘         └─────────┬─────────┘
                 │                             │                             │
                 └─────────────────────────────┼─────────────────────────────┘
                                               │
                       ┌───────────────────────┴───────────────────────┐
                       │                                               │
                       ▼                                               ▼
         ┌───────────────────────────┐                   ┌───────────────────────────┐
         │       Redis Cluster       │                   │    Object Storage (S3)    │
         │ (Sessions, Limits, Locks) │                   │  (Backups, Media, Attach) │
         └───────────────────────────┘                   └───────────────────────────┘
```

## ۲. طراحی لایه داده‌های مشترک و سریع با Redis

کلاستر Redis وظیفه نگهداری و هماهنگی وضعیت‌های بلادرنگ (Real-Time Ephemeral State) را میان تمامی نمونه‌های سرور بر عهده دارد:

### ۲.۱. مدیریت نشست‌ها و ابطال توکن (Sessions & JWT Blacklist)
* **استراتژی Stateless با ابطال متمرکز:** توکن‌های JWT به صورت خودکفا (Self-Contained) اعتبارسنجی می‌شوند؛ اما شناسه‌های ابطال‌شده (`jti`) در هنگام خروج کاربر (`logout`) یا سلب دسترسی امنیتی (`enum_revoke`) درون Redis ذخیره می‌شوند.
* **طول عمر کلید (TTL):** معادل زمان انقضای توکن (۸ ساعت / ۲۸,۸۰۰ ثانیه). پس از اتمام TTL، کلید خودبه‌خود از حافظه حذف می‌شود (بدون نیاز به زباله‌روبی دستی).

### ۲.۲. سقف‌های ضد حملات و OTP توزیع‌شده (Distributed Rate Limiting)
* **الگوریتم پنجره لغزان (Sliding Window Log via Redis Sorted Sets):**
  - ثبت درخواست‌های ورود به ازای هر IP و هر شماره تلفن در پنجره‌های ۱۰ دقیقه‌ای.
  - اعمال سقف ارسال کد OTP (حداکثر ۵ ارسال در ۱۰ دقیقه به ازای شماره همراه).
  - اعمال سقف تلاش ورود (حداکثر ۲۰ ورود در ۱۰ دقیقه به ازای هر IP).
* **تأخیر تصاعدی (Exponential Backoff):** ذخیره تعداد تلاش‌های اشتباه متوالی (`login_fail`) در Redis و قفل تدریجی بدون نیاز به قفل سخت‌گیرانه دائمی.

### ۲.۳. یکتایی عملیات و مهار تکرار (Idempotency & Deduplication)
* **ثبت شناسه جهش (`uid`):** هر عملیات همگام‌سازی دارای یک شناسه یکتا است. سرورها با دستور اتمیک `SET payesh:sync:uid:<uid> 1 NX EX 86400` از اجرای دوباره عملیات تکراری در شرایط ارسال مجدد شبکه جلوگیری می‌کنند.

### ۲.۴. پیام‌رسانی و انتشار رویدادها (Redis Pub/Sub)
* همگام‌سازی فوری هشدارهای زنگ مدرسه (`bell_now`)، اعلان‌های فوری (`notifications`)، و باطل‌سازی کش‌های محلی سرورها از طریق کانال‌های انتشار/اشتراک Redis.

## ۳. طراحی ساختار نام‌گذاری و کلیدها در Redis (Redis Key Schema)

تمامی کلیدها با پیشوند سلسله‌مراتبی استاندارد `payesh:<محیط>:<ماژول>:<هدف>` سازمان‌دهی می‌شوند:

```
┌──────────────────────────────────────┬─────────────┬───────────┬───────────────────────────────────────────┐
│ الگوی کلید (Key Pattern)             │ ساختار داده │ طول عمر   │ کاربرد و توضیحات                         │
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:auth:revoked_jti:<jti>        │ STRING      │ 28800s    │ بلک‌لیست نشست‌های باطل‌شده (Logout/Revoke) │
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:auth:otp:<phone>              │ HASH        │ 300s      │ هش کد تایید OTP، تعداد تلاش و زمان ایجاد │
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:auth:cooldown:<phone>         │ STRING      │ 30s       │ فاصله زمانی اجباری میان دو درخواست پیامک │
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:auth:daily_cap:<day>:<phone>  │ STRING/INCR │ 86400s    │ سقف روزانه ارسال پیامک به یک شماره (Max 5)│
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:auth:ip_rate:<ip>             │ ZSET        │ 600s      │ پنجره لغزان درخواست‌های ارسال از هر IP    │
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:auth:login_rate_ip:<ip>       │ ZSET        │ 600s      │ پنجره لغزان درخواست‌های لاگین از هر IP   │
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:auth:login_fail:<phone>       │ HASH        │ 1800s     │ شمارنده شکست‌های متوالی و زمان رفع مسدودی│
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:sync:idempotency:<uid>        │ STRING      │ 86400s    │ جلوگیری از اجرای تکراری جهش‌های آفلاین   │
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:lock:<resource>:<id>          │ STRING (NX) │ 10s       │ قفل توزیع‌شده اتمیک (Redlock Algorithm)  │
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:cache:scope:<user_id>         │ STRING      │ 300s      │ کش خروجی برش داده‌های کاربر (Scope)      │
├──────────────────────────────────────┼─────────────┼───────────┼───────────────────────────────────────────┤
│ payesh:pubsub:broadcast              │ CHANNEL     │ —         │ انتشار سراسری رویدادها بین نمونه‌های سرور│
└──────────────────────────────────────┴─────────────┴───────────┴───────────────────────────────────────────┘
```

## ۴. لایه ذخیره‌ساز ابری اشیاء (Object Storage Layer — S3 / ArvanCloud)

برای حذف وابستگی به سیستم فایل محلی سرورها (Local Disk)، کلیه فایل‌های حجیم و فایل‌های پشتیبان به زیرساخت ذخیره‌سازی ابری مبتنی بر پروتکل S3 (مانند ابر آروان یا MinIO محلی) منتقل می‌شوند:

```
                                ┌───────────────────────────┐
                                │   کاربر (مرورگر / اپلیکیشن) │
                                └─────────────┬─────────────┘
                                              │
                 ┌────────────────────────────┴────────────────────────────┐
                 │ ۱. درخواست آپلود (دریافت Presigned URL)                  │ ۳. آپلود مستقیم فایل
                 ▼                                                         ▼
       ┌───────────────────┐                                     ┌───────────────────┐
       │  Payesh Instance  │                                     │   Object Storage  │
       │    (API Server)   │                                     │  (ArvanCloud S3)  │
       └───────────────────┘                                     └───────────────────┘
```

### ۴.۱. تفکیک باکت‌ها (Bucket Segregation)

```
┌──────────────────────────────┬──────────────────┬──────────────────────────────────────────────────┐
│ نام باکت (Bucket Name)       │ سطح دسترسی       │ کاربرد                                           │
├──────────────────────────────┼──────────────────┼──────────────────────────────────────────────────┤
│ payesh-backups-encrypted     │ Private (0600)   │ نسخه‌های پشتیبان دیتابیس با رمزنگاری AES-256     │
├──────────────────────────────┼──────────────────┼──────────────────────────────────────────────────┤
│ payesh-media-attachments     │ Private / Signed │ تصاویر پرونده، پیوست تکالیف و مدارک تحصیلی       │
├──────────────────────────────┼──────────────────┼──────────────────────────────────────────────────┤
│ payesh-static-assets         │ Public / CDN     │ بسته‌های آفلاین PWA، فونت‌ها و تصاویر عمومی      │
└──────────────────────────────┴──────────────────┴──────────────────────────────────────────────────┘
```

### ۴.۲. الگوی بارگذاری مستقیم بدون سربار سرور (Direct Upload via Presigned URLs)
برای جلوگیری از اشغال پهنای باند و حافظه سرورهای برنامه توسط فایل‌های چند مگابایتی:
1. کلاینت درخواست ایجاد لینک آپلود موقت ارسال می‌کند (`POST /api/media/upload-ticket`).
2. سرور بعد از احراز هویت و بررسی حجم مجاز، یک **Presigned PUT URL** با انقضای ۵ دقیقه‌ای صادر می‌کند.
3. کلاینت فایل را مستقیماً به باکت S3 ابری ارسال کرده و پس از اتمام، شناسه آبجکت را به سرور اطلاع می‌دهد.

## ۵. راهکار تاب‌آوری، دسترسی‌پذیری بالا و بازیابی پس از بحران (HA & Failover)

### ۵.۱. ساختار افزونه‌پذیر Redis (Redis Sentinel & Cluster Architecture)

```
        ┌─────────────────────────────────────────────────────────────────┐
        │                 Redis High Availability Cluster                 │
        ├──────────────────────┬──────────────────┬───────────────────────┤
        │ Master Node (Write)  │ ──(Replication)─►│ Replica Node 1 (Read) │
        └──────────┬───────────┘                  └───────────────────────┘
                   │                                         ▲
                   │                                         │
                   ▼                                         │
        ┌──────────────────────┐                  ┌──────────┴────────────┐
        │  Sentinel Quorum     │ ──(Auto Failover)│ Replica Node 2 (Read) │
        │  (3 Sentinel Nodes)  │                  └───────────────────────┘
        └──────────────────────┘
```

* **کشف خودکار خطا (Heartbeat & Quorum):** ۳ گره نگهبان (Sentinel) وضعیت مستر را رصد می‌کنند. در صورت قطعی مستر بیش از ۲ ثانیه، سنتینل‌ها رأی‌گیری کرده و به صورت آنی (زیر ۳ ثانیه) یکی از رپلیکاها را به مستر ارتقا می‌دهند.
* **تاب‌آوری در سمت کلاینت Node.js (ioredis Auto-Reconnect):** سرورهای برنامه پایش به صورت خودکار تغییر مستر را تشخیص داده و بدون قطع ارتباط کاربران به آدرس جدید سوئیچ می‌کنند.

---

### ۵.۲. استراتژی تخریب برازنده (Graceful Degradation / Fallback)

در شرایط فرضی بسیار نادر که ارتباط با Redis برای چند ثانیه قطع شود:

```
[قطع ارتباط با Redis] ──► [فعال‌سازی Circuit Breaker محلی] ──► [تایید آفلاین JWT + لاگ هشدار]
```

1. **اعتبارسنجی نشست‌ها:** توکن‌های JWT دارای امضای رمزنگاری‌شده معتبر درون‌خطی هستند؛ در زمان قطعی Redis، سرورها به صورت Fallback امضای HMAC-SHA256 و تاریخ انقضا (`exp`) را بدون چک کردن بلک‌لیست تایید می‌کنند تا سرویس متوقف نشود.
2. **ریت‌لیمیتر محلی:** تا زمان برقراری مجدد Redis، شمارنده محلی درون حافظه موقت هر پاد فعال می‌شود.
3. **ثبت وقایع اضطراری:** کلیه رخدادهای زمان قطعی در لاگ ممیزی (`audit`) ثبت‌شده و پس از بازگشت Redis همگام می‌گردند.

## ۶. نمونه پیاده‌سازی ماژول توزیع‌شده Redis (Zero-Regression Driver)

نمونه کد طراحی‌شده برای لایه سرویس Redis در سرورهای پایش:

```javascript
/* ==========================================================================
   server/redis.js — ماژول اتصال توزیع‌شده به Redis با پشتیبانی از Sentinel
   ========================================================================== */
'use strict';

class DistributedState {
  constructor(client) {
    this.client = client;
  }

  // ۱. بررسی و ثبت شناسه جهش برای جلوگیری از دوباره‌کاری (Idempotency)
  async checkAndSetUid(uid, ttlSeconds = 86400) {
    const key = `payesh:sync:idempotency:${uid}`;
    const result = await this.client.set(key, '1', 'EX', ttlSeconds, 'NX');
    return result === 'OK'; // true = عملیات تازه است، false = قبلاً پردازش‌شده
  }

  // ۲. مدیریت ریت‌لیمیتر پنجره لغزان
  async checkRateLimit(ip, maxRequests = 20, windowSeconds = 600) {
    const key = `payesh:auth:login_rate_ip:${ip}`;
    const now = Date.now();
    const clearBefore = now - (windowSeconds * 1000);

    const multi = this.client.multi();
    multi.zremrangebyscore(key, 0, clearBefore);
    multi.zcard(key);
    multi.zadd(key, now, `${now}-${Math.random()}`);
    multi.expire(key, windowSeconds);

    const results = await multi.exec();
    const count = results[1][1];
    return count < maxRequests;
  }

  // ۳. ثبت ابطال نشست (Revocation)
  async revokeJti(jti, ttlSeconds = 28800) {
    const key = `payesh:auth:revoked_jti:${jti}`;
    await this.client.set(key, String(Date.now()), 'EX', ttlSeconds);
  }

  // ۴. بررسی بلک‌لیست بودن نشست
  async isJtiRevoked(jti) {
    const key = `payesh:auth:revoked_jti:${jti}`;
    const exists = await this.client.exists(key);
    return exists === 1;
  }
}

module.exports = { DistributedState };
```

## ۷. نتیجه‌گیری و مزایای معماری جدید

با اجرای این طرح:
1. ظرفیت هم‌زمانی سامانه به صورت نامحدود و متناسب با تعداد پادهای سرور افزایش می‌یابد.
2. هیچ فایل سنگینی پهنای باند و منابع محاسباتی سرورهای اصلی را هدر نمی‌دهد.
3. در صورت خرابی یا راه‌اندازی مجدد هر نمونه از سرورها، **هیچ نشستی قطع نشده و هیچ داده‌ای مخدوش نخواهد شد**.

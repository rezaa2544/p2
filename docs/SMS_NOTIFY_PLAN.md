## ۱. معماری کلی — یک دروازه، سه ورودی

امروز پیامک از یک نقطه می‌رود (ارسال گروهی دستی). با این طرح سه
منبع تازه اضافه می‌شود، ولی **همه از یک دروازه** رد می‌شوند:

```
غیبت ─┐
نمره ─┼─→ notifyRequest()  →  [صف: pending]  →  تأیید مدیر ─→ ارسال
رویداد┘         │                                     │
                │              (اگر خودکار روشن)      │
                └──────────────────────────────────────┘
```

**چرا یک دروازه؟** چون سقف روزانه، کسر اعتبار، هشدار حجم و ثبت در
`sms_log` باید **یک‌جا** اعمال شوند. اگر هر ماژول خودش پیامک بفرستد،
سه ماه بعد یکی از آن‌ها از سقف رد می‌شود و کسی نمی‌فهمد چرا.

این دقیقاً همان الگوی `00-data-layer.js` است که برای دسترسی به داده
جواب داد.

### ماژول تازه

`src/js/45-sms-notify.js` — «اطلاع‌رسانی خودکار پیامکی»

طبق اصل دوم (تفکیک اصولی کد)، همهٔ منطق صف در یک فایل با سرفصل
فارسی. ماژول ۴۵ می‌شود (بعد از `44-*`)، در انتهای `_order.json`
چون به `smsParts`/`smsWalletOf`/`esc` وابسته است.

## ۲. مدل داده

### ۲.۱ جدول تازه: `notify_queue`

```js
{
  id, school_id,
  kind: 'absence' | 'grade' | 'event',   // نوع پیام
  student_id,          // موضوع پیام (برای رویداد عمومی: null)
  class_id,            // برای فیلتر و نمایش
  parent_ids: [17, 22],// گیرندگان — پدر و مادر هر دو
  body,                // متن نهایی؛ مدیر می‌تواند ویرایش کند
  parts,               // تعداد قطعهٔ پیامک (از smsParts)
  status: 'pending' | 'approved' | 'sent' | 'rejected' | 'cancelled',
  source_ref,          // شناسهٔ رکورد منشأ (attendance.id یا grades.id)
  source_hash,         // اثرانگشت وضعیت منشأ هنگام ساخت — بخش ۳.۳
  created_at,          // ISO کامل با ساعت
  created_by,          // چه کسی باعثش شد (دبیر)
  decided_at, decided_by,  // مدیر کِی و چه کسی
  auto: 0|1,           // در حالت خودکار ساخته شد؟
  correction_of        // اگر پیام اصلاحی است، شناسهٔ پیام اشتباه
}
```

⚠️ **`created_at` باید ساعت هم داشته باشد** — نه فقط تاریخ. کل
مکانیزم پنجرهٔ مهلت به این بند است. (رکوردهای موجود پروژه اغلب فقط
`todayISO()` دارند؛ اینجا `new Date().toISOString()` لازم است.)

### ۲.۲ تنظیمات — در `schools.notify_rules`

از الگوی موجود `schools.place_rules` تقلید می‌کنیم (دور ۳۸):

```js
NOTIFY_DEFAULTS = {
  enabled:        false,  // کل سامانه خاموش
  autoSend:       false,  // ← خواستهٔ ۲: پیش‌فرض خاموش
  graceMinutes:   20,     // پنجرهٔ مهلت اصلاح دبیر
  dailyCap:       300,    // سقف روزانهٔ پیامک
  bulkWarn:       50,     // هشدار ارسال دسته‌جمعی
  kinds: { absence:true, grade:false, event:true },
  gradeThreshold: 10      // فقط نمرهٔ زیر ۱۰ پیامک شود
}
```

**چرا `grade` پیش‌فرض خاموش است؟** پیامک نمره حجم بالایی می‌سازد
(هر آزمون × هر دانش‌آموز) و حساسیت خانوادگی دارد. مدرسه باید آگاهانه
روشنش کند. اگر مخالفید بگویید تا عوض کنم.

**چرا `graceMinutes` پیش‌فرض ۲۰ است؟** شما ۱۵ تا ۳۰ گفتید؛ وسط بازه
انتخاب شد و قابل تنظیم است.

## ۳. جلوگیری از اشتباه دبیر — چهار لایه

شما گفتید مهم‌ترین بخش است. هر چهار پیشنهادتان را بررسی کردم؛
**هر چهار را نگه می‌دارم** چون هرکدام حفرهٔ متفاوتی را می‌بندد:

| لایه | چه خطایی را می‌گیرد | اگر نباشد |
|---|---|---|
| ۳.۱ مرور نهایی | تیک اشتباه، جابه‌جایی ردیف | پیام غلط اصلاً ساخته می‌شود |
| ۳.۲ پنجرهٔ مهلت | دبیر خودش فوراً می‌فهمد | مدیر درگیر خطای جزئی می‌شود |
| ۳.۳ اصلاحیه | خطای دیرهنگام، پس از ارسال | خانواده با اطلاع غلط می‌ماند |
| ۳.۴ سابقهٔ تغییرات | اختلاف با اولیا | حرف دبیر مقابل حرف ولی |

### ۳.۱ صفحهٔ مرور نهایی پیش از ثبت

**تغییر رفتار:** امروز `att-set` هر تیک را فوراً `insert` می‌کند.
پیشنهاد: تیک‌ها در حافظهٔ موقت (`S.attDraft`) جمع شوند و با دکمهٔ
«تأیید و ثبت» یک‌جا نوشته شوند.

خلاصهٔ پیش از ثبت:

```
📋 مرور نهایی — دهم تجربی ۱ · ۱۲ شهریور ۱۴۰۵
   ۳ نفر غایب:  علی رضایی · مریم احمدی · حسن کریمی
   ۱ نفر تأخیر: زهرا موسوی
   ۲۶ نفر حاضر
   ⚠️ برای ۳ غایب پیامک به اولیا ساخته می‌شود.
   [ تأیید و ثبت ]   [ بازگشت و اصلاح ]
```

⚠️ **دام:** اگر دبیر وسط کار مرورگر را ببندد، پیش‌نویس نباید گم شود.
پیش‌نویس در `Store` ذخیره می‌شود، نه فقط در `S`.

⚠️ **سازگاری عقب‌رو:** `att-all` («همه حاضر») باید روی پیش‌نویس کار
کند نه مستقیم روی پایگاه‌داده — وگرنه دو مسیر ناهماهنگ می‌شود.

### ۳.۲ پنجرهٔ مهلت اصلاح — و مشکلی که باید حل شود

🔴 **مانع فنی:** رکورد `attendance` مُهر زمان ندارد. نمی‌شود فهمید
غیبت ۵ دقیقه پیش ثبت‌شده یا سه روز پیش.

سه راه بررسی شد:

| راه | ارزیابی |
|---|---|
| افزودن `created_at` به `attendance` | ❌ رکوردهای موجود (۱۰٬۴۶۰ تا) مُهر ندارند و حجم `db` را بالا می‌برد — الان ۴٫۶۴MB از سقف ۵MB |
| خواندن زمان از دفترچهٔ تغییرات (`op.at`) | ⚠️ کار می‌کند ولی جست‌وجوی خطی در دفترچه، به‌ازای هر ثبت |
| ✅ **مُهر زمان روی خودِ رکورد صف** | صف تازه است و `created_at` دارد؛ مقایسه با «الان» کافی است |

**راه سوم انتخاب شد.** پنجرهٔ مهلت به **رکورد صف** بند است نه رکورد
حضور و غیاب:

- دبیر غیبت ثبت می‌کند → رکورد صف با `status:'pending'` و
  `created_at` دقیق ساخته می‌شود
- اگر ظرف ۲۰ دقیقه دبیر **همان** غیبت را اصلاح کند و
  `created_by === S.user.id` باشد → رکورد صف `cancelled` می‌شود،
  بی‌سروصدا و بدون دخالت مدیر
- پس از ۲۰ دقیقه، یا اگر شخص دیگری اصلاح کند → مسیر ۳.۳

⚠️ **دو شرط `&&` نه `||`:** هم درون پنجره، هم همان دبیر. اگر فقط
شرط زمان بگذاریم، مدیر هم می‌تواند بی‌رد پا پیام را حذف کند.

مزیت جانبی: صفر بایت به ۱۰٬۴۶۰ رکورد حضور و غیاب اضافه نمی‌شود.

### ۳.۳ اصلاحیهٔ خودکار

اگر پیام رفته و بعد وضعیت عوض شد:

```
اصلاحیه: علی رضایی در تاریخ ۱۲ شهریور غایب نبوده است.
پیام پیشین ما اشتباه بود. پوزش می‌خواهیم. — دبیرستان نمونه
```

**چطور تشخیص داده می‌شود؟** فیلد `source_hash`: اثرانگشت
`student_id + date + status` هنگام ساخت پیام. هر تغییر در رکورد
منشأ، هش تازه‌ای می‌دهد. اگر پیامی با `status:'sent'` وجود داشته
باشد که هشش با وضعیت فعلی نخواند ⇒ اصلاحیه لازم است.

**اصلاحیه از صف رد می‌شود یا مستقیم؟** پیشنهاد من: **همان قاعدهٔ
پیام اصلی**. اگر `autoSend` روشن است مستقیم، وگرنه صف مدیر — ولی با
نشان قرمز «اصلاحیه» و در **بالای** فهرست.

⚠️ **دام حلقهٔ بی‌نهایت:** اصلاحیه خودش نباید هش تولید کند، وگرنه
اصلاحیهٔ اصلاحیه ساخته می‌شود. رکوردهای دارای `correction_of` از
سنجش هش کنار گذاشته می‌شوند.

⚠️ **دام رفت‌وبرگشت:** اگر دبیر غایب→حاضر→غایب کند، نباید دو اصلاحیه
برود. اصلاحیه بر پایهٔ **آخرین وضعیت ارسال‌شده** ساخته می‌شود، و اگر
وضعیت به همان حالت پیام اولیه برگردد، اصلاحیهٔ معلق **لغو** می‌شود.

### ۳.۴ سابقهٔ تغییرات — ۹۰٪ آماده است

`applyOp` در `03-persistence.js:100` **از قبل** `op.by` و `op.at` را
روی هر تغییر می‌گذارد، و `36-audit-activity.js` نمایشش می‌دهد.

پس فقط یک نمای فیلترشده لازم است: در پروندهٔ دانش‌آموز، زیر برگهٔ
حضور و غیاب:

```
سابقهٔ این رکورد:
  ۱۲ شهریور ۰۸:۱۵ — آقای محمدی: ثبت «غایب»
  ۱۲ شهریور ۰۸:۳۱ — آقای محمدی: تغییر به «حاضر»  ← درون پنجرهٔ مهلت
```

⚠️ `op.by` **ادعای سمت مرورگر** است (قرارداد امنیتی: `op.by` با
`jwt.sub` سنجیده شود). تا روز اتصال سرور، این سابقه برای **شفافیت**
معتبر است نه برای **اثبات حقوقی**. در رابط کاربری نباید طوری نمایش
داده شود که انگار سند انکارناپذیر است.

## ۵. هزینه و صف ارسال

پاسخ کوتاه به پرسش شما: **بله، هم سقف روزانه و هم هشدار حجم لازم
است.** سه محافظ:

### ۵.۱ هشدار پیش از دسته‌جمعی (`bulkWarn`, پیش‌فرض ۵۰)

```
⚠️ ۱۲۷ پیام در صف تأیید است.
   برآورد مصرف: ۲۵۴ قطعه پیامک
   موجودی کیف:  ۸۴۰ قطعه
   پس از ارسال: ۵۸۶ قطعه
   [ تأیید و ارسال همه ]  [ انصراف ]
```

### ۵.۲ سقف روزانه (`dailyCap`, پیش‌فرض ۳۰۰)

پیام‌های بیش از سقف **رد نمی‌شوند** — با نشان «فراتر از سقف روزانه»
در صف می‌مانند تا مدیر آگاهانه تصمیم بگیرد.

⚠️ **چرا رد نمی‌کنیم؟** اگر روزی واقعاً ۴۰۰ غیبت باشد (مثلاً روز
برفی)، دور انداختن ۱۰۰ اطلاع‌رسانی بدتر از تمام‌شدن اعتبار است.
سقف یعنی **ترمز**، نه **دیوار**.

### ۵.۳ اعتبار ناکافی

منطق موجود `19-actions.js:566` بررسی موجودی دارد. برای صف باید
پیش از **ارسال** سنجیده شود نه پیش از **ساخت** — وگرنه پیام‌ها اصلاً
ساخته نمی‌شوند و مدیر نمی‌فهمد چه چیزی را از دست داده.

⚠️ **دام اتمی‌نبودن:** اگر مدیر ۱۲۷ پیام را تأیید کند و اعتبار وسط
کار تمام شود، نباید نیمی رفته و نیمی گم‌شده باشد. ارسال دسته‌ای در
`batchWrites` و به‌ترتیب؛ هرچه نرفت در صف با وضعیت `pending` می‌ماند.

## ۶. رابط کاربری

### صفحهٔ تازه: `notifyqueue` — «صف پیام‌های اولیا» (فقط مدیر)

```
📨 صف پیام‌های اولیا                    موجودی: ۸۴۰ قطعه

⚠️ حالت ارسال خودکار فعال است — پیام‌ها بدون تأیید شما می‌روند.  [خاموش کردن]

[ همه ] [ غیبت ۱۲ ] [ نمره ۳ ] [ رویداد ۱ ] [ 🔴 اصلاحیه ۱ ]

☐ | 🔴 اصلاحیه | علی رضایی | دهم تجربی ۱ | ۰۸:۳۱ | [نمایش] [ویرایش] [✓] [✗]
☐ | غیبت      | مریم احمدی | دهم تجربی ۱ | ۰۸:۱۵ | [نمایش] [ویرایش] [✓] [✗]

[ تأیید انتخاب‌شده‌ها ]  [ رد انتخاب‌شده‌ها ]
```

- **ویرایش متن پیش از تأیید** (خواستهٔ ۱) — پنجرهٔ ویرایش با شمارندهٔ
  زندهٔ قطعه، چون ویرایش مدیر ممکن است پیام را ۲ قطعه‌ای کند
- **دسته‌جمعی** (خواستهٔ ۱) — با هشدار ۵.۱

### هشدار همیشگی حالت خودکار (خواستهٔ ۲)

نوار قرمز در `renderShell` — **در همهٔ صفحات مدیر**، نه فقط صفحهٔ صف.
شما گفتید «تا فراموش نشه»؛ اگر فقط در صفحهٔ صف باشد، مدیری که سراغ
صف نمی‌رود هرگز نمی‌بیندش — و دقیقاً همان مدیری است که خودکار را
روشن کرده.

### گزارش روزانه (خواستهٔ ۲)

کارت در داشبورد مدیر: «امروز ۲۷ پیامک خودکار رفت — [مشاهده]».
پس‌رصد، نه پیش‌تأیید.

### تنظیمات

در تنظیمات مدرسه، بخش «اطلاع‌رسانی پیامکی». روشن‌کردن `autoSend`
پنجرهٔ تأیید صریح می‌آورد:

```
⚠️ با روشن‌کردن ارسال خودکار، پیام‌ها بدون بازبینی شما به اولیا
   می‌روند. خطای دبیر در حضور و غیاب مستقیم به خانواده اطلاع
   داده می‌شود.
   [ می‌پذیرم و روشن کن ]   [ انصراف ]
```

## ۷. آزمون‌ها

حداقل ۱۸ آزمون در `tests/smoke.js`:

**صف و تأیید** (۵): ساخت رکورد · تأیید تک · تأیید دسته‌جمعی ·
رد · ویرایش متن پیش از تأیید

**پنجرهٔ مهلت** (۴): لغو درون پنجره · **عدم** لغو پس از پنجره ·
**عدم** لغو توسط کاربر دیگر · مرز دقیق (دقیقهٔ ۲۰ و ۲۱)

**اصلاحیه** (۴): ساخت پس از تغییر · **عدم** ساخت برای پیام معلق ·
عدم حلقه (اصلاحیهٔ اصلاحیه) · رفت‌وبرگشت غایب→حاضر→غایب

**هزینه** (۳): هشدار حجم · رفتار سقف روزانه · اعتبار ناکافی وسط دسته

**امنیت و حریم خصوصی** (۲): هیچ کد ملی در هیچ قالبی ·
مدیر مدرسهٔ الف صف مدرسهٔ ب را نبیند

⚠️ **درس دور ۳۸:** آزمون‌ها روی دادهٔ نمونهٔ خام بی‌صدا سبز می‌شوند.
هر آزمون باید **شمارندهٔ خروجی** بسنجد (چند پیام ساخته شد؟)، نه فقط
نبود خطا. اگر صف صفر رکورد دارد، آزمون باید **بیفتد** نه رد شود.

## ۹. اثر بر حجم — سنجیده، نه حدس‌زده

حجم فعلی `db` = **۴٫۶۴MB** مقابل سقف ~۵MB. این طرح حجم اضافه می‌کند
و باید مراقب بود:

| قلم | برآورد |
|---|---|
| هر رکورد صف | ~۲۵۰ بایت (متن پیام بزرگ‌ترین بخش) |
| مدرسهٔ ۵۰۰ نفره، ۵٪ غیبت روزانه | ۲۵ رکورد در روز |
| یک سال تحصیلی (۱۸۰ روز) | ۴٬۵۰۰ رکورد ≈ **۱٫۱MB** |

🔴 **این از سقف رد می‌شود.** پس از همین ابتدا: رکوردهای `sent` و
`rejected` پس از **۳۰ روز** پاک‌سازی می‌شوند (خلاصه‌شان در `sms_log`
که از قبل هست باقی می‌ماند).

### ۹.۱ سنجش واقعی (پیش از گام ۱) — 🔴 برآورد غلط بود

| قلم | برآورد طرح | سنجش واقعی |
|---|---|---|
| هر رکورد صف | ۲۵۰ بایت | **۴۳۶ بایت** (۱٫۷×) |
| مدرسهٔ ۵۰۰ نفره، یک سال | ۱٫۱MB | **۱٫۸۷MB** |
| مدرسهٔ ۱۵۰۰ نفره، یک سال | — | **۵٫۶۱MB** (به‌تنهایی از سقف بیشتر) |
| با پاک‌سازی ۳۰ روزه | — | **۳۱۹KB** ✅ |

دو تصمیم اصلاحی از این سنجش:
۱. فیلدهای `null` ذخیره **نمی‌شوند** (۴۳۶ → ۳۶۰ بایت، ۱۷٪ صرفه).
۲. پاک‌سازی ۳۰ روزه از «خوب است داشته باشیم» به **الزام** تبدیل شد.

### ۹.۲ طول پیام — کشف تازه: نصف‌کردن هزینه

`smsParts` بررسی شد و درست است (۷۰ نویسه، `Array.from`). ولی
قالب‌های پیشنهادی طرح **۲ قطعه** درمی‌آمدند یعنی دو برابر هزینه:

| قالب | نسخهٔ طرح | نسخهٔ بازنویسی‌شده |
|---|---|---|
| غیبت | ۷۴ نویسه ⇒ ۲ قطعه | «غایب بود» ⇒ **۶۴ نویسه ⇒ ۱ قطعه** ✅ |
| تأخیر | ۷۳ نویسه ⇒ ۲ قطعه | «با تأخیر آمد» ⇒ **۶۹ نویسه ⇒ ۱ قطعه** ✅ |
| نمره | ۱۲۱ نویسه ⇒ ۲ قطعه | ۸۸ نویسه ⇒ ۲ قطعه |
| اصلاحیه | ۱۱۰ نویسه ⇒ ۲ قطعه | ۷۸ نویسه ⇒ ۲ قطعه |

غیبت پرتکرارترین پیام است؛ یک‌قطعه‌ای‌کردنش **۵۰٪ هزینهٔ پیامک
مدرسه** را کم می‌کند. حذف «\nدبیرستان نمونه» و کوتاه‌کردن جمله کافی بود.

⚠️ آزمون نگهبان با **طولانی‌ترین نام واقعی** می‌سنجد، نه نام کوتاه.

### ۹.۳ گیرندگان

توزیع `parent_links`: ۵۲۰ دانش‌آموز یک ولی، ۳ دانش‌آموز دو ولی
(میانگین ۱٫۰۱). هزینه = قطعه × گیرنده، پس در عمل ≈ تعداد پیام.

⚠️ **این اعداد برآوردند نه سنجش.** پیش از گام ۱، حجم واقعی یک رکورد
صف را با `JSON.stringify` می‌سنجم و اگر با برآورد نخواند، همین‌جا
گزارش می‌دهم. (درس دور ۳۶: بنچمارک تک‌محوره فریب می‌دهد.)

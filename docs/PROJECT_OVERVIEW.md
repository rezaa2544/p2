# نمای کلی پروژه پایش

## 1. پایش چیست؟

پایش یک سامانه مدیریت مدرسه با رابط فارسی/RTL، تقویم جلالی، نقش‌های چندگانه، مدیریت مدرسه و داده‌های آموزشی است. پروژه دو سطح اجرایی دارد:

- **Client / Offline distribution:** رابط وب ماژولار که با build به یک فایل مستقل `index.html` تبدیل می‌شود و برای سناریوی آفلاین طراحی شده است.
- **Server / Integrated platform:** سرویس Node.js برای API، احراز هویت، همگام‌سازی، دادهٔ PostgreSQL، cache/coordination با Redis، observability و عملیات پشتیبان‌گیری/بازیابی.

این تفکیک مهم است: «خروجی وب تک‌فایلی و آفلاین» به معنی «کل مخزن بدون backend» نیست.

## 2. حوزه‌های اصلی خدمت

- مدیریت چند مدرسه و کاربران
- نقش‌ها و مجوزهای تفکیک‌شده
- دانش‌آموز، کلاس و درس
- حضور و غیاب و نمرات
- برنامه هفتگی و تقویم جلالی
- اطلاعیه، زنگ و گزارش عمومی
- همگام‌سازی و حل تعارض
- احراز هویت و مدیریت نشست
- گزارش‌ها و قابلیت‌های مدیریتی
- اشتراک/Paywall برای برخی قابلیت‌ها
- API، سلامت، metrics و tracing
- backup/restore و مسیرهای DR
- قابلیت‌های امنیتی، audit و کنترل دامنهٔ داده

فهرست دقیق قابلیت‌ها را باید با کد، API reference و roadmap جاری تطبیق داد؛ این صفحه نقشهٔ مفهومی است نه ادعای کامل بودن.

## 3. معماری در یک نگاه

```
src/ + public/templates
        │
        ├── build.js ──> index.html  (offline distribution)
        │
        └── browser runtime

server/
  ├── HTTP/API + auth + routes
  ├── domain/data services
  ├── PostgreSQL (authoritative persistence)
  ├── Redis (cache/ephemeral/coordination)
  ├── workers/outbox/sync
  └── observability + DR

migrations/ ──> PostgreSQL schema evolution
authz/       ──> authorization model/contracts
tests/       ──> runtime/unit/integration verification
tools/       ──> build, validation, audit and operational tooling
docs/        ──> architecture, governance, roadmap and evidence
```

برای جزئیات، [ARCHITECTURE.md](ARCHITECTURE.md) و [REPOSITORY_MAP.md](REPOSITORY_MAP.md) مرجع بعدی هستند.

مدل authorization فعلی مخزن ۹ نقش اصلی دارد:

| نقش | نام فنی | مأموریت اصلی |
|---|---|---|
| مدیر کل سامانه | superadmin | مدیریت خود پلتفرم، مدارس، ادارات، تنظیمات، سلامت، عملیات و دسترسی‌های سطح بالا |
| اداره آموزش‌وپرورش | edu_office | دید تجمیعی و منطقه‌ای مدارس تحت پوشش، گزارش، نظارت و ابلاغ |

| دبیر | teacher | اجرای عملیات آموزشی کلاس‌های مجاز |
| دانش‌آموز | student | استفاده از خدمات آموزشی و مشاهده اطلاعات شخصی |

معاون، متصدی دفتر، حسابدار، مسئول خوابگاه و سایر عوامل اجرایی در مستندات محصول به‌عنوان personaهای کاری دیده می‌شوند؛ این‌ها الزاماً در مدل فعلی role مستقل authorization نیستند و باید با مدل دسترسی جاری تطبیق داده شوند.

### قرارداد نمایش پیشرفت قابلیت‌ها

درصد کنار هر قابلیت **شاخص پیشرفت مهندسی فعلی** است، نه درصد صرفاً «وجود فایل». این شاخص بر پایهٔ پیاده‌سازی، تست، یکپارچگی و شواهد اجرایی فعلی خوانده می‌شود.

- **🟢 100% ✓** = کامل پیاده‌سازی و تست شده و شواهد جاری کافی دارد.
- **🟢 90–99%** = عمدتاً کامل؛ فقط بخشی از استقرار/E4/یکپارچگی نهایی باقی است.
- **🟡 70–89%** = بخش اصلی پیاده‌سازی و تست شده، اما verification یا integration مهمی باز است.
- **🟠 40–69%** = پیاده‌سازی قابل‌توجه وجود دارد، ولی تکمیل یا اثبات عملیاتی باقی است.
- **🔴 1–39%** = اولیه/نیمه‌پیاده‌سازی/برنامه‌ریزی.
- **⬜ 0%** = پیاده‌سازی قابل اتکا ثبت نشده است.

**قانون تیک سبز:** فقط **100% ✓** تیک سبز می‌گیرد. وجود ماژول، route، migration یا مستندات به‌تنهایی تیک سبز ایجاد نمی‌کند. تا بسته‌شدن Gate 8.2، هیچ درصدی به معنی Production Ready ملی نیست.

# 17. چرخه یک روز کاری مدرسه

**پیشرفت: 🟡 80%**

1. مدیر داشبورد و کارهای در انتظار را می‌بیند.
2. برنامه و زنگ جاری مشخص است.
3. دبیر کلاس خودش را می‌بیند.
4. حضور و غیاب ثبت می‌شود.
5. در صورت وجود الگوی غیبت، داده برای پیگیری در دسترس قرار می‌گیرد.
6. دبیر آموزش/تکلیف/نمره را ثبت می‌کند.
7. مدیر موارد نیازمند تأیید را می‌بیند.
8. در صورت الگوی خطر، مشاور وارد صف پیگیری می‌شود.
9. ولی اطلاعات مجاز فرزند را می‌بیند.
10. اعلان‌های لازم در کانال مربوط ارسال می‌شوند.
11. گزارش‌های مدرسه به‌روز می‌شوند.

# 19. معماری محصول از دید خدمات

Client:

src/js + styles + templates
→ build
→ index.html
→ browser/offline
→ local persistence
→ sync/conflict
→ Server API

Server:

Client
→ Node.js API
→ authentication
→ authorization/policy
→ domain routes/services
→ PostgreSQL به‌عنوان منبع حقیقت
→ Redis برای cache/ephemeral/coordination
→ worker/outbox/sync
→ observability/backup/DR

این تفکیک مهم است: «client تک‌فایلی و offline-first» به معنی «کل سامانه بدون backend» نیست.

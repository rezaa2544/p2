## ۲. پیاده‌سازی اسکریپت سناریوهای اصلی k6 (بند ۱)

### ۲.۱. سناریوی ورود پرحجم و اعتبارسنجی نشست (`scenarios/01-login.js`):

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Trend, Rate } from 'k6/metrics';

const loginDuration = new Trend('login_duration_ms', true);
const loginFailureRate = new Rate('login_failure_rate');

export default function () {
  const vu = __VU;
  const phone = `0912${String(vu % 1000000).padStart(7, '0')}`;
  
  // ۱. درخواست ارسال کد OTP
  const sendRes = http.post('http://api.payesh.ir/api/v1/auth/send-code', JSON.stringify({ phone }), {
    headers: { 'Content-Type': 'application/json' },
  });
  
  check(sendRes, { 'send-code status 200': (r) => r.status === 200 });

  // ۲. ورود با کد و کد ملی
  const loginPayload = JSON.stringify({
    phone: phone,
    code: '123456',
    national_id: '0012345678'
  });

  const t0 = Date.now();
  const res = http.post('http://api.payesh.ir/api/v1/auth/login', loginPayload, {
    headers: { 'Content-Type': 'application/json' },
  });
  loginDuration.add(Date.now() - t0);

  const ok = check(res, {
    'login status 200': (r) => r.status === 200,
    'has cookie': (r) => r.headers['Set-Cookie'] !== undefined
  });

  loginFailureRate.add(!ok);
  sleep(1);
}
```

## ۳. آزمون اشباع و شکست پایگاه‌داده (Database Saturation Test - بند ۲)

### ۳.۱. هدف و متدولوژی
افزایش تدریجی و مداوم تعداد کاربران فعال هم‌زمان (Ramping VUs) تا زمان رسیدن پردازنده دیتابیس به ۱۰۰٪ و شناسایی دقیق **نقطه شکست (Knee Point)**:

```
[ترافیک ورودی: ۱۰K ──► ۵۰K ──► ۱۰۰K ──► ۲۵۰K ──► ۵۰۰K RPS] ──► [شناسایی گلوگاه PostgreSQL]
```

```
┌────────────────────────────────────────────────────────────────────────┐
│                  منحنی پاسخ‌دهی دیتابیس در تست اشباع                  │
├────────────────────┬──────────────┬──────────────┬─────────────────────┤
│ ترافیک (RPS)       │ زمان p95     │ مصرف CPU دیت │ وضعیت سیستم         │
├────────────────────┼──────────────┼──────────────┼─────────────────────┤
│ ۵۰,۰۰۰ RPS         │ ۱۲ ms        │ ۲۸٪          │ 🟢 وضعیت کاملاً سبز  │
│ ۱۵۰,۰۰۰ RPS        │ ۲۸ ms        │ ۵۵٪          │ 🟢 پایدار و روان    │
│ ۳۰۰,۰۰۰ RPS        │ ۸۵ ms        │ ۷۸٪          │ 🟡 نزدیک به آستانه  │
│ ۴۵۰,۰۰۰ RPS        │ ۲۹۰ ms       │ ۹۴٪          │ 🟡 آستانه تحمل (SLO)│
│ ۵۵۰,۰۰۰+ RPS       │ > ۱۲۰۰ ms    │ ۱۰۰٪         │ 🔴 اشباع و Connection Drop│
└────────────────────┴──────────────┴──────────────┴─────────────────────┘
```

* **پارامترهای مورد پایش:** زمان انتظار در صف اتصالات (Connection Pool Wait Time)، قفل‌های ردیفی در جدول نمرات، و تاخیر همگام‌سازی دیسک WAL (Write-Ahead Log Flush Latency).

## ۴. آزمون تاب‌آوری در زمان قطع Redis (Redis Chaos & Fallback Test - بند ۳)

### ۴.۱. سناریوی آزمون آشوب (Chaos Engineering)
در حین اجرای بار سنگین ۱۰۰,۰۰۰ کاربر هم‌زمان، اتصال کلاستر Redis به طور ناگهانی قطع می‌شود (`docker pause redis-master` یا `iptables DROP`).

```
[ترافیک ۱۰۰,۰۰۰ کاربر فعال] ──► [قطع ناگهانی Redis] ──► [سنجش رفتار سرورهای پایش]
```

### ۴.۲. رفتارهای الزامی سیستم (Graceful Degradation Checklist):
1. **عدم بازگرداندن خطای 500 Internal Server Error:** سرورها بلافاصله Circuit Breaker داخلی را فعال کرده و ترافیک را مدیریت می‌کنند.
2. **تایید اعتبار نشست‌ها بدون وقفه:** توکن‌های JWT به صورت خودکفا با امضای رمزنگاری‌شده تایید می‌شوند.
3. **فعال‌سازی ریت‌لیمیتر محلی حافظه:** تا زمان بازگشت Redis، شمارنده‌های موقت درون حافظه هر پاد فعال می‌مانند.
4. **زمان بازیابی (Self-Healing):** پس از اتصال مجدد Redis، نودها در کمتر از ۳ ثانیه اتصال را بازسازی کرده و لاگ‌های اضطراری را تخلیه می‌کنند.

## ۵. آزمون ازدحام و تاخیر صف‌ها (Queue Lag & Scalability Test - بند ۴)

### ۵.۱. هدف آزمون
تزریق ناگهانی **۵۰۰,۰۰۰ پیامک و نوتیفیکیشن** در یک پنجره ۶۰ ثانیه‌ای و اندازه‌گیری سرعت تخلیه صف توسط ورکرها.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        شاخص‌های ارزیابی صف ورکرها                      │
├───────────────────────────────────┬────────────────────────────────────┤
│ حجم کل کارها (Job Influx)         │ ۵۰۰,۰۰۰ پیامک اطلاع‌رسانی اولیا    │
│ حداکثر تاخیر مجاز در صف (Queue Lag)│ کمتر از ۹۰ ثانیه برای کل صف        │
│ توان پردازش ورکرها (Throughput)    │ بیش از ۶,۰۰۰ پیامک در ثانیه (Jobs/s)│
│ مدیریت شماره‌های اشتباه (DLQ)     │ انتقال خودکار به Dead-Letter Queue │
```

## ۶. آزمون راه‌اندازی سرد و بازیابی از بحران (Cold Start & Warm-up Test - بند ۵)

### ۶.۱. شبیه‌سازی فاجعه (Disaster Recovery Simulation)
راه‌اندازی مجدد هم‌زمان تمام سرورهای برنامه و دیتابیس با **حافظه موقت (Cache) کاملاً خالی**:

```
[راه‌اندازی کلاستر با کش خالی] ──► [هجوم ترافیک صبحگاهی] ──► [اجرای اسکریپت Cache Warm-up]
```

### ۶.۲. معیارهای موفقیت در Cold Start:
* **زمان بازیابی کامل (RTO):** کمتر از **۶۰ ثانیه**.
* **مهار طوفان کش (Thundering Herd):** عدم افزایش خطای اتصال پایگاه‌داده به دلیل قفل‌های توزیع‌شده Singleflight.
* **بارگذاری ۱۰٪ مدارس داغ:** لود بیش از ۱۰,۰۰۰ مدرسه پرجمعیت در کش Redis پیش از پذیرش ترافیک عمومی.

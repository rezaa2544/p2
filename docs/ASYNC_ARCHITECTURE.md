# معماری ناهم‌زمان — پایش (ویو ۸)

> هدف: کارهای سنگین از مسیر درخواست بیرون بیفتند و هیچ رویدادی گم
> نشود. الگو: **Transactional Outbox + Worker**.

---

## ۱) نمای کلی

```
 تغییر داده (مثل حذف نرم)
        │
        ▼
 ┌──────────────────────────────┐        ┌─────────────────────────┐
 │ فروشگاه (اسنپ‌شات = منبع     │        │ جدول server_outbox       │
 │ حقیقت) — رویداد در همان       │ ─آینه→ │ (پستگرس؛ بهترین‌تلاش)    │
 │ ذخیرهٔ تغییر ثبت می‌شود        │        └─────────────────────────┘
 └──────────────┬───────────────┘
                │  صف درون‌فروشی
                ▼
 ┌──────────────────────────────┐
 │ کارگر (server/worker.js)     │  هر ۱ ثانیه (قابل تنظیم):
 │ • رویدادهای pending را می‌خواند│  - هندلرِ نوعِ رویداد را صدا می‌زند
 │ • موفق ⇒ processed            │  - کش/خارج‌ازمسیرِ درخواست انجام می‌شود
 │ • شکست ⇒ retry++ و در نهایت   │
 │   failed (بدون حذف رویداد)    │
 └──────────────────────────────┘
```

## ۲) چرا رویداد گم نمی‌شود؟

رویداد در **همان لحظه‌ای** که تغییر اصلی ثبت می‌شود وارد صف می‌شود و هر
دو در یک اسنپ‌شات ذخیره می‌گردند — یا هر دو هستند یا هیچ‌کدام. کرشِ
سرور بین «تغییر» و «پردازش» فقط پردازش را عقب می‌اندازد؛ پس از بالا
آمدن، کارگر از همان اسنپ‌شات ادامه می‌دهد. جدول پستگرس فقط آینه است
(اگر در دسترس نباشد، رفتار عوض نمی‌شود).

## ۳) چرخهٔ عمر رویداد

| وضعیت | معنا |
|---|---|
| `pending` | در صف پردازش (وضعیت اولیه؛ رویدادهای قدیمی بدون فیلد هم `pending` فرض می‌شوند) |
| `processed` | هندلر با موفقیت اجرا شد؛ `processed_at` ثبت شده |
| `failed` | پس از `maxRetries` تلاش (پیش‌فرض ۵، `PAYESH_WORKER_MAX_RETRIES`) — رویداد **حذف نمی‌شود**؛ برای بازرسی/تلاش دستی می‌ماند |

فیلدها: `status`, `retry_count`, `last_error`, `processed_at` (در حافظه +
ستون‌های جدول `server_outbox`).

## ۴) اجزا

| جزء | فایل | نقش |
|---|---|---|
| صندوق رویدادها | `server/outbox.js` | `append` (ثبت با وضعیت اولیه) و `mark` (به‌روزرسانی چرخهٔ عمر)؛ سقف ۱۰۰۰ رویداد |
| کارگر | `server/worker.js` | پیمایش `pending`ها، اعزام به هندلر، تلاش مجدد، نگهبان ورود دوباره؛ `tick()` برای تست قطعی |
| اتصال | `server/index.js` | ساخت کارگر پس از `createOutbox` + `worker.start()`؛ توقف در `exit/SIGTERM/SIGINT` |
| آینهٔ پستگرس | `tools/migrate-to-pg.js` | جدول `server_outbox` + ایندکس وضعیت |

### هندلرهای فعال امروز

| نوع رویداد | هندلر | کار |
|---|---|---|
| `*.deleted` (از `server/delete-service.js`) | باطل‌کردن کش مدرسه (`cache.invalidateCollection`) | خارج‌شدن کارِ پس‌از‌حذف از مسیر درخواست |

### افزودن هندلر تازه

```js
const worker = createWorker({
  store, outbox,
  handlers: Object.assign(handlers, {
    'report.generate': async (evt) => { /* ساخت گزارش از روی payload */ }
  })
});
```

قواعد هندلر:
- **ایدمپوتانت باشد** — امکان اجرای دوباره (پس از کرش) وجود دارد.
- سریع بماند؛ کارِ واقعاً سنگین را به زیرصف اختصاصی ببرید.
- خطا پرتاب کند = تلاش مجدد؛ پرتاب‌نکردن = `processed`.

## ۵) چه چیزهایی هنوز در مسیر درخواست‌اند و چرا

- **ارسال پیامک (`server/sms.js`):** قرارداد قفل‌شدهٔ «قفل ۸۱.۱»
  (همه‌یاش‌هیچ، ایدمپوتانس `(queue_id, parent_id)`، سقف روزانه، کسر
  اعتبار در همان لحظه). ناهم‌زمان‌کردنِ این مسیر نیازمند بازمهندسیِ
  قرارداد است و باید جداگانه (با تأیید ناظر) انجام شود — زیرساختِ
  اوت‌باکس/کارگرِ همین ویو پایهٔ آن کار خواهد بود.
- گزارش‌های سبک (`/api/public-report`) درجا پاسخ داده می‌شوند.

## ۶) پیکربندی

| متغیر | پیش‌فرض | معنا |
|---|---|---|
| `PAYESH_WORKER_INTERVAL_MS` | `1000` | فاصلهٔ تیک‌های کارگر |
| `PAYESH_WORKER_MAX_RETRIES` | `5` | سقف تلاش پیش از `failed` |

- **پراکندگی جغرافیایی:** نسبت استان‌ها مطابق جمعیت واقعی دانش‌آموزی (برای تست‌های تفکیک‌شدهٔ آینده).

### ۲.۳ روش بارگذاری (bulk load به PostgreSQL)

قرارداد ابزار مولد: **`tools/seed-national.js`** — ⚠️ این ابزار هم‌اکنون در `main` نیست و روی
شاخهٔ مرج‌نشدهٔ چت ۳ قرار دارد؛ ادغام آن پیش‌نیاز اجرای این بند است. الزامات قرارداد:

1. تولید قطعه‌قطعه (چانک) به صورت CSV/`COPY FROM` در دسته‌های ۵۰۰هزارردیفی؛ بدون تراکنش‌های غول‌پیکر.
2. بارگذاری در جداول مرحله‌ای؛ اعمال `CONSTRAINT`/ایندکس‌های پرهزینه **پس** از بارگذاری + `ANALYZE`.
3. مقادیر فقط از دامنهٔ مجاز `server/validate.js` (enumها) — دادهٔ نامعتبر یعنی باگ مولد.
4. کلیدها از سکانس‌های رسمی (ممنوعیت `max(id)+1` — §5 نقشه راه).
5. **قطعی (deterministic) با seed ثابت** تا هر اجرا دیتاست یکسان بدهد و نتایج قابل مقایسه باشند.
6. بودجهٔ زمانی: بارگذاری کامل < ۴ ساعت روی سخت‌افزار بخش ۵؛ گزارش نرخ ردیف/ثانیه.
7. **راستی‌آزمایی پس از بارگذاری (اجباری):** شمارش هر جدول، بررسی سلامت FK، صدک‌های توزیع
   اندازهٔ مدارس، نمونه‌برداری تصادفی ۱٬۰۰۰ رکوردی — خروجی در `LOAD_TEST_RESULTS.md`.

## ۳. سناریوهای تست

نرخ نوشتن در هر سناریو متناسب با نسبت RPS آن به پیک (۲٬۵۰۰ نوشتن/ث در ۲۰هزار RPS) تنظیم می‌شود.
ترکیب ترافیک در همهٔ سناریوها: ~۸۰٪ خواندن (صفحه‌بندی‌شده) / ~۱۲٪ نوشتن (حضور+نمره+پروفایل) /
~۵٪ همگام‌سازی / ~۳٪ ورود — مطابق پروفایل بار مدل ظرفیت.

### ۳.۱ آزمون بار پایدار (Load)

| پارامتر | مقدار |
|---|---|
| هدف | اثبات پایداری در بار روزانهٔ سنگین؛ خط پایه برای مقایسهٔ بقیهٔ سناریوها |
| پروفایل بار | **۵٬۰۰۰ RPS پایدار** (۶۲۵ نوشتن/ثانیه، ≈ ۲۱۰ ورود/ثانیه) |
| مدت | **۳۰ دقیقه** |
| خیز بار (ramp) | ۳ دقیقه‌ای خطی از صفر |
| معیار قبولی | همهٔ SLOهای §۱.۱ برقرار؛ `pool wait` < ۵ms؛ اصابت کش > ۸۰٪؛ میانگین CPU < ۷۵٪ |
| معیار شکست | نقض هر SLO برای بیش از ۲ دقیقهٔ متوالی، یا هر خطای داده (تعارض نوشتنِ بی‌دلیل، 409 غیرمنتظرهٔ انبوه) |

### ۳.۲ آزمون پیک (Peak — صبح مهر)

| پارامتر | مقدار |
|---|---|
| هدف | اثبات ظرفیت هدف طراحی: بدترین روز سال |
| پروفایل بار | **۲۰٬۰۰۰ RPS** + **۲٬۵۰۰ نوشتن/ثانیه** + **۸۳۳ ورود/ثانیه** + ۸۳۳ همگام‌سازی/ثانیه |
| مدت | **۱۵ دقیقه** |
| خیز بار | ۵ دقیقه‌ای پلکانی (۵هزار → ۱۰هزار → ۲۰هزار) |
| معیار قبولی | همهٔ SLOهای §۱.۱؛ `pool wait` < ۱۰ms؛ IOPS < ۸۰٪ ظرفیت دیسک؛ هیچ مدرسه‌ای (نقطه داغ) بی‌پاسخ نماند |
| معیار شکست | نقض هر SLO برای بیش از ۱ دقیقه، اشباع استخر اتصال، یا خطای 5xx بالای ۰.۵٪ در هر پنجرهٔ ۳۰ثانیه‌ای |

### ۳.۳ آزمون استرس (Stress — تا شکست)

| پارامتر | مقدار |
|---|---|
| هدف | یافتن نقطهٔ شکست واقعی و اثبات **زوال کنترل‌شده** (نه فروپاشی) |
| پروفایل بار | خیز از ۵هزار تا **۵۰٬۰۰۰ RPS** (پله‌های ۵هزار، هر پله ۵ دقیقه) — ادامه تا شکست |
| مدت | ≈ ۴۵–۶۰ دقیقه (تا شکست) |
| خیز بار | همان پله‌ها؛ پس از شکست، بار به ۵هزار برگردانده شود |
| معیار قبولی | نقطهٔ شکست ≥ ۳۰هزار RPS مستند شود؛ در اشباع، سامانه با 429/503 پاسخ دهد (نه آویختن)؛ پس از کاهش بار، بدون مداخلهٔ دستی به حالت سالم برگردد؛ **صحت داده ۱۰۰٪** (شمارش + چک‌سام) |
| معیار شکست | شکست زیر ۳۰هزار؛ آویختگی/قفل کامل؛ از دست رفتن یا فساد حتی یک نوشتنِ تأییدشده؛ کرش حلقه‌ای بدون بازیابی |

### ۳.۴ آزمون ضربه (Spike)

| پارامتر | مقدار |
|---|---|
| هدف | شبیه‌سازی موج ناگهانی (اعلان سراسری / بازگشایی مدارس / اتصال مجدد پس از قطعی) |
| پروفایل بار | **جهش ۵هزار → ۲۵هزار RPS در ۳۰ ثانیه**، نگه‌داشت ۵ دقیقه، بازگشت به ۵هزار |
| مدت | ≈ ۱۲ دقیقه |
| خیز بار | خودِ جهش (۳۰ ثانیه) — بدون نرم‌سازی |
| معیار قبولی | هیچ پنجرهٔ ۳۰ثانیه‌ای با خطای بالای ۱٪؛ بازگشت به همهٔ SLOها ظرف ≤ ۲ دقیقه پس از اوج؛ مقیاس‌پذیر خودکار (در صورت فعال‌بودن) گره اضافه کند؛ صف‌های ناهمگام تخلیه شوند |
| معیار شکست | خطای بالای ۵٪ بیش از ۱ دقیقه، خیز آبشاری (هر نود پشت‌سرهم)، یا رشد بی‌بازگشت صف/اتصال |
| واریانت | **طوفان همگام‌سازی پس از قطعی:** ۵هزار مدرسه با بسته‌های ۵۰۰تایی انباشته به‌طور هم‌زمان وصل شوند (سناریوی ۰۶ زیرساخت موجود) |

### ۳.۵ آزمون خیس‌خوردن (Soak)

| پارامتر | مقدار |
|---|---|
| هدف | کشف نشت حافظه/اتصال، رشد صف، تورم دیتابیس و فرسایش تدریجی (§17/§21 نقشه راه) |
| پروفایل بار | **۱۰٬۰۰۰ RPS پایدار** (۱٬۲۵۰ نوشتن/ثانیه) با چرخهٔ شبانه‌روزی ترافیک |
| مدت | **۷۲ ساعت** |
| خیز بار | ۵ دقیقه‌ای تا ۱۰هزار، سپس پایدار |
| معیار قبولی | انحراف هیپ < ۵٪ بین ساعت ۲۴ تا ۷۲ (بدون روند صعودی)؛ تعداد اتصال‌ها و عمق صف‌ها پایدار؛ رشد `dead tuples` با وکیوم مهار شود؛ هیچ قطعی؛ صحت دادهٔ نهایی ۱۰۰٪ |
| معیار شکست | هر روند صعودی پایدار در هیپ/اتصال/صف/تاخیر؛ OOM یا راه‌اندازی مجدد خودبه‌خود؛ رشد کنترل‌نشدهٔ اندازهٔ دیتابیس |

- نقطهٔ اکسپورت: `server/metrics.js` پشت دروازهٔ `METRICS_TOKEN` (هرگز از لبه روت نشود).

| زیرساخت | شبکه (ورودی/خروجی هر نود)، خطای اتصال/ریست |

```text
۳. گرم‌کردن کش (۵ دقیقه بار کم)

۵. خنک‌سازی + چک صحت داده (شمارش/چک‌سام نوشتن‌ها)
۶. ثبت در docs/LOAD_TEST_RESULTS.md
```

## ۶. معیار GO / NO-GO برای Wave 18

### ۶.۱ چک‌لیست پذیرش

- [ ] هر ۵ سناریوی §۳ با نتیجهٔ **قبولی** اجرا شده باشند.
- [ ] همهٔ اعداد با دیتاست کامل بخش ۲ (نه دادهٔ کوچک‌شده) به دست آمده باشند.
- [ ] نقطهٔ شکست (سناریوی استرس) ≥ ۳۰هزار RPS و زوال کنترل‌شده مستند شده باشد.
- [ ] صحت داده پس از استرس و سوآک: ۱۰۰٪ (شمارش + چک‌سام + بررسی تعارض‌های `sync_conflicts`).
- [ ] `config/thresholds.json` با SLOهای §۱.۱ هم‌تراز شده باشد.
- [ ] گیت‌های پایه پس از اجرا سبز: ‏smoke ۵۴۷/۵۴۷ · check-authz ۰ · secret-scan ۱۱/۱۱ · رگرسیون کامل.
- [ ] همهٔ خروجی‌ها در `docs/LOAD_TEST_RESULTS.md` (زمان، کامیت، محیط، نمودارها) ثبت شده باشد.
- [ ] هیچ شرط NO-GO از §32 نقشه راه فعال نشده باشد.

### ۶.۲ برنامهٔ اقدام در صورت شکست

1. **ثبت شواهد همان لحظه:** خروجی k6، اسنپ‌شات داشبوردها، لاگ‌های مرتبط با `trace_id`.
2. **ریشه‌یابی با جدول گلوگاه‌های مدل ظرفیت (§4):** تطبیق نشانه با نقطهٔ اشباع شناخته‌شده.
3. **ارجاع به مالک:** دیتابیس ← Arena 1 · کش/Redis/ورکر ← Arena 4 · کلاینت/همگام‌سازی ← Arena 3 · امنیت ← چت ۱.
4. **اجرای مجدد:** فقط سناریوی شکست‌خورده + اسموک رگرسیون؛ حداکثر **۳ دور** — بعد از آن توقف و
   ارجاع به ناظر با گزارش مستند (طبق قرارداد گزارش §24 نقشه راه).
5. **خط قرمز:** هر فساد یا از دست رفتن داده ⇒ توقف فوری کل موج، اعلام حادثه، و رسیدگی از مسیر
   `docs/DR_RUNBOOK.md` — هیچ توجیهی برای ادامه وجود ندارد.

## ۷. محدودیت‌های صادقانه

### ۷.۱ آنچه در سندباکس فعلی قابل اجرا نیست

| محدودیت | دلیل |
|---|---|
| تولید ۲۰هزار+ ریت | سندباکس ۲ هسته / ۴ گیگابایت است؛ سقف واقع‌بینانهٔ مولد ≈ ۰.۵–۱ هزار ریت |
| اجرای k6 | در این محیط نصب نیست؛ فقط هارنس داخلی ممکن است |
| دیتاست ۱۰ میلیون‌نفری | دیسک و زمان بارگذاری در سندباکس کافی نیست |
| سوآک ۷۲ ساعته | نشست‌محوربودن محیط سندباکس تضمین اجرا نمی‌دهد |
| خوشهٔ واقعی | نه خوشهٔ چندگرهٔ اپ، نه Primary/Standby واقعی، نه سنتینل ردیس در این محیط |
| فراهم‌کنندهٔ پیامک/لبه/CDN | فقط حالت شبیه‌سازی (بدون ارسال واقعی، بدون شبکهٔ لبه) |

### ۷.۲ آنچه نیازمند زیرساخت واقعی است

- استیجینگ کامل مطابق §۵.۱ (سخت‌افزار، شبکهٔ هم‌منطقه، استک رصد).
- ناوگان مولد بار (§۵.۲) و دسترسی شبکهٔ اختصاصی به استیجینگ.
- ادغام شاخهٔ چت ۳ (ابزار `seed-national.js` و تست‌های موج ۱۸) در `main` — بدون آن، اجرای رسمی ممکن نیست.
- اجرای واقعی بر اساس نقشهٔ راه به ترتیب وابستگی‌ها: **پیش از امضای ظرفیت، موج‌های ۱ (ادغام)،
  ۳ و ۱۰ باید کامل باشند** (اتصال‌ها/ایندکس‌ها/پارتیشن‌بندی روی دادهٔ واقعی).

### ۷.۳ آنچه همین‌جا قابل انجام است

- صحت‌سنجی منطق مولد دیتاست روی دادهٔ کوچک (مثلاً ۱۰هزار کاربر).
- اجرای اسموکِ بار (تا ~۵۰۰ ریت) برای یافتن خطاهای فاحش مسیر درخواست.
- بازبینی خشک اسکریپت‌های k6 و هم‌ترازسازی `thresholds.json`.

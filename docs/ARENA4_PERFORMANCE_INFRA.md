## ۲) معماریِ کارایی — نمای کل

مدلِ اجرایی: **تک‌فایلیِ آفلاین‌اول در کلاینت + تک‌پروسهٔ نود بدونِ
وابستگی در سرور**؛ مقیاس‌پذیریِ افقی با بی‌حالت‌کردنِ سرور و برون‌سپاریِ
وضعیت به ردیس (بندِ ۳) — نه با بازنویسی.

```
کلاینت (صفِ آفلاین → /api/sync)          سرورِ نود (بی‌حالت)
        │                                        │
        ▼                                        ├─ لایهٔ اعتبارسنجی/مجوز (آرنا ۲)
   بوتِ کش‌شده (TTL ۵د) ◄─── ابطالِ سراسری ─────┤
                                                 ├─ کارگرِ سنگین: persist/بکاپ/گزارش
                                                 ├─ کش: L1 حافظه + L2 ردیس
                                                 ├─ اوت‌باکس → همگام‌سازی/ممیزی
                                                 └─ ردیابی → Jaeger (OTLP/HTTP)
```

### ۲٫۱ اعدادِ کلیدی (ویو ۹ — `tests/wave9-performance.js` ‏۳۹/۳۹)

| سنجه | قبل | بعد |
|---|---|---|
| بلاکِ رشتهٔ اصلی در هر تیکِ ذخیره‌سازی | ~۴۶ میلی‌ثانیه | بیشینه ۱۶٫۸ · صدکِ ۹۵ ‏۰٫۳ میلی‌ثانیه |
| بلاکِ `POST /api/admin/backup` | ~۴۶ میلی‌ثانیه در هر درخواست | بیشینه ۰٫۶ میلی‌ثانیه (۸ درخواستِ پشت‌هم) |
| خواندنِ استاتیک | ‏`readFileSync` ‏~۲MB در هر درخواست | ناهمگام + کش (پس از نخستین درخواست: صفر I/O) |
| رویدادِ ممیزی | ‏`appendFileSync` هم‌زمان | صف → دستهٔ پس‌زمینه |

### ۲٫۲ خط‌کشِ حضوروغیاب (قانونِ پایشِ §۰.5.26)

میانهٔ ثبتِ حضوروغیابِ کلاسِ ۱۳ نفره: **۳۶۴ میلی‌ثانیه** (پایهٔ تازه).
هر کامیتی که فایل‌های فهرستِ §۰.5.24 را لمس کند و میانه را بالای
**۶۰۰ میلی‌ثانیه** ببرد ⇒ رجعتِ رسمی، توقف و گزارش.

### ۲٫۳ انضباطِ مسیرِ رندر

- خواندن‌های فهرستیِ سنگین از `queryRead`/سازنده‌های صفحه‌بندی‌شده عبور

- ایندکس‌های `idxGroup`/`idxUnique` الزامی‌اند؛ جستجوی خطی در مسیرِ رندر ممنوع.

## ۳) ردیس و وضعیتِ توزیع‌شده

### ۳٫۱ درایور و حالت‌ها (`server/redis.js`)

چهار حالت با قراردادِ یکسان: **`memory` (فال‌بکِ توسعه/تست) ·
`standalone` · `sentinel` · `cluster`**. انتخاب با متغیرهای محیطی
(`REDIS_URL` / `REDIS_SENTINELS` / `REDIS_CLUSTER_NODES`)؛ بدونِ ردیس،
فال‌بکِ درون‌حافظه‌ایِ هم‌قرارداد فعال می‌شود تا توسعه/تست هرگز وابسته به
زیرساخت نباشد. گیتِ آماده‌بودنِ ردیس (‏P0-13) در بوت سخت است.

### ۳٫۲ چه چیزی در ردیس است (و چه چیزی نیست)

| داده | جای ذخیره | چرا |
|---|---|---|
| شمارنده‌های نرخ (`rate:<prefix>:<id>`) | ردیس — ‏`incrWithTtl` اتمیک (شفا‌بخشیِ کلیدِ یتیم) | درست زیرِ هم‌زمانی؛ فال‌اوپن مستند در لبه |
| کشِ بوت (TTL ۵ دقیقه) | ردیس + ‏L1 حافظه | داغ‌ترین خواندنِ سامانه |
| کلیدِ توان‌رسانی/ایدِمپوتنسی (۲۴ ساعت) | ردیس | چند‌نمونه‌ای |
| نشست‌ها/ابطال (`revocation`) | ردیس | ابطالِ توزیع‌شدهٔ خروج/نشست‌ها |
| دادهٔ مدرسه | **فقط** فروشگاهِ فایل + پستگرس (آرنا ۱) | هیچ‌گاه وضعیتِ حیاتی در حافظه/کش |

### ۳٫۳ عملیات: پیکربندی، پشتیبان، بازیابی

- پیکربندیِ سه‌گره‌ایِ سنیتنل: `ops/redis/redis-node-{1,2,3}.conf` +
  `ops/redis/sentinel-{1,2,3}.conf` + `ops/redis/README.md` و
  `docs/REDIS_CLUSTER_SETUP.md`.
- پشتیبانِ خودکار: `tools/redis-backup.sh` (کرونِ هر ۶ ساعت: ‏`SAVE` +
  ‏`BGREWRITEAOF` + نگهداریِ ۷ روز + آپلودِ اختیاریِ ‏S3؛ رمز فقط از مسیرِ
  ‏`REDISCLI_AUTH` و هرگز در خطِ فرمان). تستِ کامل: `tests/redis-backup.js` ‏۸/۸
  — شاملِ بازیابیِ خصمانه. (اصلاحِ مسابقهٔ ‏SIGPIPE زیرِ بار در دروازهٔ
  انتشار انجام شد.)
- ممیزیِ کلیدها: `tools/redis-audit.js` (`payesh:*`، بدونِ ‏`KEYS *`).
- روالِ بازیابیِ عملیاتی + دریلِ ایزوله: `docs/REDIS_RESTORE_PROCEDURE.md`.

## ۴) لایهٔ کش

| لایه | پیاده‌سازی | سیاست |
|---|---|---|
| L1 حافظه | `localUserBootstrapCache` در `server/cache.js` | محدود: سقفِ ۲۰۴۸ ورودی (`PAYESH_L1_MAX_ENTRIES`) + ‏LRU + ‏TTL — پیش از ویو ۹ فقط-رشد بود (نشتِ حافظه در مقیاسِ ملی) |
| L2 ردیس | کشِ بوت با ‏TTL ‏۵ دقیقه | کلیدهای اسکوپ‌شده؛ بی‌اعتبارسازی با رویداد |
| ابطالِ سراسری | ‏Pub/Sub کانالِ `payesh:pubsub:inval` | هر جهشِ داده → ابطال در همهٔ نمونه‌ها |
| استاتیک | `server/static-cache.js` | پس از نخستین درخواست صفر I/O |
| توان‌رسانی | ذخیرهٔ توزیع‌شدهٔ کلیدِ ایدمپوتنسی (۲۴ ساعت) | جلوگیری از دوقلوشدنِ عملیات زیرِ تلاشِ مجدد |

**قانونِ سخت (بندِ ۲۵ نقشه‌راه + ‏SKILLS):** هیچ کشی بدون بنچمارک اضافه
نمی‌شود؛ بنچمارکِ مرجع `tests/wave9-performance.js` و سوئیت‌های کشِ فاز ۴
است. کش هرگز «منبعِ حقیقت» نمی‌شود — فقط شتاب‌دهندهٔ خواندن.

## ۵) کارگرها و معماریِ ناهمگام

| قطعه | فایل | نقش |
|---|---|---|
| کارگرِ سنگین | `server/workers/heavy.js` + `worker-service.js` | ذخیره‌سازی/بکاپ/گزارشِ عمومی خارج از رشتهٔ اصلی (ویو ۹) |
| اوت‌باکسِ تراکنشی | `server/outbox.js` (‏P0-17 + ویو ۸) | هر جهش مهم یک رویداد؛ هم‌تراز با فروشگاه (گم نمی‌شود)؛ با پستگرس در `server_outbox` هم می‌نشیند؛ سقفِ ۱۰۰۰ = صف، نه انبار |
| چرخهٔ عمرِ رویداد | `server/worker.js` | ‏`pending` → پردازش → ‏`mark()`؛ مصرف‌کننده‌ها: همگام‌سازیِ چندنمونه‌ای، بازسازی، حسابرسی |
| ممیزیِ پس‌زمینه | دسته‌بندیِ نوشتِ ممیزی | حذفِ ‏`appendFileSync` از مسیرِ درخواست |

**چرا اوت‌باکس:** هم‌راستایی با «مدولار مونولیت پیش از میکروسرویس» —
زیرساختِ رویدادمحور بدونِ شکستنِ مرزهای فعلی؛ هر مصرف‌کنندهٔ آینده
(نوتیفیکیشن ملی، گزارشِ تجمیعی) مشترکِ همان صف می‌شود.

## ۷) تست بار (Load Testing)

### ۷٫۱ زیرساخت — کامل

```
tests/performance/
├── scenarios/      01-login · 02-bootstrap · 03-attendance
│                   04-grades · 05-notifications · 06-sync-batch   (k6)
├── config/         thresholds.json (آستانه‌های SLO) + environments.json
├── suites/helpers/ ابزار مشترک + فیکسچرها
└── run-benchmarks.sh
```

**آستانه‌های سراسری (`thresholds.json`):** خطا `rate<0.01` · مدتِ درخواست
‏`p95<250ms` و ‏`p99<500ms`؛ هر سناریو آستانهٔ اختصاصی دارد (ورود
‏p95<150، بوت ‏p95<180، حضوروغیاب ‏p95<250 و…).

**محیط‌ها (`environments.json`):** ‏local · staging (`staging.payesh.ir`) ·
production (`api.payesh.ir`) · کلاسترِ اختصاصیِ تستِ بارِ ‏K8s.

### ۷٫۲ مدلِ ظرفیت (پیش‌نیازِ نقشه‌راه، قبل از تستِ ملی)

پیش از هر اجرای مقیاسِ ملی باید برای پنج محور مدل‌سازی شود: نرخِ ورود،
نرخِ همگام‌سازی، نوشتِ حضوروغیاب، گزارش‌ها، نوتیفیکیشن‌ها. خروجیِ مدل =
هدفِ عددیِ هر سناریوی ‏k6 (کاربرِ هم‌زمان، شیبِ رمپ، مدتِ سوک).

### ۷٫۳ وضعیتِ اجرا

| مورد | وضعیت |
|---|---|
| سناریوها + آستانه‌ها + دونده | ✅ در ریپو |
| اجرای محلیِ مرجع | ⏳ باینریِ ‏k6 در ساندباکسِ توسعه نیست — بندِ ۷ دروازهٔ انتشار: اجرای استیجینگ پیش از ‏Go-Live الزامی |
| میانهٔ حضوروغیاب <۶۰۰ میلی‌ثانیه | ✅ پایهٔ محلی ۳۶۴ میلی‌ثانیه (قانونِ §۰.5.26 فعال) |

## ۸) استقرار (Deployment)

### ۸٫۱ مدلِ فعلی — دستورِ کارِ کامل در `docs/DEPLOY.md`

تک‌پروسهٔ نود (وبِ تک‌فایلی + ‏`/api/*` + ذخیره‌سازی + بکاپِ خودکارِ
درون‌پروسه)، وابستگیِ خارجیِ صفر. اجزای دستورِ کار:

1. سخت‌افزارِ حداقل/پیشنهاد (۲ هسته · ۲–۴ گیگ رم · ‏SSD) و چک‌زنجیرهٔ
   پیش‌شروع (نود ۲۰+، ساعتِ دقیق برای ‏JWT).
2. نصبِ اولیه (کاربرِ غیرروت، پوشهٔ دادهٔ بیرونِ ریپو).
3. متغیرهای محیطی در ‏`.env.deploy` (رازها فقط محیطی — ‏SKILLS §مدیریت رمز).
4. ‏TLS: مسیرِ قفل‌شده = گواهیِ ‏Let's Encrypt با ‏certbot + تمدیدِ خودکار
   (پروکسی در خودِ نود نیست).
5. سرویسِ ‏systemd (`payesh.service`) با محدودسازیِ منابع.
6. داده/بکاپ/استورِ بیرونی — تصمیمِ قفل‌شده: **آروان‌کلاود Object Storage**.
7. روالِ به‌روزرسانی + چک‌لیستِ ‏go-live (همه باید سبز باشند) + **دروازهٔ
   انتشارِ آرنا ۵** به‌عنوانِ قفلِ نهایی.

### ۸٫۲ ترتیبِ قفل‌شدهٔ پیش‌نیازها

> ۱) درگاهِ پیامک + استعلامِ کد ملی ← ۲) سرور + دامنه + ‏DEPLOY ← ۳) ‏go-live.
> درگاهِ پیامک پیش‌نیازِ واقعیِ ‏go-live است، نه ‏TLS.

### ۸٫۳ چندنمونه‌ای شدن

پیش‌نیازها همین‌جا سبزند: سرورِ بی‌حالت، وضعیت در ردیس (نرخ/کش/ابطال)،
ایدِمپوتنسیِ توزیع‌شده، ابطالِ کش با ‏Pub/Sub، اوت‌باکس برای همگام‌سازیِ
چندنمونه‌ای. سند: `docs/MULTI_INSTANCE_READINESS.md`. بالانسر پیشنهادی:
‏nginx یا لبهٔ کاره (بند ۹).

## ۹) تکمیلِ بخش‌های ناتمام (‏K8s · CDN · WAF)

### ۹٫۱ ‏WAF و ضدِ ‏DDoS — ✅ پیاده؛ اِعمالِ نهایی در لبه

- درونِ برنامه: `server/waf.js` — **فقط-تشخیص** (امتیازدهی + سرآیندِ
  ‏`X-WAF-Verdict` + ثبتِ `waf_detect` در ممیزی). هیچ بلاکی در برنامه نیست
  تا خطای مثبتِ کاذب کاربران را نبندد.
- لبه: دستورِ کارِ کامل در `docs/WAF_DDOS_SETUP.md` — مسیرِ اصلیِ تولید:
  ‏Cloudflare (قوانینِ مدیریت‌شده + نرخِ ‏100r/m روی ‏`/api/*` + فایروالِ
  ‏origin فقط روی ‏IPهای کاره)؛ مسیرِ جایگزین: `nginx/nginx.conf` همین ریپو
  (تستِ `nginx -t` در ‏CI امنیتی فعال است).
- تست: `tests/waf-ddos.js` + واحدِ ‏WAF در `.github/workflows/security.yml`.
- **اقدامِ باقی:** فعال‌سازیِ لبه هم‌زمان با خریدِ دامنه/سرویس (عملیاتی، نه کدی).

### ۹٫۲ ‏CDN — تصمیم و نقشه

خروجیِ پروژه **یک فایلِ ‏HTML** است؛ بنابراین مدلِ ‏CDN ساده و کم‌ریسک است:

| تصمیم | شرح |
|---|---|
| ارائهٔ پروندهٔ ثابت | پشتِ ‏CDN (آروان‌کلاود/کاره) با کشِ لبه؛ نسخه‌بندی با هشِ محتوا در زمانِ بیلد |
| ‏API | هرگز کشِ ‏CDN نمی‌خورد (فقط ‏`/api/*` ‏no-cache + عبور از ‏WAF لبه) |
| فایل‌های پیوست/بکاپ | فقط در فضای شیئیِ آروان (تصمیمِ قفل‌شدهٔ ‏DEPLOY §۶) — نه ‏CDN عمومی |
| معیارِ پذیرش | بوتِ سردِ کلاینت روی شبکهٔ ۳G با ‏k6/سناریوی ۰۲ زیرِ آستانهٔ ‏p95 بماند |

### ۹٫۳ ‏Kubernetes — معماریِ مرجع (نه استقرارِ امروز)

خطِ مشیِ نقشه‌راه: **مدولار مونولیت پیش از میکروسرویس** — پس ‏K8s برای
اجرای تولیدِ امروز لازم نیست و تنها جای قطعی‌شدهٔ آن **کلاسترِ اختصاصیِ
تستِ بار** است (محیطِ `cluster` در `environments.json`). معماریِ مرجع برای
روزی که مقیاسِ ملی چند-نمونه را اجباری کند:

```
Deployment (تصویرِ نود، بدونِ حالت)      ← فایلِ پیکربندی نمونه: ضمیمهٔ الف
  ├─ پروبِ آمادگی/زنده‌بودن: /api/health
  ├─ رازها: JWT_SECRET/REDIS_*/… فقط از Secret
  └─ HPA بر پایهٔ سی‌پی‌یو + طولِ صفِ اوت‌باکس
Service + Ingress (TLS در اینگرس/لبه)
Redis (سنیتنلِ ۳گره‌ای — پیکربندیِ موجود در ops/redis)
PostgreSQL HA (مالکیتِ آرنا ۱)
```

الزام‌های هم‌زمانیِ پادها همین‌ک در کد سبز است (بند ۸٫۳)؛ تنها کارِ باقی،
نوشتنِ مانیفست‌ها پس از انتخابِ فراهم‌کننده است — **تصمیمِ آگاهانه این
است که پیش از نیاز، زیرساخت نسازیم** (اصلِ «کش/زیرساخت بدون بنچمارک و
نیاز ممنوع»).

## ۱۰) قوانینِ سختِ آرنا ۴

از ‏NATIONAL_ROADMAP_ARCHITECTURE_ADDENDUM و ‏SKILLS_MASTER:

1. هیچ ‏Source of Truth تازه‌ای ساخته نمی‌شود (داده: فروشگاه+پستگرس؛ وضعیت: ردیس).
2. کش بدون بنچمارک ممنوع؛ کش هرگز جایگزینِ منبعِ داده نمی‌شود.
3. فال‌بکِ حافظه‌ای برای وضعیتِ حیاتی در تولید ممنوع (فال‌بکِ حافظه فقط
   برای توسعه/تست و نرخ — با رفتاری که مستند و تست شده است، نه بی‌صدا).
4. هر تغییرِ کارایی باید عددِ قبل/بعد بدهد (قراردادِ گزارشِ آرنا §۲۴ نقشه‌راه).
5. هیچ تغییرِ زیرساختی بدون دریلِ بازیابی (بندِ ۳٫۳) پذیرفته نیست.
6. رازها فقط محیطی؛ توکن/رمز هرگز در فایلِ پروژه یا خطِ فرمان.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: payesh-api }
spec:
  replicas: 2
  selector: { matchLabels: { app: payesh-api } }
  template:
    metadata: { labels: { app: payesh-api } }
    spec:
      containers:
        - name: api
          image: payesh/api:VERSION      # ساخت از همین ریپو (نود ۲۰)
          ports: [ { containerPort: 3000 } ]
          envFrom: [ { secretRef: { name: payesh-secrets } } ]   # JWT/REDIS_*/OTP
          readinessProbe: { httpGet: { path: /api/health, port: 3000 } }
          livenessProbe:  { httpGet: { path: /api/health, port: 3000 } }
          resources: { requests: { cpu: 500m, memory: 512Mi }, limits: { memory: 1Gi } }

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: payesh-api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: payesh-api }
  minReplicas: 2
  maxReplicas: 10
  metrics: [ { type: Resource, resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } } } ]
```

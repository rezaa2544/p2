# معماری مقیاس ملی: ۱۰ میلیون دانش‌آموز، ۵ میلیون کاربر همزمان

> هدف: ثبت ۱۰٬۰۰۰٬۰۰۰ دانش‌آموز و استفادهٔ همزمان ۵٬۰۰۰٬۰۰۰ کاربر، بدون لگ، باگ یا هنگ، با بیشترین امنیت.
> فرض: سرور به‌قدر کافی قوی است. این سند دربارهٔ **کد** است.

---

## اصل حاکم بر کل طراحی

> **بار هر مرورگر باید ثابت و مستقل از مقیاس کشور باشد.**

اگر مرورگر یک دانش‌آموز با بزرگ‌شدن کشور سنگین‌تر شود، سامانه در مقیاس ملی شکست می‌خورد. اگر ثابت بماند، ۱۰ میلیون یا ۱۰۰ میلیون دانش‌آموز **هیچ تفاوتی نمی‌کند**.

نکتهٔ کلیدی: کد سمت کلاینت **حالت مشترک بین کاربران ندارد**. هر مرورگر مستقل است. پس ۵ میلیون کاربر همزمان یعنی ۵ میلیون نسخهٔ مستقل — مقیاس افقی و بی‌نهایت. تنها شرط، ثابت‌ماندن بار هر نسخه است.

### ۱. لایه ایندکس — `src/js/28-indexes.js`

حذف جستجوی خطی از مسیرهای داغ.

**مسئلهٔ صحت (مهم‌ترین بخش):** ایندکس اگر با تغییر داده به‌روز نشود، **باگ داده‌ای** تولید می‌کند — بدتر از کندی. راه‌حل: هر ایندکس با شمارندهٔ نسخهٔ مجموعه اعتبارسنجی می‌شود و `applyOp` در هر تغییر شمارنده را جلو می‌برد:

```js
function applyOp(op, record=true){
  if(typeof idxInvalidate==='function') idxInvalidate(op.c);  // ← باطل‌سازی خودکار
  ...
}
```

پس ایندکس **هرگز دادهٔ کهنه نمی‌دهد** — با ۷ تست مستقل اثبات شد (افزودن/به‌روزرسانی/حذف بلافاصله دیده می‌شوند).

**ایندکس‌های ساخته‌شده:** `idxById`, `idxEnrollByClass`, `idxEnrollByStudent`, `idxAttByClassDate`, `idxAttByStudent`, `idxGradesByStudent`, `idxScheduleByTeacher`, `idxClassesBySchool`.

**نرخ اصابت اندازه‌گیری‌شده: ۱۰۰٪** (۱۶۱٬۶۴۷ hit در برابر ۴۰ build).

## چرا ۱۰ میلیون دانش‌آموز کار می‌کند

```
پایگاه‌داده سرور: ۱۰٬۰۰۰٬۰۰۰ دانش‌آموز
        │
        │  /api/bootstrap  ← سرور محدوده را از روی توکن تعیین می‌کند
        ▼
   برش کاربر: ۸ KB (دانش‌آموز) تا ۱ MB (مدیر)
        │
        ▼
   مرورگر: ۳۵ms رندر، حافظه ثابت
```

**۵ میلیون کاربر همزمان = ۵ میلیون مرورگر مستقل**، هرکدام با ۸KB تا ۱MB. هیچ‌کدام روی دیگری اثر ندارد.

بار سرور: با batching offline-first و ۰.۰۰۰۹۵ req/s سرانه ⇒ ۵ میلیون کاربر همزمان ≈ ۴٬۷۵۰ req/s — با سرور قوی و چند نمونه پشت load balancer کاملاً عملی.

## امنیت: چرا محدودسازی داده مهم‌ترین تصمیم امنیتی است

پیش از این، مرورگر **هر** کاربر کل دیتابیس را داشت. یعنی یک دانش‌آموز با باز کردن کنسول مرورگر می‌توانست نمرات، کد ملی و اطلاعات تماس **همهٔ** کاربران را ببیند. هیچ فیلتر سمت کلاینتی این را حل نمی‌کند.

با `29-scope.js`:

| نقش | آنچه سرور مجاز است بفرستد |
|---|---|
| دانش‌آموز | فقط رکوردهای خودش |
| ولی | فقط فرزندان تأییدشده |
| دبیر | فقط کلاس‌های خودش، پنجرهٔ ۴۵ روزه |
| مدیر | فقط مدرسهٔ خودش |
| اداره | 🔒 **فقط آمار تجمیعی — هیچ رکورد فردی** |
| سوپرادمین | آمار ملی + فهرست صفحه‌بندی‌شده |

**قواعد الزامی سرور:**
1. محدوده از **توکن** تعیین شود، نه از پارامتر کلاینت (وگرنه دور زدنی است)
2. هرگز دادهٔ خارج از محدوده فرستاده نشود
3. هر عملیات ورودی از صف sync **مجدداً** اعتبارسنجی شود
4. رمزها هش شوند (bcrypt/argon2)
5. paywall در لایهٔ API اعمال شود، نه فقط UI

آزمون امنیتی پس از بهینه‌سازی: XSS در همهٔ مسیرها escape شد، دامنهٔ دید نقش‌ها دست‌نخورده ماند، ایندکس‌ها کنترل دسترسی را دور نزدند.

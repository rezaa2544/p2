# معماری پایش

## فلسفه‌ی طراحی

پایش با یک محدودیت سخت طراحی شده: **باید بدون هیچ اینترنت، سرور یا نصبی کار کند.** مدرسه‌ای در روستا باید بتواند فایل را روی فلش بزند و همان‌جا استفاده کند.

این محدودیت همه‌ی تصمیم‌های فنی را شکل داده است.

## ۱. تک‌فایلی بودن

خروجی نهایی یک `index.html` است که همه‌چیز در آن جاسازی شده:

| دارایی | روش جاسازی |
|---|---|
| فونت Vazirmatn | `data:font/woff2;base64,…` داخل `@font-face` |
| لوگو | data URI |
| استایل‌ها | تگ `<style>` درون‌خطی |
| منطق برنامه | تگ `<script>` درون‌خطی |

**هیچ** درخواست شبکه‌ای در زمان اجرا انجام نمی‌شود. تست `tests/run.js` این را تضمین می‌کند.

## ۲. توسعه‌ی ماژولار، توزیع تک‌فایلی

کار کردن روی یک فایل ۴۲۷ کیلوبایتی غیرممکن است. پس:

```
src/js/*.js  +  src/styles/*.css  ──build.js──▶  index.html
```

`build.js` صرفاً الحاق (concatenation) انجام می‌دهد — نه ترنسپایل، نه باندلر، نه وابستگی npm. به همین دلیل `build.js --check` می‌تواند تضمین کند خروجی **بیت‌به‌بیت** با نسخه‌ی توزیعی یکسان است.

> ترتیب ماژول‌ها در `src/js/_order.json` تعریف شده و **مهم** است، چون ماژول‌ها در یک scope مشترک اجرا می‌شوند.

## ۳. لایه‌ی داده: Event Log

داده به‌جای ذخیره‌ی مستقیم وضعیت، به‌صورت **گزارش تغییرات** نگهداری می‌شود:

```
داده‌ی پایه (تولید شبه‌تصادفی با SEED ثابت)
        +
لاگ تغییرات (localStorage)
        =
وضعیت فعلی
```

```js
applyOp(op)   // یک تغییر را اعمال و در لاگ ثبت می‌کند
applyLog()    // کل لاگ را روی داده‌ی پایه بازپخش می‌کند
resetAll()    // لاگ را پاک می‌کند → بازگشت به حالت اولیه
```

**چرا؟**
- داده‌ی دمو با `SEED` ثابت همیشه یکسان بازتولید می‌شود (تست‌پذیری)
- حجم ذخیره‌سازی فقط به تعداد تغییرات کاربر بستگی دارد، نه اندازه‌ی کل داده
- بازگشت به حالت اولیه بی‌دردسر است

## ۴. مسیریابی و وضعیت

یک شیء سراسری `S` وضعیت را نگه می‌دارد:

```js
S = { user, route, filters, tab, page, child, stack, boss }
```

**پیمایش:**
- `go(route)` → وضعیت فعلی را در `S.stack` می‌گذارد و `history.pushState` می‌زند
- `goBack()` → از پشته برمی‌گرداند
- رویداد `popstate` به دکمه‌ی Back گوشی وصل است

این باعث می‌شود در موبایل، دکمه‌ی برگشت سیستم‌عامل دقیقاً مثل یک اپ بومی کار کند.

## ۵. رندر

الگوی رندر «رشته‌محور» است — بدون Virtual DOM، بدون فریم‌ورک:

```js
render()          // ریشه را می‌سازد: ورود یا پوسته
  renderShell()   // منو + نوار بالا + محتوا
    renderRoute() // switch روی S.route → viewXxx()
```

هر `viewXxx()` یک رشته‌ی HTML برمی‌گرداند. رویدادها با **event delegation** روی `data-act` مدیریت می‌شوند، پس نیازی به اتصال مجدد listenerها بعد از هر رندر نیست.

## ۶. دسترسی مبتنی بر نقش

دسترسی در دو لایه اعمال می‌شود:

**لایه‌ی منو** — `NAV[role]` تعیین می‌کند چه چیزی دیده شود
**لایه‌ی داده** — توابع `visibleClasses()`، `visibleSubjects()`، `myAnnouncements()` داده را بر اساس نقش فیلتر می‌کنند

```
superadmin  → همه‌ی مدارس
edu_office  → مدارس منطقه‌ی تحت پوشش
manager     → فقط مدرسه‌ی خودش
teacher     → فقط کلاس‌هایی که تدریس می‌کند
student     → فقط پرونده‌ی خودش
parent      → فقط پرونده‌ی فرزندانش
```

## ۷. تقویم شمسی

پیاده‌سازی کامل و مستقل، بدون کتابخانه:

```js
toJalali(gy,gm,gd)   → [jy,jm,jd]
toGregorian(jy,jm,jd)→ [gy,gm,gd]
isLeapJ(jy)          → تشخیص کبیسه
monthMatrix(jy,jm)   → ماتریس روزهای ماه برای نمایش تقویم
```

تاریخ‌ها **داخلی به‌صورت ISO میلادی** ذخیره می‌شوند و فقط هنگام نمایش به شمسی تبدیل می‌شوند. این از انبوه باگ‌های تبدیل جلوگیری می‌کند.

## ۸. سیستم اشتراک (Paywall)

پنل اولیا پشت دیوار پرداخت است:

```js
renderRoute() {
  if (parentLocked() && !['subscription','notifications','announcements'].includes(S.route))
    return viewLocked();
  …
}
```

نقش‌های چندگانه هم پشتیبانی می‌شود — یک کاربر می‌تواند همزمان دبیر و ولی باشد (`panelsOf(u)` و `panelPicker()`).

## محدودیت‌های آگاهانه

| محدودیت | دلیل |
|---|---|
| بدون فریم‌ورک | حذف وابستگی و حفظ تک‌فایلی بودن |
| بدون بک‌اند | کارکرد کامل آفلاین |
| `localStorage` | تنها ذخیره‌ساز همیشه‌دردسترس در مرورگر |
| بدون رمز کاربری | ورود فقط تلفن + کد + کد ملی (📄 `docs/PLAN_PHONE_AUTH.md`)؛ ستونِ `password` آرشیوی است و در ورود خوانده نمی‌شود |
| Scope مشترک ماژول‌ها | بهای سادگی build؛ با `_order.json` مدیریت می‌شود |

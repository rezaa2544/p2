## ۲) KPI-1 — کوچک‌سازی `index.html` (بدون تغییر معنایی)

### چه شد
`tools/minify-source.js` — کوچک‌سازِ **محافظه‌کارِ** خانگی (فقط stdlib) که در
`build.js` روی هر ماژول اعمال می‌شود:

- حذف کامنت‌های JS (بلوکی/خطی) **خارج از** رشته/template literal/regex؛
  کامنت بلوکی → یک فاصله تا توکن‌ها نچسبند.
- حذف تورفتگی ابتدای خط و فاصلهٔ انتهای خط فقط در «حالت کد».
- حذف خطوط خالی کد.
- CSS: حذف کامنت/تورفتگی/خط خالی (رشته‌ها و `url(...)` دست‌نخورده).

### چه نشد (عمداً)
- **هیچ توکنی تغییر نام نمی‌دهد** و **هیچ newline کدی حذف نمی‌شود** →
  معناشناسی ASI تغییرناپذیر؛ assertهای ساختاری تست‌ها (مثل `function render(`)
  برقرار می‌مانند.
- داخل رشته‌ها و templateها (شامل HTML چندخطی UI) **بایت‌به‌بایت** حفظ می‌شود؛
  متن فارسی رابط از کوچک‌ساز عبور نمی‌کند.

### نکتهٔ فنی: تشخیص regex از تقسیم
Heuristic استاندارد «توکن معنادار قبلی»: بعد از `( , = : [ ! & | ? ; { } + - * / % ~ ^ < >`
و کلیدواژه‌های `return/case/typeof/...` regex مجاز است؛ بعد از شناسه/عدد/`)`/`]`
تقسیم. صحت روی هر ۹۵ ماژول با `new Function(...)` (پارس V8) در تست گیت می‌شود.

### اعداد
- باندل JS: ‏1,727,554 → ‏1,343,964 (~٪۲۲−) · CSS: ‏186,551 → ‏~179,000
- `index.html`: ‏2,257,641 → **1,657,003 بایت**

## ۳) KPI-2 — زمان build < 70ms

پروفایل `--cpu-prof` نشان داد هزینهٔ build پس از کوچک‌سازی: strip ‏(~۸۵ms)،
نوشتن دو خروجی (~۳۰ms)، خواندن راهنمای ۲.۴MB برای مُهر (~۱۲ms). سه اصلاح:

1. **کش افزایشی strip** — دوفایلی (`.build-cache.meta.json` + `.build-cache.blob`؛
   هر دو gitignore): کلید = mtime+size هر ماژول؛ فقط فایل‌های تغییرکرده دوباره
   strip می‌شوند. قالب blob با off/len برش می‌خورد تا `JSON.parse` یک بلاب
   بزرگ (~۱۶ms) حذف شود. کش خراب/غایب = بازساخت کامل (همیشه صحیح).
   `PAYESH_BUILD_NO_CACHE=1` مسیر بدون کش.
2. **skip نوشتن بی‌تغییر** — مقایسهٔ Buffer (بدون decode) با خروجی موجود؛
   دو نوشتن ~۱.۶MB در buildهای بی‌تغییر حذف شد.
3. **مُهر راهنما با خواندن جزئی** — مُهر `payesh-build` در `<head>` است؛ فقط
   ۸KB اول خوانده می‌شود؛ خواندن/نوشتن کامل فقط وقتی مُهر باید عوض شود.

نتیجه: **~58–66ms** (فرایند کامل node شامل ~28ms استارتاپ خود node).
قرارداد `build --check` (بیت‌به‌بیت با index.html) دست‌نخورده برقرار است.

## ۴) KPI-3 — پارس store < 50ms

### تحلیل
پارس ۵.۸MB JSON با متن فارسی: V8 برای رشته‌های **ASCII خالص** مسیر یک‌بایتی
سریع‌تری دارد. سنجش گزینه‌ها روی استور مرجع (میانهٔ گرم):

| گزینه | زمان |
|---|---|
| `JSON.parse(readFileSync(f,'utf8'))` (قبلی) | ~58ms |
| `JSON.parse(readFileSync(f))` (Buffer مستقیم) | ~48ms |
| قالب ستونی + بازسازی | ~66ms (رد شد — بازسازی گران) |
| **قالب ASCII-escaped + پارس Buffer** | **~35–40ms** ✅ |

### چه شد
- `server/json-fast.js` → `stringifyAscii(obj)`: خروجی `JSON.stringify` با
  escape همهٔ نویسه‌های غیر ASCII به `\uXXXX`. با **LUT یادسپار + regex
  run-based** (~۴۴ms برای کل استور؛ نسخهٔ سادهٔ per-char ۱۲۳ms بود).
- اعمال در هر سه نویسندهٔ استور: ورکر persist ‏(`server/workers/heavy.js` —
  بیرون از event-loop)، فال‌بک سنکرون خاموشی (`server/index.js`)، و seed.
- `loadStore` هم از Buffer مستقیم پارس می‌کند (رشتهٔ میانی ۵.۸MB حذف).

### قرارداد سازگاری
خروجی **JSON استاندارد و ۱۰۰٪ هم‌ارز** است؛ هر مصرف‌کننده (از جمله نسخه‌های
قدیمی `loadStore`، ابزارهای بیرونی، `jq`) بدون تغییر می‌خواند. جفت‌های
surrogate ‏(emoji) به‌صورت escaped-pair معتبر حفظ می‌شوند (تست A3).
بها: +۲۲٪ حجم فایل روی دیسک (۵.۸→۷.۱MB) — آگاهانه در برابر برد مسیر داغ بوت.

## ۵) KPI-4 و فاز کلاینت

### ۵.۱ پروفایل کلاینت (jsdom، ۲۵ رندر × ۵ مسیر)
داغ‌ترین توابع خودِ برنامه: `queueBytes` ‏(~۴۴۰ms — stringify کل صف sync در
**هر** رندر از مسیر syncBadge→queueRatio) و `fa`/`jalali` ‏(~۲۴۰ms —
`toLocaleString`/`Intl` per-cell در جدول‌ها).

### ۵.۲ چه شد
- **`fa`/`jalali` ‏(01-helpers.js):** memoize با Map کران‌دار (۴۰۹۶/۲۰۴۸ ورودی؛
  سررسید = پاک‌سازی کامل). ورودی→خروجی قطعی است پس کش همیشه صحیح است.
  `DateTimeFormat` هم یک‌بار ساخته می‌شود.
- **`queueBytes` ‏(27-sync.js):** کش با کلید (مرجع آرایه، طول، TTL ‏250ms) +
  به‌روزرسانی افزایشی برای push (فقط قلم‌های تازه شمرده می‌شوند).
  چون هر حذف/تخلیه آرایه را با `filter` نو می‌سازد، مرجعِ نو = بازمحاسبهٔ کامل؛
  حلقهٔ `enforceQueueCaps` همیشه مقدار تازه می‌بیند (تست B4).
- نتیجه: مسیر داغ `fa+jalali+queueBytes ×۱۰۰` از ~۱۰۰ms به **~1ms**.
  سهم باقی‌ماندهٔ رندر در jsdom عمدتاً `innerHTML` خود jsdom است (در مرورگر
  واقعی بسیار سریع‌تر)؛ گیت رندر برای مهار رگرسیون درجه‌دوم آینده گذاشته شد.

### ۵.۳ p95 API — صداقت اندازه‌گیری
عدد baseline بریف (248ms) از سنجش staging با k6 است؛ k6/staging در سندباکس در
دسترس نیست (مستند در `docs/PERFORMANCE_TESTING_PLAN.md` — اجرای رسمی k6 روی
staging). سنجش این ویو **درون‌پردازه** است (bootstrap + reports + students +
grades؛ ۸۰–۱۰۰ درخواست): p95 ≈ **4–14ms**، یعنی هزینهٔ خود مسیر پردازش سرور
~۲۴۰ms پایین‌تر از سقف هدف است. تفاوت با staging (شبکه/TLS/proxy) خارج از
کنترل کد است؛ suite‌های k6 موجود (`tests/performance/suites/`) پس از رفع
انسداد CI/staging همان آستانه‌ها را رسمی می‌سنجند.

## ۷) قراردادهای صحت (برای نگهدارندهٔ بعدی)

1. **`build --check` مقدس است:** هر تغییر در `tools/minify-source.js` باید
   `CACHE_VERSION` در `build.js` را جلو ببرد (کش کهنه = خروجی کهنه).
2. **کوچک‌ساز حق ندارد داخل رشته/template/regex دست ببرد** — تست A14
   (حفظ ۴۴۴ رشتهٔ literal ماژول نمونه) و M4 (فونت base64) نگهبانند.
3. **قالب استور باید JSON استاندارد بماند** — هیچ قالب باینری/سفارشی.
   تست C1 ‏(offline-optimization) سازگاری عقب‌رو را می‌خکوب می‌کند.
4. **کش‌های کلاینت فقط روی توابع قطعی** ‏(fa/jalali) یا با ابطال صریح
   (queueBytes: مرجع/طول/TTL). کش جدید = تست «کهنه سرو نمی‌شود» الزامی.
5. عدد جدید = «میانهٔ ≥۵ اجرا» + ثبت روش در همین سند.

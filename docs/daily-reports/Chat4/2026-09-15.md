## 2. In-Depth Invariant Analysis: Memory Pressure & Fail-Closed Semantics

### A. The 512MB Hard Memory Ceiling & `noeviction` Dynamics
- In PR #234, Chat4 landed explicit configuration pins (`ops/redis/redis-node-1..3.conf:40-41`):
  ```conf
  maxmemory 512mb
  maxmemory-policy noeviction
  ```
- **Architectural Trade-off Assessment:**
  1. **Security & State Integrity (Idempotency, Locks, OTP, Revocation, Session Versions):**
     - Under `noeviction`, Redis **refuses writes (`OOM command not allowed when used memory > 'maxmemory'`)** rather than silently evicting older keys.
     - For security-sensitive keys (`revoked:*`, `sessver:*`, `payesh:idempotency:*`, `payesh:otp:state`), this is strictly the correct behavior: silent eviction of a revocation tombstone or session version would reopen closed replay/token vulnerability windows.
  2. **Cache Survivability (`payesh:cache:bootstrap:*`, `payesh:cache:school:*`):**
     - Because cache entries live in the exact same Redis instance without a volatile eviction policy, memory exhaustion caused by high session volume or idempotency records will cause `redis.set` in `server/cache.js:187` to fail.
     - **Observed Code Defense:** `server/cache.js` wraps Redis cache writes in try/catch or async failure chains. A write failure to L2 does **not** crash the application; it logs an error and falls back to database reads. However, performance degrades to un-cached DB queries.
     - **Recommendation for Staging/Production Architecture:** When moving beyond single-instance staging, separate volatile caching (`volatile-lru` or dedicated Redis cache instance) from persistent transactional state (OTP, Outbox, Locks, Revocation).

### B. Redis Cluster Cross-Slot Safety Assessment
- In standalone or Sentinel topology (1 Master + 2 Replicas), all keys reside on the single active master, so multi-key operations (`sMembers` followed by multiple `del`, or Lua CAS scripts) operate without slot restriction.
- If deployed in Redis Cluster (`REDIS_CLUSTER_NODES` mode in `server/redis.js:106`), multi-key operations between `payesh:cache:school:<schoolId>` and `payesh:cache:bootstrap:<userId>` would span across disparate hash slots and trigger `CROSSSLOT Keys in request don't hash to the same slot` errors unless keys share identical hashtag brackets (e.g. `{school:<id>}`).
- This confirms that **Redis Cluster is currently documented-only** and not production-ready without hashtag normalization.

## 1. Technical Response to Read-Only Findings (F-C1-6 & F-C1-7)

### A. Finding F-C1-6: Memory Limit and Eviction Policy Contradiction
- **Observed Configuration Collision:**
  - *Infrastructure & Ops:* `ops/redis/redis-node-1..3.conf:40-41` and `infra/redis/docker-compose.sentinel.yml:25,68,86` specify `maxmemory 512mb` and `maxmemory-policy noeviction`. Supported by `docs/HA_REDIS.md:65`.
  - *Architecture & Capacity Specs:* `docs/CACHE_STRATEGY_DESIGN.md:186-187` declares `32gb` with `volatile-lru`, while `docs/CAPACITY_MODEL.md:75` specifies `24GB` with `allkeys-lru`.
- **Security & Operational Consequences:**
  - Under `allkeys-lru` or `volatile-lru`, Redis under memory pressure will silently evict keys. Because security-critical tokens (`revoked:<jti>`, `sessver:<userId>`, `payesh:otp:state`, `payesh:idempotency:<uid>`) currently share the same Redis keyspace, **LRU policies create an intolerable Fail-OPEN security risk** (eviction of a revoked JTI or bumped session version immediately revives revoked credentials; eviction of idempotency records allows duplicate financial/grade mutations).
  - Conversely, under `512mb` with `noeviction`, Redis adheres to strict **Fail-CLOSED** semantics: security records are never discarded, but writes fail with OOM errors when memory saturates. This protects data integrity at the cost of service availability for new writes.
- **Chat4 Technical Position (Recommendation to ChatGPT / Repository Owner):**
  - **Source of Truth:** Infrastructure configuration (`ops/redis/` and `infra/redis/`) must remain authoritative for security.
  - **Remediation Path:** Redis state must be topologically split into two distinct instances:
    1. *Redis-State (Noeviction, persistent, replicated):* Dedicated to `payesh:otp:state`, `revoked:*`, `sessver:*`, `payesh:idempotency:*`, and distributed locks.
    2. *Redis-Cache (Volatile-LRU):* Dedicated strictly to L2 application cache (`payesh:cache:*`).
  - Decisions to alter policy documents or deployment descriptors are reserved for ChatGPT governance adjudication.

### B. Finding F-C1-7: TTL Requirement vs Persistent Core Keys
- **Observed Inconsistency:**
  - `docs/CAPACITY_MODEL.md:228` mandates TTL on all keys (15 minutes for idempotency, prohibiting any unexpiring keys).
  - *Reality in Code:* `payesh:idempotency:*` sets TTL = 86400s (24h) in `server/cache.js:335,338`. Furthermore, three critical architectural keys are intentionally persistent with TTL = -1:
    1. `payesh:otp:state` (`server/otp-store.js:153`)
    2. `payesh:outbox:seq` (`server/outbox.js:34`)
    3. `sessver:<userId>` (`server/revocation.js:47`)
- **Chat4 Technical Assessment:**
  - The assertion in `CAPACITY_MODEL.md:228` that "all keys must have TTL" is incompatible with the operational requirements of an outbox sequencer (which requires monotonic sequence persistence) and user session invalidation (which requires persistent version counters).
  - When running under `noeviction`, persistent keys do not leak dynamically unless new unique persistent keys are allocated unboundedly. `payesh:otp:state` and `payesh:outbox:seq` are static singletons; `sessver:<userId>` scales with total registered users (approx 80 bytes per user).
  - The 24h TTL for idempotency (instead of 15m) is essential for OCC and daily offline sync queues. Shortening it to 15m without modifying client replay window contracts would cause duplicate request execution on delayed retries.

## ۰) چرا این رجیستر وجود دارد

نقص‌های G1-G11 مأموریت FT-METRIC-01 همگی یک ویژگی مشترک داشتند: **هیچ‌کدام باگ کد نبودند — همگی نقصِ فرایندِ اعتبارسنجی بودند.** کد کار می‌کرد، ولی ادعاها دربارهٔ کد از شواهد جلوتر بودند. کنترل‌های زیر قرار است برای همهٔ مأموریت‌های آیندهٔ benchmark/metric قابل‌اجرا باشند.

تحلیل تکرار (هرمس §۶ RECURRENCE) نشان داد که `docs/STRICT_VERIFICATION_GATE.md` موجود — با وجود داشتن یک بخش کامل FALSE-GREEN BLOCKERS و قرارداد V-01..V-12 — **فقط به `VERIFICATION_REGISTRY.json` متصل است، نه به `tools/ft/`**؛ mutation testing را الزام نمی‌کند و تطبیق شمارش فایل/آزمون را چک نمی‌کند. یعنی کنترل موجود دامنهٔ کافی ندارد و این رجیستر آن شکاف را پر می‌کند.

## ۱) متن کنترل‌ها (وفادار به منبع)

### COR-1 — جدا کردن design-inference از output-inference
هیچ گزارشی نباید از ویژگی طراحی یک معیار (چگونه امتیاز می‌دهد) به نتیجه‌ای دربارهٔ خروجی واقعی مدل برسد، مگر اینکه دادهٔ خام قابل‌دسترسی و قابل‌بازتولید باشد. وقتی دادهٔ خام مفقود است، فقط دو مجاز است: «قادر به دیدن X نیست (ثابت)» و «منشأ عددی قابل تعیین نیست».
هرگز نوشته نشود: «delta شامل سیگنال X نیست» وقتی خروجی خام در دسترس نیست.

### COR-2 — تطبیق شمارش فایل‌ها
هر گزارش باید تعداد فایل‌های نام‌برده در جدول را با `git status --untracked-files=all | wc -l` و با verdict تطبیق دهد. اگر خود گزارش به‌عنوان خروجی شمرده نمی‌شود، صریحاً نوشته شود: «N فایل پروژه + خود این گزارش».

### COR-3 — تفکیک correlation / causation / hypothesis
در یک مطالعهٔ observational (یک run، یک ordering)، همبستگی فقط می‌تواند به «همبستگی دارد و سازگار است» ترجمه شود. علت نیازمند است: (الف) آزمون کنترل‌شده (shuffle/ablation)، یا (ب) رد کردن همهٔ فرضیه‌های رقیب با شواهد. هر گزارش باید بگوید چه چیزی observed شده و چه چیزی hypothesis است.

### COR-4 — قرارداد scoring باید صریح تست شود
اگر `format_status` و `content_score` مستقل‌اند، یک regression test باید این استقلال را pin کند: یک ورودی FORMAT_FAIL با score غیرصفر. اگر gating وجود دارد، تست باید آن را pin کند. قرارداد نباید از comment کد استخراج شود.

### COR-5 — دادهٔ خام benchmark باید committed باشد
هیچ خروجی خام inference یا benchmark نباید gitignored باشد. اگر حجم یا حساسیت دارد، در artifact registry با hash + manifest ذخیره شود. بدون دادهٔ خام، هر نتیجهٔ benchmark وضعیت NOT REPRODUCIBLE دارد.

### COR-6 — آمار مدل باید از manifest استخراج شود
هیچ عددی در MODEL_REGISTRY نباید دستی نوشته شود. هر عدد باید با یک فرمان قابل‌بازتولید از `run-manifest.json` تولید شود. کلمهٔ «converged» نباید برای یک loss curve افزایشی استفاده شود.

### COR-7 — mutation testing باید exit code ثبت کند
هر mutation testing باید: (۱) در یک script دائمی باشد، (۲) exit code واقعی هر mutation ثبت شود، (۳) حداقل یک FAIL الزامی باشد. اگر mutationی کشف نشد، coverage gap اعلام شود، نه «all caught».

### COR-8 — الزام sanity identity برای توابع امتیازدهی (۲۰۲۶-۱۰-۱۰)
هر تابعی که شباهت/هم‌پوشانی/overlap را محاسبه می‌کند باید برای ورودیِ یکسان مقدار **۱.۰** برگرداند: `f(x, x) === 1.0`. این یک دروازهٔ یک‌خطی است که هرگونه اشتباهِ نوع در مسیر امتیازدهی (مثل صدا زدن `.size` روی یک Array، یا `.length` روی یک Set) را **در همان ثانیه** آشکار می‌کند، بدون نیاز به دادهٔ خام یا تحلیل پیچیده.
هیچ تابع امتیازدهی‌ای نباید بدون پاس‌کردنِ این sanity به‌عنوان «VERIFIED» یا «کارا» ثبت شود. اگر `f(x,x) !== 1.0`، کل خروجی‌های آن تابع نامعتبرند، حتی اگر با دادهٔ واقعی تکرارپذیر باشند — تکرارپذیریِ خروجیِ یک تابعِ غلط، فقط تکرارپذیریِ باگ است.

### COR-9 — تفکیک «بازتولید» از «میانگین‌گیری مجدد» (۲۰۲۶-۱۰-۱۰)
هیچ گزارشی نباید فیلدی به نام `recomputed_*` یا `*_ok` را به‌عنوان «بازتولید مستقل از دادهٔ خام» معرفی کند، در حالی که در عمل فقط میانگینِ مقادیرِ موجود در همان گزارشِ قبلی را گرفته است. اگر «recomputed» از روی اعدادِ از-پیش-محاسبه‌شده ساخته می‌شود، باید صراحتاً «باز-میانگین‌گیریِ درون‌ساختاری» نامیده شود و **نباید** به‌عنوان تأییدِ صحتِ تابعِ امتیازدهی تفسیر شود. بازتولیدِ واقعی یعنی فراخوانیِ دوبارهٔ تابع روی ورودیِ اولیه.

## ۵) چک‌لیست اجباری کنترل‌های دستی

پایان هر مأموریتِ benchmark/metric، بدون استثنا:

- [ ] **COR-1:** هر ادعای علّی دربارهٔ خروجی مدل، یا دادهٔ خامِ committed دارد، یا به «قادر به دیدن X نیست» / «قابل تعیین نیست» تنزل یافته است.
- [ ] **COR-2:** شمارش فایل‌های گزارش با خروجی `git status --untracked-files=all | wc -l` تطبیق دارد؛ خودِ گزارش صریحاً جدا شمرده شده است.
- [ ] **COR-3:** هر همبستگی با کلمهٔ «همبستگی» (یا معادل) گزارش شده است؛ هر فرضیه با کلمهٔ «فرضیه» مشخص شده است؛ هیچ فرضیه‌ای بدون رد کردن رقیب‌ها به علت تبدیل نشده است.
- [ ] **COR-4:** قرارداد scoring به‌صورت regression test واقعی pin شده است، نه فقط comment کد.
- [ ] **COR-5:** خروجی خامِ inference/benchmark در `tools/ft/` موجود و committed است، یا در artifact registry با hash + manifest ثبت شده است. اگر نه: نتیجه NOT REPRODUCIBLE است.
- [ ] **COR-6:** هر عدد در MODEL_REGISTRY با یک فرمان از manifest تولید شده است؛ هیچ عددی دستی نیست؛ کلمهٔ «converged» برای loss curve افزایشی به کار نرفته است.
- [ ] **COR-7:** mutation testing در script دائمی اجرا شده، exit code هر mutation ثبت شده، حداقل یک FAIL الزامی بوده، و هر SURVIVED به‌صورت coverage gap اعلام شده است.

## ۹) ثبت نقص: FT-METRIC-01-R1 (باگ `tb.size` روی Array)

> این بخش پاسخ مأموریت مرحلهٔ ۶ است: ثبت پایدار با شناسه نقص، علت فنی، دلیل تشخیص‌داده‌نشدن، regression test، شواهد و hashها، دامنهٔ اثر، وضعیت قبل/بعد، و معیار بسته‌شدن.

### ۹.۱ شناسه و عنوان
**FT-METRIC-01-R1** — باگ `tb.size` روی یک `Array` در `overlap()` و `sim()`: هر فراخوانی مسیر PLAIN (غیر-DIFF) همیشه ۰ برمی‌گرداند، حتی برای ورودیِ یکسان.

### ۹.۲ علت فنی (root cause)

`tb` یک **Array** است (خروجیِ `toks()`، که `split(/\W+/).filter(...)` برمی‌گرداند)، ولی کد از ویژگیِ `.size` مربوط به `Set` استفاده می‌کند. `tb.size` همیشه `undefined` است.

```javascript
function overlap(resp, exp) {
  const ta = new Set(toks(resp));
  const tb = toks(exp);              // ← Array
  if (!ta.size || !tb.size) return 0; // ← !undefined === true → همیشه اجرا می‌شود
  // ... خطوط زیر هرگز اجرا نمی‌شوند
}
```

`!undefined === true`، پس گارد `||` همیشه `true` ارزیابی می‌شود و تابع **قبل از رسیدن به منطکِ پیمایش**، `return 0` می‌زند. حلقهٔ `hit` و `return hit / tb.size` **کد مرده (dead code)** هستند.

دو تابعِ مستقل در دو فایلِ مستقل به‌طور یکسان آلوده‌اند:
- `tools/ft/metric-v2.js:overlap()` (خطوط ۱۱۴-۱۲۱)
- `tools/ft/benchmark.js:sim()` (خطوط ۲۲-۳۰)

### ۹.۳ چرا کشف نشد — دلیل تشخیص‌داده‌نشدن

این نقص از سه لایهٔ اعتبارسنجی عبور کرد:

| لایه | چرا مسکوت ماند |
|---|---|
| ۱۹/۱۹ suite | **تست 4b مسیر PLAIN را امتحان می‌کرد — ولی false-green بود.** `v1_content_score` (خط ۳۷۹) مستقل از `contractOf` همیشه `overlap(resp, exp)` را فراخوانی می‌کند، پس 4b دقیقاً تابع آلوده را لمس می‌کرد. ولی assertion آن `assert.strictEqual(r.v1_content_score, 0, …)` زیر کد دارای-باگ **برای هر ورودی‌ای** برقرار است، چون `overlap` همیشه ۰ برمی‌گرداند. 4b نتیجه را از طریقِ ویژگیِ fixture (نبودِ کلمات >۲ حرفی) توضیح می‌داد، در حالی که دلیلِ واقعیِ صفر، باگ بود. **این عمیق‌ترین لایه بود: تستی که مسیر آلوده را پوشش می‌داد ولی باگ را تأیید می‌کرد، نه که از آن محافظت کند.** |

**درس اصلی:** هر سه لایه فرض می‌کردند «خروجیِ ۰ از یک تابعِ کارا است». هیچ‌کدام نداشت `f(x,x)` را امتحان می‌کرد — یعنی هیچ‌کدام COR-8 را اجرا نمی‌کردند.

دو نتیجه: (۱) assertion مربوط به 4b هیچ ویژگی‌ای را تشخیص نمی‌دهد — هر دو fixture زیر کد دارای-باگ ۰ می‌دهند. (۲) زیر v1 اصلاح‌شده، fixture اصلی 4b **۱.۰۰۰۰** می‌گیرد (نه ۰) چون `response == expected` و خطوط هدر (`diff`, `git`, `fix`) کلمات مشترک >۲ حرفی دارند. **یعنی 4b پس از اصلاح باگ قرمز می‌شود** — بدون باگ سبز نمی‌شود. علت ریشه‌ای: فرضِ طراحی 4b این بود که v1 نمادها را نمی‌بیند (درست)، ولی 4b ورودی `response == expected` دارد که کلمات مشترکِ هدر را شامل می‌شود.

# معماری نرم‌افزار (software-architecture)

این مهارت برنامه‌ریزی ساختار کلان یک نرم‌افزار را پوشش می‌دهد: تقسیم به
لایه‌ها/ماژول‌ها، تعیین جریان داده‌ها، تعریف رابط‌ها و رعایت اصول مقیاس‌پذیری.

## When to Use

- طراحی سیستم‌های بزرگ یا چندماژوله (مثل پلتفرم چندکاربره).
- وقتی اضافه‌کردن یک قابلیت جدید کدهای زیادی را درگیر می‌کند (نشانه ضعف
  مرزها).
- بازبینی اینکه آیا یک تغییر پرهزینه است یا ارزان.
- Don't use for: تصمیمات کوچک و قابل برگشت (کتابخانه، نام‌گذاری) — برای
  آن‌ها از `code-review` استفاده کن.

## Procedure

1. **نیازمندیها را استخراج کن.** چه قابلیتی، برای چه کاربری، با چه محدودیتی.
2. **ماژول‌های اصلی را تعریف کن.** لایه ارائه، منطق کسب‌وکار، لایه داده،
   زیرساخت. هر ماژول یک مسئولیت مشخص دارد (Separation of Concerns).
3. **مرزها را صریح کن.** کدام ماژول با کدام صحبت می‌کند؟ وابستگیها باید
   یک‌طرفه باشند (به سمت مرکز/کسب‌وکار)، نه دوبطرفه.
4. **دیاگرام رسم کن.** Component diagram برای ساختار، sequence diagram برای
  جریان داده. ابزار: متن/ASCII یا یک ابزار رسم.
5. **الگوی معماری را انتخاب کن:**
   - Monolith / Modular Monolith — شروع پروژه، ساده
   - Layered — جداسازی واضح لایه‌ها
   - Microservices — فقط زمانی که لازم باشد و تیم بتواند نگهداری کند
   - Event-Driven + Outbox — برای پردازش غیرهمزمان
6. **رابط‌ها را تعریف کن.** API contract بین ماژول‌ها؛ پارامترها، خطاها و
   رفتار مرز.
7. **مقیاس‌پذیری و انعطاف را بررسی کن.** آیا اضافه‌کردن یک قابلیت جدید
   نیازمند تغییر در چندین لایه است؟ آیا یک بخش قابل scale شدن جدا از بقیه است؟
8. **rollback و migration را از اول طراحی کن.** هر تصمیم پرهزینه (data model،
   identifier، tenant boundary) باید مسیر برگشت داشته باشد.
9. **به معماری موجود پروژه ربط بده.** در پروژه پایش: `server/` (backend)،
   `src/` (client)، `build.js` (خروجی single-file)، `migrations/` (DB).

## Pitfalls

- **معماری کاغذی بدون پیاده‌سازی** — دیاگرام خوب، کد بد.
- **شروع با microservices** برای پروژه‌ای که هنوز monolith آن پایدار نیست.
- **مرزهای مبهم** — هر تغییری به چند ماژول سرایت می‌کند.
- **غفلت از rollback** در تصمیمات پرهزینه.
- **استفاده از SOLID به‌عنوان شعار** به جای ابزار تصمیم.

## Verification

- هر ماژول یک مسئولیت قابل توضیح دارد.
- وابستگیها یک‌طرفه و شفاف هستند.
- یک قابلیت جدید بدون تغییر در بیش از یک ماژول قابل اضافه شدن است
  (به استثنای رابط‌های مشترک).
- مسیر rollback برای هر تصمیم پرهزینه ثبت شده است.
